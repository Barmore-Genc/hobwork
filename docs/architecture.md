# Hobwork architecture

Hobwork is a personal code engine for a household. You (or an AI agent working for you) put scripts, scheduled jobs, HTTP APIs and small dashboards into it, and it runs them. Everything is reachable over MCP, so an agent can build and maintain automations end to end: write code, write tests, run them, merge, deploy, and debug from logs.

Named after hobs, the house spirits that quietly do chores around the home. Each automation lives in a hob: a git repository with handlers, a DB and an optional UI (see [Hobs](#hobs)).

## Goals

- Agents can create and change automations without a human reviewing code.
- Changes never break what is running without tests having run first.
- Every deployed version is recoverable with one click.
- Scripts run sandboxed, with controlled network access and secrets they can use but never read.
- Dashboards look like part of one app and work in the browser and in the Apple apps.
- Scripts can reach the phone: notifications, NFC, alarms, Screen Time.

## Non-goals

- Multi-tenant hosting or scaling. Each hob runs as zero or one instance.
- Protecting against hostile users. Users are a household. The sandbox protects against buggy or misled agent code.
- Replacing a general app platform. Dashboards are small internal UIs.

## Components

```
                 +-------------------------------------------------+
  Browser  ----> |                 Hobwork host                    |
  Apple apps --> |  HTTP API / web UI / dashboards                 |
  Agents (MCP)-> |  MCP server                                     |
  git push ----> |  git smart HTTP                                 |
  ssh ---------> |  SSH gateway                                    |
                 |                                                 |
                 |  repos (bare git)   host DB (SQLite)            |
                 |  hob DBs            scheduler / event bus       |
                 +-----------+-------------------------------------+
                             | Gondolin (QEMU + KVM/HVF)
            +----------------+----------------+
            |                |                |
      hob runtime       agent workspace   pipeline run
      VM (0 or 1 per    VM (per branch)   VM (fresh per
      hob)                                run)
```

- **Host**: Node (>= 24.12 for `node:sqlite`'s authorizer and defensive mode, runs TypeScript directly), pnpm. One process. Runs as a systemd service on `colossus` (Arch Linux, x86_64, KVM). Docker is possible with `--device /dev/kvm` but not the primary target.
- **Web UI**: React, TypeScript, Tailwind, Vite. Served by the host.
- **Guest image**: a Hobwork-specific Gondolin image built from Alpine with Node (full ICU data), pnpm, git, e2fsprogs, tzdata and the platform dependency set including `@hobwork/sdk` and `@hobwork/theme` (`images/`, built inside Docker by `images/build.sh`). VMs grow the root disk at boot (`diskSize`); root disk writes are discarded when a VM stops.
- **SDK** (`@hobwork/sdk`): the handler context type hob code builds against (hob DB, logs, Home Assistant, secrets, devices), plus the OpenRouter helper, the browser client for hob UIs, the Vite config and test helpers.
- **Apple apps**: the iOS and macOS app in `apple/` (one SwiftUI target, bundle ID `dev.bgenc.hobwork` on both). It shows the web UI and dashboards in a `WKWebView` and exposes native capabilities (notifications, and on iOS alarms, Screen Time, Focus, NFC and Health; on macOS Focus) to scripts.

The host never executes hob code itself. Anything from a hob repo runs inside a Gondolin VM.

## Sandboxing (Gondolin)

[Gondolin](https://github.com/earendil-works/gondolin) runs each sandbox as a QEMU micro-VM. The host implements the guest's network stack and filesystem in TypeScript, which gives us:

- **Egress allowlist**: only HTTP(S) to allowed hosts. Blocked requests get a 403. Internal ranges are blocked by default. Gondolin's range check does not cover NAT64, 6to4 or IPv4-compatible encodings of private IPv4 addresses, or the global IPv6 prefixes of the LAN, so the sandbox also passes an `isIpAllowed` hook (`server/src/public-address.ts`) that refuses those, other reserved ranges, and the networks of the host's own interfaces (re-read every 30 seconds). NAT64 and 6to4 addresses of public IPv4 hosts are allowed.
- **Secret placeholders**: the guest sees `GONDOLIN_SECRET_...` in env vars. The host swaps in the real value only over https, only in the `Authorization` header and the headers the secret lists, and only for the hosts the secret is bound to. A placeholder in any other header, or over plain http, gets the request refused with 403 `hobwork_secret_not_allowed` (`secretGuard` in `server/src/sandbox/gondolin.ts`, which runs in `onRequest` and again before the interceptor's `upstream`), since Gondolin itself would fill it into every header. Query string and body substitution are off.
- **Mounts**: host directories or in-memory filesystems mapped into the guest.
- **Ingress**: HTTP gateway into a server listening on `127.0.0.1` in the guest.

Gondolin does not work under Bun (HTTPS egress hangs, gondolin#73), which is why the host is Node.

All Gondolin use goes through a small `Sandbox` interface in the host (`server/src/sandbox/sandbox.ts`) so the backend can be swapped (e.g. Docker) if it ever needs to be. It covers: create a VM (memory, CPUs, disk size, image, mounts, env, egress allowlist, secrets, internal host handler, interceptor), exec with streamed output, timeout and kill, ingress to a guest port, file read/write, and stop. `@earendil-works/gondolin` is pinned to an exact version because the project is young and changes often.

- **Exec** runs `/bin/sh -lc <command>`. Several commands can run at once in one VM, including next to a long-running server.
- **Kill and timeout**: Gondolin cannot signal a guest process (aborting an exec only stops waiting). Every exec gets a unique `HOBWORK_EXEC_ID` env var, which child processes inherit. A kill runs a second exec that finds the processes with that variable in `/proc/*/environ` and sends SIGTERM, then SIGKILL after 2s. This also catches children that started their own session.
- **Environment**: every VM gets the host's time zone (`TZ`, or the zone Node resolves when it is unset) and locale (`LANG`, `LANGUAGE`, `LC_*`) from `server/src/sandbox/system-env.ts`, so dates and formats match the host, which also schedules crons in its time zone. Nothing else from the host's environment reaches a VM. The image has `tzdata` and the full ICU data, so every zone and locale works in Node and shell tools.
- **Interceptor**: a VM can be created with an interceptor for some hosts (`openrouter.ai` and `*.openrouter.ai` for the [AI gateway](#ai-limits)). Gondolin's `onRequest` hook hands allowed requests to those hosts to it, together with an `upstream` function that fills in secrets and sends the request on (`server/src/sandbox/intercept.ts`). Gondolin applies secrets only to requests it forwards itself, so `upstream` uses a second set of Gondolin HTTP hooks with the same placeholders (`secretFiller`), which keeps Gondolin's per-host rules for secrets. The host connects to intercepted hosts with its own `fetch`, without Gondolin's check against internal addresses, so only well-known public hosts are intercepted. Gondolin buffers answers from `onRequest`, so a streamed answer reaches the guest in one piece when it is complete.
- **QEMU seccomp filter**: with `HOBWORK_QEMU_SANDBOX=1` (Linux only) the host starts QEMU through `server/src/sandbox/qemu-sandboxed.sh`, which adds `-sandbox on,obsolete=deny,elevateprivileges=deny,spawn=deny,resourcecontrol=deny` (the options libvirt uses) to the command line Gondolin builds. Gondolin only lets the host pick the QEMU binary, so a wrapper is the only place to add arguments. It picks `qemu-system-$(uname -m)` from `PATH`. Off by default until `pnpm -C server test:vm` has passed with it on `colossus`.
- **Blocked egress** is reported to the host through a callback (for logging). Gondolin checks its allowlist only after resolving the name, so a host that does not resolve would get a 502 and never reach the callback. The sandbox therefore checks the hostname against the allowlist first (`isRequestAllowed`, same pattern matching as Gondolin), which answers 403 and reports it.

On x86_64 the host replaces Gondolin's kernel command line (`server/src/sandbox/gondolin.ts`). With the default one, create to first command took 2.5s:

- QEMU's `microvm` machine has no CMOS RTC, and the kernel's `rtc_cmos` probe waits about 1.3s before it gives up (`initcall_blacklist=cmos_init`).
- The i8042 probe costs about 80ms (`i8042.noaux i8042.nomux i8042.nopnp`).
- Kernel and init output go to the emulated UART, and every byte is a VM exit. That is about 450ms (`quiet`, `console=tty0`). `HOBWORK_VM_CONSOLE=1` puts the console back on `ttyS0`, so Gondolin's boot error messages include the guest log.

The rest is SeaBIOS (about 125ms; qboot measured no faster), the kernel, and Gondolin's init script (module loading, DHCP, sandboxfs mount, CA bundle). The VM test suite (`pnpm -C server test:vm`) passes on `colossus` (55 tests).

### VM kinds

| Kind | Lifetime | Filesystem | Purpose |
|---|---|---|---|
| Hob runtime | 0 or 1 per hob. Starts on demand, stops after idle timeout | Deployed build of `main`, read-only | Runs handlers |
| Agent workspace | Per branch. Stops when idle, restarts on demand | Branch checkout, read-write | Agent bash, dev server, tests while iterating |
| Pipeline run | Fresh per run, discarded after | Clean checkout of the candidate commit | Install, typecheck, lint, test, build |
| Branch preview | 0 or 1 per branch. Starts on demand, stops after idle timeout | Build of the branch's latest commit, read-only | Runs a branch's handlers for its preview |

### VM budget

Every VM reserves its memory and vCPUs from one host budget before it boots (`budgetedSandboxFactory` in `server/src/sandbox/budget.ts` wraps the sandbox factory, so every kind goes through it) and gives them back when it stops or fails to boot. The budget is `HOBWORK_VM_MEMORY_MB` and `HOBWORK_VM_CPUS`. By default it is the host's memory minus a quarter (at least 1 GiB) and twice the host's CPU count, never less than the biggest VM. Runtime VMs (also used by branch previews) default to 512 MB and 2 vCPUs, workspace and pipeline VMs (also used by builds) to 2048 MB and 4 vCPUs. `hobwork.json` `resources` (`runtime`, `workspace`, `pipeline`, each with `memoryMb` and `cpus`) asks for less; values above the defaults are capped.

The scheduler (`server/src/sandbox/scheduler.ts`) grants a request that fits at once, so a hob can borrow capacity nobody else wants. When the budget is full, requests wait in one queue per hob. The next one is chosen by priority (the main runtime, then builds, branch previews and pipeline runs, then workspaces) and, among equals, by the hob using the least memory, which gives every active hob an equal share over time. For the next request the scheduler stops idle workspace VMs (`stopIfIdle` in `server/src/workspaces.ts`: no running command, unused for 30 seconds): any of them for a runtime, build, preview or pipeline run, the ones of the hobs furthest over their equal share first, and for a workspace only those of other hobs over their share. A request waits `HOBWORK_VM_WAIT_SECONDS` (default 60) and then fails with "Hobwork is busy: there was no room to start a VM for <hob>. Try again in a minute.". Handlers get a 503 for it, which does not count against the version's health.

## Hobs

A hob is a git repository plus its deployed state, data and secrets. Examples: "filament tracker", "sleep alarms", "HA announcements". The code calls a hob a project (the `projects` table, `project_id` columns, `/api/projects` routes, SDK types), so this document calls code things by their code names and the concept a hob.

### Repository layout

New hobs are created from a template with everything configured:

```
AGENTS.md              how Hobwork works, rules for agents (Lambda model, tests, migrations)
hobwork.json           entry points (crons, webhooks, routes, triggers) and settings
package.json           scripts: typecheck, lint, test, build; extra deps (discouraged)
tsconfig.json
vite.config.ts         UI build + Vitest config, from hobworkViteConfig() in @hobwork/sdk/vite
src/                   handlers and shared code
ui/                    dashboard pages (React + Tailwind)
migrations/*.sql       hob DB migrations, applied in order
tests/                 Vitest tests
```

### Entry points

All entry points are declared in `hobwork.json`. The host reads it directly and never has to run hob code to find out what a hob does. The pipeline validates it against a JSON schema. It may have comments and trailing commas like `tsconfig.json` (JSONC); everything reads it with `parseHobworkJson` from `@hobwork/sdk/hobwork-json`, which reports errors with line and column.

```json
{
  "icon": "🧵",
  "crons": {
    "morning-alarm": { "schedule": "0 6 * * 1-5", "handler": "src/morning-alarm.ts" }
  },
  "webhooks": {
    "filament-scanned": { "handler": "src/scan.ts" }
  },
  "routes": {
    "GET /spools": { "handler": "src/spools.ts" }
  },
  "triggers": {
    "desk-button": {
      "homeassistant": {
        "trigger": "device",
        "domain": "zha",
        "device_id": "...",
        "type": "remote_button_short_press",
        "subtype": "button_1"
      },
      "handler": "src/desk-button.ts"
    }
  },
  "egress": ["api.example.com"],
  "idleTimeout": "1h"
}
```

- **Crons**: run on a schedule. The host owns the schedule.
- **Webhooks**: called from outside at `/hooks/<hob>/<name>/<token>`. The token is a rotatable secret. The request is passed to the handler.
- **Routes**: authenticated API for the hob's own dashboard, at `/api/...` on the hob's app origin (see [Hob app origins](#hob-app-origins)) and at `/p/<hob>/api/...` on the Hobwork host for agents. `"GET /spools/:id"` answers `GET /api/spools/42` with `ctx.params.id = "42"`. Static segments win over parameters, and `HEAD` is served by the `GET` route.
- **Triggers**: events from integrations (Home Assistant, devices). The trigger payload is passed to the handler. A trigger has either a `homeassistant` block or a `device` block; `{ "device": { "capability": "notifications", "event": "action" } }` runs when someone taps an action on a notification the hob sent (see [Notifications](#notifications)).

`icon` is not an entry point: it is one emoji or the path of an image in the repo, for the hob's favicon, home screen icon and hob lists (see [Hob icons](#hob-icons)).

A handler file exports a default function that receives the invocation context:

```ts
import type { Handler } from "@hobwork/sdk";

export default (async (ctx) => {
  const res = await ctx.fetch("https://health-export.example/api/sleep/last");
  ...
}) satisfies Handler;
```

The context (`packages/sdk/src/index.ts`) has `invocation` (ID, kind, name, whether it was started by hand), `request` (a standard `Request`, for routes and webhooks), `params`, `payload` (trigger variables, or what a manual invocation passed), `fetch` (the guest's own `fetch`, which the egress allowlist controls), `log`, `db`, `ha`, `secrets`, and `device(name)` and `devices()` (see [Devices](#devices-apple-apps)). `RequestHandler` is the variant with `request` always set. A route or webhook answers with the handler's return value: a `Response` is sent as is, `undefined` as 204, anything else as JSON. A thrown error answers 500 with the invocation ID and no details, since webhook callers are outside the household; the error and stack trace are in the invocation record.

The SDK API is the context rather than imported functions, so handler bundles contain no SDK runtime code and tests build a context by hand.

### Dependencies

The guest image contains one **platform dependency set** (React, Tailwind, Vite, Vitest, TypeScript, oxlint, zod, date-fns and similar) on the VM's own disk. Every hob uses the same versions, so they are updated together.

- Updating the platform set means rebuilding the image. Deployed builds bundle their dependencies (see [Runtime](#runtime)), so they keep running unchanged; each hob's next workspace, pipeline run or build uses the new versions.
- Hobs can add extra npm packages in their `package.json`, installed on top of the platform set. This is allowed but discouraged, and `AGENTS.md` says so.

How the layering works (prototyped in `server/src/sandbox/gondolin.test.ts`):

- The platform set also holds what the pipeline needs to render hob icons: `sharp` and `@twemoji/svg` (see [Hob icons](#hob-icons)).
- The platform set is a normal pnpm install at `/opt/hobwork/platform` (`images/platform/package.json` and its lockfile, exact versions). `/node_modules` is a symlink to `/opt/hobwork/platform/node_modules`, and `/opt/hobwork/platform/node_modules/.bin` is on `PATH`.
- Node, TypeScript, Vite and Vitest all resolve packages by walking up parent directories to `/node_modules`, so a hob anywhere in the VM finds the platform packages and their types with no configuration. `NODE_PATH` is not used because ES modules ignore it.
- A hob's `package.json` lists only its extras (the template has scripts and no dependencies). `pnpm install` puts them in the hob's own `node_modules`, which is found before `/node_modules`, so an extra could also override a platform package.
- `images/platform/package.json` is the single definition of the platform set. The host reads it (`server/src/platform.ts`) to tell extras apart: a dependency not in it (and not `@hobwork/sdk`) is an extra. Workspace and pipeline VMs run `pnpm install` only when a hob has extras.
- The template sets `autoInstallPeers: false` in `pnpm-workspace.yaml`. Without it, pnpm installs a second React for an extra that has React as a peer dependency. With it, the peer resolves to the platform React through the same parent-directory lookup.
- Installing extras needs egress to `registry.npmjs.org`. Egress is fixed when a VM is created, so pipeline VMs can reach the registry (and nothing else) for the whole run, not only during the install step. Workspace VMs can reach it too, so agents can `pnpm add` extras.
- **Install protections**: workspace and pipeline VMs set `pnpm_config_minimum_release_age=4320` (3 days, in minutes) in their environment (`server/src/guest-vm.ts`). An environment setting beats a hob's `pnpm-workspace.yaml`, and unlike a global config file it does not depend on where the VM's `HOME` or `XDG_CONFIG_HOME` point (Gondolin sets the latter to `/tmp`). Versions published in the last 3 days are not installed, since most malicious releases are caught and pulled within that time. pnpm 12 runs dependency install scripts only for packages listed as `true` under `allowBuilds` in the hob's `pnpm-workspace.yaml` and fails the install with `ERR_PNPM_IGNORED_BUILDS` for any other package that has one; the image and the template allow none. The pipeline's validate step (`server/src/pipeline/pnpm-settings.ts`) refuses a `pnpm-workspace.yaml` that sets `minimumReleaseAge` below the default, `minimumReleaseAgeExclude`, `minimumReleaseAgeIgnoreMissingTime` or `dangerouslyAllowAllBuilds`, that sets `pnpmfile`, `globalPnpmfile`, `registry` or `registries`, or that is not valid YAML. It also refuses a `.pnpmfile.cjs` or `.pnpmfile.mjs` at the hob's root (a pnpmfile is code that runs during install and gets around `allowBuilds`) and a `.npmrc` that sets a registry, a pnpmfile, a lower `minimum-release-age`, `minimum-release-age-ignore-missing-time`, `dangerously-allow-all-builds`, `script-shell` or `node-options`. Builds of versions without a stored build apply the same check (`checkInstallConfig`), and appends a notice to its output when the candidate changes the `allowBuilds` list compared to the deployed version, so the pipeline run shows it. The pipeline and the build of a version without a stored build install extras with `pnpm install --frozen-lockfile --ignore-pnpmfile`, so what was tested is what is deployed. A hob with extras and no `pnpm-lock.yaml`, or a lockfile that does not match `package.json`, fails with a message to run `pnpm install` in the workspace and commit the lockfile. Workspace VMs still run a plain `pnpm install` so agents can add packages. Workspace code runs there anyway, so the pnpmfile and `.npmrc` checks only apply to what merges.

`@hobwork/sdk` is part of the platform set. The image build copies `packages/sdk` (its `package.json`, `src/` and schema) to `/opt/hobwork/platform/node_modules/@hobwork/sdk`, so hob code resolves it through `/node_modules` like any platform package, in workspace, pipeline and runtime VMs alike. It is versioned with the image: an SDK change needs an image rebuild, like other platform updates. Rejected: mounting `packages/sdk` from the host read-only, which would let the SDK drift from what a deployed version was tested against. The SDK is shipped as TypeScript source, except `hobwork-json.js` and `vite.js`, which are JavaScript with `.d.ts` files: Vite loads the imports of `vite.config.ts` with Node, and Node does not strip types under `node_modules`. TypeScript works for types and for Vite builds, and handler bundles contain no SDK runtime code (see [Entry points](#entry-points)), so nothing is compiled. The runner in `packages/sdk/src/runner/` is host code and reaches runtime VMs differently (see [Runtime](#runtime)).

### Workspace file layout

Agent workspaces mount the branch checkout from the host read-write at `/workspace`, so the host (MCP file tools, git) and the VM see the same files. `node_modules` inside it lives on the VM's own disk (a bind mount the `Sandbox` sets up for `Mount.vmDisk` paths, hidden from the host side). It only holds extras, is reinstalled when the VM starts, and is gone when it stops.

Measured with `pnpm -C server bench:sandbox vfs` on the Mac (generated hob: 40 TSX modules using zod, date-fns and React, 20 Vitest files; 2GB VM; medians of 3):

| Layout | `tsc --noEmit` 2 vCPU | `vitest run` 2 vCPU | `tsc --noEmit` 4 vCPU | `vitest run` 4 vCPU |
|---|---|---|---|---|
| (a) everything mounted, full `node_modules` in the mount | 1.79s | 23.3s | 1.55s | 11.4s |
| (b) everything on the VM disk | 0.90s | 12.7s | 0.74s | 5.1s |
| (c) source mounted, platform set from the image | 0.95s | 12.2s | 0.78s | 5.3s |
| (d) source mounted, full `node_modules` on the VM disk | 0.96s | 12.2s | 0.83s | 5.3s |

- The Gondolin filesystem bridge doubles the time when `node_modules` goes through it, and copying the platform set into a mount takes 10s. With `node_modules` on the VM disk, a mounted checkout is as fast as a checkout on the VM disk, so there is no reason to copy the checkout into the VM.
- Vitest time is dominated by module imports, not the filesystem: every test file runs isolated and imports `date-fns` from scratch (~750ms in the guest, ~420ms in a Docker container on the same Mac). `--no-isolate` brings the run to 1.2s. Pipeline and workspace VMs get 4 vCPUs.
- The template's Vitest config sets `isolate: false`, with `restoreMocks`, `unstubGlobals` and `unstubEnvs` so mocks and stubs do not leak between tests. On the template with 10 extra test files importing zod and date-fns (4 vCPUs): 3.6-3.9s isolated, 3.0-3.7s with `pool: 'threads'`, 0.8s with `isolate: false`. Test files share one module cache, which `AGENTS.md` tells agents.

### Branches and workspaces

- Each hob is a bare repo on the host: `data/repos/<hob>.git`.
- `main` is the deployed version. Nobody pushes to it directly. The only way in is a merge through the pipeline.
- Agents do work on branches. Each branch can have an **agent workspace** VM with the branch checked out.
- A workspace's checkout lives on the host at `data/workspaces/<hob>/<branch>/`, with the branch's files in `files/` and the git directory in `git/`. The VM mounts only `files/`. The host runs all git commands for the workspace (`commit`, `diff`, `log`) with an explicit git directory, so nothing the VM writes (git config, hooks, filters) is ever executed on the host. `commit` pushes to the branch in the bare repo.
- Branch data is isolated: a workspace gets a copy of the hob DB taken when the workspace VM starts. Tests get an empty DB with migrations applied. See [Data](#data).

Workspace VMs (`server/src/guest-vm.ts`):

- Started by the first `bash` call on a branch: 4 vCPUs, 2GB memory, 4GB root disk, `files/` at `/workspace` with `node_modules` on the VM disk. `bash`'s `cwd` is relative to `/workspace`. Extras are installed on start. A failed install does not fail the start, so the agent can still run commands and see the error with `pnpm install`.
- Egress: the branch's `hobwork.json` `egress`, the hosts of the hob's secrets, and `registry.npmjs.org`. Secrets are passed as placeholders like in the runtime. When `egress` or the secrets change, the next `bash` call replaces the VM (unless a command is still running), so agents can test a new host without a restart tool. Blocked requests are logged to the hob log with the branch name.
- Idle stop: a VM with no `bash` call for `HOBWORK_WORKSPACE_IDLE_MINUTES` (default 30) is stopped, unless a command is running. Every `bash` call updates `last_used_at` when it starts and when it ends. The default is well above the 10 minute `bash` timeout. A stopped VM starts again on the next call. Stopping loses processes and the VM-disk `node_modules`, and nothing else, since the files are on the host.
- The host stops all workspace and pipeline VMs on SIGINT and SIGTERM.
- Pipeline VMs use the same resources and layout with a fresh VM per run and only the registry allowed.
- Both are enabled when a guest image exists (`images/build/<arch>` or `HOBWORK_IMAGE_DIR`). Without one the host logs that `bash` and `merge` are unavailable.

### Deleting hobs

Only people delete hobs, in the web UI (the hob's overview, confirmed by typing the name) through `DELETE /api/projects/<name>` with `{ confirm: "<name>" }`. There is no MCP tool, CLI command or workspace API for it: an agent that is misled or confused could otherwise destroy a hob and its data, and deleting is rare enough to leave to a person.

Deletion (`server/src/project-deletion.ts`) runs in the hob's delivery queue, so it waits for a running merge or restore. It stops the runtime VM right away without waiting for running invocations, unschedules crons, unsubscribes HA triggers (`removeProject` in the trigger registry), stops and removes branch workspaces (VMs, checkouts, branch DBs), closes the hob DB, and deletes the builds. The hob row goes from the host DB and takes versions, pipeline runs, invocations, logs, webhook tokens, workspaces and secret assignments with it (foreign keys cascade). Secrets stay in the library for other hobs.

It is a soft delete for the parts that cannot be rebuilt: the bare repo and the hob DB directory move to `<dataDir>/trash/<name>-<time>/` (`repo.git`, `data/`) with a `deleted.json` holding who deleted it, when it is purged, and the rows needed to bring it back: versions (with their agent, user and `restored_from`), the creation time, secret assignments, webhook token hashes, NFC tag IDs and the IDs of agent tokens and OAuth connections whose hob list includes it (entries from before these fields were added have versions only). The daily housekeeping job (`server/src/housekeeping.ts`) removes entries older than 7 days. Backups may run less often than a hob gets deleted by mistake, and they cover live hobs only (snapshots from before the deletion keep it for their retention), so the trash is the way back in the meantime. The name can be used for a new hob right away.

### Restoring deleted hobs

The web UI's Deleted hobs page (`/deleted`, linked from the hobs list and the deletion notice) lists the trash with who deleted each hob, when, its last version and when it is purged: `GET /api/trash` returns `{ trashDays, projects: [{ id, project, deletedAt, purgeAfter, deletedBy, versions, lastVersion, nameTaken }] }`, where `id` is the trash directory name. `POST /api/trash/<id>/restore` with `{ name? }` restores it under its old name or, when a hob took that name (`nameTaken`), under another one; the page asks for one then. Like deleting, it is for people only (session and CSRF header, no MCP tool).

Restoring (`restoreProject` in `server/src/project-deletion.ts`) runs in the delivery queue of the new name. It moves `repo.git` and `data/` back, inserts the hob row with its old creation time and its versions with their numbers, and brings back secret assignments whose secret still exists, webhook tokens (so webhook URLs keep working), NFC tags (they are written on physical tags), its own [AI models and limits](#ai-limits) and its place in the hob lists of agent tokens and OAuth connections that still exist ([access limits](#access-limits)). The restored hob gets a new ID. Agents and users that no longer exist become null. Run history, logs, AI usage records (so spend limits start over), pipeline runs, branch workspaces and branch HA approvals stay deleted; branches are still in the repo. The trash entry is removed, a `project` event goes to the hob log, and the runtime loads it like after a host restart: crons and HA triggers are scheduled, and the deployed version is built on its first invocation since builds were deleted. The DB already has the version's migrations.

### Renaming hobs

People rename a hob on its overview (`POST /api/projects/<name>/rename` with `{ name }`, `server/src/project-rename.ts`). There is no MCP tool: renaming changes URLs other systems call (webhooks, the app address, git remotes) and interrupts running work, and agents never need it to change a hob. The MCP instructions say so.

Every row in the host DB references the hob by ID, so the rename changes only `projects.name`. The rest is on disk and in memory, keyed by name:

- It runs in the hob's delivery queue, so it waits for a running merge or restore; merges queued for the old name afterwards fail with "was renamed".
- Everything the hob runs stops first, like for a deletion: the runtime VM and branch preview VMs without waiting for running invocations (they end as failed), crons, HA triggers, and branch workspace VMs (a running `bash` command or SSH session ends). Branch DBs and the hob DB are closed.
- `repos/<name>.git`, `projects/<name>/` (the DB), `builds/<name>/` and `workspaces/<name>/` (checkouts with uncommitted changes and branch DB copies) move to the new name. A target that exists refuses the rename, and a failure moves everything back and loads the hob under its old name again.
- Workspace checkouts get their `origin` pointed at the moved repo, since a clone keeps the repo's path. Workspace VMs are stopped once more after the move in case a command started one on the old paths meanwhile.
- The runtime forgets the old name and loads the new one, which schedules crons and subscribes HA triggers again. VMs start on the next invocation or `bash` call. Secrets, webhook tokens, NFC tags, device notifications and commands, HA approvals and app sessions follow the hob ID. A `project` event in the log records the rename and who did it.
- The code is not changed: `package.json` keeps the old name until an agent changes it.

Old names (`project_renames`, migration 0023) keep external links working: webhooks at `/hooks/<old name>/...` and routes at `/p/<old name>/...` reach the hob, a GET on the old app origin (`<old name>.<apps host>`) redirects (302) to the same path on the new one, where the app signs in again, and `GET /api/projects/<old name>` returns the hob so the web UI moves old links to the new name. Other API and MCP calls with the old name fail with `Hob "<old>" was renamed to "<new>"`, and git over HTTP says to change the remote URL. Branch preview origins and SSH users (`<hob>/<branch>`) use the new name only. A hob that takes the name, by creation, rename or restore, ends the old name's use; deleting the hob removes its old names.

## Agent access

Three ways in. All of them act on the same repos and workspaces.

1. **MCP** (primary; the only option for Claude Cowork and chat clients). See the tool list below.
2. **git smart HTTP**: `git clone https://hobwork/git/<hob>.git`, work locally with Claude Code, push a branch. A pre-receive hook rejects pushes to `main`. After pushing, the agent calls `merge` over MCP (or over SSH).
3. **SSH gateway**: `ssh <hob>/<branch>@hobwork` opens a shell in that branch's workspace VM. Also provides a `hobwork` CLI inside workspaces (`hobwork merge`, `hobwork logs -f`, `hobwork status`). See [SSH gateway](#ssh-gateway).

### MCP tools

Hobs: `list_hobs` (with each hob's storage use), `create_hob` (from template), `get_hob` (entry points, current version, status, [storage use](#storage-use), the app URL, each branch's preview URL, and the hob's AI models, limits and spend, read-only; see [AI limits](#ai-limits)).

Workspaces and files: `create_branch`, `list_branches` (with each branch's app URL), `set_branch_home_assistant` (see [Hobwork to HA](#hobwork-to-ha-actions)), `read_file`, `write_file`, `edit_file`, `delete_file`, `list_files`, `search`, `bash` (runs in the branch workspace VM), `commit`, `diff`, `log`.

Delivery: `merge` (runs the pipeline, squash-merges and deploys on success, returns failures otherwise), `pipeline_status`, `list_versions`, `restore_version`.

Runtime: `invoke` (call a route or run a cron, webhook or trigger by hand, on `main` or with `branch` on a branch preview), `list_invocations` (filter by `branch`), `get_logs`, `tail_logs`, `rotate_webhook_token` (with `branch`, a URL for the branch preview).

Secrets: `list_secrets` (the library: names, hosts, headers, pending hosts and assignments, never values), `assign_secret`, `unassign_secret` and `request_secret_hosts` (asks the user to approve hosts and returns a link to the approval page). Only users create secrets and set values, and hosts change only when a user sets or approves them. See [Secrets and network](#secrets-and-network).

SSH keys: `add_ssh_key`, `list_ssh_keys` and `revoke_ssh_key`, for the calling agent's own keys. See [SSH gateway](#ssh-gateway).

Home Assistant: `ha_list_devices`, `ha_list_entities`, `ha_get_state`, `ha_list_services`, `ha_list_device_triggers` (ready-made trigger definitions for a device), `ha_get_automation` (an automation's or script's config, whether it is on and when it last ran), `ha_find_related` (the automations and scripts that use a device or entity, and the other way round), `ha_list_traces` and `ha_get_trace` (recent runs of an automation or script, step by step), `ha_history` (state changes from the recorder), `ha_logbook` (changes and events with what caused them), `ha_system_log` (HA's own warnings and errors), `ha_list_statistics` and `ha_statistics` (long-term statistics per 5 minutes, hour, day, week or month), and `ha_listen` (wait for a trigger to fire, so an agent can ask the user to press a button and see the resulting payload). Listings take filters and are paged, since real installs have thousands of entities. All of these are read-only and use HA's WebSocket API, some of it admin-only, so the HA token must belong to an administrator. Times from HA (seconds or milliseconds since the epoch) are returned as ISO 8601. Traces are looked up by the automation's `id` from its config, so automations without one have none.

Devices: `list_devices` (names, owners, capabilities, connection). Read-only; see [Devices](#devices-apple-apps).

The MCP server's instructions point agents to the hob's `AGENTS.md` and explain the core rules.

The endpoint is streamable HTTP at `/mcp`, stateless (a fresh server per request), authenticated with a bearer token: a static agent token or an OAuth access token (see MCP auth under [Users and authentication](#users-and-authentication)). File tools act on the branch workspace checkout on the host and reject paths and symlinks that lead outside it. `main` is readable through a host-only checkout reset to the branch tip on each read. Writes, `bash` and `commit` on `main` are refused. `search` matches in a worker thread with a deadline, so an agent-supplied regular expression cannot block the host. `bash` runs through the workspace VM's `exec` (see `ExecWorkspaceVm` in `server/src/workspaces.ts`) with a timeout, and long output is cut in the middle.

### SSH gateway

`server/src/ssh/`, on `HOBWORK_SSH_PORT` (default 2222, `off` disables it), built on the `ssh2` package (pure JavaScript; its optional native `cpu-features` build is not allowed in `pnpm-workspace.yaml`). The host key is an Ed25519 key generated on first start at `data/ssh_host_ed25519_key` (mode 0600).

- **Auth**: public keys only, each registered to an agent (`agent_ssh_keys`: name, key type, base64 key data, SHA-256 fingerprint, comment, where it was added and by whom, `revoked_at`). Every key has a name. Revoked keys keep their row, and a key can be added again once its earlier row is revoked. Users add and revoke keys with `POST /api/agents/<id>/ssh-keys` (`{ name, publicKey }`) and `POST /api/ssh-keys/<id>/revoke`; `GET /api/agents` lists them per agent with `addedFrom`. Agents manage their own keys over MCP: `add_ssh_key(name, public_key)`, `list_ssh_keys` and `revoke_ssh_key(id)`, only for their own agent. A key an agent adds records the agent token or OAuth grant it used, and revoking that token or grant revokes the key, so cutting off an agent's access also cuts off the SSH keys it gave itself, and such a key has that token's or grant's [access limits](#access-limits). Keys added by a user or on the host are not tied to a token or grant. Without the web UI: `pnpm --filter @hobwork/server add-ssh-key <agent-name> <key-name> [key.pub]` (creates the agent if needed, reads stdin without a file).
- **User name** is the target: `<hob>/<branch>`. OpenSSH accepts a slash in the user name (checked with OpenSSH 10.3). `<hob>+<branch>` works too, for clients or URLs where a slash is awkward. Hob names contain neither character and branch names cannot contain `+`, so the first `/` or `+` splits. The target is checked after authentication, so a bad target gets a message rather than a bare "Permission denied".
- **Sessions**: a shell (`exec bash --login`) or `ssh host '<command>'` runs in the branch's workspace VM with `/workspace` as the working directory, starting the VM like `bash` does. Gondolin supports stdin, a PTY and PTY resize on an exec, so interactive shells get a real terminal with the client's `TERM` and window size, and window changes follow. Without a PTY request (`ssh host cmd`, `ssh -T`) stdin, stdout and stderr stay separate and binary-safe. The exit status is passed back. A dropped connection kills the command (same `/proc` environ kill as `bash`). `main` is refused like `bash` on `main`. Port forwarding, agent forwarding, X11, SFTP and git over SSH are not supported.
- **Idle stop**: a session counts as a running command, so the VM is not stopped while it lasts, and `last_used_at` is updated when it starts and ends.

**`hobwork` CLI** (`packages/sdk/src/cli/main.ts`): `status` (branch head, uncommitted changes, `main`'s version and what is deployed, last pipeline run of the branch, the app URLs of the branch and `main`), `diff`, `commit "<message>"`, `merge "<summary>"`, `logs [-f] [-n N]`, `invocations [-n N]`, `sql "<statement>"` (see [Branch and test DBs](#branch-and-test-dbs)), `ha state|states` (see [Hobwork to HA](#hobwork-to-ha-actions)). A merge failure exits with status 1, usage errors with 2. The workspace has no git directory, so `hobwork commit` is how SSH users commit.

- **Delivery**: mounted read-only from the host at `/opt/hobwork/cli`, with a `/usr/local/bin/hobwork` wrapper written when the VM starts. Like the runtime runner, it speaks the host's internal API and so has to match the host version; baking it into the image would need a rebuild for every API change. It uses only Node built-ins.
- **Endpoint**: the workspace VM's internal handler (`server/src/workspace-api.ts`), bound to the VM's hob and branch, answers `/v1/workspace/*` at `hobwork.internal`. The CLI uses `node:http`, since `fetch` gives up waiting for response headers after 5 minutes and a merge can take longer. `logs -f` long-polls with a cursor (up to 30 seconds per request).
- **Identity**: the agent that runs the command. A workspace VM is shared by every agent working on the branch, so binding an agent to the VM would credit one agent with another's commit or merge. Every SSH session and every MCP `bash` call opens a workspace session: a random token, valid while the command runs, passed as `HOBWORK_SESSION`. Child processes inherit it, the CLI sends it back in `x-hobwork-session`, and the handler accepts it only for its own workspace. Calls without a valid token (e.g. from a background process that outlived its session) are refused. The same holds for the workspace VM's `/v1/db`, `/v1/ha` and `/v1/devices` (checked in `server/src/guest-vm.ts`; `hobwork sql` and `hobwork ha` and the SDK clients send the header when `HOBWORK_SESSION` is set). Runtime VMs have no session and are not affected. Other processes in the same VM could read a token from `/proc`; that is within the household trust model (see [Non-goals](#non-goals)).

### Rules for agents

Written into `AGENTS.md` in every hob and into the MCP server instructions:

- Handlers are like AWS Lambda functions. Nothing in memory survives between invocations. Store state with the SDK (hob DB).
- Every change needs tests. `merge` runs typecheck, lint, tests and build, and refuses on failure.
- Migrations are forward-only and additive (add tables and columns, do not drop or rename), so older versions keep working after a restore.
- Use `get_logs` and `list_invocations` to debug. Do not guess.
- There are no long-running processes. Anything that needs to persist goes in the hob DB.
- Prefer the platform dependency set. Add extra packages only when nothing in it does the job.

## Delivery pipeline

`merge` on a branch:

1. Start a fresh pipeline VM with the candidate: the branch rebased (or merged) onto current `main`.
2. Validate `hobwork.json`. When it has comments or trailing commas and `vite.config.ts` still reads it with `JSON.parse` (hobs created before JSONC), this step fails and shows the template's `vite.config.ts` as the replacement.
3. Install extra dependencies, if the hob has any. Platform packages are already in the image.
4. `typecheck`, `lint`, `test`, `build` (package.json scripts from the template). `build` bundles handlers and dashboards with Vite, then Hobwork renders the hob icon into the build (see [Hob icons](#hob-icons)).
5. Apply new migrations to a copy of the production DB, as a dry run (see [Data](#data)).
6. On success: squash-merge into `main` with the agent's summary as the commit message, apply migrations for real, deploy.
7. On failure: return the failing step with its output to the agent. No human is involved. The agent fixes and calls `merge` again.

There is no human approval step. Users see the result as a new version in the UI.

Pipeline runs are recorded (step, status, output, duration) and visible to agents through `pipeline_status`.

Details:

- `merge` takes only committed changes and refuses while the workspace has uncommitted ones.
- The candidate is built in a temporary host-side clone: the branch is squashed into one commit (author: the agent, committer: Hobwork, message: the agent's summary) and rebased onto `main`. Squashing first means only the branch's end result has to apply. On conflict, the conflicting files are returned and the agent redoes the change on a new branch from `main`.
- Merges and restores run one at a time per hob, so each candidate is tested against the `main` it lands on.
- The pipeline VM gets a clean checkout of the candidate with no git directory. `hobwork.json` and `package.json` are read on the host from git, never from the checkout. Extra dependencies are the `package.json` dependencies not in the platform set (see [Dependencies](#dependencies)).
- After a successful merge, the branch and its workspace checkout are reset to the new `main` (ignored files like `node_modules` stay), so the agent can keep working on the same branch. If the branch changed while the merge ran, it is left as it was.
- The pipeline VM backend is a seam (`StartPipelineVm` in `server/src/pipeline/runner.ts`), implemented on the `Sandbox` in `server/src/guest-vm.ts`. `server/src/pipeline/host-backend.ts` runs commands on the host without a sandbox and exists only for tests.

## Versions and rollback

- Every merge is one squash commit on `main` = one version. Version 1 is the template commit from hob creation.
- The UI lists versions with their summaries. "Restore this version" commits that version's tree as a new commit on `main`, records it as a new version and deploys it, without running the pipeline. History is never rewritten.
- Restoring code does not roll back data. Additive migrations keep this safe.
- **Auto-revert**: if a new version fails completely (runtime does not start, or every invocation fails for several minutes after deploy), Hobwork restores the previous version automatically and records why, so the agent can see it.

Auto-revert details (`server/src/runtime/auto-revert.ts`):

- Only versions deployed by a merge are watched. Restores, including the auto-revert's own, are not, so a broken old version cannot start a loop.
- "Does not start": the VM does not boot, or the runner exits or does not answer within 60s. The runner imports every handler before it reports ready, so a handler that throws at import time counts.
- "Every invocation fails": within 1 hour of the deploy, no invocation succeeded, at least 5 failed, and the first and the latest failure are at least 3 minutes apart. One success ends the watch. The time span keeps a short outage of something a handler calls from reverting a good version; the count keeps a single failed cron from doing it.
- The target is version N-1, since versions on `main` are linear. The restore goes through the normal restore path with Hobwork as the author and the reason as the summary (`Auto-revert to version 4: version 5 did not start`). An `auto-revert` event in the hob log says why. The merge that deployed the broken version reports the start failure and the pending revert in its result.

## Runtime

- Each deployed hob has 0 or 1 runtime VMs. There is no scaling beyond 1. Concurrent invocations run in the same VM.
- The VM starts on the first invocation (HTTP request, cron tick, trigger) and stops after an idle timeout. Default 1 hour, configurable per hob in `hobwork.json`. Cold start cost is the VM boot (0.5s on the Mac, 0.7s on `colossus`).
- **Lifetime**: `idleTimeout` is clamped to 2^31-1 ms (larger delays make `setTimeout` fire at once). A VM is also replaced 1 hour after it started (`DEFAULT_MAX_LIFETIME_MS` in `runtime.ts`), however busy it is, so code that got into it through one invocation does not see invocations hours later. The VM is retired like an old one after a deploy: it leaves service at once, its running invocations finish (up to the invocation timeout), and the next invocation starts a new VM. A VM is retired the same way after an invocation times out (the handler may still be running) or the runner crashes.
- **Runner ingress**: the host writes a random per-VM token to `/tmp/hobwork-runner-token` in the guest before starting the runner, which reads and deletes the file at startup, so it is not in the environment or on disk when handler code runs. The runner answers 401 to every request (`/ready` included) without `Authorization: Bearer <token>`. Handler code runs in the runner's own process, so this keeps out other processes in the VM and anything that reaches the ingress port, not code that already runs in the runner, which can read process memory.
- **Response size**: a handler's response body is limited to 24MB (`MAX_RESPONSE_BODY_BYTES`); a larger one fails the invocation. The host also stops reading a runner response over that size as base64 JSON plus 1MB.
- **Log attribution**: a runner's log lines attach to an invocation only when the invocation belongs to the same hob and the same branch (or main), so a preview's VM cannot write into main's invocations.
- Inside the VM a Hobwork **runner** (Node) loads the deployed build and serves invocations from the host over the Gondolin ingress.
- The host owns scheduling and trigger subscriptions. A cron tick, webhook call or trigger wakes the VM if it is asleep.
- Deploy: start the new VM, wait until it is ready, switch traffic, drain and stop the old one.
- Handlers call back to the host (DB, logs, Home Assistant, devices) through the SDK over an internal endpoint that only the hob's VMs can reach.

Implementation (`server/src/runtime/`):

- **What runs** is the newest version on `main`. The host reads its `hobwork.json` from git and keeps it in memory; after a host restart it reads it back from the versions table. On start the host registers the crons and HA triggers of every hob's current version, including version 1 of a new hob.
- **Build artifacts.** A build is the hob's `dist/` after `pnpm run build`, stored at `data/builds/<hob>/<tree>/`. The pipeline deletes its checkout after the run, so its build step copies `dist/` there first, after the pipeline VM has stopped so build code cannot change `dist/` during the copy. Builds are keyed by git tree, not commit: a restore commits an old tree as a new commit and finds that version's build already there, so a restore does not build again. A version with no stored build (the template commit of a new hob, or versions from before builds were kept) is built on deploy or first invocation in a fresh pipeline VM (install extras, `pnpm run build`, the icon, no tests). Only directories and regular files are copied, since the runtime VM mounts the build and a symlink written by hob code could point at host files: files are opened with `O_NOFOLLOW` and checked with `fstat`, and a symlink or any other entry makes the build fail with its path. Builds are limited to 256MB, counted as bytes copied.
- **Old builds** (`server/src/runtime/build-cleanup.ts`) are deleted after every deploy and by the daily housekeeping job. A hob keeps the builds of its newest 10 versions, of the versions its runtime VM runs or is starting, and any build less than an hour old (a pipeline stores its candidate's build before the merge records the version, and a restore may be building one). A restore of a version whose build was deleted builds it again, like a version from before builds were kept. The daily job also removes build directories of hobs that no longer exist.
- **Handler bundles.** The template's `vite.config.ts` only calls `hobworkViteConfig()` from `@hobwork/sdk/vite`, so build changes reach hobs with the guest image. It builds two Vite environments in one `vite build`: the dashboard (`index.html` at the hob root with its code in `ui/`, built to `dist/index.html` and `dist/assets/`) and the handlers. Every handler in `hobwork.json` becomes `dist/handlers/<path without extension>.js`, an ES module with all dependencies bundled in (Node built-ins stay external), so the runtime VM needs no `node_modules`.
- **Runner delivery.** The runner is `packages/sdk/src/runner/` and uses only Node built-ins. The host mounts that directory read-only at `/opt/hobwork/runner` and runs `node /opt/hobwork/runner/main.ts`, with the build read-only at `/app`. The runner is host code, not SDK API: it speaks the host's invoke protocol, so it has to match the host version, and outside `node_modules` Node runs its TypeScript directly. Hob code depends only on the context type from the SDK in the image, so context changes must stay additive for builds tested against an older SDK to keep working.
- **Protocol** (`packages/sdk/src/runner/protocol.ts`). The host POSTs `/invoke` on the runner's ingress with the invocation (ID, kind, name, manual), the handler path, the serialized request (method, URL, headers, base64 body), route params and payload. The runner answers with the serialized response or the error (name, message, stack). `GET /ready` answers once every handler module loaded. Console output inside an invocation (tracked with `AsyncLocalStorage`) and `ctx.log` lines are batched to `POST http://hobwork.internal/v1/logs` and flushed before the invocation answers. Output outside any invocation goes to the runner's stdout, which the host records as runtime logs.
- **VMs** get 512MB and 2 vCPUs, the hob's `egress` plus the hosts of its secrets, the secrets as placeholders, and an internal handler bound to the hob. A blocked egress request is logged as an `egress-blocked` event. Secrets are fixed when a VM starts, so an invocation that finds them changed starts a new VM and retires the old one.
- **Deploy** (the delivery `Deploy` hook): ensure the build, apply the version's new migrations to the hob DB (a failure counts as "did not start" and triggers auto-revert), switch crons and HA triggers (`syncProjectTriggers`) to the new version, start the new VM and wait for `/ready`, switch, then retire the old VM: wait for its running invocations (up to the invocation timeout) and stop it. Without a runtime VM backend the bookkeeping still happens and invocations fail with an explanation.
- **Invocations** time out after 5 minutes on the host. Gondolin cannot signal the handler, so it may keep running until the VM stops. A runner that exits is logged as a `crash`, and the next invocation starts a new VM.
- **Routes** answer on two addresses. On the Hobwork host, `/p/<hob>/api/*` takes only an agent token (`Authorization: Bearer`) within its [access limits](#access-limits); the check is a `RouteAuthorizer` function in `server/src/runtime/http.ts`. Session cookies are not accepted there, since no page on the Hobwork origin calls hob routes. On the hob's app origin, `/api/*` takes only that origin's app session (see [Hob app origins](#hob-app-origins)). `authorization`, `cookie` and `proxy-authorization` headers are never passed to the handler. Request bodies are limited to 10MB. Handler responses on the Hobwork host (routes and webhooks) get `Content-Security-Policy: sandbox; default-src 'none'` and `X-Content-Type-Options: nosniff`, and lose `Set-Cookie`, so a handler that reflects input into HTML cannot run script with the Hobwork session.
- **Crons and HA triggers** of a branch never run on their own: the scheduler and HA subscriptions only use the deployed version. A branch's crons and triggers run through `invoke` with `branch`.
- **Webhooks** at `/hooks/<hob>/<name>/<token>` accept any method. Tokens are 256 random bits, stored as SHA-256 hashes in `webhook_tokens`, and created or replaced with `rotate_webhook_token`, which shows the URL once. A webhook without a token cannot be called. Unknown hob, webhook and token all answer 404. The handler sees the URL without the token.
- **Crons** use standard 5-field syntax, parsed by `server/src/runtime/cron.ts` rather than a dependency: numbers, ranges, lists, steps, month and weekday names, and Vixie cron's rule that a day matches either day field when both are restricted. Times are in the host's local time zone. A time skipped by a DST change does not run, a time that happens twice runs once, and ticks missed while the host is down are not caught up.
- **HA triggers** fire through the trigger registry's `invoke` hook as invocations of kind `trigger` with HA's trigger variables as `payload`. Refused or failing triggers, and HA connection losses that drop trigger events, are logged as `trigger` events in the affected hobs' logs.

### Branch previews

A branch can be tried out before it is merged: its UI at its own app origin, its routes, and its crons, webhooks and triggers by hand. `server/src/runtime/runtime.ts` runs a preview like a deployed version, keyed by hob and branch.

- **What runs**: the branch's latest commit in the bare repo, so only committed changes. Rejected: running the workspace checkout, which would show half-written files and need a build per request. Each request reads the branch head; a new commit makes the next request start a new VM and retire the old one, like a deploy. Previews have version `null`.
- **Build**: on first use, from that commit in a fresh pipeline VM (`createBuilder`, the same as for a version without a stored build). Builds are keyed by tree, so a branch that is merged unchanged reuses its build.
- **VM**: a separate runtime VM per branch with the same runner, resources (512MB, 2 vCPUs), egress and secrets as the deployed version, labelled `preview <hob>/<branch>`. It stops after the branch's `idleTimeout`, at most 15 minutes. Rejected: a runner inside the workspace VM, which lives as long as agents run commands and has the registry in its egress allowlist.
- **Data**: the branch DB copy from [Branch and test DBs](#branch-and-test-dbs), with the preview commit's migrations applied the same way as for workspace queries. A workspace VM start copies production again, so preview data does not survive it.
- **Records**: invocations and log lines carry the branch (`invocations.branch`, `logs.branch`; `NULL` for the deployed version). Auto-revert never watches previews.
- **Cleanup**: deleting a hob stops its preview VMs and closes their branch DBs. Build cleanup keeps the builds that preview VMs run or are starting with; a preview's build is never one of the kept versions, so it goes with the next cleanup after its VM stops (a preview VM stopping runs one).
- **App origin**: `<branch label>--<hob>.<apps host>`, with its own app session (a session for main or another branch is rejected), through the same sign-in handoff as main with `branch` in `/auth/app`.
- **Branch labels** (`server/src/apps/origins.ts`): a whole host label is at most 63 characters of `a-z`, `0-9` and `-`. A branch that is already a lowercase label of at least three characters, with single hyphens, keeps its name (`add-spools--filament`). Any other branch (uppercase, `/`, `.`, `_`, two characters or fewer, which would put `--` at positions 3 and 4 like `xn--`, or too long) becomes a slug of its name plus the first 6 hex digits of its SHA-256 (`feature/Spools` becomes `feature-spools-3f9a1c`), so labels never collide. Labels never contain `--`, and hob names cannot, so the last `--` splits the label. Hob names are at most 40 characters, which leaves at least 21 for the branch. The host resolves a label by computing the labels of the hob's branches (cached for 5 seconds).
- **Webhooks**: `/hooks/<branch label>--<hob>/<name>/<token>`, with tokens per branch (`branch_webhook_tokens`), created with `rotate_webhook_token` and `branch`. Main's tokens do not work on a branch URL and the other way round. The host checks the token (`branchesWithWebhookToken`) before it resolves the branch label, which runs git, so a request with a wrong token costs no git work.
- **Home Assistant**: see [Hobwork to HA](#hobwork-to-ha-actions).
- **Web UI**: the hob page lists branches with their last commit, recent runs, a Preview page with the app in an iframe, and the Home Assistant switch. Activity has a filter for the live version and each branch, and the activity across hobs names the branch of preview runs and events. `GET /api/projects/<name>/branches` returns this; `GET /api/projects/<name>/invocations?branch=<name>` filters (`main` for the live version).

### Internal endpoint

The SDK talks to the host at `http://hobwork.internal/` (HTTPS works too, through Gondolin's TLS interception). The hostname does not exist anywhere. Every sandbox is created with its own `internal` handler, and Gondolin's egress `onRequest` hook answers requests for `hobwork.internal` with that handler's `Response` before any DNS lookup, allowlist check or upstream connection.

- The handler is bound to the VM when it is created, so the host knows which hob, version and workspace a call comes from without a token in the guest.
- Nothing else on the host is reachable. Host services on `127.0.0.1`, `10.0.2.2` and internal ranges are blocked by the egress policy, and no TCP port is forwarded.
- Secrets are substituted after `onRequest`, and none is bound to `hobwork.internal`, so the handler only ever sees placeholders.

Rejected: an allowed internal host (a real host port through `allowedInternalHosts`) would need auth tokens in the guest and exposes a real socket.

### Invocations and logs

Every invocation is recorded: ID, hob, version, kind (route, webhook, cron, trigger), whether it was started by hand, start, duration, result, error with stack trace. Console output from handlers is captured per invocation. Pipeline output and runtime lifecycle events (start, stop, crash, auto-revert) go to the same log store.

Output from guests is bounded on the host. The runtime's stdout and stderr are split into lines of at most 8192 characters (`server/src/runtime/line-splitter.ts`; the rest of a longer line is dropped, so a guest that never writes a newline cannot grow host memory). Each VM may log 100 lines in a burst and 10 per second on average while no invocation is running (`log-limiter.ts`); excess lines are dropped and the next line that gets through is preceded by a `N log lines dropped` warning. Inside an invocation the per-invocation line limit applies. Command output (`bash`, pipeline steps, builds) is collected as its first and last 14,900 characters with a marker of how much was cut (`HeadTailOutput` in `server/src/mcp/output.ts`), while it streams, so it never sits in host memory in full.

Agents read this through MCP (`list_invocations`, `get_logs`, `tail_logs`) and the `hobwork logs` CLI over SSH. Users see it on a hob's Activity (invocations, filtered by kind, status and time, and each one with its error, stack trace and lines) and Log (all lines, only lifecycle events, or warnings and errors) pages. The top-level Activity page lists runs of every hob with the same filters plus a hob filter (`GET /api/activity`), and a Problems view (`GET /api/activity/problems`) that merges failed runs with lifecycle events at warn or error level: blocked requests, rollbacks, crashes, DB warnings, refused triggers and failed deploys, paged by time. The nav shows how many problems happened since the browser last showed that view (`GET /api/activity/attention?since=`, the time kept in `localStorage`, at most a week back). A partial index on `logs (time) WHERE event IS NOT NULL` keeps these queries off the full log. The Log page follows new lines over [live updates](#live-updates): on a `logs` change for its hob it asks for `GET /api/projects/<name>/logs?after=<cursor>`, again while a whole page (200 lines) comes back, and once more after reconnecting. Rejected: a long poll per open Log page, which held a request open per page next to the socket that already says when lines arrive.

Storage (`server/migrations/0004_runtime.sql`, `server/src/runtime/logs.ts`):

- `invocations`: kind (`route`, `webhook`, `cron`, `trigger`), name (route key or entry name), `manual`, status (`running`, `ok`, `error`), HTTP status for routes and webhooks, error and stack. Invocations still running at host start are marked failed.
- `logs`: one row per line with source (`handler`, `runtime`, `pipeline`), level, an optional invocation, and for lifecycle lines an event kind (`start`, `stop`, `crash`, `deploy`, `auto-revert`, `egress-blocked`, `trigger`, `pipeline`, `migration`, `db`, `secret`, `ai-limit`). Pipeline runs stream each step's output into the log store line by line (`server/src/pipeline/output-log.ts`, prefixed `run <id> <step>:`), plus one summary line per step. A run stores at most 5,000 lines and a burst limiter applies; when the cap is hit a marker line says so. `pipeline_status` has each step's output as its first and last 14,900 characters. Log line IDs are the cursor for `get_logs` and `tail_logs`.
- Bounds: messages are cut to 8,000 characters in the middle, an invocation keeps at most 1,000 lines (then one line saying the rest was dropped), and rows older than 30 days or beyond the newest 200,000 lines per hob are pruned hourly. MCP output is cut at whole lines with a cursor to continue, and `tail_logs` waits at most 60 seconds.

## Data

- **Host DB**: SQLite for Hobwork's own state (users, agents, tokens, hobs, versions, invocations, logs, pipeline runs, secrets, AI settings and requests).
- **Hob DBs**: one SQLite file per hob at `data/projects/<hob>/db.sqlite`, owned by the host. Hob code reaches it through the SDK, which sends queries to the host. VMs do not open DB files directly, because SQLite locking and WAL shared memory do not work reliably through the guest filesystem bridge across VMs.
- All SQLite databases use WAL, `busy_timeout`, `synchronous = NORMAL`, `foreign_keys = ON` and `STRICT` tables. Hob DB connections also turn on SQLite's defensive mode.

### Query API

Handlers get `ctx.db` (`packages/sdk/src/index.ts`): `query(sql, params)` (rows), `get` (first row), `run` (`changes`, `lastInsertRowid`) and `batch(statements)`. Parameters are an array for `?` or an object for named placeholders. Values are null, numbers, strings, bigints, booleans (stored as 1 and 0) and `Uint8Array`. Blobs and bigints travel as `{ $blob }` and `{ $bigint }` in JSON.

- **Transport**: the runner POSTs `{ statements, transaction, invocation }` to `http://hobwork.internal/v1/db` (`DbRequest` in `packages/sdk/src/runner/protocol.ts`). The answer is the rows and change counts, or the SQLite error with the index of the failing statement (`DbError` in the handler).
- **Transactions**: there are no interactive transactions. A transaction held open across HTTP round trips would hold the hob's write lock while handler code runs, and a handler that crashes or times out would leave it open. `batch` sends all its statements in one request, and the host runs them in one `BEGIN IMMEDIATE` transaction that rolls back on the first error. Read-then-write logic uses single statements (`UPDATE ... WHERE`, `INSERT ... ON CONFLICT`, `RETURNING`) or a batch.
- **Rules** (`packages/sdk/src/db/execute.ts`, enforced with SQLite's authorizer and a small lexer): one statement per SQL string (node:sqlite would silently ignore the rest); no schema changes, which belong in migrations so the dry run sees them; no `BEGIN` or `SAVEPOINT`; no `ATTACH`, `VACUUM` or `load_extension`, which could read or write files on the host; only introspection PRAGMAs (`table_info` and similar); no writes to `hobwork_migrations`. Results are limited to 10,000 rows.
- **Execution**: each open hob DB has a worker thread with one connection (`server/src/data/db-pool.ts`), so a slow query blocks that hob's queries and not the host. A query that runs longer than 30s is abandoned: SQLite cannot be interrupted from Node, so the worker is terminated and the next query opens a new connection. Workers close after 5 idle minutes. A worker sets `PRAGMA trusted_schema = OFF`, so triggers and views in a DB that a migration produced cannot call unsafe functions. node:sqlite has no `setLimit`, so `SQLITE_LIMIT_ATTACHED` is not available; the authorizer above is what keeps `ATTACH` out of queries.
- **Isolation**: the internal handler is bound to the VM when it is created, so a runtime VM reaches only its hob's DB and a workspace VM only its branch DB.

### Migrations

- `migrations/NNNN_name.sql` in the repo, applied in version order, each in its own transaction, and recorded with a SHA-256 checksum in `hobwork_migrations` in the hob DB. Forward-only: there are no down migrations. The host reads the files from git, never from a checkout, and refuses symlinks, so a migration cannot make the host read other files.
- **Migrations run in a VM, never on the host.** Migration SQL is written by agents. On the host it could `ATTACH` other DBs, or end its own transaction with `COMMIT` and then `VACUUM INTO` any path, so it runs in a short-lived VM (`server/src/data/migration-vm.ts`, runner `packages/sdk/src/db/migrate-main.ts`) with no network. The host snapshots the DB into a fresh directory (`VACUUM INTO` from the DB's worker), mounts the directory at `/migrate` with `input.json` (the migration files), and the runner applies the migrations to `db.sqlite` there, with `journal_mode = DELETE` so one file comes back. The VM is stopped before the host reads anything. The host takes back only `db.sqlite` (`server/src/data/db-file.ts`): opened with `O_NOFOLLOW` and `O_NONBLOCK`, a regular file, at most twice the snapshot's size (at least 512 MB), copied byte by byte into a new file it owns, which must start with the SQLite header and pass `PRAGMA integrity_check`. Anything else in the directory, and the runner's own answer beyond "ok" or an error text, is ignored. A DB that fails a check never replaces the real one. Costs about a second of VM boot per run.
  A migration that fails leaves the DB as it was, since the copy is thrown away (before, earlier migrations of the same run stayed applied). Without a guest image the host applies them itself as a fallback, with an authorizer that denies `ATTACH`, `DETACH` and `load_extension` and a check that refuses `VACUUM` statements; it is not the path a normal host takes.
- **Deploy** applies the new migrations of the deployed version before it starts. It reads which versions the production DB has applied, and starts no VM when nothing is pending. Otherwise queries to the hob DB wait while the migration runs (the snapshot, the VM, the checks and the swap, a few seconds), so no write lands between the snapshot and the swap. Then the DB's worker is closed (which checkpoints the WAL), the WAL files are removed and the new file is renamed over `db.sqlite`. A restore of an older version has fewer migrations, and nothing is undone.
- **Dry run** (the pipeline's `migrations` step, `server/src/data/project-data.ts`): all migrations are applied to an empty in-memory DB (what tests and new hobs start from), then the new ones to a copy of the production DB. Both run in one VM, and the checks below read the DB that comes back, not what the VM reports. The production DB's worker writes the copy with `VACUUM INTO`, a consistent snapshot while handlers keep writing. node:sqlite's `backup()` was tried first and took seconds per copy under Vitest. The step fails with the SQL error, and also when:
  - an applied migration's file changed,
  - a new migration creates a table without `STRICT` (tables from earlier migrations are not checked again),
  - a table, view or column that existed before is gone afterwards.
- **Additive check**: comparing the schema before and after (tables and views with their columns, from `pragma_table_list` and `pragma_table_xinfo`) catches `DROP TABLE`, `DROP COLUMN` and both kinds of `RENAME` in any spelling. It still allows SQLite's usual way to change constraints: create a new table, copy the rows, drop the old table and rename the new one to the old name with the same columns. Rejected: matching `DROP` and `RENAME` in the SQL text, which cannot tell that rebuild apart from a real drop. Dropping indexes and triggers is allowed, since older versions still run without them.

### Branch and test DBs

- **Workspaces**: when a workspace VM starts, the host copies the production DB to `data/workspaces/<hob>/<branch>/db.sqlite` (an empty DB if the hob has none yet). Before each query from the VM, the branch's own `migrations/` that the copy has not seen are applied in a migration VM like a deploy, on a copy of the branch DB that replaces it (no gate is needed, since queries to one branch DB run one at a time). The host remembers the migrations each branch DB was brought up to, so only a change to `migrations/` starts a VM. The branch DB is in the workspace directory but outside the `files` directory the workspace VM mounts, so the VM cannot write it. If an applied one was edited, which is normal while developing, the branch DB starts over from a fresh production copy. The workspace VM reaches the branch DB at `hobwork.internal/v1/db`, and `hobwork sql "<statement>"` runs a statement on it.
- **Tests**: `@hobwork/sdk/testing` has `createTestDb()`, a fresh in-memory `node:sqlite` DB inside the VM with every migration from `migrations/` applied and the same executor and rules as the host, and `createTestContext()`, a handler context with one. Each call gives an empty DB, so tests are independent, and nothing crosses the VM boundary, so tests work the same in workspace and pipeline VMs. Rejected: an internal handler with a host-side empty DB for pipeline VMs, which would make tests share one DB and depend on the host.

### Warnings

- Statements slower than 500ms on a production DB are logged as `db` events (with the invocation, when the runner sent one), at most once per statement text every 10 minutes, and counted.
- DB size (file plus WAL) is checked at most once a minute after queries, and after migrations. Every time it crosses another 100 MB, a `db` warning is logged.
- `get_hob` shows `database`: size, a size warning once over 100 MB, and the slow query count, slowest time and last slow statement since the host started.

### Storage use

The hobs list in the web UI shows how much disk each hob uses, with the hob DB broken out since it is the part that grows (a tooltip has every part). `GET /api/projects`, `GET /api/projects/<name>` and the `list_hobs` and `get_hob` MCP tools return it as `storage`, in bytes (`server/src/storage.ts`):

- `database`: `data/projects/<hob>/` (the DB file, WAL and shared memory).
- `branchDatabases`: the `db.sqlite*` files in each `data/workspaces/<hob>/<branch>/`. `workspaces`: everything else there (checkouts and their git directories).
- `repo`: `data/repos/<hob>.git`. `builds`: `data/builds/<hob>/`.
- `logs`: the text of the hob's log lines and invocation errors and stacks in the host DB (`octet_length`), which shares one file with every other hob. Row and index overhead is left out.
- `total`: the sum. Sizes are apparent file sizes, and symlinks are not followed.

Walking a hob's directories is too slow for every request, so the host keeps the last measurement in memory, keyed by hob ID so a renamed hob keeps it until the next one. A rename measures the hob again under its new name, and a deletion drops its entry. Requests answer from it, and a hob with no measurement or one older than 5 minutes is measured again in the background, one hob at a time. `storage` is `null` until the first measurement. The host measures every hob when it starts. Rejected: storing sizes in the host DB, which needs a migration for numbers that are cheap to measure again after a restart.

## Backups

The host backs itself up to an S3-compatible bucket (AWS S3, Backblaze B2, Cloudflare R2, Hetzner Object Storage, MinIO) with [Kopia](https://kopia.io), daily at 03:30 local time by default (`server/src/backup/`).

- **What**: the host DB, every hob DB, every hob repo, `secret.key` and the SSH host key. Left out: builds (rebuilt on demand), workspaces (branches are in the repos; uncommitted workspace files are lost) and the Home Assistant and Pocket ID dev data.
- **Consistency while the host runs**: each run writes a copy into `data/backup-staging/`, laid out like a data dir. DBs are copied with `VACUUM INTO` from a worker thread, as for the migration dry run. Repos are copied with `git clone --mirror --no-local`, which goes through git's pack protocol and gets a consistent set of refs and objects while pushes and merges go on. Rejected: copying under the per-hob merge lock, which does not cover pushes over HTTP and SSH. The hob list comes from the copied host DB, so a hob created during the run is left out whole. Kopia then snapshots the staging dir, which is deleted afterwards.
- **Incremental**: Kopia splits files into content-defined chunks (4 MB on average) and uploads only chunks the repository does not have yet, so an unchanged DB or repo costs nothing and a changed DB costs the chunks around the change. Compression is zstd.
- **Secret key**: included, since the encrypted values in the host DB are useless without it. The Kopia repository is encrypted with its own password (`HOBWORK_BACKUP_PASSWORD`), which must be kept outside Hobwork, e.g. in a password manager: without it nothing can be restored, and anyone with it and the bucket credentials can read every secret. With `HOBWORK_SECRET_KEY` there is no key file, so that key must be kept the same way.
- **Kopia**: the host runs the `kopia` binary (`HOBWORK_KOPIA_BIN`, default `kopia` on `PATH`). Tested with 0.17.0, the version on `colossus` (`/usr/bin/kopia`, AUR `kopia-bin`); it uses no flags or JSON fields newer than that. Credentials and the password reach it through its environment (`KOPIA_PASSWORD`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`), never through arguments or logs. Its config, cache and logs are in `data/kopia/`. The first run connects to the repository, or creates it when the bucket prefix is empty, with `--no-persist-credentials` and the fixed identity `hobwork@hobwork`, so a host restored on another machine continues the same history. Kopia runs its own maintenance after snapshots.
- **Retention**: Kopia's global policy keeps 14 daily, 8 weekly and 12 monthly snapshots (`HOBWORK_BACKUP_KEEP_DAILY|WEEKLY|MONTHLY`), no hourly ones, and Kopia's defaults of the latest 10 and 3 annual ones. The policy is set again when the numbers change.
- **Runs**: the host's cron scheduler starts them (`HOBWORK_BACKUP_SCHEDULE`, a cron expression, `off` for manual backups only). A lock file (`data/backup.lock`) keeps the host and the CLI from running two at once. Each run is a row in `backup_runs` with its start, duration, snapshot ID, size, file count, uploaded bytes (how much the repository's blobs grew, since Kopia 0.17 does not report uploads) and error. Failures are logged as `BACKUP FAILED: ...`. Runs left as running by a stopped host are marked failed on start. Settings in the web UI shows the last backup, the next one, recent runs and a "Back up now" button (`GET|POST /api/backups`, users only).
- **Config**: backups are on when `HOBWORK_BACKUP_S3_BUCKET` is set, together with `HOBWORK_BACKUP_S3_ACCESS_KEY_ID`, `HOBWORK_BACKUP_S3_SECRET_ACCESS_KEY` and `HOBWORK_BACKUP_PASSWORD`. Optional: `HOBWORK_BACKUP_S3_ENDPOINT` (a host, or a URL where `http://` turns TLS off; default `s3.amazonaws.com`), `HOBWORK_BACKUP_S3_PREFIX` (default `hobwork/`), `HOBWORK_BACKUP_S3_REGION`.
- **Setting up on `colossus`**: Kopia 0.17.0 is already installed. Create a bucket (and a key limited to it) at the S3 provider, put the `HOBWORK_BACKUP_*` settings into the systemd unit's environment (or a credential file), store the password in the password manager, and run `backup now` once to create the repository and check the settings.
- **CLI**: `pnpm --filter @hobwork/server backup now|list|verify [--percent <n>]|restore <empty-dir> [--snapshot <id>]`. `verify` runs `kopia snapshot verify`, which reads every snapshot's directories and a random share of the files (default 10 percent).
- **Restore**: on the new machine, with the same `HOBWORK_BACKUP_*` settings, run `pnpm --filter @hobwork/server backup restore <empty-dir>` (the newest snapshot, or `--snapshot <id>` from `backup list`). It connects with a throwaway Kopia config, restores into the dir and sets the key files to mode 0600. Then start the host with `HOBWORK_DATA_DIR` pointing there (and the old `HOBWORK_SECRET_KEY`, if one was used). On start the host reinstalls repo hooks; workspaces are cloned again when used and builds are rebuilt on the first invocation. By hand, the same is `kopia repository connect s3 ...`, `kopia snapshot list --all` and `kopia snapshot restore <id> <dir>`.
- **Tests**: unit tests use a fake `kopia`. `HOBWORK_BACKUP_TESTS=1` runs an integration test against MinIO with Kopia in Docker (`dev/backups/`): two backups with a change in between, where the second uploads a small fraction of the first, then a restore into an empty dir and a host started on it with its hobs, DBs and secrets intact.

## Releases

The host ships as a tarball built by `.github/workflows/release.yml`. Pull requests, pushes to `main`, `v*` tags and manual runs all run install (frozen lockfile), typecheck, lint and test. Except on pull requests, it then packages the host on an x86_64 runner and attaches the tarball to a GitHub release for a tag, or keeps it as a workflow artifact for 30 days otherwise. `release/package.sh <version>` does the packaging and runs anywhere with git, Node and pnpm, but packages only for the architecture it runs on.

- **Contents**: `hobwork-<version>-linux-x86_64.tar.gz` (about 160MB, 560MB unpacked) holds one directory, `hobwork-<version>-linux-x86_64/`, laid out like the repo: the committed `server/` source and migrations, `packages/sdk`, `packages/theme`, `templates/project`, `images/platform`, the built `web/dist`, the x86_64 guest image at `images/build/x86_64` built from the same commit (it contains `packages/sdk`), production `node_modules` installed for linux-x64, and `VERSION` with the version and commit. A `.sha256` file sits next to it. The version is the tag without its `v`, or `<branch>-<short commit>` otherwise.
- **`node_modules`**: installed with `pnpm install --prod --filter @hobwork/server --filter @hobwork/sdk --filter @hobwork/theme` in the staged tree (the server uses `jsonc-parser`, a dependency of the SDK). `pnpm deploy` would give the server a standalone directory and break its relative imports of `packages/sdk` and `packages/theme`. pnpm's links are relative symlinks, so the tree works from any path; the script fails on an absolute one.
- **From the machine**: Node >= 24.12 (`colossus` runs 26), `qemu-system-x86_64` and `qemu-img` 7.2 or newer (Gondolin 0.12 uses `-netdev stream`; `qemu-img` makes the copy-on-write root disks), git with `git http-backend` (part of git on Arch and Debian), Kopia 0.17 when backups are on, and read-write `/dev/kvm` for the service user.
- **Install and upgrade**: releases go to `/opt/hobwork/releases/`, with `/opt/hobwork/current` a symlink to the running one. The data dir lives elsewhere (`HOBWORK_DATA_DIR=/var/lib/hobwork`), since the default `data/` is inside the release.

  ```sh
  sha256sum -c hobwork-1.2.0-linux-x86_64.tar.gz.sha256
  sudo tar -xzf hobwork-1.2.0-linux-x86_64.tar.gz -C /opt/hobwork/releases
  sudo ln -sfn releases/hobwork-1.2.0-linux-x86_64 /opt/hobwork/current
  sudo systemctl restart hobwork
  ```

  The systemd unit runs `/usr/bin/node server/src/index.ts` with `WorkingDirectory=/opt/hobwork/current` and the `HOBWORK_*` settings in its environment. Host CLIs run the same way, e.g. `cd /opt/hobwork/current && HOBWORK_DATA_DIR=/var/lib/hobwork node server/src/cli/create-token.ts <name>` (the release has no pnpm). Rolling back is pointing `current` at the previous release. Host DB migrations are forward-only, so an older release then runs against a DB that newer migrations may have changed.
- **Private repo**: downloading a release needs a GitHub token with read access to the repo's contents, e.g. `gh release download v1.2.0 -R Barmore-Genc/hobwork` on a machine that is signed in to `gh`, then copying the files over.

## Secrets and network

- **Library and assignments**: there is one library of secrets. A secret has a name for people (`Spoolman API key`, unique ignoring case, at most 80 characters), a value, the hosts it may be sent to, and optionally the names of headers besides `Authorization` it may be sent in (`headers`, JSON in the `secrets` table from migration 0031, lowercased, at most 10, no connection headers like `host`). Only people set headers, like hosts; agents see them in `list_secrets`. Existing secrets have none, so hobs that put a secret in another header (for example `X-Api-Key`) fail with the 403 above until someone adds the header; secrets in a URL or body were never filled in. A hob gets a secret only when it is assigned to it, and each assignment picks the env name the hob sees (`SPOOLMAN_TOKEN` in one hob, `API_KEY` in another). A hob has at most one assignment per secret and one secret per env name. Env names are env var style and must not replace variables the guest relies on (`PATH`, `NODE_OPTIONS`, `HOBWORK_*` and similar). Host patterns follow Gondolin: `api.example.com` or `*.example.com`. `*` alone and `hobwork.internal` are refused.
- **Who does what**: only people create secrets and set their values (web UI or the host command). A secret can be created without hosts; it is then sent nowhere. Agents can list the library, assign and unassign secrets, and ask for hosts over MCP, and nothing else. An agent that could set hosts could assign any secret to a hob and send its value anywhere, so hosts an agent asks for apply only after a person approves them.
- **Host requests** (`secret_host_requests`): `request_secret_hosts(secret, hosts, reason)` stores the full list of hosts the agent wants and a reason, and returns a link to `/secrets/requests/<id>`. That page shows only the request: the secret, the agent, the reason, and each host as added, kept or removed compared to the current hosts. Approving replaces the secret's hosts with the requested ones (logged like any change, as the approving user). A newer request for the same secret supersedes an unanswered one. The Secrets page links to a waiting request, and `list_secrets` shows its hosts as `pendingHosts`. Web API: `GET /api/secrets/host-requests/<id>`, `POST .../approve|deny`. Assignments, and changes and deletions of assigned secrets, are logged as `secret` events in each affected hob's log with who did it (user, agent, or the host command line).
- **Storage** (`server/src/secrets.ts`, `secrets` and `secret_assignments` tables): values are encrypted with AES-256-GCM, a random 96-bit IV per value, and `hobwork-secret:v2:<secret id>` as additional authenticated data, so a ciphertext copied to another row does not decrypt. The name is left out so a secret can be renamed without re-encrypting. `secrets` records the user who created and last changed it (null for the host command), `secret_assignments` the user or agent that assigned it.
- **Migration from hob and global secrets** (0010): each old hob secret becomes a library secret assigned to its hob, and each global secret becomes one library secret assigned to every existing hob that did not have its own secret of that name, so no hob's secrets change on upgrade. Old names become both the library name and the env name. When several old secrets shared a name (a global one and hob overrides, or several hobs), the global one keeps it and hob ones get the hob appended (`SHARED (filament)`); old names are env var style, so this cannot clash. The migration is SQL and has no key, so it keeps each ciphertext and stores its old additional data in `legacy_aad`. When the host opens the store with the key, it re-encrypts those values with the new additional data and clears the column. A value that does not decrypt (wrong key) is left as it was and fails when a VM needs it, as before.
- **Key**: `HOBWORK_SECRET_KEY` (32 bytes as hex or base64) when set. Otherwise `data/secret.key`, generated on first start with mode 0600. The host refuses to start when the file is readable by other users. The file protects against a leaked copy of `hobwork.db` alone. Hobwork's own backups include it, inside the encrypted Kopia repository (see [Backups](#backups)). The env var, e.g. from a systemd credential, keeps the key out of backups. With a different key, existing secrets do not decrypt and VM starts fail with that message instead of using wrong values.
- **In VMs**: the host decrypts values only to hand them to the `Sandbox`'s `secrets` option, keyed by env name. The guest sees `GONDOLIN_SECRET_...` placeholders in env vars of the assigned env names, and the runner gives handlers `ctx.secrets` (env name to placeholder). Gondolin replaces a placeholder with the value in request headers to the bound hosts only, after the internal handler ran, so neither handler code nor the host's internal endpoint sees values. Substitution in URLs and bodies is off.
- **APIs**: no API or MCP tool returns values. MCP: `list_secrets` (the library with each secret's hosts, headers and assignments, or with `hob` the hob's env names), `assign_secret(hob, secret, env_name)`, `unassign_secret(hob, env_name)` and `request_secret_hosts`; no tool takes a value, and hosts from an agent wait for approval. `get_hob` lists the env names. The web API in `server/src/api/routes.ts` needs a signed-in user and the CSRF header, so agent and OAuth tokens get 401 on every secret endpoint, assignments included (agents assign only over MCP): `GET /api/secrets` (the library with assignments), `POST /api/secrets` with `{ name, value, hosts?, headers?, assign?: { project, envName } }` (create, optionally assigning in the same step), `PATCH /api/secrets/<id>` with `{ name?, value?, hosts?, headers? }`, `DELETE /api/secrets/<id>` (also unassigns it everywhere), `GET /api/projects/<name>/secrets` (the hob's secrets by env name), `PUT /api/projects/<name>/secrets/<ENV_NAME>` with `{ secretId }` (assign) and `DELETE` on the same path (unassign). On the host, `pnpm --filter @hobwork/server secret list|create|update|delete|assign|unassign` does the same from a shell and reads values from stdin.
- **UI**: the Secrets page lists the library with the hobs each secret is assigned to, and creates, changes (name, value, hosts and headers), deletes (the confirmation names the hobs that use it) and assigns secrets. A hob's Secrets tab lists its secrets by env name with who added them and when, assigns an existing secret or creates and assigns a new one, and removes them.
- **Egress**: a runtime VM may reach the `hobwork.json` `egress` hosts and the hosts of the secrets assigned to the hob. Requests to OpenRouter go through the [AI gateway](#ai-limits). Workspace VMs get the same plus `registry.npmjs.org`, pipeline VMs only the registry. Blocked requests get a 403 and an `egress-blocked` line in the hob log with the host and port, so an agent can see why a fetch failed. A request refused because a secret is in a header it may not go in, or would go over http, gets a 403 and a `warn` line with event `secret` naming the secret and header, at most once a minute per host and reason for each VM. Changes to `hobwork.json` show up in the version diff in the UI.
- Secret changes apply without a restart: runtime and workspace VMs compare a fingerprint of the hob's assigned secrets (secret IDs, env names, hosts, headers, update times) and are replaced on the next invocation or `bash` call, so assigning, unassigning, changing or deleting a secret reaches running VMs and their egress allowlist.

## Dashboards and UI

- Hob UIs are plain React + Tailwind pages: `index.html` at the hob root with the code in `ui/`, built by the pipeline with Vite to `dist/index.html` and `dist/assets/`, and served by the host from the deployed version's build at the root of the hob's own origin (`server/src/apps/`, `server/src/runtime/project-ui.ts`). A version without a stored build is built on the first request, as for invocations.
- Serving: only a signed-in user's app session for that origin (see [Hob app origins](#hob-app-origins)). A path serves the file from the build if there is one, except `dist/handlers/`, and `index.html` for paths without an extension, so client-side routes work. The host adds `<base href="/">` to `index.html` (unless it has one), so relative URLs from older builds (`./assets/...`) resolve on any client-side route; the template builds with `base: '/'`. Files under `assets/` are cached as immutable (Vite hashes their names), `index.html` is revalidated. The host also serves the theme (`/theme/...`) on app origins. Old links to `/p/<hob>/<path>` on the Hobwork host redirect to the app origin.
- The host provides one theme stylesheet with CSS variables (colors, radii, fonts, light/dark). The template's Tailwind setup maps these to utility classes (`bg-surface`, `text-muted`, ...). Anything that uses them stays on theme, including third-party components.
- The theme lives in `packages/theme/` (`@hobwork/theme`), which the image build copies into the platform set next to the SDK, so hob builds import `@hobwork/theme/tailwind.css` like the web UI does and the mapping is versioned with the image. The template's `index.html` loads `/theme/theme.css` from the host (marked `vite-ignore`, so Vite leaves the URL alone), and `ui/index.css` imports Tailwind and the mapping. The host serves `theme.css` at `/theme/theme.css` and its fonts (Bricolage Grotesque for headings, Atkinson Hyperlegible Next for text, from the fontsource packages) at `/theme/fonts/`. `tailwind.css` is the Tailwind v4 `@theme inline` mapping, so utilities read the variables and follow light/dark without `dark:` variants. Pages follow the system setting unless the root element has `data-theme="light"` or `"dark"`.
- Variables: colors `--hw-bg`, `--hw-surface`, `--hw-surface-raised`, `--hw-border`, `--hw-fg`, `--hw-muted`, `--hw-accent` (fills), `--hw-accent-fg` (accent text), `--hw-on-accent`, `--hw-success`, `--hw-warning`, `--hw-danger`, `--hw-on-danger`, `--hw-focus`; radii `--hw-radius-sm|md|lg`; fonts `--hw-font-sans|display|mono`. Utilities drop the prefix: `bg-surface`, `text-muted`, `text-accent-fg`, `border-border`, `rounded-md`, `font-display`.
- The Hobwork web UI (`web/`) uses the same stylesheet and mapping. The host serves the built UI (`web/dist`) for every path the other handlers (API, auth, git, MCP, hob routes, webhooks, theme) do not take, with `index.html` as the fallback for client-side routes. In development the Vite server proxies `/api` (with WebSockets), `/auth`, `/theme`, `/oauth`, `/.well-known` and `/mcp` to the host, and hob apps are opened on the host's own port.
- No component library in core. Hobs can add any npm package.
- `@hobwork/sdk/browser` is the browser client for the hob's own routes: `api.get|post|put|patch|delete(path, body?)` requests `/api/<path>` on the app origin with the app session and the CSRF header, parses JSON and throws a `RouteError` with the handler's error message; `callRoute` is the same as a plain `fetch`.
- The Hobwork web UI shows a hob's UI in an iframe of its app origin on the hob's app page ("Open app", shown when the deployed build has `index.html` or is not built yet), with a link to open it in its own tab. `GET /api/projects/<name>` returns the origin as `appUrl`. The iframe signs in through the same redirects, which need no user action while the Hobwork session exists. The Apple app shows the same page in its web view.

### Hob app origins

Hob UIs run agent-written JavaScript. On the Hobwork origin that code would run with the user's session and could call Hobwork's API as the user, for example to change which hosts a secret may be sent to. So every hob UI has its own origin, with its own session that grants nothing but that hob's UI and routes.

- **Origins**: `HOBWORK_APPS_URL` (default: `apps.` in front of the host of `HOBWORK_PUBLIC_URL`, same scheme and port) names the apps host. A hob's app is at `<scheme>://<hob>.<apps host>`, a branch preview at `<branch label>--<hob>.<apps host>` (see [Branch previews](#branch-previews)). Both are a single DNS label below the apps host, so one wildcard DNS record and one wildcard certificate cover every hob and branch. The host tells app requests apart by the `Host` header: a host name one label below the apps host is an app origin, anything else is Hobwork (`server/src/apps/origins.ts`).
- **Same site**: the Hobwork web UI shows the app in an iframe. Browsers only send SameSite=Lax cookies to a framed page, and through the sign-in redirects inside it, when the frame is the same site as the page around it: same scheme and registrable domain. `hobwork.example.com` and `filament.apps.hobwork.example.com` (or `filament.apps.example.com`) are the same site; a different registrable domain would make app cookies third-party cookies, which browsers increasingly block. In development, `hobwork.localhost` and `filament.apps.hobwork.localhost` are the same site in Chromium, while plain `localhost` and `filament.apps.localhost` are not (checked with Playwright: `Sec-Fetch-Site` and cookies in the iframe), so the dev setup uses `http://hobwork.localhost:<port>` and the host warns when `HOBWORK_PUBLIC_URL` is on `localhost`.
- **Sign-in handoff** (`server/src/apps/http.ts`):
  1. A request to an app origin without its app session: a page load (`GET` accepting HTML) is redirected to `<HOBWORK_PUBLIC_URL>/auth/app?project=<name>[&branch=<branch>]&returnTo=<full app URL>`; other requests get 401.
  2. `/auth/app` checks that `returnTo` is on exactly the app origin of that hob and branch (scheme, host and port) and not under `/_hobwork/`, and answers 400 otherwise. Without a Hobwork session it sends the browser to `/login?returnTo=/auth/app?...`; the Pocket ID flow (`/auth/login` keeps `returnTo` in its flow cookie) and the passkey flow (the web UI reloads `returnTo` when it is under `/auth/`) both come back to it.
  3. With a session, it creates a code (256 bits, stored as a SHA-256 hash in `app_codes`, 60 seconds, single use, bound to the Hobwork session, hob and branch) and redirects to `<app origin>/_hobwork/callback?code=...&returnTo=<path and query>`.
  4. The app origin exchanges the code on the server. It deletes the code in the same statement that reads it, so a code works once even when used on the wrong origin, and turns it into an app session: a random token stored as a hash in `app_sessions` with the Hobwork session's ID, hob and branch. The cookie (`hobwork_app`, `__Host-hobwork_app` on https) is HttpOnly, SameSite=Lax, host-only and lasts as long as the Hobwork session. `returnTo` is checked again (a path on the same origin, not `//` or `/\`); anything else goes to `/`.
- **What an app session can do**: load that origin's UI and call its routes, nothing else. It is looked up by token together with the hob and branch of the origin it arrives on, so another hob's origin, a branch preview and Hobwork's own API (which only reads `hobwork_session`) reject it. The `__Host-` prefix on https keeps a sibling app from planting a cookie for another app with a `Domain` attribute; each app's cookie is host-only, so no other origin receives it.
- **Sign-out**: app sessions reference the Hobwork session with `ON DELETE CASCADE`, so signing out of Hobwork (or the session expiring) ends every app session made from it. The allowlist is checked on every request, like for Hobwork sessions.
- **CSRF**: sibling apps are same-site, so their requests carry SameSite=Lax cookies. Route writes on an app origin need `x-hobwork-csrf: 1` (which a cross-origin page cannot send without a CORS preflight, which is never allowed), and `Origin` and `Sec-Fetch-Site`, when present, must be the app origin itself and `same-origin`. The Hobwork web UI answers with `frame-ancestors 'self'`, so apps cannot frame it either.
- **Content security policy**: every response from an app origin (UI, assets, route responses, errors) carries one `Content-Security-Policy` and `X-Content-Type-Options: nosniff`, so most XSS bugs in agent-written UIs cannot run script: `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; font-src 'self' data:; connect-src 'self'; form-action 'self'; object-src 'none'; base-uri 'self'; frame-ancestors <HOBWORK_PUBLIC_URL>` (`server/src/runtime/csp.ts`). The theme and its fonts are served from the app origin, so `'self'` covers a Vite + React + Tailwind build (Vite writes no inline scripts). Inline styles stay allowed for React `style` props. `base-uri` is `'self'` rather than `'none'` because the host adds `<base href="/">` to the page. Branch previews serve builds like the deployed version, so they get the same policy. `csp` in `hobwork.json` adds sources per directive (`script-src`, `style-src`, `img-src`, `font-src`, `connect-src`, `media-src`, `frame-src`, `worker-src`, `manifest-src`, `form-action`): `http(s)://` and `ws(s)://` origins (host with optional `*.` prefix, port and path), `data:` and `blob:` where they are not code (not in `script-src`, `worker-src`, `frame-src`, `manifest-src`, `form-action`), and `'unsafe-inline'`, `'unsafe-eval'` and `'wasm-unsafe-eval'` in `script-src` only. A bare `*`, scheme-only sources, nonces and every other directive (`frame-ancestors`, `base-uri`, `object-src`, `default-src`) are rejected by the schema, and the host drops anything that does not pass the same check before it builds the header. The policy comes from the hob's `hobwork.json` at the commit the app serves (deployed version, or the branch for a preview); a config that cannot be read gets the default. A route handler that sets its own `Content-Security-Policy` gets both sent (the browser enforces every policy, so the handler can only tighten). Routes on the Hobwork origin keep `sandbox; default-src 'none'`.
- **Framing**: only the Hobwork web UI may frame an app (`frame-ancestors <HOBWORK_PUBLIC_URL>` in that policy). The web UI's app and preview iframes are sandboxed without `allow-top-navigation`, so an app cannot navigate the Hobwork page (`APP_FRAME_SANDBOX` in `web/src/ui.tsx`). The Apple app shows apps inside the web UI's iframe like a browser, and keeps links to app origins in its web view (`apple/Hobwork/Web/LinkPolicy.swift`).
- **Production setup**: a wildcard DNS record `*.apps.hobwork.example.com` pointing at the reverse proxy, a wildcard certificate for it (Let's Encrypt issues those only with the DNS-01 challenge, which Caddy and Traefik do with a DNS provider plugin), and the proxy forwarding those hosts to Hobwork with the original `Host` header. `HOBWORK_TRUSTED_PROXIES` names the proxy's address (e.g. `127.0.0.1` for a proxy on the same machine), so the host sees each client's own address (see [Client address](#client-address)). Hobwork itself stays at `hobwork.example.com`, and `HOBWORK_APPS_URL=https://apps.hobwork.example.com` (the default for that public URL). Use https: the `__Host-` cookie prefixes depend on it.
- Rejected: one origin per hob on the same host with different ports (cookies ignore ports, so every app would receive every other app's cookies); paths on the Hobwork origin with a sandboxed iframe (`sandbox` without `allow-same-origin` gives the page an opaque origin, so it cannot keep a cookie of its own, and opening the app in its own tab would lose the sandbox).

### Hob icons

Each hob has an icon for its app's favicon and home screen icon and for hob lists. `icon` in `hobwork.json` is one emoji (`"🧵"`) or the path of an SVG, PNG, JPEG or WebP file in the repo (`"ui/icon.svg"`); the schema describes it and the template sets a placeholder, so agents see it. Hob code never deals with sizes or formats.

- **Rendering**: in the pipeline VM, right after `pnpm run build`, the host runs `node /opt/hobwork/icons/main.ts <hob>` in the checkout. The renderer is `packages/sdk/src/icons/`, mounted read-only from the host like the runner and the CLI, since it writes files the host serves. It uses `sharp`, `@twemoji/svg` and `@hobwork/sdk/hobwork-json` from the platform set, and fontconfig finds Inter (from Alpine's `font-inter`, copied in by `images/build.sh`) through `/opt/hobwork/fonts/fonts.conf`. It writes `dist/_hobwork/icons/icon-<size>.png` for 32 (favicon), 180 (`apple-touch-icon`), 192 and 512 (web manifest; the hob list uses 192), replacing anything the build put under `dist/_hobwork/`. Rejected: rendering on the host, which would put an image library with a native binary into the host for untrusted input.
- **Look**: emoji are drawn from Twemoji SVGs rather than a font, so they look the same everywhere and stay sharp at 512px. Images are fit into the square. All sizes but the favicon are opaque squares (the theme's surface color behind emoji and transparency), because iOS fills transparent home screen icons with black and masks the corners itself; the favicon keeps transparency. Without `icon`, the icon is the hob name's first letter in bold Inter on one of the theme's accent, success, focus, danger and warning colors, picked by a hash of the name.
- **Failures**: a wrong icon (not one emoji, a missing file, a path outside the repo, a file that is not an image) fails the pipeline's build step with a message for the agent. When a build for a restore or branch preview renders no icon, the build is kept without icons.
- **App origins**: `index.html` gets `<link rel="icon">`, `<link rel="apple-touch-icon">` and `<link rel="manifest">` at the start of `<head>` when the build has icons, so the page's own links win. `/_hobwork/icons/<file>` and `/_hobwork/manifest.webmanifest` (name, `start_url` `/`, `display` `standalone`, the 192 and 512 icons) answer without an app session, because browsers fetch the manifest without cookies; they only use a build that is already stored, so they never start a build, and show nothing but the hob's name and icon.
- **Hobwork**: `GET /api/projects` and `GET /api/projects/<name>` return `iconUrl` (`/api/projects/<name>/icon`, session required), which answers the deployed version's 192px icon, or the default letter as SVG when the deployed build has no icons (versions from before icons, or not built yet). The web UI shows it in the hob list and on hob pages. The Apple app shows the web UI, so it gets the icons there.

### Live updates

Open web UI pages refresh what they show when something changes, whoever changed it: a person in another tab, an agent over MCP, git or SSH, the runtime or the scheduler.

- **Socket**: `GET /api/live` is a WebSocket (`ws` package, like the device socket; `server/src/live.ts`). The upgrade needs a web session and an `Origin` that is exactly `HOBWORK_PUBLIC_URL`, and answers 401 or 403 otherwise. Browsers send cookies with WebSocket requests from any page and never check origins for them, and hob apps on sibling origins are the same site, so the origin check is what keeps them out. Every 30 seconds the host checks the session again, closing with 4001 when it ended (signed out, or no longer on the allowlist), and pings; a page that missed a ping is dropped. Pages send nothing. The host ends these sockets when it closes the server.
- **Messages**: `{ "type": "changes", "changes": [...] }`. A change names what changed and never carries it, so a page loads it again with the usual API calls and gets only what it may see: `{ kind: "projects" }` (hobs created, deleted, renamed or restored), `{ kind: "project", project }` (versions, status, the deployed version, webhook tokens), `{ kind: "invocations", project, id }` (a run started or finished), `{ kind: "logs", project }`, `{ kind: "branches", project }` (created, deleted, committed to, previews starting and stopping, Home Assistant approvals), `{ kind: "secrets" }` (the library, assignments and host requests), `{ kind: "agents" }` (agents, keys, OAuth connections and SSH keys), `{ kind: "devices" }` (paired, renamed, removed, connected or not), `{ kind: "trash" }` and `{ kind: "backups" }`. Deleting, restoring or renaming a hob also sends `agents` and `secrets`, whose lists name hobs. Changes within 100ms go out as one message, each once, so a handler writing many lines costs one message. Every signed-in person may see everything, so every socket gets every change.
- **Host**: the code that changes state publishes changes on an in-process bus (`server/src/changes.ts`), keyed by the host DB so code that only has the DB can publish and test hosts stay apart. Publishing happens where state changes (`recordVersion`, `startInvocation`, `appendLogs`, the secret store, `createBranch`, the runtime's VM start and stop, ...), not in routes, so changes by agents and the runtime reach pages too. Last-used times, which change on every agent call, are not published. Host commands (`create-token`, `secret`, ...) run in their own process, so pages show their changes when they next load. Pushes over git HTTP are published as branch changes when `git http-backend` ends.
- **Web UI**: one socket per browser tab (`web/src/live.ts`), opened by the first page that listens and closed 10 seconds after the last one stops, so moving between pages keeps it. It reconnects with backoff (1 to 30 seconds, with jitter) and right away when the tab becomes visible or the network comes back; after reconnecting every page loads again, since changes during the gap are lost. `useLoad` takes a filter of the changes that concern it, and lists with "show older" (activity, problems) load their first page again and keep the older pages shown (`usePaged`). A page loads again at most once a second however busy the host is.

## Users and authentication

- **Users**: a small fixed set (the household). Login with OIDC (pocket-id) and passkeys (WebAuthn), so Hobwork works for other people who do not run pocket-id.
- **Who may sign in**: `HOBWORK_ALLOWED_USERS`, a comma-separated list of email addresses and `sub:<subject>` entries. An email only matches when the provider marks it verified. There is no first-user bootstrap: an open window where the first person to sign in becomes a user is a risk when the IdP serves more people than the household, and the allowlist is one line of config. The first sign-in of an allowed identity creates the user. The allowlist is checked on every request, so removing someone signs them out. `*` instead of a list lets in everyone the provider signs in, for a provider that already limits who can use Hobwork (a Pocket ID client restricted to a group); it cannot be combined with entries. An empty or unset allowlist still lets nobody in, so a missing setting never opens the host.
- **OIDC**: authorization code flow with PKCE (S256), state and nonce, through `openid-client` against `HOBWORK_OIDC_ISSUER` with `HOBWORK_OIDC_CLIENT_ID` and `HOBWORK_OIDC_CLIENT_SECRET` (client_secret_basic; without a secret the client is public). The redirect URI is `<HOBWORK_PUBLIC_URL>/auth/callback`. The login state (state, nonce, PKCE verifier, return path) lives on the host in `oidc_flows` (10 minutes, single use, at most 1,000 at a time); the browser only holds a random ID (stored hashed) in an HttpOnly cookie, `__Host-hobwork_oidc` when `HOBWORK_PUBLIC_URL` is https, so a page on a sibling subdomain cannot plant a flow of its own. Users and their identities are separate tables (`users`, `user_identities`). A new identity whose verified email matches an existing user joins that user, unless that user is already linked to another subject of the same issuer: one identity per issuer, so once linked, only that `(issuer, sub)` signs in as them, and a new subject with the same email is refused.
- **Sessions**: random 256-bit tokens, stored as SHA-256 hashes in the host DB, valid 30 days. The cookie is HttpOnly, SameSite=Lax, and `__Host-` prefixed and Secure when `HOBWORK_PUBLIC_URL` is https. The host refuses to start with an `http` `HOBWORK_PUBLIC_URL` (or `HOBWORK_APPS_URL`) unless the host name is loopback (`localhost`, `*.localhost`, `127.0.0.0/8`, `[::1]`), so cookies and tokens never travel in clear text past the local machine. A request that sends a cookie name more than once (a sibling subdomain can set one with `Domain=` on the parent) has that cookie dropped, so a doubled session or flow cookie counts as no session or no flow (`parseCookies` in `server/src/http.ts`).
- **CSRF**: state-changing requests with a session cookie must send `x-hobwork-csrf: 1` (a cross-site page cannot set it without a CORS preflight, which the host never allows), and their `Origin` and `Sec-Fetch-Site`, when present, must be the public origin and same-origin. Code that serves other routes uses `requireUser` (writes the 401/403) or `sessionUser` from `server/src/auth/auth.ts`, which do both checks. Hob routes on the Hobwork host take only agent tokens; hob UIs call them on their own origin with an app session and the same CSRF rules, checked against the app origin (see [Hob app origins](#hob-app-origins)). Cookies never reach the handler.
- **Hob status** in the UI: `updating` while a pipeline run is in progress, `running` while the runtime VM is up, otherwise `ready` (starts on demand). The current version is the deployed one from the runtime, which can lag behind the newest version while a deploy runs or after it failed.
- **Passkeys**: WebAuthn through `@simplewebauthn/server` and `@simplewebauthn/browser`. The RP ID is the host name of `HOBWORK_PUBLIC_URL` and the expected origin is `HOBWORK_PUBLIC_URL`. Credentials are discoverable (resident key required) with user verification required, so sign-in needs no user name. They live in `passkeys`, attached to `users`, with a random WebAuthn user handle per user (`users.webauthn_id`). Challenges are stored in the host DB (`webauthn_challenges`, 5 minutes, used once) and referenced by a `flowId`. Endpoints: `POST /auth/passkey/options` and `POST /auth/passkey` (signed out, CSRF header required), `GET /api/passkeys`, `POST /api/passkeys/options`, `POST /api/passkeys`, `PATCH /api/passkeys/<id>` (`{ name }`, rename), `DELETE /api/passkeys/<id>`. The allowlist still decides: a passkey only signs in a user who is allowed. Each passkey has a name (at most 64 characters) so people tell several apart in Settings. A new passkey takes the name the person gives; without one, the name of its password manager or platform authenticator, looked up by the AAGUID in the registration (Apple Passwords, Google Password Manager, Windows Hello, 1Password and others); else the device the browser runs on, which the web UI sends as `device` (`Mac`, `iPhone`, ...); else `Passkey`.
- **Bootstrap without an identity provider**: only a signed-in user can add a passkey, so there is no open enrollment. For someone without pocket-id, the host operator runs `pnpm --filter @hobwork/server sign-in-link <email> [--name <name>]`. The email must be on `HOBWORK_ALLOWED_USERS`; the command finds or creates the user with that email and prints a one-time link (`/auth/link?token=...`, 15 minutes, hashed in `sign_in_links`) that signs them in and opens Settings to add a passkey. Like `/auth/device`, the link is refused (403) when the request's `Sec-Fetch-Site` is anything but `none` (address bar, mail and chat apps), so a page cannot sign a browser in to someone else's account by linking to it. A missing header is allowed there, since older browsers do not send it and the link is single use. Running the command vouches for the email, like the provider does for OIDC.
- **Web UI API** (all need a session): `GET /api/session` (also works signed out, lists sign-in methods), `GET /api/projects`, `GET /api/projects/<name>/icon` (see [Hob icons](#hob-icons)), `GET /api/projects/<name>` (versions; the deployed version's entry points with next cron runs, webhook token dates and each entry point's last invocation; reachable hosts; DB status; whether it has a UI), `POST /api/projects/<name>/versions/<n>/restore`, `GET /api/projects/<name>/invocations` (`kind`, `status`, `since`, `before`, `branch`, `limit`; newest first with `more`), `GET /api/projects/<name>/branches` and `PUT|DELETE /api/projects/<name>/branches/<branch>/home-assistant` (see [Branch previews](#branch-previews)), `GET /api/projects/<name>/invocations/<id>` (with stack and log lines), `GET /api/projects/<name>/logs` (`view=all|events|problems`, `after`, `limit`), `GET /api/live` (a WebSocket, see [Live updates](#live-updates)), `POST /api/projects/<name>/webhooks/<webhook>/token` (a new URL, shown once), `DELETE /api/projects/<name>` (see [Deleting hobs](#deleting-hobs)), `POST /api/projects/<name>/rename` (see [Renaming hobs](#renaming-hobs)), `GET /api/trash` and `POST /api/trash/<id>/restore` (see [Restoring deleted hobs](#restoring-deleted-hobs)), `GET /api/activity`, `GET /api/activity/problems` and `GET /api/activity/attention` (across hobs), `GET|PUT|DELETE /api/settings/homeassistant` and `POST /api/settings/homeassistant/test` (see [Home Assistant](#home-assistant)), `GET|PUT /api/settings/ai` and `GET|PUT /api/projects/<name>/ai` (see [AI limits](#ai-limits)), `GET|PUT /api/projects/<name>/home-assistant-services` (see [Hobwork to HA](#hobwork-to-ha-actions)), the device endpoints under [Host implementation](#host-implementation), the secrets endpoints under [Secrets and network](#secrets-and-network), `GET|POST /api/agents`, `POST /api/agents/<id>/tokens`, `POST /api/tokens/<id>/revoke`, `POST /api/agents/<id>/ssh-keys`, `POST /api/ssh-keys/<id>/revoke`, `POST /api/connections/<id>/revoke` (an OAuth connection), `GET /api/oauth/requests/<id>` and `POST .../approve|deny` (the consent page). Restores by a user are recorded with the user (`versions.user_id`) and use their name and email as the git author.
- **Agents**: separate identities, not tied to a user. Users create and revoke agent access in the UI.
- **MCP auth**: Hobwork is the OAuth 2.1 authorization server for its own MCP endpoint, following the MCP authorization spec revision 2026-07-28, which claude.ai, Claude Desktop, Cowork and Claude Code custom connectors use. Static agent tokens keep working next to it. Tested with the MCP SDK client, with Claude Code (`claude mcp add`, then `claude mcp login`) and with claude.ai custom connectors.
  - Discovery: a 401 from `/mcp` carries `WWW-Authenticate: Bearer resource_metadata="<public URL>/.well-known/oauth-protected-resource/mcp"` (also served without the `/mcp` suffix). Protected resource metadata (RFC 9728) names the resource `<HOBWORK_PUBLIC_URL>/mcp` and the issuer `<HOBWORK_PUBLIC_URL>`, whose metadata (RFC 8414) is at `/.well-known/oauth-authorization-server`. MCP clients must use the `/mcp` URL under `HOBWORK_PUBLIC_URL`, since the resource has to match. Hobwork has no OAuth scopes: the `scope` parameter is stored but ignored, and the person picks the connection's access on the consent page (see [Access limits](#access-limits)).
  - Clients: Client ID Metadata Documents (the spec's preferred way, `client_id_metadata_document_supported`) and dynamic client registration (RFC 7591, deprecated in the spec but still the fallback of many clients) at `/oauth/register`. A client ID that is an https URL with a path is fetched on demand (https only, public addresses only, checked at connect time, no redirects, 16 KiB, 5 seconds; blocked ranges include the IPv4 private ranges, IPv4-mapped IPv6, `::/96` (IPv4-compatible), `64:ff9b::/96` and `64:ff9b:1::/48` (NAT64), `2002::/16` (6to4), `2001::/32` (Teredo), `fc00::/7`, `fe80::/10` and multicast) and cached for its `max-age`, between 1 minute and 1 day. Claude uses `https://claude.ai/oauth/mcp-oauth-client-metadata` and Claude Code `https://claude.ai/oauth/claude-code-client-metadata`. Registered clients live in `oauth_clients`; ones never approved are deleted after a day. Public clients (`none`) and `client_secret_basic`/`client_secret_post` are supported. Redirect URIs must be https or http on localhost/127.0.0.1/[::1] and match exactly, except that loopback ones match on any port (RFC 8252), which Claude Code needs.
  - Flow: `/oauth/authorize` takes the authorization code flow with PKCE S256 only and an optional `resource` (RFC 8707) that must be the MCP resource. Errors before the client and redirect URI are validated go to the web UI (`/connect?error=...`), never to the redirect URI. A valid request is stored (`oauth_requests`, 15 minutes) and the browser goes to the consent page `/connect?request=<id>`, which needs a signed-in user like every page. The page shows the app name, its domain for metadata document clients (or a warning that the app is unverified), what it can do, the redirect host, and a warning for loopback redirects. Approving creates an agent named after the client (with a number added when the name is taken; the user can rename it) and a grant (`oauth_grants`), and redirects with a code (5 minutes, single use) plus `state` and `iss` (RFC 9207).
  - Tokens: `/oauth/token` exchanges the code (checking PKCE, redirect URI, client and resource) and refreshes. Access tokens (`hwa_...`) last 1 hour; refresh tokens (`hwr_...`) last 30 days and rotate on every use, so a connection in regular use stays connected. Reusing a rotated refresh token or a used code revokes the whole grant. Tokens are 256 random bits stored as SHA-256 hashes (`oauth_tokens`). `/oauth/revoke` (RFC 7009) revokes an access token, or a refresh token together with its grant. MCP accepts an access token only for the resource it was issued for.
  - Limits, since registration and authorization requests need no sign-in: `/oauth/register` takes 30 registrations per hour and `/oauth/authorize` 60 requests per 10 minutes from one [client address](#client-address), with IPv6 addresses counted per /64 (in memory, fixed windows). Over the limit, registration answers 429 `temporarily_unavailable` with `Retry-After`, and authorization sends the browser to `/connect?error=too_many_requests`. The tables are capped as well: at most 200 registered clients that were never approved and at most 200 pending authorization requests (15 minutes each). A new one evicts the oldest instead of being refused, so a flood cannot keep a real client out.
  - The consent page asks what the connection may do (see [Access limits](#access-limits)) and starts on read-only access to all hobs, so full access takes a choice; `POST /api/oauth/requests/<id>/approve` takes `{ agentName, access? }`.
  - Agents that connected this way show their connections on the Agent access page with their access, where revoking one ends its tokens. Agents stay; they can also hold static keys and SSH keys.
- **git HTTP**: agent token as the password. A read-only token can fetch but not push (any path or `service` parameter that mentions `receive-pack`, in any case or encoding, is refused with 403), and a token limited to some hobs gets 403 on the others. `git http-backend` gets the [client address](#client-address) as `REMOTE_ADDR`.

### Client address

The OAuth limits and `git http-backend` need the address of the client, which behind a reverse proxy is the proxy's (`server/src/client-address.ts`). `HOBWORK_TRUSTED_PROXIES` lists the proxies (IP addresses and CIDR ranges, IPv4 and IPv6, comma-separated; empty by default, and an invalid entry stops the host from starting). List only addresses of proxies you run: any address in the list can name any client, so a range that also covers other machines on the network lets them make up their address. A request from a trusted proxy gets its client from `X-Forwarded-For`: the entries of every such header, walked from the right, skipping trusted addresses, and the first untrusted one is the client. Entries to the left of it came from the client and can be made up. When every entry is trusted, the leftmost is the client. A malformed entry on the way (not an IP address, or an IP address with a zone) stops the walk and the proxy's address is used. Entries may carry a port (`1.2.3.4:80`, `[2001:db8::1]:80`). Requests from any other address use the socket address and ignore the header, since anyone can send it. `Forwarded` (RFC 7239) is not read. IPv4-mapped IPv6 addresses (`::ffff:127.0.0.1`, how a dual-stack socket reports IPv4 clients) count as IPv4, in the setting and in requests, and IPv6 addresses are compared in one spelling. The OAuth limits count all IPv6 addresses of a /64 as one client, since one person usually holds a whole /64.

### Access limits

Every agent token and OAuth connection has an access limit, chosen when the key is created (web UI or `create-token`) or on the consent page. Credentials from before limits existed, and ones created without a choice, have full access. The model is two independent settings:

- **Read only, or build and change**. Read-only access allows the MCP tools annotated `readOnlyHint` (listings, `get_hob`, `read_file`, `list_files`, `search`, `diff`, `log`, `pipeline_status`, `list_versions`, `list_invocations`, `get_logs`, `tail_logs`, `list_secrets`, `list_ssh_keys`, `list_devices` and the `ha_*` tools), fetching over git, and `GET`/`HEAD` on hob routes. Every other tool is left out of the tool list and refused, so a new tool is refused to read-only access unless it is marked read-only. Read-only access cannot add SSH keys, open SSH sessions or push.
- **All hobs, or a list of hobs**. With a list, tools that take a `hob` refuse other hobs, `list_hobs` shows only the listed ones, `list_secrets` shows the library but only assignments to the listed hobs, `create_hob` and the `ha_*` tools (which read the whole house) are left out, hob routes and git answer 403 for other hobs, and SSH sessions to other hobs are refused. "All hobs" includes hobs created later. Hobs are stored by ID (`agent_token_projects`, `oauth_grant_projects`), so a renamed hob stays in the list and a deleted one drops out. The trash entry records which tokens and connections listed it, and restoring puts it back in the lists of those that still exist. Tools that do not concern a hob (devices, `request_secret_hosts`, the agent's own SSH keys) work with either setting.

Storage: `read_only` and `all_projects` on `agent_tokens` and `oauth_grants` (`server/migrations/0021_credential_access.sql`). `server/src/access.ts` parses, stores and loads access; `verifyAgentToken` and `verifyAccessToken` return it with the agent. MCP applies it in `server/src/mcp/access.ts`, which wraps `registerTool` before any tool is registered. An SSH key an agent adds over MCP has the access of the token or connection it used (looked up at sign-in), so a limited credential cannot give itself wider access through SSH; keys a person adds have full access. The `hobwork` CLI in a workspace acts only on that workspace's hob, so the SSH check covers it.

APIs: `POST /api/agents` with `{ name, access? }`, `POST /api/agents/<id>/tokens` with `{ access? }`, and the consent approval take `access: { readOnly: boolean, projects: string[] | null }` (`null` for all hobs; a list must name existing hobs and not be empty). `GET /api/agents` returns `access` for every token and connection. On the host: `pnpm --filter @hobwork/server create-token <agent-name> [--read-only] [--project <name>]...`.
- **SSH**: public keys registered to an agent (see [SSH gateway](#ssh-gateway)).
- Agents can do everything on hobs except delete, rename or restore them, manage users and agents, change the Home Assistant connection, pair, remove or notify devices (deployed handlers notify them), and create secrets or set their values and hosts (they can assign existing secrets to hobs).

## Devices (Apple apps)

- The app keeps a WebSocket to the host and registers the device and its capabilities.
- Scripts call capabilities through the SDK: `ctx.device("kaan-iphone").notifications.send(...)`.
- Capabilities: notifications, alarms (AlarmKit), Screen Time (FamilyControls, ManagedSettings, DeviceActivity), Focus, NFC and Health (HealthKit). The macOS app has notifications and Focus: macOS 26 has no AlarmKit or Core NFC, ManagedSettings and most of DeviceActivity are unavailable there, and HealthKit has no data on a Mac.
- The iOS app closes its socket in the background, so most calls reach a phone by push: the notification service extension runs them. The macOS app keeps running with its window closed and keeps its socket open, reconnecting when the Mac wakes; the same extension handles pushes there. If a capability needs the app in the foreground (NFC), the push is a notification to tap, which opens the app straight into the action.
- The apps send only what a person explicitly chose to share. They send no location, no device identifiers (`identifierForVendor`, the advertising ID), no Wi-Fi or network names, and nothing else that could look like tracking. New capabilities follow this rule.
- NFC tags written by Hobwork contain `<public URL>/nfc/<tag>`, which opens the app (universal link) when it is built with the host in its Associated Domains, and a host page otherwise. Hobs can also write any link, and handle scans of tags with other links (see NFC scans).

### Device protocol

- **Discovery**: the app asks for the host URL in a native view and checks it with `GET /.well-known/hobwork` (no auth), which answers `{ "hobwork": 1, "name": <host name of the public URL>, "version": <host version> }`.
- **Pairing**: the app opens `ASWebAuthenticationSession` at `<public URL>/devices/connect?name=<device name>&platform=ios|macos&challenge=<PKCE S256, base64url, 43 characters>&state=<random>&redirect_uri=<redirect URI>`. `redirect_uri` must be exactly `<public URL>/devices/paired` (a universal link, so no other app can catch the code; the app waits for it with `ASWebAuthenticationSession.Callback.https`) or the older `hobwork://paired`, which apps built without the host's domain in Associated Domains keep using; `state` is optional and at most 512 characters. The page needs a signed-in person like every page (so Pocket ID or a passkey happens inside the session), shows the device name, suggests the name hobs use for it (a slug: `Kaan's iPhone` becomes `kaans-iphone`, which the person can change) and asks to approve. Approving redirects to the redirect URI the app sent, `?code=<code>&state=<state>` added (code: 5 minutes, single use; a wrong verifier also uses it up). Cancelling redirects to the same URI with `?error=access_denied&state=<state>`. If the link is opened in a browser instead of the app, `GET /devices/paired` shows a page that tells the person to open the Hobwork app and start pairing again from there. The app sends `POST /api/devices/token` with JSON `{ code, codeVerifier }` (`code_verifier` works too) and gets `{ deviceId: number, name, token }`; errors answer 400 `{ error }`. The exchange creates the device, owned by the person who approved; if another device took the name in between, the new one gets a number (`kaans-iphone-2`). The device token (`hwd_...`, stored hashed) does not expire; people remove devices in the web UI, and the app removes its own device when someone signs out in it (`DELETE /api/devices/self`, Bearer device token, 204), which works exactly like removing it in the web UI: the web view's session and its app sessions end, the push token is forgotten and the socket closes with 4001. The app keeps the token in the Keychain. Every device endpoint, the WebSocket upgrade included, answers 401 for a removed or unknown token, which the app takes as unpaired, and 403 `{ "error": "not_allowed" }` for a device whose owner is no longer on `HOBWORK_ALLOWED_USERS`: the app keeps its token, since it works again once the owner is added back, and retries slowly.
- **Web session in the app**: device tokens never go to the WebView. The app calls `POST /api/devices/web-session` (Bearer device token) with JSON `{ returnTo }` (a path on the Hobwork origin, default `/`; anything else answers 400) and gets `{ url }`: a one-time `<public URL>/auth/device?token=...` (60 seconds, single use) that sets a normal Hobwork session cookie for the device's owner and redirects to `returnTo`. A used or expired link redirects to `/login?error=link_expired`. The app loads that URL in its `WKWebView` (persistent data store) directly with `load(URLRequest)`, which then signs in to hob apps through the usual app-origin redirects (for example `returnTo=/auth/app?project=filament&returnTo=...`). The link answers 403 unless `Sec-Fetch-Site` is `none` (what WebKit sends for a load the app starts) or missing, so a page cannot sign the web view in to someone else's account by linking there (login CSRF); a link followed from a page, JavaScript navigation included, does not work. The session belongs to the device (`sessions.device_id`): each new sign-in replaces the previous one, and removing the device ends it and every app session made from it.
- **Connection**: `GET /api/devices/ws` upgraded to a WebSocket, `Authorization: Bearer hwd_...` (401 or 403 before the upgrade otherwise, as for the HTTP endpoints). Messages are JSON text frames, objects with a `type`; the host ignores types it does not know:
  - app → host `hello`: `{ appVersion, platform: "ios" | "macos", capabilities: string[], push?: { token, environment: "sandbox" | "production" } }`. Sent on every connect, and first: the host sends no calls before it and closes a connection without one after 30 seconds. `push.token` is the APNs device token in hex; `push: null` turns push off. `capabilities` lists only what is set up and allowed on the device (`notifications`, `alarms`, `screenTime`, `focus`, `nfc`, `health`); the host rejects calls to others with `unsupported`. The push token can also be updated with `PUT /api/devices/push` (`{ token, environment }` or `{ token: null }`, 204) while disconnected. The platform is fixed at pairing.
  - host → app `call`: `{ id, capability, method, args, expiresAt? }` (commands carry `expiresAt`, and the app answers `expired` without running one that has passed it); app → host `result`: `{ id, ok: true, value }` or `{ id, ok: false, error: { code, message } }`. For `notifications.send` the host waits 15 seconds for a result; other calls are commands (see Commands). After every `hello` the host sends a `call` for each pending, unexpired command of the device, oldest first.
  - app → host `event`: `{ capability, name, data }` (see Events and triggers). The same object without `type` can be sent with `POST /api/devices/events` (Bearer device token, 204), for when iOS wakes the app in the background to handle an action and a socket would take too long.
  - Both sides send `{ "type": "ping" }` every 30 seconds and answer `{ "type": "pong" }`. The host counts any message as a sign of life and closes a connection that stays silent through two of its pings.
  - A device that connects again replaces its old connection. Close codes: 4000 replaced by a newer connection, 4001 the device was removed, 4002 protocol error (no hello, a message that is not a JSON object), 4003 no answer to two pings, 4004 the owner was taken off `HOBWORK_ALLOWED_USERS` (checked at every ping; the device token works again if they are added back), 1001 host shutting down.
- **Push**: APNs with a token (`.p8`) key: `HOBWORK_APNS_KEY_FILE`, `HOBWORK_APNS_KEY_ID`, `HOBWORK_APNS_TEAM_ID`, topic `dev.bgenc.hobwork` for both apps, to `api.sandbox.push.apple.com` or `api.push.apple.com` by the environment the app reported. Without them push is off and notifications only reach connected devices. A token APNs reports as gone (410, `BadDeviceToken`, `DeviceTokenNotForTopic`) is forgotten until the app sends a new one. A push token belongs to one device: registering it (`hello` or `PUT /api/devices/push`) takes it off any other device, such as an earlier pairing of the same phone, and removing a device forgets its token.
- **SDK**: `ctx.device(name)` returns the capabilities; `ctx.devices()` lists devices (`name`, `platform`, `owner`, `capabilities`, `connected`, `lastSeenAt`). Devices whose owner is no longer on `HOBWORK_ALLOWED_USERS` are left out, get nothing, and lose their socket; the web UI still lists them, so people can remove them. Deployed handlers use devices. Workspaces and branch previews list them, but their calls answer `read_only`, since code there is work in progress and a stray notification reaches a real person. Every capability and method is typed in `packages/sdk/src/devices.ts`. Tests fake them with `createTestContext({ device: (name) => ({ notifications: { send } }) })`; methods a fake leaves out reject. Agents see devices and their capabilities with the `list_devices` MCP tool; they cannot pair, remove or call devices.

#### Notifications

- **Sending**: `ctx.device(name).notifications.send({ title, body?, actions?: [{ id, title }], data? })` returns `{ id, delivery: "app" | "push" }`. The title is at most 200 bytes and the body at most 2,000 bytes as UTF-8, with up to 4 actions with IDs of letters, digits, `-` and `_` and titles of at most 64 characters; `data` is up to 4 KB of JSON that comes back with an action and is never sent to the device. The push payload is then measured, since JSON escaping can grow it past APNs' 4,096 bytes, so every notification that is accepted can go by push. Failures throw a `DeviceError` with a code: `unknown_device`, `unsupported` (the app never reported `notifications`), `unreachable` (not connected and no push), `too_large` (the push payload would be over 4,096 bytes; nothing is sent), `push_failed` (APNs refused it or could not be reached), `bad_request`, `read_only`, or the app's own code. Calls are logged with the invocation.
- **Over the socket** when the device is connected: `call` with capability `notifications`, method `send` and args `{ id, project, title, body?, actions }`. The app shows it with `id` as the request identifier and answers `ok: true` (the value is ignored), or an error (for example `not_authorized` when notifications are off), which fails the send. A timeout or a dropped connection falls back to push.
- **By push** otherwise: `apns-push-type: alert`, priority 10, `apns-id` and `apns-collapse-id` set to the notification ID (so a notification that reached the app both ways shows once), expiring after a day. Payload: `{ aps: { alert: { title, body }, sound: "default", "thread-id": <hob> }, hobwork: { id, project, actions } }`; the title and body are only in `aps.alert`. With actions, `aps` also has `category: "hobwork.<id>"` and `mutable-content: 1`: actions differ per notification, so the app's notification service extension registers that category from `hobwork.actions` before the system shows it.
- **Actions**: a tap sends `event` `{ capability: "notifications", name: "action", data: { id, action } }`. The host checks that the notification went to that device and had that action, and runs each trigger of the hob that sent it declared as `{ "device": { "capability": "notifications", "event": "action" }, "handler": ... }` in `hobwork.json`, with `ctx.payload` `{ device, capability: "notifications", event: "action", notificationId, action, data? }` (`NotificationActionEvent`). Each notification answers once, when its triggers start; repeats after that are ignored. A tap on a hob without such a trigger (or whose triggers cannot be read) is logged as a `trigger` warning in its log and leaves the notification unanswered, so the app sending the event again runs the trigger once the hob has one. Notifications are kept 30 days (`device_notifications`).

#### Commands

- Every device call except `notifications.send` is a command, recorded in `device_commands` (`id` UUID, device, hob, invocation, `capability`, `method`, `args` as sent, `status` `pending`/`done`/`failed`/`expired`, `result`, `created_at`, `expires_at`, `answered_at`). Commands expire 10 minutes after creation and are kept 30 days.
- The host checks arguments per method before anything is sent (`bad_request` saying what is wrong; unknown fields are refused too) and the push payload size (`too_large` over 4,096 bytes). The app checks them again.
- **Delivery**, in order:
  1. **Socket**: a `call` with `id` = the command ID when the device is connected. A background command whose socket stays silent for 10 seconds, or whose connection closes before it answers, also goes by push, since a half-open socket after a network change still looks connected.
  2. **Command push** for background methods when the device is not connected: `apns-push-type: alert`, priority 10, `apns-id` and `apns-collapse-id` = the command ID, `apns-expiration` = `expiresAt`. Payload `{ aps: { alert: { title: <hob>, body: <fallback> }, "mutable-content": 1, "interruption-level": "passive", "thread-id": <hob> }, hobwork: { project, command: { id, capability, method, args, expiresAt } } }`. The notification service extension runs the command, posts the result and replaces the text with what happened. The fallback body (for example `Screen Time change for this device. Open Hobwork if it did not apply.`) shows if it fails or runs out of time. Background pushes (`content-available`) are throttled and dropped after a force quit, so they are not used.
  3. **Prompt push** for foreground methods (NFC): an ordinary alert (`sound: "default"`, no `mutable-content`) such as `Write an NFC tag` / `<hob> is waiting. Tap to start.`, with the same `hobwork.command` plus `"foreground": true`. Tapping it opens the app, which runs the command from the payload.
  4. **On hello**, as described under Connection.
- A command that no path reached (not connected and no push, or APNs refused it) fails at once with `unreachable` or `push_failed` and is marked `failed`, so it does not run later by surprise.
- The app and its extensions remember the IDs of commands they ran (1 day), so a command that arrives more than once runs once and answers again. Commands past `expiresAt` answer `expired` without running.
- **Results**: `result` over the socket, or `POST /api/devices/results` (Bearer device token, JSON `{ id, ok: true, value }` or `{ id, ok: false, error: { code, message } }`, up to 1 MB; 204, 404 for an ID that is not this device's command, 400 for another body). The first result wins; later ones answer 204 and are ignored. A result for a command the host already marked `expired` is still recorded, since the app ran it.
- **Waiting**: the handler waits 30 seconds for background methods and 2 minutes for foreground ones, then gets `DeviceError('timeout')`, whose message says that the command was sent and may still run until `expiresAt`. Results after that go to the hob log with the invocation (info when ok, warn for failures). A command still pending at `expires_at` becomes `expired` (checked every minute, on hello and on each new command), with a warn line in the hob log.
- Calls are logged with the invocation (`Device kaan-iphone: alarms.set answered {...}`).

#### Capabilities

Background methods: all of `alarms`, `screenTime`, `focus` and `health`. Foreground methods: all of `nfc`. Besides the codes listed per capability, the app answers `bad_request`, `not_authorized` (the person has not allowed it), `expired` and `locked`. Date-times are ISO 8601 with a time zone. Times of day are local `"HH:MM"`. `days` are `"mon"` to `"sun"`, a non-empty list without repeats. Names of app sets, schedules and limits are slugs of up to 40 characters.

- **alarms** (AlarmKit): `set({ title, at?, time?, days?, id? })` → `{ id }`, with exactly one of `at` (one-off, in the future) or `time` (repeating on `days`, or once at the next occurrence without them; `days` only with `time`). A known `id` (UUID) replaces that alarm. `timer({ title, seconds, id? })` → `{ id }`, a countdown of 1 to 86,400 seconds with a Live Activity. `cancel({ id })` → `{}`, for unknown IDs too. `list()` → `[{ id, title, state: "scheduled" | "countdown" | "paused" | "alerting", at?, time?, days?, seconds? }]`, only alarms Hobwork made. Titles are at most 100 characters. Error: `limit_reached`.
- **screenTime** (FamilyControls, ManagedSettings, DeviceActivity): the person creates named app sets in the app's settings with `FamilyActivityPicker`. Selections are opaque tokens that only work on that device, so handlers use set names and see counts. `sets()` → `[{ name, apps, categories, sites }]`. `block({ set, until? })` → `{}` shields the set now, in a `ManagedSettingsStore` named after it; with `until` (in the future) a one-off DeviceActivity schedule ends it, applied by the monitor extension without the app. DeviceActivity intervals must be at least 15 minutes, so it starts at `min(now, until - 15 min)`. `unblock({ set })`. `schedule({ name, set, start, end, days? })` shields from `start` to `end` (they must differ) weekly on `days` or every day; the same `name` replaces a schedule. `removeSchedule({ name })`. `limit({ name, set, minutes, days? })` shields the set until midnight once it was used `minutes` (1 to 1,439) that day. `removeLimit({ name })`. `status()` → `{ blocked: [{ set, until? }], schedules: [...], limits: [{ ..., reached }] }`. Errors: `unknown_set`, `interval_too_short`. Until Apple approves the distribution entitlement, the TestFlight build archives without Family Controls and does not report `screenTime`.
- **focus**: iOS and macOS have no API to turn a Focus on or off. The app offers a Focus filter (`SetFocusFilterIntent`) with a `label`, which the person adds to a Focus in Settings (System Settings on a Mac); the system runs it when that Focus turns on or off. `status()` → `{ active: string[] }` (labels). Changes arrive as the `changed` event.
- **nfc** (Core NFC, foreground, system scan sheet): `write({ text? })` → `{ tag, url }`. The host creates a random tag ID (22 base64url characters) owned by the hob in `nfc_tags` and sends `{ tag, url: "<public URL>/nfc/<tag>", text? }`; the app writes one NDEF URI record, plus a text record with `text` (at most 1,024 bytes). A failed or expired write deletes the tag again. `write({ url, text? })` → `{ url }` writes any link instead and creates no tag: an absolute URL without whitespace or control characters, with the scheme `http`, `https`, `mailto`, `tel`, `sms`, `facetime`, `facetime-audio` or `shortcuts` (what iOS opens from a tag without an app), no user name or password in `http`/`https` URLs, and at most 2,048 bytes after the host normalizes it (WHATWG URL serialization: lowercase scheme and host, `https://example.com` becomes `https://example.com/`). The host sends `{ url, text? }` with the normalized URL, and the result is that URL. Tag sizes vary (NTAG213 holds 137 bytes of NDEF, NTAG216 868), so long links answer `too_small`. `read()` → `{ records: [{ type: "url" | "text" | "other", value }], tag? }`, with `tag` when the first URL is a Hobwork tag URL of this host. Errors: `cancelled`, `not_writable`, `too_small`.
- **health** (HealthKit): the person picks the shared types in the app's settings: `sleep`, `steps`, `heartRate`, `restingHeartRate`, `activeEnergy`, `bodyMass`, `workouts`, `mindfulness`. `query({ type, from, to, limit? })` → `[{ type, start, end, value?, unit?, stage?, workoutType? }]`, with `from` before `to` and at most `limit` samples (1 to 1,000, default 1,000). `stage` is the sleep stage (`inBed`, `asleep`, `awake`, `core`, `deep`, `rem`). Units are count, count/min, kcal, kg and min. Errors: `locked` (Health data cannot be read while the phone is locked), `not_shared`.

#### Events and triggers

- Triggers in `hobwork.json`: `{ "device": { "capability": "focus", "event": "changed", "device": "kaans-iphone" }, "handler": "src/focus.ts" }`. Valid pairs: `notifications`/`action`, `focus`/`changed`, `nfc`/`scanned`, `health`/`samples`; the schema refuses others. `device` is optional and limits the trigger to one device by name. `url` (`nfc`/`scanned` only, 1 to 2,048 characters) limits it to scanned links that start with it; a `url` that parses as a URL is normalized first, so `"https://Example.com"` matches `https://example.com/a` but not `https://example.com.evil.example/`, and `"https:"` matches every https link.
- `ctx.payload` is `{ device, capability, event, ...data }` (`DeviceEvent`): `NotificationActionEvent`, `FocusChangedEvent` `{ label, active }`, `NfcScannedEvent` `{ tag?, url, records? }` (`tag` for Hobwork tags, whose `url` is `<public URL>/nfc/<tag>`; `records` when the app read the tag itself; `device` is null for a scan from the tag's web page), `HealthSamplesEvent` `{ type, samples }`.
- Routing: `notifications`/`action` goes to the hob that sent the notification (see Notifications). `nfc`/`scanned` of a Hobwork tag goes only to the hob that owns the tag (triggers without `url`, or whose `url` matches the tag URL), with a `trigger` warning in its log when it has no matching trigger. `nfc`/`scanned` of any other link, `focus`/`changed` and `health`/`samples` go to every hob whose deployed version declares a matching trigger; for other links only triggers with a matching `url` match, so hobs that only handle their own tags never see them. Events with invalid data (a label over 64 characters, an unknown Health type, more than 500 samples, an unknown tag, a scan without a tag or a URL, a URL over 8,192 bytes, more than 16 records, a record over 8,192 bytes or of another type) are dropped, as are events from devices whose owner is off the allowlist. The events endpoint takes bodies up to 1 MB.
- Health samples come from background delivery (`HKObserverQuery`) in batches of at most 500, each sample once (an `HKAnchoredObjectQuery` anchor per type).
- **NFC scans** of Hobwork tags come from the app's "Scan tag" button, from `hobwork://nfc/<tag>`, from a universal link to `https://<public host>/nfc/<tag>`, or from iOS background tag reading, which opens the URL in Safari when there is no universal link. Universal links need the app built with that domain in Associated Domains (build setting `HOBWORK_APPLINKS_HOST`, empty by default); the host serves `/.well-known/apple-app-site-association` with `applinks.details: [{ appIDs: [<HOBWORK_APPLE_APP_ID, default 63QQLP356Q.dev.bgenc.hobwork>], components: [{ "/": "/nfc/*" }, { "/": "/devices/paired" }] }]` and `webcredentials: { apps: [<same app ID>] }` (which `ASWebAuthenticationSession` needs to finish on a universal link). The app adds `webcredentials:<host>` with `applinks:<host>` in Associated Domains and uses the universal link for pairing when the host it pairs with is `HOBWORK_APPLINKS_HOST`.
- **Scan event data** from the app: `{ tag, records? }` for a Hobwork tag of its host, `{ url, records? }` for any other link. The host also treats a `url` of the form `<public URL>/nfc/<tag>` as that tag. `records` is `[{ type: "url" | "text" | "other", value }]` as in `nfc.read()`; the app sends at most 16 and leaves out records over 8,192 bytes. A tag without a URL record sends nothing.
- **Tags with other links**: iOS background tag reading opens a link in Safari (or the app that claims it), and an app can only claim universal links of domains whose `apple-app-site-association` lists it, so Hobwork cannot take over taps of tags with `https://example.com/...`. What works instead:
  - The app's "Scan tag" button reads any tag and sends its first link with the records.
  - The App Intent "Scan NFC Tag" (`ScanTagIntent`, `supportedModes: .foreground(.immediate)`, also an App Shortcut) opens the app and does the same, for the Action Button, Control Center (the Shortcuts control) or Siri. Core NFC scans need the app on screen, so this cannot run in the background.
  - The App Intent "Send Tag to Hobwork" (`SendTagIntent`, `supportedModes: .background`) takes a link and posts the scan event with `POST /api/devices/events` without opening the app. In the Shortcuts app, a personal automation "When I tap an NFC tag" (for one tag, which Shortcuts identifies by the tag's serial number and not its content) runs it with the link typed in, so any tag, even one without a link, runs hobs with a single tap. The event cannot tell a tap from a shortcut run by hand, so handlers should not treat it as proof that someone was at the tag.
- **Tag page** `GET /nfc/<tag>`, rendered by the host: an unknown tag answers 404. Without a session the page shows a link to `hobwork://nfc/<tag>` and a sign-in link that returns to the page, and records nothing. For a signed-in person it records the scan (`device: null`) and redirects (303) to `/nfc/<tag>?scanned`, which shows the result, so reloading does not scan again. A request from another site (`Sec-Fetch-Site` missing or other than `none` or `same-origin`, or a foreign `Origin`) only gets a "Run it" button that posts to the same URL.

#### Host implementation

`server/src/devices/`: `store.ts` (tables from `server/migrations/0016_devices.sql`: `devices`, `device_pairing_codes`, `device_sign_in_links`, `device_notifications`; from `0020_device_commands.sql`: `device_commands`, `nfc_tags`), `commands.ts` (argument checks per method, push texts), `registry.ts` (one connection per device, calls matched to results by ID with timeouts; a result is only accepted from the connection the call went to), `socket.ts` (the WebSocket, on the `ws` package), `devices.ts` (notifications, commands with their delivery, results and expiry, and events routed to triggers), `nfc-page.ts` (the tag page), `apns.ts` (HTTP/2 with `node:http2`, one connection per APNs origin, closed after 5 idle minutes because NAT gateways drop idle connections silently; a request without an answer in 10 seconds drops its connection and is sent once more on a new one; ES256 provider tokens signed with `node:crypto` and renewed every 40 minutes or when APNs answers `ExpiredProviderToken`), `routes.ts`, and `internal.ts` (`POST http://hobwork.internal/v1/devices` for runtime and workspace VMs). The web UI lists devices under Settings, Devices (`GET /api/devices`, `PATCH /api/devices/<id>` to rename, `POST /api/devices/<id>/revoke`, which also closes the device's socket and ends its web view's session) and has the pairing page (`GET /api/devices/pairing?<the query of /devices/connect>`, `POST /api/devices/pairing/approve` with `{ request, name }`, `POST /api/devices/pairing/deny` with `{ request }`).

## Home Assistant

The host keeps one WebSocket connection to HA, authenticated with a long-lived access token. The connection is pinged, and reconnects with exponential backoff (1s up to 60s) when it drops.

Connection settings (`server/src/homeassistant/settings.ts`, `homeassistant_settings` table):

- People set the URL and token in the web UI (Settings, Home Assistant), which shows the connection status, HA version and the last error, and has "Test connection" (a separate connection that signs in and closes, nothing saved) and "Disconnect" (forgets the token). Agents have no tool or API for any of it.
- The token is write-only: no response contains it. It is encrypted with AES-256-GCM using the secrets key (see [Secrets and network](#secrets-and-network)) with its own additional data. Keeping the saved token while changing the URL is refused, and a test only uses the saved token for the saved URL, so the token is never sent to an address someone typed in without also typing the token.
- Precedence: `HOBWORK_HA_URL` and `HOBWORK_HA_TOKEN`, when set, win over the saved setting, and the settings page shows the connection as set in the server configuration and cannot change it. The host operator's configuration is the explicit choice, and a page that looked editable but did nothing would mislead.
- Saving or disconnecting calls the client's `reload()`, which reads the setting again. Saving also reloads every hob's entry points, so triggers that failed while HA was not set up get subscribed.

### HA to Hobwork (triggers)

HA's WebSocket API has `subscribe_trigger`: the client sends a trigger definition in HA's own automation syntax, HA evaluates it, and pushes a message every time it fires. Hobwork uses this directly:

1. On deploy, the host reads the `homeassistant` triggers from `hobwork.json` and subscribes each one with `subscribe_trigger`.
2. A Zigbee button is pressed. ZHA or Zigbee2MQTT turns it into a device trigger, event or state change in HA. HA matches it against the subscription and pushes the trigger variables to Hobwork.
3. The host invokes the handler with the trigger variables, waking the hob VM if needed.

Any trigger HA supports works (device, state, numeric_state, event, zone, time, template), with the same syntax as in an HA automation, and HA does the filtering. The `homeassistant` block is passed to HA unchanged. HA accepts both the current `"trigger": "state"` key and the older `"platform": "state"`; templates and docs use `trigger`, and device triggers from `ha_list_device_triggers` (which use `platform`) work as they are. The handler receives HA's trigger variables (`{ trigger: { platform, entity_id, from_state, to_state, ... } }`), the same object `ha_listen` returns.

On deploy the host diffs the hob's triggers against its active subscriptions: unchanged triggers keep their subscription, changed ones are subscribed again, removed ones are unsubscribed. A trigger HA refuses (bad syntax, unknown device) is reported in the deploy result. On reconnect (e.g. HA restart) the host subscribes again. Triggers that fire while the connection is down are lost, and this is logged with the time range.

Agents find device IDs, entities and trigger payloads through the HA MCP tools. `ha_listen` lets an agent subscribe a trigger temporarily and ask the user to press the button, to see the real payload before writing the handler.

Home Assistant stays the source of truth for its own data. The MCP instructions and the template's `AGENTS.md` tell agents to read states, history and device details from HA instead of copying them into the hob DB, unless the user asks for a copy or the feature cannot work without one.

HA automations can also call a Hobwork webhook (`rest_command`), for anything easier to express on the HA side.

### Hobwork to HA (actions)

Handlers get `ctx.ha` (`packages/sdk/src/homeassistant.ts`): `callService(domain, service, data?, target?, { returnResponse? })`, `getState(entityId)` (undefined for an unknown entity), `getStates({ domain?, entityIds? })` and `fireEvent(type, data?)`. Calls go through the host, so the HA token never enters a VM and VMs do not need access to the LAN. Announcements on Google Home speakers are `tts.speak` or `media_player.play_media` calls.

- **Transport**: the runner POSTs `HaRequest` (`packages/sdk/src/runner/protocol.ts`) with the invocation ID to `http://hobwork.internal/v1/ha`, and the host answers it with its HA client (`server/src/homeassistant/internal.ts`). Failures answer `{ ok: false, error: { code, message } }` with HA's code and message, or Hobwork's (`not_configured` and `not_connected` 503, `timeout` 504, `read_only` 403, `bad_request` 400). The SDK throws them as `HomeAssistantError`. The runner and the handler bundle each have a copy of that class, so its `instanceof` checks a `Symbol.for` brand.
- **Logs**: every call is logged with its invocation, as a `runtime` line: service calls and events at `info`, reads at `debug`, failures at `warn`. The host checks that the invocation belongs to the VM's hob, and the lines count toward the invocation's 1,000 line limit.
- **Allowed services**: a hob calls only the services on its list (`project_ha_services`: a domain like `light` or one service like `light.turn_on`), which is empty for new hobs. `haResponse` checks it on every call, for the deployed version and previews alike (`server/src/homeassistant/services.ts`). A refused call answers `not_allowed` (403), which the SDK throws as `HomeAssistantError`, and is logged as a `warn` line ("Home Assistant: denied light.turn_on. This hob may not call ... People change this on the hob's Home Assistant page in Hobwork"). `hassio.*`, `homeassistant.*`, `shell_command.*`, `recorder.purge` and `recorder.purge_entities` are blocked for every hob even when listed, and cannot be added to a list. People edit the list on the hob's Home Assistant page (`GET|PUT /api/projects/<name>/home-assistant-services`), agents with `update_ha_services` (add and remove entries, with the same hob access as other tools); `get_hob` shows it. Changes are written to the hob log with who made them. Agents can add entries, so the list limits what a bug in a handler can do, not what a compromised agent can do. The same list holds the events a hob may fire, as `event:<type>` entries (type case is kept; letters, digits, `_`, `.`, `-`). `fireEvent` of an unlisted type answers `not_allowed` and is logged as a `warn` line. Events Home Assistant uses for itself are blocked even when listed: `homeassistant_*`, `hassio_*`, `*_registry_updated`, `call_service`, `state_changed`, `service_registered`, `service_removed`, `component_loaded`, `core_config_updated`, `themes_updated`, `panels_updated`, `logbook_entry`, `automation_triggered`, `automation_reloaded`, `script_started`, `scene_reloaded`, `user_added`, `user_removed`, `mobile_app_notification_action` and `shopping_list_updated`. Hobs that existed before the events (migration 0032 queues them in `project_ha_events_backfill`) get the types of `fireEvent('type')` calls with string literals in the deployed source and of `Home Assistant: fire event <type>` log lines on the first start, like the services. Hobs that existed before the list (migration 0029 queues them in `project_ha_services_backfill`) get, on the first start, the domains of the `callService('domain', 'service')` calls with string literals in the deployed source (`.js`, `.ts`, `.tsx`, not tests or `node_modules`) and of the `Home Assistant: domain.service` lines in their log, minus blocked domains. Calls that name the domain in a variable cannot be read from source; the hob log says so when the code has some. A hob whose code cannot be read is tried again on the next start.
- **Branch previews** read states. Service calls and events answer `not_approved` (403) unless "Let this branch control Home Assistant" is on for that branch. People turn it on on the hob page (`PUT|DELETE /api/projects/<name>/branches/<branch>/home-assistant`), agents with the `set_branch_home_assistant` MCP tool; `branch_ha_approvals` stores who (user or agent) and when, and the hob page shows it. This keeps work in progress from switching real devices by accident. It is not a boundary against agents, which can merge to `main` anyway. It is checked on every call, so turning it off applies right away. A denied call is logged as a `warn` line with the invocation (`Home Assistant: denied light.turn_on ... Turn it on with the set_branch_home_assistant MCP tool ...`), so the agent sees why.
- **Workspaces** read states only (`getState`, `getStates`, also as `hobwork ha state` and `hobwork ha states`). Code run there is work in progress and tests, and a test that switches off the heating by mistake has real effects, so service calls and events answer `read_only`. Tests fake `ctx.ha` with `createTestContext({ ha: { ... } })`, whose unstubbed methods reject. Pipeline VMs have no internal endpoint for HA. Rejected: an opt-in for service calls from workspaces; a deployed handler run with `invoke` does the same thing, with its version and logs recorded.

## Integrations

- **OpenRouter** (`packages/sdk/src/openrouter.ts`): `openrouter(ctx, { apiKey?, timeout? })` returns `chat(request, { timeout?, signal? })` (the completion and its text) and `json(request, { timeout?, signal? })`. It POSTs to `https://openrouter.ai/api/v1/chat/completions` through `ctx.fetch` with the `OPENROUTER_API_KEY` placeholder in the `Authorization` header, so the user binds that secret to `openrouter.ai` and the value never reaches the handler. `json` without a schema uses JSON mode. With a schema it sends `response_format: json_schema` (strict by default) with `provider.require_parameters` so OpenRouter only routes to providers that support it, and validates the reply. Schemas are Standard Schema with Standard JSON Schema (`~standard.validate` and `~standard.jsonSchema`), which zod 4 implements, so the SDK needs no zod dependency. Errors throw `OpenRouterError` with the HTTP status (or the error's code when OpenRouter reports it in an HTTP 200 answer), OpenRouter's message with the provider's own message (`metadata.raw`) appended, and the error metadata. When `json` with a schema finds no provider for the request's parameters, the message says the model may not support structured output. `timeout` (milliseconds, per call or as the client default) and `signal` stop a call that waits too long; they throw `OpenRouterError` with code `timeout` or `aborted`. Without them a call has no timeout of its own, and the invocation timeout applies. Checked once against OpenRouter: chat, tool calls, JSON mode, structured output and error answers.

  `check(prompt, { model?, input?, timeout?, signal? })` and `pick(prompt, choices, options)` are the intended use of AI in hobs: an `if` (boolean) and a `pick` (one of a list of strings, or an object of choice to description), for conditions, categorizing, tagging and filtering. They are not for agentic workflows, chat interfaces or long text. The prompt goes in the system message and `input` (a string, or JSON) alone in the user message between `<data>` tags, with the model told to treat it as data. They send `response_format: json_schema` with `{ answer: boolean }` or `{ answer: enum }`, `temperature: 0`, `max_tokens: 100` and `provider.require_parameters`, on `DEFAULT_JUDGE_MODEL` (`google/gemini-2.5-flash-lite`, a cheap non-reasoning model) unless `model` is given. The answer is validated strictly and a bad one throws `OpenRouterError` with code `invalid_output`, without a retry. `pick` throws a `TypeError` for empty or duplicate choices. The names follow `chat` and `json`: short verbs on the client.

### AI limits

People decide which AI models hobs may use through OpenRouter and how much, so a hob cannot run up a large bill. Hob code is untrusted, so the limits are enforced on the host, in the VMs' egress path, not in the SDK.

- **Where** (`server/src/ai/gateway.ts`): runtime, preview and workspace VMs are created with an [interceptor](#sandboxing-gondolin) for `openrouter.ai` and `*.openrouter.ai`, so every request to OpenRouter goes through the gateway, whether it comes from the SDK helper, a raw `fetch` or another client. The API key is a placeholder that is only filled in when the gateway sends the request on, after its checks. Pipeline VMs have no secrets and cannot reach OpenRouter. A key bound to other hosts, or another AI provider, is not covered.
- **What passes**: only https on port 443 (plain http to OpenRouter is refused, so the key is never sent in the clear, and so is any other port) and only these paths under `/api/v1`: `POST` `/chat/completions`, `/completions`, `/messages`, `/responses` and `/embeddings`, and `GET` `/models` (and `/models/<author>/<slug>/endpoints`), `/key` and `/generation`. Anything else (API keys, credits, other methods) is refused, since the API key is filled in for every OpenRouter path.
- **What counts**: `POST` requests. `GET` requests (model lists, key info) pass through. The gateway reads the JSON body's `model` and `models` (OpenRouter's fallbacks), and asks OpenRouter for usage on `/chat/completions` and `/completions` (`usage: { include: true }`, unless the request sets `usage`). It reads prompt and completion tokens and the cost in US dollars from the answer's `usage`, in JSON or from the last server-sent event that has it (chat, Messages and Responses formats). When an answer with a 2xx status has no cost, the gateway estimates it from the token counts and the model's prices in OpenRouter's public model list (`server/src/ai/pricing.ts`, fetched by the host and kept for an hour). The model is the one that answered, else the requested one. A model without a known price (or a model list that could not be fetched) is priced at $15 per million prompt tokens and $75 per million completion tokens. An answer with no token counts either has them guessed from the sizes of the request and the answer (four characters per token). Answers with error statuses cost nothing. Spend limits therefore always see a cost for a successful request.
- **Models**: a host-wide list and a per-hob list of model patterns (`openai/gpt-5-mini`, `google/*`; `*` matches anything, case-insensitive). No list allows every model; an empty list allows none. A model must match both lists, so a hob can narrow the host list but not widen it. With a list, requests that name no model are refused, since OpenRouter would use the account's default model.
- **Limits**: requests per minute and per hour, and spend per 24 hours and per 30 days, all rolling windows. Defaults: on, 20 per minute, 200 per hour, $1 per day, $10 per 30 days. Each can be empty for no limit, and the throttle can be turned off, which leaves only the model lists. Host-wide limits apply to every hob that has no limits of its own; a hob's own limits replace them (they can be higher). Requests still running count. Spend counts only after the answer arrived (with the estimate above when OpenRouter reported no cost), so a request can go over the spend limit once. Refused requests do not count, so a handler that retries is let through when the window moves.
- **Refusals** answer in OpenRouter's error format, so the SDK throws them as `OpenRouterError`: 403 `hobwork_https_required`, `hobwork_port_not_allowed` and `hobwork_path_not_allowed` (not counted, not recorded in usage), 403 `hobwork_model_not_allowed` (with the allowed patterns in `metadata.allowed_models`), 429 `hobwork_rate_limit` and `hobwork_spend_limit` (with `metadata.limit`, `max`, `used` and `retry_after_seconds`, and a `Retry-After` header). Messages say what happened, when to try again and that people change the settings on the hob's AI page. Each refusal is also a `warn` line with event `ai-limit` in the hob log, at most once a minute per hob, VM kind and branch, with the branch for previews and `Workspace <branch>:` for workspaces.
- **Records** (`server/src/ai/usage.ts`, `ai_requests` from `server/migrations/0028_ai_limits.sql`): one row per `POST`, with hob, branch, VM kind, path, model, HTTP status, tokens, cost and whether and why it was refused. A request whose upstream fails is recorded as 502. Housekeeping deletes rows older than 90 days. Settings are in `ai_settings` (one row) and `project_ai_settings`, as JSON, with who changed them.
- **Who changes them**: only people, in the web UI: Settings, AI (host-wide models and limits, and spend per hob over 30 days) and a hob's AI tab (spend in the last 24 hours and 30 days, requests in the last minute and hour, spend by model, and the hob's models and limits). Web API, signed-in users only, so agent tokens get 401: `GET|PUT /api/settings/ai` (`{ models, limits }`) and `GET|PUT /api/projects/<name>/ai` (`{ models, limits }`, where `null` uses the host-wide setting). Agents see the hob's models, limits and spend in `get_hob` and cannot change them.
- Settings are read on every request, so changes apply to running VMs right away.
