# Hobwork architecture

Hobwork is a personal code engine for a household. You (or an AI agent working for you) put scripts, scheduled jobs, HTTP APIs and small dashboards into it, and it runs them. Everything is reachable over MCP, so an agent can build and maintain automations end to end: write code, write tests, run them, merge, deploy, and debug from logs.

Named after hobs, the house spirits that quietly do chores around the home. Each automation lives in a hob: a git repository with handlers, a DB and an optional UI (see [Hobs](#hobs)).

## Goals

- Agents can create and change automations without a human reviewing code.
- Changes never break what is running without tests having run first.
- Every deployed version is recoverable with one click.
- Scripts run sandboxed, with controlled network access and secrets they can use but never read.
- Dashboards look like part of one app and work in the browser and in the Apple apps.
- Scripts can reach the phone: notifications, NFC, alarms, Health.

## Non-goals

- Multi-tenant hosting or scaling. Each hob runs as zero or one instance.
- Protecting against hostile users. Users are a household. The sandbox protects against buggy or misled agent code.
- Replacing a general app platform. Dashboards are small internal UIs.

## Components

```
                 +-------------------------------------------------+
  Browser  ----> |                 Hobwork host                    |
  Apple apps --> |  HTTP API / web UI / dashboards                 |
  Agents (MCP)-> |  MCP server                                     |
  git push ----> |  git smart HTTP                                 |
  ssh ---------> |  SSH gateway                                    |
                 |                                                 |
                 |  repos (bare git)   host DB (SQLite)            |
                 |  hob DBs            scheduler / event bus       |
                 +-----------+-------------------------------------+
                             | Gondolin (QEMU + KVM/HVF)
            +----------------+----------------+
            |                |                |
      hob runtime       agent workspace   pipeline run
      VM (0 or 1 per    VM (per branch)   VM (fresh per
      hob)                                run)
```

- **Host**: Node (>= 24.12 for `node:sqlite`'s authorizer and defensive mode, runs TypeScript directly), pnpm. One process. Runs as a systemd service on `colossus` (Arch Linux, x86_64, KVM). Docker is possible with `--device /dev/kvm` but not the primary target.
- **Web UI**: React, TypeScript, Tailwind, Vite. Served by the host.
- **Guest image**: a Hobwork-specific Gondolin image built from Alpine with Node (full ICU data), pnpm, git, e2fsprogs, tzdata and the platform dependency set including `@hobwork/sdk` and `@hobwork/theme` (`images/`, built inside Docker by `images/build.sh`). The image has an unprivileged `agent` user (uid and gid 1000), `doas` and `su-exec`. Gondolin's guest helpers are built from the vendored sources in `images/build.sh`, because upstream's FUSE mount has no `allow_other` (only root could read `/workspace`) and shows files owned by the host's user: the vendored `sandboxfs` lets any user in and shows every file as owned by uid and gid 1000. VMs grow the root disk at boot (`diskSize`); root disk writes are discarded when a VM stops.
- **SDK** (`@hobwork/sdk`): the handler context type hob code builds against (hob DB, logs, Home Assistant, secrets, devices), plus the OpenRouter helper, the browser client for hob UIs, the Vite config and test helpers.
- **Push relay**: a Rust service in `relay/` that sends APNs pushes for every host (see Push relay under Devices).
- **Apple apps**: the iOS and macOS app in `apple/` (one SwiftUI target, bundle ID `dev.bgenc.hobwork` on both). It shows the web UI and dashboards in a `WKWebView` and exposes native capabilities (notifications, and on iOS alarms, Focus, NFC and Health; on macOS Focus) to scripts, and haptics, printing, the share sheet, the clipboard and local notifications to hob UIs (see [Web bridge](#web-bridge)).

The host never executes hob code itself. Anything from a hob repo runs inside a Gondolin VM.

## Sandboxing (Gondolin)

[Gondolin](https://github.com/earendil-works/gondolin) runs each sandbox as a QEMU micro-VM. The host implements the guest's network stack and filesystem in TypeScript, which gives us:

- **Egress allowlist**: only HTTP(S) to allowed hosts. Blocked requests get a 403. Internal ranges are blocked by default. Gondolin's range check does not cover NAT64, 6to4 or IPv4-compatible encodings of private IPv4 addresses, or the global IPv6 prefixes of the LAN, so the sandbox also passes an `isIpAllowed` hook (`server/src/public-address.ts`) that refuses those, other reserved ranges, and the networks of the host's own interfaces (re-read every 30 seconds). NAT64 and 6to4 addresses of public IPv4 hosts are allowed.
- **Private targets** (`server/src/sandbox/egress.ts`): an `egress` entry is `host` (any port) or `host:port` (`[IPv6]:port`), which allows only that port; Gondolin's own allowlist knows no ports, so the sandbox gets the hosts alone and checks ports in `isRequestAllowed` and `isIpAllowed` (which run again on every redirect hop and on each new connection). Private, LAN and tailnet addresses (the reserved ranges above, 100.64.0.0/10 and the host's own networks) stay blocked unless the host's operator lists the target in `HOBWORK_PRIVATE_EGRESS` and the hob's `egress` lists it too, so a hob cannot unlock the LAN on its own. The setting is comma-separated `host:port`, `ip:port`, `[ipv6]:port` or `network/prefix:port` entries (`100.66.127.125:7912,192.168.1.0/24:8123,nas.lan:5000`); every entry needs a port, so allowing a NAS's web UI does not open its SSH. A host name entry allows whatever private address the name resolves to. Loopback (127.0.0.0/8, ::1, 0.0.0.0/8) can never be listed and is refused at connect time even for a listed name, since the host's own services (Hobwork itself) listen there; an invalid entry stops the host from starting. Gondolin's `blockInternalRanges` is off, since `isIpAllowed` does that check itself, with the operator's exceptions. Plain http works on any port: Gondolin recognizes HTTP by the request line, not the port (`classifyTcpFlow` in `vendor/gondolin/dist/src/qemu/network-stack.js`), and builds the URL from the `Host` header, port included. Secrets are still only filled in over https (`secretGuard`), so a hob cannot send one to a private plain-http target. A request refused for being private is logged with the address and says that the operator has to allow it. The project page in the web UI lists the hob's targets and marks private ones as on the home network, or crossed out when the host does not allow them (`describeEgress`).
- **Secret placeholders**: the guest sees `GONDOLIN_SECRET_...` in env vars. The host swaps in the real value only over https, only in the `Authorization` header and the headers the secret lists, and only for the hosts the secret is bound to. A placeholder in any other header, or over plain http, gets the request refused with 403 `hobwork_secret_not_allowed` (`secretGuard` in `server/src/sandbox/gondolin.ts`, which runs in `onRequest` and again before the interceptor's `upstream`), since Gondolin itself would fill it into every header. Query string and body substitution are off.
- **Mounts**: host directories or in-memory filesystems mapped into the guest.
- **Ingress**: HTTP gateway into a server listening on `127.0.0.1` in the guest.

Gondolin does not work under Bun (HTTPS egress hangs, gondolin#73), which is why the host is Node.

All Gondolin use goes through a small `Sandbox` interface in the host (`server/src/sandbox/sandbox.ts`) so the backend can be swapped (e.g. Docker) if it ever needs to be. It covers: create a VM (memory, CPUs, disk size, image, mounts, env, egress allowlist, secrets, internal host handler, interceptor), exec with streamed output, timeout and kill, ingress to a guest port, file read/write, and stop. `@earendil-works/gondolin` 0.12.0 is vendored in `vendor/gondolin` (the published npm package, a workspace package) and changed there; `vendor/gondolin/CHANGES.md` lists the changes, which a Gondolin upgrade has to carry or drop.

- **Exec** runs `/bin/sh -lc <command>`. Several commands can run at once in one VM, including next to a long-running server.
- **Kill and timeout**: Gondolin cannot signal a guest process (aborting an exec only stops waiting). Every exec gets a unique `HOBWORK_EXEC_ID` env var, which child processes inherit. A kill runs a second exec that finds the processes with that variable in `/proc/*/environ` and sends SIGTERM, then SIGKILL after 2s. This also catches children that started their own session.
- **Environment**: every VM gets the host's time zone (`TZ`, or the zone Node resolves when it is unset) and locale (`LANG`, `LANGUAGE`, `LC_*`) from `server/src/sandbox/system-env.ts`, so dates and formats match the host, which also schedules crons in its time zone. Nothing else from the host's environment reaches a VM. The image has `tzdata` and the full ICU data, so every zone and locale works in Node and shell tools.
- **Interceptor**: a VM can be created with an interceptor for some hosts (`openrouter.ai` and `*.openrouter.ai` for the [AI gateway](#ai-limits)). Gondolin's `onRequest` hook hands allowed requests to those hosts to it, together with an `upstream` function that fills in secrets and sends the request on (`server/src/sandbox/intercept.ts`). Gondolin applies secrets only to requests it forwards itself, so `upstream` uses a second set of Gondolin HTTP hooks with the same placeholders (`secretFiller`), which keeps Gondolin's per-host rules for secrets. The host connects to intercepted hosts with its own `fetch`, without Gondolin's check against internal addresses, so only well-known public hosts are intercepted. Gondolin streams answers from `onRequest` to the guest (vendored change, see [Request and answer bodies](#sandboxing-gondolin)), but the gateway reads the whole answer to count its cost, so a streamed answer still reaches the guest in one piece when it is complete.
- **Request and answer bodies**: Gondolin buffers a request body before it reaches `onRequest` or goes upstream, up to 64MB (`maxHttpBodyBytes`; larger ones get 413). The vendored Gondolin has an `httpHooks.streamRequestBody` hook: a request it opts in reaches `onRequest` with its body as a stream, `Content-Length` and chunked alike, with backpressure to the guest and no size limit. `SandboxOptions.streamInternal` decides for `hobwork.internal` requests; nothing else opts in, because the interceptor and forwarded requests would then have no limit. Only workspace pushes use it (`streamsWorkspaceGitBody`). It also streams the `Response` that `onRequest` returns instead of buffering it (which capped answers at 64MB): with its `Content-Length` when it has one, else chunked.
- **VM lifetime**: Gondolin kills QEMU only on a normal exit of the host process. Without isolation the host starts QEMU through `server/src/sandbox/qemu-watched.sh`, which execs QEMU in its own place (so `hostPid()` is QEMU's pid) and leaves a shell behind that SIGKILLs QEMU within a second of the host process dying, whether from a signal, a crash or SIGKILL. With isolation, bwrap's `--die-with-parent` does the same. As a fallback inside the guest, `sandboxd` resets the VM 10s after the host closes its control port (QEMU never reconnects it), and QEMU's `-no-reboot` turns the reset into an exit.
- **QEMU seccomp filter**: with `HOBWORK_QEMU_SANDBOX=1` (Linux only) `qemu-watched.sh` starts QEMU through `server/src/sandbox/qemu-sandboxed.sh`, which adds `-sandbox on,obsolete=deny,elevateprivileges=deny,spawn=deny,resourcecontrol=deny` (the options libvirt uses) to the command line Gondolin builds. Gondolin only lets the host pick the QEMU binary, so a wrapper is the only place to add arguments. It picks `qemu-system-$(uname -m)` from `PATH`. Off by default until `pnpm -C server test:vm` has passed with it on `colossus`. With isolation on, `qemu-namespaced.sh` runs it inside QEMU's namespace.
- **Isolation**: with `HOBWORK_SANDBOX_ISOLATION=namespaces` (Linux only; default `off`) QEMU and the guest's filesystem run outside the host process, each in its own unprivileged user, mount, PID, network, IPC and UTS namespaces under `bwrap` (`server/src/sandbox/isolation.ts`), so a QEMU escape or a bug in the filesystem bridge does not reach the data dir, `secret.key`, other hobs' files or the host process. The host keeps the network stack, secrets, the control channel, ssh and ingress, so guest-controlled parsing of TCP, DNS, HTTP and the exec protocol stays in the host process. macOS keeps everything in-process. The `Sandbox` interface is the same in both modes.
  - **VM directory**: per VM the host creates `vm/v<random>/` under `$RUNTIME_DIRECTORY` (set by systemd for `RuntimeDirectory=hobwork`, so `/run/hobwork`) or else `<tmpdir>/hobwork-<uid>`, all mode 700. It holds `vm/` with the control, ssh, ingress and network sockets and the root disk overlay (created with `qemu-img` there instead of by Gondolin in `os.tmpdir()`), `fs/` with the VFS worker's socket, and `qemu.bwrap`, QEMU's bwrap options. It is removed when the VM stops or exits.
  - **QEMU** starts through `server/src/sandbox/qemu-namespaced.sh` (Gondolin only lets the host pick the binary), which runs `bwrap --args` with those options: `--unshare-all --die-with-parent --new-session --cap-drop ALL --clearenv`, an empty root with `/usr` and the libraries read-only (and, for a `qemu-system-*` on `PATH` outside them, its install prefix or `/nix/store`, with its bin directory on the namespace's `PATH`), its own `/proc`, `/dev` and `/tmp`, `/dev/kvm` when the host has it, the guest image read-only and the VM directory. It has no network (Unix sockets in a bound directory still work), none of the host's environment (`HOBWORK_SECRET_KEY`, OIDC credentials) and no data dir. The shim also points QEMU's `virtiofs0` chardev at the worker's socket. Gondolin's SIGTERM and SIGKILL go to the outer `bwrap`, and `--die-with-parent` ends QEMU with it, so `exited` and `stop()` work as before. `hostPid()` returns the outer `bwrap`'s pid, not QEMU's.
  - **VFS worker** (`server/src/sandbox/vfs-worker.ts`): a Node process per VM that serves the VM's mounts with Gondolin's `FsRpcService` on the fs socket. The host starts it under `bwrap` before QEMU, passes the mount list (guest path, host path, `readonly`, `maxBytes`, `hide`, `vmDisk`) and the MITM CA certificate as one JSON line on stdin, and waits for its `ready` line (30s). Its namespace has Node, the release's `server/src/sandbox`, `server/package.json`, `node_modules` and `vendor/gondolin` read-only, its socket directory, and the VM's mount directories (read-only for read-only mounts). `RealFSProvider` checks a path with `realpath` and then opens it, so a symlink the guest swaps in between escapes the mount; in the worker's namespace there is nothing outside the VM's own mounts to escape to, and the worker cannot reach the host's sockets. Both modes build mount providers with `server/src/sandbox/mounts.ts`. The worker also serves `/etc/gondolin`: an empty, read-only ingress `listeners` file (the host keeps ingress routes itself, so the guest can no longer change them) and `mitm/ca.crt` (the certificate only; the key stays with the host). It accepts one connection and exits when QEMU closes it or the host closes its stdin. If it dies, the host stops the VM.
  - **Host side**: Gondolin's own fs bridge listens on `<VM directory>.fs.sock`, outside what QEMU can see, and nothing connects to it. Its VFS gets an empty `MemoryProvider` per mount, which keeps the guest's mount list right, so `Sandbox.readFile` and `writeFile` go through the guest instead of Gondolin's host-side shortcut for mounted paths.
  - **Gondolin internals**: the worker needs the mount router, the frame codec and the MITM CA loader, which Gondolin does not export. `server/src/sandbox/gondolin-internals.ts` imports them by file path and refuses to load with another Gondolin version than 0.12.0. The Gondolin changes that would replace this and the shim are in `docs/todo.md`.
  - **Start check**: when isolation is on, the host runs `bwrap` with the same namespace options at start and refuses to start with the reason if it fails (bwrap missing, `kernel.unprivileged_userns_clone`, `user.max_user_namespaces`, Ubuntu's `kernel.apparmor_restrict_unprivileged_userns`, or `RestrictNamespaces=` or a `SystemCallFilter` in the unit). It does not fall back to plain QEMU.
  - **Limits**: everything still runs as the host's user, so a process that escapes both QEMU and its namespace can `ptrace` or signal the host, and kernel bugs reachable from an unprivileged user namespace remain. Each VM costs one more Node process (about 100MB RSS, ready in about 0.2s, started while Gondolin prepares the VM), which the VM budget does not count.
  - **Tests**: `server/src/sandbox/isolation.test.ts` checks the bwrap options and that a process in QEMU's namespace cannot read a data dir. With `HOBWORK_VM_TESTS=1` and isolation on, it checks through `/proc/<pid>/root` of the real QEMU and worker processes that neither sees the data dir and the worker sees only its VM's mounts, that a symlink the guest swaps to a file outside the mount while reading never returns that file, and that the VM stops when its worker dies. The same race did not leak with the in-process VFS either (macOS, 20s, two swapping and three reading guest processes): the check and the open run in one synchronous step on Node's one thread, so a swap from the guest alone rarely lands between them. The race test guards the property, and the `/proc/<pid>/root` checks show there is nothing outside the mounts for the worker to reach. `dev/sandbox-isolation/` runs them and the VM suite in Docker on a Linux host with KVM.
  - Off by default until the VFS worker is replaced by a fix for the VFS race in the vendored Gondolin ("Sandbox account" in `docs/todo.md`). The VM suite passes with it on `colossus` (KVM, `microvm`, `-cpu host`). To turn it on: install bubblewrap, set `RuntimeDirectory=hobwork` and `HOBWORK_SANDBOX_ISOLATION=namespaces` in the unit, and restart.
- **Blocked egress** is reported to the host through a callback (for logging). Gondolin checks its allowlist only after resolving the name, so a host that does not resolve would get a 502 and never reach the callback. The sandbox therefore checks the hostname against the allowlist first (`isRequestAllowed`, same pattern matching as Gondolin), which answers 403 and reports it.

On x86_64 the host replaces Gondolin's kernel command line (`server/src/sandbox/gondolin.ts`). With the default one, create to first command took 2.5s:

- QEMU's `microvm` machine has no CMOS RTC, and the kernel's `rtc_cmos` probe waits about 1.3s before it gives up (`initcall_blacklist=cmos_init`).
- The i8042 probe costs about 80ms (`i8042.noaux i8042.nomux i8042.nopnp`).
- Kernel and init output go to the emulated UART, and every byte is a VM exit. That is about 450ms (`quiet`, `console=tty0`). `HOBWORK_VM_CONSOLE=1` puts the console back on `ttyS0`, so Gondolin's boot error messages include the guest log.

The rest is SeaBIOS (about 125ms; qboot measured no faster), the kernel, and Gondolin's init script (module loading, DHCP, sandboxfs mount, CA bundle). The VM test suite (`pnpm -C server test:vm`) passes on `colossus` (55 tests).

### VM kinds

| Kind | Lifetime | Filesystem | Purpose |
|---|---|---|---|
| Hob runtime | 0 or 1 per hob. Starts on demand, stops after idle timeout | Deployed build of `main`, read-only | Runs handlers |
| Agent workspace | Per branch. Stops when idle, restarts on demand | Branch checkout, read-write | Agent bash, dev server, tests while iterating |
| Pipeline run | Fresh per run, discarded after | Clean checkout of the candidate commit | Install, typecheck, lint, test, build |
| Branch preview | 0 or 1 per branch. Starts on demand, stops after idle timeout | Build of the branch's latest commit, read-only | Runs a branch's handlers for its preview |

### VM budget

Every VM reserves its memory and vCPUs from one host budget before it boots (`budgetedSandboxFactory` in `server/src/sandbox/budget.ts` wraps the sandbox factory, so every kind goes through it) and gives them back when it stops or fails to boot. The budget is `HOBWORK_VM_MEMORY_MB` and `HOBWORK_VM_CPUS`. By default it is the host's memory minus a quarter (at least 1 GiB) and twice the host's CPU count, never less than the biggest VM. Runtime VMs (also used by branch previews) default to 384 MB and 0.5 vCPUs, workspace and pipeline VMs (also used by builds) to 1536 MB and 2 vCPUs. `hobwork.json` `resources` (`runtime`, `workspace`, `pipeline`, each with `memoryMb` and `cpus`) asks for less; values above the defaults are capped. `cpus` may be a fraction, down to 0.25, where the host can hold a VM to one.

QEMU takes only whole vCPUs, so a VM boots with the ceiling of `cpus` (at least one) and the host holds it to the rest with cgroup v2 (`cpu-quota.ts`): the host creates a cgroup for the VM, writes the share to `cpu.max`, moves QEMU and every process below it into that cgroup, and reads the cgroup back to check that they all arrived (`capVmCpu`). CFS bandwidth control then holds the VM to that share: a runtime VM at 0.5 core takes twice as long to finish a CPU-bound handler as one at a whole core. QEMU's own emulation work is outside the cap and adds a few percent. A handler serves one request at a time on one thread, so a runtime VM rarely reaches its share.

The guest cannot enforce this itself, because the guest owns the VM: anything running in it can undo a limit set from inside. The host decides once, before the first VM it caps, whether it can cap one at all (`probeCpuQuota` in `server/src/sandbox/cpu-quota.ts`): cgroup v2 must be mounted, its `cpu` controller available, and a quota writable. A cgroup that holds the host's own process cannot pass controllers on to its children, so a delegated one needs a child to park the host's process in first, which the probe does when it must (`parkSelf`). Where any of that fails, which includes every Mac, `cpus` must be a whole number: `hobwork.json` that asks for a fraction fails validation (`/resources/runtime/cpus: this host cannot cap a VM at 0.5 vCPUs, because it does not run Linux. Ask for a whole number of vCPUs, at least 1.`), the runtime default is one vCPU, and the budget reserves a share only where one is in force.

The scheduler (`server/src/sandbox/scheduler.ts`) grants a request that fits at once, so a hob can borrow capacity nobody else wants. When the budget is full, requests wait in one queue per hob. The next one is chosen by priority (the main runtime, then builds, branch previews and pipeline runs, then workspaces) and, among equals, by the hob using the least memory, which gives every active hob an equal share over time. For the next request the scheduler stops idle workspace VMs (`stopIfIdle` in `server/src/workspaces.ts`: no running command, unused for 30 seconds): any of them for a runtime, build, preview or pipeline run, the ones of the hobs furthest over their equal share first, and for a workspace only those of other hobs over their share. A request waits `HOBWORK_VM_WAIT_SECONDS` (default 60) and then fails with "Hobwork is busy: there was no room to start a VM for <hob>. Try again in a minute.". Handlers get a 503 for it, which does not count against the version's health.

## Hobs

A hob is a git repository plus its deployed state, data and secrets. Examples: "filament tracker", "sleep alarms", "HA announcements". The code calls a hob a project (the `projects` table, `project_id` columns, `/api/projects` routes, SDK types), so this document calls code things by their code names and the concept a hob.

### Repository layout

New hobs are created from a template with everything configured:

```
AGENTS.md              how Hobwork works, rules for agents (Lambda model, tests, migrations)
hobwork.json           entry points (crons, webhooks, routes, triggers) and settings
package.json           scripts: typecheck, lint, test, build; extra deps (discouraged)
tsconfig.json
vite.config.ts         UI build + Vitest config, from hobworkViteConfig() in @hobwork/sdk/vite
src/                   handlers and shared code
ui/                    dashboard pages (React + Tailwind), optional with index.html
migrations/*.sql       hob DB migrations, applied in order
tests/                 Vitest tests
```

### Entry points

All entry points are declared in `hobwork.json`. The host reads it directly and never has to run hob code to find out what a hob does. The pipeline validates it against a JSON schema. It may have comments and trailing commas like `tsconfig.json` (JSONC); everything reads it with `parseHobworkJson` from `@hobwork/sdk/hobwork-json`, which reports errors with line and column.

```json
{
  "icon": "🧵",
  "crons": {
    "morning-alarm": { "schedule": "0 6 * * 1-5", "handler": "src/morning-alarm.ts" }
  },
  "webhooks": {
    "filament-scanned": { "handler": "src/scan.ts" }
  },
  "routes": {
    "GET /spools": { "handler": "src/spools.ts" }
  },
  "triggers": {
    "desk-button": {
      "homeassistant": {
        "trigger": "device",
        "domain": "zha",
        "device_id": "...",
        "type": "remote_button_short_press",
        "subtype": "button_1"
      },
      "handler": "src/desk-button.ts"
    }
  },
  "static": {
    "/photos": { "dir": "photos" }
  },
  "egress": ["api.example.com"],
  "idleTimeout": "1h"
}
```

- **Crons**: run on a schedule. The host owns the schedule. `timeZone` (optional) puts the schedule in an IANA zone (`"Europe/Istanbul"`), or `"person"` runs it once for each person at that time in their own zone, with `ctx.payload` a `PersonCronPayload` (`{ person }`); see [People and time zones](#people-and-time-zones). Without it, the host's zone.
- **Webhooks**: called from outside at `<hob app origin>/_hobwork/hooks/<name>/<token>`, for example `https://filament.apps.hobwork.example.com/_hobwork/hooks/scanned/<token>`. The token is a rotatable secret. The request is passed to the handler.
- **Routes**: authenticated API for the hob's own dashboard, at `/api/...` on the hob's app origin (see [Hob app origins](#hob-app-origins)) and at `/p/<hob>/api/...` on the Hobwork host for agents. `"GET /spools/:id"` answers `GET /api/spools/42` with `ctx.params.id = "42"`. Static segments win over parameters, and `HEAD` is served by the `GET` route.
- **Static files**: `static` maps paths of the hob's app to directories of its files (`ctx.files`), which the host serves without starting the VM. See [Files](#files).
- **Triggers**: events from integrations (Home Assistant, devices). The trigger payload is passed to the handler. A trigger has either a `homeassistant` block or a `device` block; `{ "device": { "capability": "notifications", "event": "action" } }` runs when someone taps an action on a notification the hob sent (see [Notifications](#notifications)).

`icon` is not an entry point: it is one emoji or the path of an image in the repo, for the hob's favicon, home screen icon and hob lists (see [Hob icons](#hob-icons)).

A handler file exports a default function that receives the invocation context:

```ts
import type { Handler } from "@hobwork/sdk";

export default (async (ctx) => {
  const res = await ctx.fetch("https://health-export.example/api/sleep/last");
  ...
}) satisfies Handler;
```

The context (`packages/sdk/src/index.ts`) has `invocation` (ID, kind, name, whether it was started by hand), `request` (a standard `Request`, for routes and webhooks), `params`, `payload` (trigger variables, or what a manual invocation passed), `fetch` (the guest's own `fetch`, which the egress allowlist controls), `log`, `db`, `files` (see [Files](#files)), `ha`, `secrets`, and `device(name)` and `devices()` (see [Devices](#devices-apple-apps)). `RequestHandler` is the variant with `request` always set. A route or webhook answers with the handler's return value: a `Response` is sent as is, `undefined` as 204, anything else as JSON. A thrown error answers 500 with the invocation ID and no details, since webhook callers are outside the household; the error and stack trace are in the invocation record.

The SDK API is the context rather than imported functions, so handler bundles contain no SDK runtime code and tests build a context by hand.

### Dependencies

The guest image contains one **platform dependency set** (React, Tailwind, Vite, Vitest, TypeScript, oxlint, zod, date-fns and similar) on the VM's own disk. Every hob uses the same versions, so they are updated together.

- Updating the platform set means rebuilding the image. Deployed builds bundle their dependencies (see [Runtime](#runtime)), so they keep running unchanged; each hob's next workspace, pipeline run or build uses the new versions.
- Hobs can add extra npm packages in their `package.json`, installed on top of the platform set. This is allowed but discouraged, and `AGENTS.md` says so.
- The image has `python3` for ad-hoc scripts in workspaces (data wrangling, one-off checks). It is tooling only: handlers are TypeScript, and Python has no package manager in the VMs. pip is not installed and `ensurepip` is deleted from the image, so Python gets no packages beyond its standard library and cannot bypass the npm install protections below.

How the layering works (prototyped in `server/src/sandbox/gondolin.test.ts`):

- The platform set also holds what the pipeline needs to render hob icons: `sharp` and `@twemoji/svg` (see [Hob icons](#hob-icons)).
- The platform set is a normal pnpm install at `/opt/hobwork/platform` (`images/platform/package.json` and its lockfile, exact versions). `/node_modules` is a symlink to `/opt/hobwork/platform/node_modules`, and `/opt/hobwork/platform/node_modules/.bin` is on `PATH`.
- Node, TypeScript, Vite and Vitest all resolve packages by walking up parent directories to `/node_modules`, so a hob anywhere in the VM finds the platform packages and their types with no configuration. `NODE_PATH` is not used because ES modules ignore it.
- A hob's `package.json` lists only its extras (the template has scripts and no dependencies). `pnpm install` puts them in the hob's own `node_modules`, which is found before `/node_modules`, so an extra could also override a platform package.
- `images/platform/package.json` is the single definition of the platform set. The host reads it (`server/src/platform.ts`) to tell extras apart: a dependency not in it (and not `@hobwork/sdk`) is an extra. Workspace and pipeline VMs run `pnpm install` only when a hob has extras.
- The template sets `autoInstallPeers: false` in `pnpm-workspace.yaml`. Without it, pnpm installs a second React for an extra that has React as a peer dependency. With it, the peer resolves to the platform React through the same parent-directory lookup.
- Installing extras needs egress to `registry.npmjs.org`. Egress is fixed when a VM is created, so pipeline VMs can reach the registry (and nothing else) for the whole run, not only during the install step. Workspace VMs can reach it too, so agents can `pnpm add` extras.
- **Install protections**: workspace and pipeline VMs set `pnpm_config_minimum_release_age=4320` (3 days, in minutes) in their environment (`server/src/guest-vm.ts`). An environment setting beats a hob's `pnpm-workspace.yaml`, and unlike a global config file it does not depend on where the VM's `HOME` or `XDG_CONFIG_HOME` point (Gondolin sets the latter to `/tmp`). Versions published in the last 3 days are not installed, since most malicious releases are caught and pulled within that time. pnpm 12 runs dependency install scripts only for packages listed as `true` under `allowBuilds` in the hob's `pnpm-workspace.yaml` and fails the install with `ERR_PNPM_IGNORED_BUILDS` for any other package that has one; the image and the template allow none. The pipeline's validate step (`server/src/pipeline/pnpm-settings.ts`) refuses a `pnpm-workspace.yaml` that sets `minimumReleaseAge` below the default, `minimumReleaseAgeExclude`, `minimumReleaseAgeIgnoreMissingTime` or `dangerouslyAllowAllBuilds`, that sets `pnpmfile`, `globalPnpmfile`, `registry` or `registries`, or that is not valid YAML. It also refuses a `.pnpmfile.cjs` or `.pnpmfile.mjs` at the hob's root (a pnpmfile is code that runs during install and gets around `allowBuilds`) and a `.npmrc` that sets a registry, a pnpmfile, a lower `minimum-release-age`, `minimum-release-age-ignore-missing-time`, `dangerously-allow-all-builds`, `script-shell` or `node-options`. Builds of versions without a stored build apply the same check (`checkInstallConfig`), and appends a notice to its output when the candidate changes the `allowBuilds` list compared to the deployed version, so the pipeline run shows it. Merges and restores also record the packages added to and removed from `allowBuilds` compared to the previous main on the version (`versions.builds_added` and `builds_removed`, JSON arrays, kept through trash). They come back as `installScripts: { added, removed }` in `list_versions` and the versions API, and the web UI's versions list flags the version with the package names. The pipeline and the build of a version without a stored build install extras with `pnpm install --frozen-lockfile --ignore-pnpmfile`, so what was tested is what is deployed. A hob with extras and no `pnpm-lock.yaml`, or a lockfile that does not match `package.json`, fails with a message to run `pnpm install` in the workspace and commit the lockfile. Workspace VMs still run a plain `pnpm install` so agents can add packages. Workspace code runs there anyway, so the pnpmfile and `.npmrc` checks only apply to what merges.

`@hobwork/sdk` is part of the platform set. The image build copies `packages/sdk` (its `package.json`, `src/` and schema) to `/opt/hobwork/platform/node_modules/@hobwork/sdk`, so hob code resolves it through `/node_modules` like any platform package, in workspace, pipeline and runtime VMs alike. It is versioned with the image: an SDK change needs an image rebuild, like other platform updates. Rejected: mounting `packages/sdk` from the host read-only, which would let the SDK drift from what a deployed version was tested against. The SDK is shipped as TypeScript source, except `hobwork-json.js` and `vite.js`, which are JavaScript with `.d.ts` files: Vite loads the imports of `vite.config.ts` with Node, and Node does not strip types under `node_modules`. TypeScript works for types and for Vite builds, and handler bundles contain no SDK runtime code (see [Entry points](#entry-points)), so nothing is compiled. The runner in `packages/sdk/src/runner/` is host code and reaches runtime VMs differently (see [Runtime](#runtime)).

### Workspace file layout

Agent workspaces mount the branch checkout from the host read-write at `/workspace`, and its git directory at `/opt/hobwork/workspace-git`. The VM can write both, so the host never opens files in them or runs git on them (see [Branches and workspaces](#branches-and-workspaces)). `node_modules` inside it lives on the VM's own disk (a bind mount the `Sandbox` sets up for `Mount.vmDisk` paths, hidden from the host side). It only holds extras, is reinstalled when the VM starts, and is gone when it stops.

Measured with `pnpm -C server bench:sandbox vfs` on the Mac (generated hob: 40 TSX modules using zod, date-fns and React, 20 Vitest files; 2GB VM; medians of 3):

| Layout | `tsc --noEmit` 2 vCPU | `vitest run` 2 vCPU | `tsc --noEmit` 4 vCPU | `vitest run` 4 vCPU |
|---|---|---|---|---|
| (a) everything mounted, full `node_modules` in the mount | 1.79s | 23.3s | 1.55s | 11.4s |
| (b) everything on the VM disk | 0.90s | 12.7s | 0.74s | 5.1s |
| (c) source mounted, platform set from the image | 0.95s | 12.2s | 0.78s | 5.3s |
| (d) source mounted, full `node_modules` on the VM disk | 0.96s | 12.2s | 0.83s | 5.3s |

- The Gondolin filesystem bridge doubles the time when `node_modules` goes through it, and copying the platform set into a mount takes 10s. With `node_modules` on the VM disk, a mounted checkout is as fast as a checkout on the VM disk, so there is no reason to copy the checkout into the VM.
- Vitest time is dominated by module imports, not the filesystem: every test file runs isolated and imports `date-fns` from scratch (~750ms in the guest, ~420ms in a Docker container on the same Mac). `--no-isolate` brings the run to 1.2s. Pipeline and workspace VMs get 2 vCPUs.
- The template's Vitest config sets `isolate: false`, with `restoreMocks`, `unstubGlobals` and `unstubEnvs` so mocks and stubs do not leak between tests. On the template with 10 extra test files importing zod and date-fns (2 vCPUs): 3.6-3.9s isolated, 3.0-3.7s with `pool: 'threads'`, 0.8s with `isolate: false`. Test files share one module cache, which `AGENTS.md` tells agents.

### Branches and workspaces

- Each hob is a bare repo on the host: `data/repos/<hob>.git`.
- `main` is the deployed version. Nobody pushes to it directly. The only way in is a merge through the pipeline.
- Agents do work on branches. Each branch can have an **agent workspace** VM with the branch checked out.
- A workspace's checkout lives on the host at `data/workspaces/<hob>/<branch>/`, with the branch's files in `files/` and the git directory in `git/`. The VM mounts both (`files/` at `/workspace`, `git/` at `/opt/hobwork/workspace-git`). The checkout has no `.git` entry, so git is always given the git directory and work tree explicitly.
- **Nothing on the host touches what the VM can write.** The host creates the checkout once (a clone of the bare repo without hardlinks and without a remote, so the VM sees no host path) and never reads, writes or runs git in it again. File tools and git run inside the VM through `hobwork-tool` (`packages/sdk/src/workspace-tools/`, mounted read-only at `/opt/hobwork/tools`, with a wrapper written at VM start), which reads a JSON request on stdin and prints one JSON line. The host reads at most 12MB of that, parses it strictly (`server/src/workspace-tools.ts`, zod schemas) and treats it as data. A nested repo's config (`core.fsmonitor`, filter drivers) or a submodule therefore runs where workspace code already runs.
- `commit`, `diff` and `changes` run in the VM, which starts on demand like for `bash`. `commit` runs `git add --all`, `git commit` and a push to `http://hobwork.internal/git/<hob>.git`; the host then checks that the branch in the bare repo is at the commit the VM reported before it answers. Author: the agent that called `commit`, committer: Hobwork. When the workspace does not exist, `commit`, `diff` and `changes` do nothing and start no VM.
- **Workspace git route** (`server/src/workspace-git.ts`): the workspace VM's internal handler serves git smart HTTP under `/git/<hob>.git/` by running `git http-backend` on the bare repo (`startGitBackend` in `server/src/git-http.ts`, shared with the public `/git/` route). Push bodies stream from the VM into `git http-backend` (see "Request and answer bodies" in [Sandboxing](#sandboxing-gondolin)), so a push can be larger than Gondolin's 64MB buffer, and fetch answers stream back. It is authorized by a workspace session token (`x-hobwork-session`; the tools the host runs get a tool token in `HOBWORK_TOOL_SESSION` that only this route accepts, and command tokens work here too), bound to the VM's hob, and a push may only update `refs/heads/<branch>` of that workspace: the host reads the ref updates at the start of the push request (at most 1MB of them) and refuses other refs, deletions, signed pushes and compressed bodies before git sees them, then pipes the rest of the body into git. The pre-receive hook still refuses `main`. Pushes into the repo from anywhere use `receive.fsckObjects` and a 512MB `receive.maxInputSize`, which git enforces while the pack streams in, so it is the only size limit on workspace pushes.
- Branch data is isolated: a workspace gets a copy of the hob DB taken when the workspace VM starts. Tests get an empty DB with migrations applied. See [Data](#data).
- **Deleting a branch** (`server/src/branch-deletion.ts`) removes its ref, workspace (with its DB copy), preview VM, webhook tokens, Home Assistant approval and app sessions and share links, while no merge of the hob runs. People delete branches on the hob page (`DELETE /api/projects/<hob>/branches/<branch>`), which throws away work that is not on `main`. Agents use `delete_branch`, which refuses while the branch has commits `main` does not have or uncommitted changes unless `discard_changes` is set.
- **Merged branch cleanup**: a merge that resets the branch onto the new `main` records the merged commit in `branch_merges` (`server/migrations/0036_branch_merges.sql`). The daily housekeeping job deletes a branch 7 days after its last merge if it still points at that commit, its workspace was not used since and it has no uncommitted changes. Creating a branch forgets an earlier merge under the same name. The hob page shows when a merged branch will be deleted.

Workspace VMs (`server/src/guest-vm.ts`):

- Started by the first `bash` call, SSH session, uncommitted-state read, file change or `commit` on a branch: 2 vCPUs, 1536MB memory, 4GB root disk, `files/` at `/workspace` with `node_modules` on the VM disk. `bash`'s `cwd` is relative to `/workspace`. Extras are installed on start. A failed install does not fail the start, so the agent can still run commands and see the error with `pnpm install`.
- Egress: the `hobwork.json` `egress` at the branch head in the project repo, the hosts of the hob's secrets, and `registry.npmjs.org`. Secrets are passed as placeholders like in the runtime. The host reads `hobwork.json` (`egress`, `resources`) and `package.json` (extras) from the repo (`branchFileReader` in `server/src/files.ts`), never from the checkout, which the VM can write: an uncommitted edit would otherwise let code in the VM widen its own egress. So an `egress` change applies after `commit`. When the committed `egress` or the secrets change, the next call that needs the VM replaces it (unless a command is still running), so agents can test a new host without a restart tool. Blocked requests are logged to the hob log with the branch name.
- Idle stop: a VM with no `bash` call or file tool call for `HOBWORK_WORKSPACE_IDLE_MINUTES` (default 30) is stopped, unless a command is running. Every `bash` call updates `last_used_at` when it starts and when it ends. The default is well above the 10 minute `bash` timeout. A stopped VM starts again on the next call. Stopping loses processes and the VM-disk `node_modules`, and nothing else, since the files are on the host.
- The host stops all workspace and pipeline VMs on SIGINT and SIGTERM.
- Pipeline VMs use the same resources and layout with a fresh VM per run and only the registry allowed.
- Both are enabled when a guest image exists (`images/build/<arch>` or `HOBWORK_IMAGE_DIR`). Without one the host logs that `bash` and `merge` are unavailable.

### Deleting hobs

Only people delete hobs, in the web UI (the hob's overview, confirmed by typing the name) through `DELETE /api/projects/<name>` with `{ confirm: "<name>" }`. There is no MCP tool, CLI command or workspace API for it: an agent that is misled or confused could otherwise destroy a hob and its data, and deleting is rare enough to leave to a person.

Deletion (`server/src/project-deletion.ts`) runs in the hob's delivery queue, so it waits for a running merge or restore. It stops the runtime VM right away without waiting for running invocations, unschedules crons, unsubscribes HA triggers (`removeProject` in the trigger registry), stops and removes branch workspaces (VMs, checkouts, branch DBs), closes the hob DB, and deletes the builds. The hob row goes from the host DB and takes versions, pipeline runs, invocations, logs, webhook tokens, workspaces and secret assignments with it (foreign keys cascade). Secrets stay in the library for other hobs.

It is a soft delete for the parts that cannot be rebuilt: the bare repo and the hob DB directory (with its [files](#files)) move to `<dataDir>/trash/<name>-<time>/` (`repo.git`, `data/`) with a `deleted.json` holding who deleted it, when it is purged, and the rows needed to bring it back: versions (with their agent, user and `restored_from`), the creation time, secret assignments, webhook token hashes, NFC tag IDs, its star and tags, and the IDs of agent tokens and OAuth connections whose hob list includes it (entries from before these fields were added have versions only). The daily housekeeping job (`server/src/housekeeping.ts`) removes entries older than 7 days. Backups may run less often than a hob gets deleted by mistake, and they cover live hobs only (snapshots from before the deletion keep it for their retention), so the trash is the way back in the meantime. The name can be used for a new hob right away.

### Restoring deleted hobs

The web UI's Deleted hobs page (`/deleted`, linked from the hobs list and the deletion notice) lists the trash with who deleted each hob, when, its last version and when it is purged: `GET /api/trash` returns `{ trashDays, projects: [{ id, project, deletedAt, purgeAfter, deletedBy, versions, lastVersion, nameTaken }] }`, where `id` is the trash directory name. `POST /api/trash/<id>/restore` with `{ name? }` restores it under its old name or, when a hob took that name (`nameTaken`), under another one; the page asks for one then. Like deleting, it is for people only (session and CSRF header, no MCP tool).

Restoring (`restoreProject` in `server/src/project-deletion.ts`) runs in the delivery queue of the new name. It moves `repo.git` and `data/` back, inserts the hob row with its old creation time and its versions with their numbers, and brings back secret assignments whose secret still exists, webhook tokens (so webhook URLs keep working), NFC tags (they are written on physical tags), its star and tags (at the end of its group), its own [AI models and limits](#ai-limits) and its place in the hob lists of agent tokens and OAuth connections that still exist ([access limits](#access-limits)). The restored hob gets a new ID. Agents and users that no longer exist become null. Run history, logs, AI usage records (so spend limits start over), pipeline runs, branch workspaces and branch HA approvals stay deleted; branches are still in the repo. The trash entry is removed, a `project` event goes to the hob log, and the runtime loads it like after a host restart: crons and HA triggers are scheduled, and the deployed version is built on its first invocation since builds were deleted. The DB already has the version's migrations.

### Organizing hobs

People and agents star, order and tag hobs to find them in a growing list (`server/src/project-list.ts`, migration 0038). They are shared by the household rather than kept per person, since agents are not tied to a user and the MCP tools change the same lists people see.

- **Stars and order**: `projects.starred` puts a hob in the starred group at the top of hob lists. `projects.position` orders hobs within their group. It is null until a hob is moved, and those hobs come after the moved ones by name, so a new hob lands at the end without the create, restore and rename code knowing about order. A move puts a hob before or after another hob of the starred or other group, or at its end, and numbers that group again from 0; moving into the other group stars or unstars it. Starring puts a hob at the end of the starred hobs, unstarring at the top of the others.
- **Tags**: `project_tags`, lowercase letters, digits and single hyphens (like hob names), at most 32 characters and 20 per hob. Input is trimmed and lowercased.
- **Search**: a small query language, the same in the web UI and MCP. A word matches hobs whose name or a tag contains it. `name:<pattern>` matches the name, as a part of it or, with `*` and `?`, as a whole. `tag:<pattern>` matches a whole tag, with the same wildcards. `is:starred` matches starred hobs. `-` in front of a term excludes what it matches, and all terms must match. Unknown filters are refused with a message naming the known ones. Searching filters the list in the host instead of using SQLite FTS5: a household has tens of hobs, and FTS5 tokens cannot match parts of names or wildcards without a trigram index kept in sync.
- **API**: `GET /api/projects?q=<search>`, `PUT /api/projects/<name>/starred` with `{ starred }`, `PUT /api/projects/<name>/tags` with `{ tags }` (the whole list), `POST /api/projects/<name>/move` with `{ starred, before?, after? }`, and `GET /api/tags` (every tag with its number of hobs). The hob list and detail include `starred` and `tags`. Changes are published as `projects` and `project`.
- **Web UI**: the hobs page has a search field with the tags as toggles, and the starred and other hobs in two groups. Rows move by dragging their handle with pointer events (mouse, pen and touch, so it works in the Apple apps' web view, where HTML drag and drop does not work with touch), scrolling the page near its edges, or with the arrow keys on the focused handle, which moves across groups at their ends. The empty starred group stays visible as a drop target unless a search is active. A hob's overview has its star and a tag editor.
- **MCP**: `list_hobs` takes `query`, and `star_hob` and `tag_hob` (`add`, `remove`) change stars and tags. Agents do not reorder hobs.

### Renaming hobs

People rename a hob on its overview (`POST /api/projects/<name>/rename` with `{ name }`, `server/src/project-rename.ts`). There is no MCP tool: renaming changes URLs other systems call (webhooks, the app address, git remotes) and interrupts running work, and agents never need it to change a hob. The MCP instructions say so.

Every row in the host DB references the hob by ID, so the rename changes only `projects.name`. The rest is on disk and in memory, keyed by name:

- It runs in the hob's delivery queue, so it waits for a running merge or restore; merges queued for the old name afterwards fail with "was renamed".
- Everything the hob runs stops first, like for a deletion: the runtime VM and branch preview VMs without waiting for running invocations (they end as failed), crons, HA triggers, and branch workspace VMs (a running `bash` command or SSH session ends). Branch DBs and the hob DB are closed.
- `repos/<name>.git`, `projects/<name>/` (the DB), `builds/<name>/` and `workspaces/<name>/` (checkouts with uncommitted changes and branch DB copies) move to the new name. A target that exists refuses the rename, and a failure moves everything back and loads the hob under its old name again.
- Workspace VMs are stopped once more after the move in case a command started one on the old paths meanwhile. Checkouts have no remote, so nothing needs pointing at the moved repo.
- The runtime forgets the old name and loads the new one, which schedules crons and subscribes HA triggers again. VMs start on the next invocation or `bash` call. Secrets, webhook tokens, NFC tags, device notifications and commands, HA approvals and app sessions follow the hob ID. A `project` event in the log records the rename and who did it.
- The code is not changed: `package.json` keeps the old name until an agent changes it.

Old names (`project_renames`, migration 0023) keep external links working: webhooks at `<old name>.<apps host>/_hobwork/hooks/...` and routes at `/p/<old name>/...` reach the hob, a GET on the old app origin (`<old name>.<apps host>`) redirects (302) to the same path on the new one, where the app signs in again, and `GET /api/projects/<old name>` returns the hob so the web UI moves old links to the new name. Other API and MCP calls with the old name fail with `Hob "<old>" was renamed to "<new>"`, and git over HTTP says to change the remote URL. Branch preview origins and SSH users (`<hob>/<branch>`) use the new name only. A hob that takes the name, by creation, rename or restore, ends the old name's use; deleting the hob removes its old names.

## Agent access

Three ways in. All of them act on the same repos and workspaces.

1. **MCP** (primary; the only option for Claude Cowork and chat clients). See the tool list below.
2. **git smart HTTP**: `git clone https://hobwork/git/<hob>.git`, work locally with Claude Code, push a branch. A pre-receive hook rejects pushes to `main`. After pushing, the agent calls `merge` over MCP (or over SSH).
3. **SSH gateway**: `ssh <hob>/<branch>@hobwork` opens a shell in that branch's workspace VM. Also provides a `hobwork` CLI inside workspaces (`hobwork merge`, `hobwork logs -f`, `hobwork status`). See [SSH gateway](#ssh-gateway).

### MCP tools

Hobs: `list_hobs` (starred first in the user's order, with tags and each hob's storage use, filtered by an optional [search](#organizing-hobs)), `star_hob`, `tag_hob`, `create_hob` (from template), `get_hob` (entry points, current version, status, [storage use](#storage-use), the app URL, each branch's preview URL, and the hob's AI models, limits and spend; see [AI limits](#ai-limits)). `set_ai_model` sets the models of a hob, or the host-wide ones for connections with access to all hobs.

Workspaces and files: `create_branch`, `delete_branch`, `list_branches` (with each branch's app URL), `set_branch_home_assistant` (see [Hobwork to HA](#hobwork-to-ha-actions)), `read_file`, `write_file`, `edit_file`, `delete_file`, `list_files`, `search`, `bash` (runs in the branch workspace VM), `commit`, `diff`, `log`.

Delivery: `merge` (runs the pipeline, squash-merges and deploys on success, returns failures otherwise), `pipeline_status`, `list_versions`, `restore_version`.

Runtime: `invoke` (call a route or run a cron, webhook or trigger by hand, on `main` or with `branch` on a branch preview), `list_invocations`, `get_logs` and `tail_logs` (the deployed version's records; `branch` names a branch for its previews or `*` for all, and `get_logs` and `tail_logs` with `invocation_id` show that run on any branch), `rotate_webhook_token` (with `branch`, a URL for the branch preview). `rotate_upload_token` creates the token scripts use for an upload (see [Files](#files)).

Apps: `show_hob` shows the user a hob's app, on `main` or a branch preview, embedded in the chat (an MCP App), and returns a share link to it. See [Share links](#share-links).

Secrets: `list_secrets` (the library: names, hosts, headers, pending hosts and assignments, never values), `assign_secret`, `unassign_secret` and `request_secret_hosts` (asks the user to approve hosts and returns a link to the approval page). Only users create secrets and set values, and hosts change only when a user sets or approves them. See [Secrets and network](#secrets-and-network).

SSH keys: `add_ssh_key`, `list_ssh_keys` and `revoke_ssh_key`, for the calling agent's own keys. See [SSH gateway](#ssh-gateway).

Home Assistant: `ha_list_devices`, `ha_list_entities`, `ha_get_state`, `ha_list_services`, `ha_list_device_triggers` (ready-made trigger definitions for a device), `ha_get_automation` (an automation's or script's config, whether it is on and when it last ran), `ha_find_related` (the automations and scripts that use a device or entity, and the other way round), `ha_list_traces` and `ha_get_trace` (recent runs of an automation or script, step by step), `ha_history` (state changes from the recorder), `ha_logbook` (changes and events with what caused them), `ha_system_log` (HA's own warnings and errors), `ha_list_statistics` and `ha_statistics` (long-term statistics per 5 minutes, hour, day, week or month), and `ha_listen` (wait for a trigger to fire, so an agent can ask the user to press a button and see the resulting payload). Listings take filters and are paged, since real installs have thousands of entities. All of these are read-only and use HA's WebSocket API, some of it admin-only, so the HA token must belong to an administrator. Times from HA (seconds or milliseconds since the epoch) are returned as ISO 8601. Traces are looked up by the automation's `id` from its config, so automations without one have none.

Devices: `list_devices` (names, owners, capabilities, connection). Read-only; see [Devices](#devices-apple-apps).

The MCP server's instructions point agents to the hob's `AGENTS.md` and explain the core rules.

The endpoint is streamable HTTP at `/mcp`, stateless (a fresh server per request), authenticated with a bearer token: a static agent token or an OAuth access token (see MCP auth under [Users and authentication](#users-and-authentication)). `write_file`, `edit_file` and `delete_file` always run in the branch's workspace VM, which starts on demand, and reject paths and symlinks that lead outside `/workspace`. Reads (`read_file`, `list_files`, `search`) come from git or from the VM by this rule: `main`, read-only credentials and branches whose workspace has no uncommitted changes read committed files from the bare repo's objects (`server/src/committed-files.ts`), with no VM; a branch with uncommitted changes (or an unknown state, such as after a host restart, which one `git status` in the VM settles) reads the checkout in the VM. The host tracks "may have uncommitted changes" in memory: it is set by file changes and by any `bash` or SSH session, and cleared only when `commit`, `diff` or `changes` shows a clean checkout while no session is open. Read-only credentials therefore never see uncommitted work: `diff` with scope `uncommitted` is refused for them. Reads are limited to 4MB per file. Writes, `bash` and `commit` on `main` are refused. Without a workspace VM backend, committed files stay readable and changes fail with an error. `search` matches with a deadline (in the VM's exec timeout, or in a worker thread for committed files), so an agent-supplied regular expression cannot block the host. `bash` runs through the workspace VM's `exec` (see `ExecWorkspaceVm` in `server/src/workspaces.ts`) with a timeout, and long output is cut in the middle.

### SSH gateway

`server/src/ssh/`, on `HOBWORK_SSH_PORT` (default 2222, `off` disables it), built on the `ssh2` package (pure JavaScript; its optional native `cpu-features` build is not allowed in `pnpm-workspace.yaml`). The host key is an Ed25519 key generated on first start at `data/ssh_host_ed25519_key` (mode 0600).

- **Auth**: public keys only, each registered to an agent (`agent_ssh_keys`: name, key type, base64 key data, SHA-256 fingerprint, comment, where it was added and by whom, `revoked_at`). Every key has a name. Revoked keys keep their row, and a key can be added again once its earlier row is revoked. Users add and revoke keys with `POST /api/agents/<id>/ssh-keys` (`{ name, publicKey }`) and `POST /api/ssh-keys/<id>/revoke`; `GET /api/agents` lists them per agent with `addedFrom`. Agents manage their own keys over MCP: `add_ssh_key(name, public_key)`, `list_ssh_keys` and `revoke_ssh_key(id)`, only for their own agent. A key an agent adds records the agent token or OAuth grant it used, and revoking that token or grant revokes the key, so cutting off an agent's access also cuts off the SSH keys it gave itself, and such a key has that token's or grant's [access limits](#access-limits). Keys added by a user or on the host are not tied to a token or grant. Without the web UI: `pnpm --filter @hobwork/server add-ssh-key <agent-name> <key-name> [key.pub]` (creates the agent if needed, reads stdin without a file).
- **User name** is the target: `<hob>/<branch>`. OpenSSH accepts a slash in the user name (checked with OpenSSH 10.3). `<hob>+<branch>` works too, for clients or URLs where a slash is awkward. Hob names contain neither character and branch names cannot contain `+`, so the first `/` or `+` splits. The target is checked after authentication, so a bad target gets a message rather than a bare "Permission denied".
- **Sessions**: a shell (`exec bash --login`) or `ssh host '<command>'` runs in the branch's workspace VM with `/workspace` as the working directory, starting the VM like `bash` does. Gondolin supports stdin, a PTY and PTY resize on an exec, so interactive shells get a real terminal with the client's `TERM` and window size, and window changes follow. Without a PTY request (`ssh host cmd`, `ssh -T`) stdin, stdout and stderr stay separate and binary-safe. The exit status is passed back. A dropped connection kills the command (same `/proc` environ kill as `bash`). `main` is refused like `bash` on `main`. Port forwarding, agent forwarding, X11, SFTP and git over SSH are not supported.
- **Idle stop**: a session counts as a running command, so the VM is not stopped while it lasts, and `last_used_at` is updated when it starts and ends.

**`hobwork` CLI** (`packages/sdk/src/cli/main.ts`): `status` (branch head, uncommitted changes, `main`'s version and what is deployed, last pipeline run of the branch, the app URLs of the branch and `main`), `diff`, `commit "<message>"`, `merge "<summary>"`, `logs [-f] [-n N]`, `invocations [-n N]`, `sql "<statement>"` (see [Branch and test DBs](#branch-and-test-dbs)), `ha state|states` (see [Hobwork to HA](#hobwork-to-ha-actions)). A merge failure exits with status 1, usage errors with 2. The workspace has no git directory, so `hobwork commit` is how SSH users commit.

- **Delivery**: mounted read-only from the host at `/opt/hobwork/cli`, with a `/usr/local/bin/hobwork` wrapper written when the VM starts. Like the runtime runner, it speaks the host's internal API and so has to match the host version; baking it into the image would need a rebuild for every API change. It uses only Node built-ins.
- **Endpoint**: the workspace VM's internal handler (`server/src/workspace-api.ts`), bound to the VM's hob and branch, answers `/v1/workspace/*` at `hobwork.internal`. The CLI uses `node:http`, since `fetch` gives up waiting for response headers after 5 minutes and a merge can take longer. `logs -f` long-polls with a cursor (up to 30 seconds per request).
- **Identity**: the agent that runs the command. A workspace VM is shared by every agent working on the branch, so binding an agent to the VM would credit one agent with another's commit or merge. Every SSH session and every MCP `bash` call opens a workspace session: a random token, valid while the command runs. The `hobwork` CLI and the SDK's DB, Home Assistant and device clients (`packages/sdk/src/runner/internal-fetch.ts`) never see it. They call a root helper (`packages/sdk/src/cli/broker.ts`, run as `doas /usr/local/bin/hobwork-broker`), which finds the token of the command the caller belongs to and sends the request to the host with `x-hobwork-session`. The host accepts a token only for its own workspace, and only for the routes below, which refuse calls without one: `/v1/workspace/*`, `/v1/db`, `/v1/ha` and `/v1/devices` (checked in `server/src/guest-vm.ts`). Runtime VMs have no session and are not affected. The helper only forwards those paths, with `GET` or `POST`.
- **Guest privilege** (`server/src/guest-vm.ts`): everything the host runs in a workspace or pipeline VM as a command (`bash`, SSH sessions, `pnpm install` at start, file and git tools) goes through `/usr/local/bin/hobwork-run`, which drops to the `agent` user with `su-exec`. Only the setup at start (`GUEST_SETUP`) and the CLI install run as root. VM setup also sets `kernel.yama.ptrace_scope=1` and remounts `/proc` with `hidepid=2`, so the agent user cannot see or attach to root's processes or other users'. For a command with a session, `hobwork-run` writes the token to `/run/hobwork/sessions/<pid>` (root only, with the process's start time) and unsets `HOBWORK_SESSION` before it starts the command. The helper walks up the parents of its caller (doas starts it as the caller's child) until it finds such a file, so authority follows the process tree of a running command: a process that outlived its command or never belonged to one (a dependency's install script run by the VM's start, a leftover background process) has no session to use, and the token is in no environment or file the agent user can read. Yama stops processes from injecting code into others they did not start. What remains: code that runs inside a command (an install script during `pnpm install` in that command, a test) can run `hobwork commit` and `hobwork merge` like the agent can, and background processes of the agent user can change files a later command runs. The tools the host runs itself in the VM (`hobwork-tool`) run as the agent user too, so their git token (`HOBWORK_TOOL_SESSION`) is readable by it; the host accepts it only for pushes to the workspace's own branch. Runtime VMs, and the migration VMs of [Data](#data), go through the same `prepareGuest` and `hobwork-run`: the runner runs as the agent user (see Runner ingress under [Runtime](#runtime)), and so does every handler, since handlers run in its process.

### Rules for agents

Written into `AGENTS.md` in every hob and into the MCP server instructions:

- Handlers are like AWS Lambda functions. Nothing in memory survives between invocations. Store state with the SDK (hob DB).
- Every change needs tests. `merge` runs typecheck, lint, tests and build, and refuses on failure.
- Migrations are forward-only and additive (add tables and columns, do not drop or rename), so older versions keep working after a restore.
- Use `get_logs` and `list_invocations` to debug. Do not guess.
- There are no long-running processes. Anything that needs to persist goes in the hob DB.
- Prefer the platform dependency set. Add extra packages only when nothing in it does the job.

## Delivery pipeline

`merge` on a branch:

1. Start a fresh pipeline VM with the candidate: the branch rebased (or merged) onto current `main`.
2. Validate `hobwork.json`. When it has comments or trailing commas and `vite.config.ts` still reads it with `JSON.parse` (hobs created before JSONC), this step fails and shows the template's `vite.config.ts` as the replacement.
3. Install extra dependencies, if the hob has any. Platform packages are already in the image.
4. `typecheck`, `lint`, `test`, `build` (package.json scripts from the template). `build` bundles handlers and dashboards with Vite, then Hobwork renders the hob icon into the build (see [Hob icons](#hob-icons)).
5. Apply new migrations to a copy of the production DB, as a dry run (see [Data](#data)).
6. On success: squash-merge into `main` with the agent's summary as the commit message, apply migrations for real, deploy.
7. On failure: return the failing step with its output to the agent. No human is involved. The agent fixes and calls `merge` again.

There is no human approval step. Users see the result as a new version in the UI.

Pipeline runs are recorded (step, status, output, duration) and visible to agents through `pipeline_status`.

Details:

- `merge` takes only committed changes and refuses while the workspace has uncommitted ones.
- The candidate is built in a temporary host-side clone: the branch is squashed into one commit (author: the agent, committer: Hobwork, message: the agent's summary) and rebased onto `main`. Squashing first means only the branch's end result has to apply. On conflict, the conflicting files are returned and the agent redoes the change on a new branch from `main`.
- Merges and restores run one at a time per hob, so each candidate is tested against the `main` it lands on.
- The pipeline VM gets a clean checkout of the candidate with no git directory. `hobwork.json` and `package.json` are read on the host from git, never from the checkout. Extra dependencies are the `package.json` dependencies not in the platform set (see [Dependencies](#dependencies)).
- After a successful merge, the branch and its workspace checkout are reset to the new `main` (ignored files like `node_modules` stay), so the agent can keep working on the same branch. The workspace VM checks that the checkout is clean and at the merged commit, the host moves the branch, and the VM fetches and resets. If the branch or the checkout changed while the merge ran, or the checkout cannot be reset, the branch is left as it was.
- The pipeline VM backend is a seam (`StartPipelineVm` in `server/src/pipeline/runner.ts`), implemented on the `Sandbox` in `server/src/guest-vm.ts`. `server/src/pipeline/host-backend.ts` runs commands on the host without a sandbox and exists only for tests.

## Versions and rollback

- Every merge is one squash commit on `main` = one version. Version 1 is the template commit from hob creation.
- The UI lists versions with their summaries. "Restore this version" commits that version's tree as a new commit on `main`, records it as a new version and deploys it, without running the pipeline. History is never rewritten.
- Restoring code does not roll back data. Additive migrations keep this safe.
- **Auto-revert**: if a new version fails completely (runtime does not start, or every invocation fails for several minutes after deploy), Hobwork restores the previous version automatically and records why, so the agent can see it.

Auto-revert details (`server/src/runtime/auto-revert.ts`):

- Only versions deployed by a merge are watched. Restores, including the auto-revert's own, are not, so a broken old version cannot start a loop.
- "Does not start": the VM does not boot, or the runner exits or does not answer within 60s. The runner imports every handler before it reports ready, so a handler that throws at import time counts.
- "Every invocation fails": within 1 hour of the deploy, no invocation succeeded, at least 5 failed, and the first and the latest failure are at least 3 minutes apart. One success ends the watch. The time span keeps a short outage of something a handler calls from reverting a good version; the count keeps a single failed cron from doing it.
- The target is version N-1, since versions on `main` are linear. The restore goes through the normal restore path with Hobwork as the author and the reason as the summary (`Auto-revert to version 4: version 5 did not start`). An `auto-revert` event in the hob log says why. The merge that deployed the broken version reports the start failure and the pending revert in its result.

## Runtime

- Each deployed hob has 0 or 1 runtime VMs. There is no scaling beyond 1. Concurrent invocations run in the same VM.
- The VM starts on the first invocation (HTTP request, cron tick, trigger) and stops after an idle timeout. Default 1 hour, configurable per hob in `hobwork.json`. Cold start cost is the VM boot (0.5s on the Mac, 0.7s on `colossus`).
- **Lifetime**: `idleTimeout` is clamped to 2^31-1 ms (larger delays make `setTimeout` fire at once). A VM is also replaced 1 hour after it started (`DEFAULT_MAX_LIFETIME_MS` in `runtime.ts`), however busy it is, so code that got into it through one invocation does not see invocations hours later. The VM is retired like an old one after a deploy: it leaves service at once, its running invocations finish (up to the invocation timeout), and the next invocation starts a new VM. A VM is retired the same way after an invocation times out (the handler may still be running) or the runner crashes.
- **Runner ingress**: the host writes a random per-VM token to `/tmp/hobwork-runner-token` in the guest before starting the runner, which reads and deletes the file at startup, so it is not in the environment or on disk when handler code runs. The runner runs as the unprivileged `agent` user (through `hobwork-run`, see Guest privilege under [SSH gateway](#ssh-gateway)), so the host gives the file to that user (mode 600) right before the start; nothing else runs as that user until the runner has deleted it. The VM gets the same setup as the other VMs: `ptrace_scope=1` and `/proc` with `hidepid=2`, so handler code and the processes it starts see no root processes. Handlers can write to `/tmp` and their home directory (`/home/agent`), not to root-owned paths. The runner answers 401 to every request (`/ready` included) without `Authorization: Bearer <token>`. Handler code runs in the runner's own process, so this keeps out other processes in the VM and anything that reaches the ingress port, not code that already runs in the runner, which can read process memory.
- **Response size**: a handler's response body is limited to 24MB (`MAX_RESPONSE_BODY_BYTES`); a larger one fails the invocation. The host also stops reading a runner response over that size as base64 JSON plus 1MB.
- **Log attribution**: a runner's log lines attach to an invocation only when the invocation belongs to the same hob and the same branch (or main), so a preview's VM cannot write into main's invocations.
- Inside the VM a Hobwork **runner** (Node) loads the deployed build and serves invocations from the host over the Gondolin ingress.
- The host owns scheduling and trigger subscriptions. A cron tick, webhook call or trigger wakes the VM if it is asleep.
- Deploy: start the new VM, wait until it is ready, switch traffic, drain and stop the old one.
- Handlers call back to the host (DB, logs, Home Assistant, devices) through the SDK over an internal endpoint that only the hob's VMs can reach.

Implementation (`server/src/runtime/`):

- **What runs** is the newest version on `main`. The host reads its `hobwork.json` from git and keeps it in memory; after a host restart it reads it back from the versions table. On start the host registers the crons and HA triggers of every hob's current version, including version 1 of a new hob.
- **Build artifacts.** A build is the hob's `dist/` after `pnpm run build`, stored at `data/builds/<hob>/<tree>/`. The pipeline deletes its checkout after the run, so its build step copies `dist/` there first, after the pipeline VM has stopped so build code cannot change `dist/` during the copy. Builds are keyed by git tree, not commit: a restore commits an old tree as a new commit and finds that version's build already there, so a restore does not build again. A version with no stored build (the template commit of a new hob, or versions from before builds were kept) is built on deploy or first invocation in a fresh pipeline VM (install extras, `pnpm run build`, the icon, no tests). Only directories and regular files are copied, since the runtime VM mounts the build and a symlink written by hob code could point at host files: files are opened with `O_NOFOLLOW` and checked with `fstat`, and a symlink or any other entry makes the build fail with its path. Builds are limited to 256MB, counted as bytes copied.
- **Old builds** (`server/src/runtime/build-cleanup.ts`) are deleted after every deploy and by the daily housekeeping job. A hob keeps the builds of its newest 10 versions, of the versions its runtime VM runs or is starting, and any build less than an hour old (a pipeline stores its candidate's build before the merge records the version, and a restore may be building one). A restore of a version whose build was deleted builds it again, like a version from before builds were kept. The daily job also removes build directories of hobs that no longer exist.
- **Handler bundles.** The template's `vite.config.ts` only calls `hobworkViteConfig()` from `@hobwork/sdk/vite`, so build changes reach hobs with the guest image. It builds two Vite environments in one `vite build`: the dashboard (`index.html` at the hob root with its code in `ui/`, built to `dist/index.html` and `dist/assets/`) and the handlers. Every handler in `hobwork.json` becomes `dist/handlers/<path without extension>.js`, an ES module with all dependencies bundled in (Node built-ins stay external), so the runtime VM needs no `node_modules`.
- **Runner delivery.** The runner is `packages/sdk/src/runner/` and uses only Node built-ins. The host mounts that directory read-only at `/opt/hobwork/runner` and runs `node /opt/hobwork/runner/main.ts` as the agent user, with the build read-only at `/app`. The runner is host code, not SDK API: it speaks the host's invoke protocol, so it has to match the host version, and outside `node_modules` Node runs its TypeScript directly. Hob code depends only on the context type from the SDK in the image, so context changes must stay additive for builds tested against an older SDK to keep working.
- **Protocol** (`packages/sdk/src/runner/protocol.ts`). The host POSTs `/invoke` on the runner's ingress with the invocation (ID, kind, name, manual), the handler path, the serialized request (method, URL, headers, base64 body), route params and payload. The runner answers with the serialized response or the error (name, message, stack). `GET /ready` answers once every handler module loaded. Console output inside an invocation (tracked with `AsyncLocalStorage`) and `ctx.log` lines are batched to `POST http://hobwork.internal/v1/logs` and flushed before the invocation answers. Output outside any invocation goes to the runner's stdout, which the host records as runtime logs.
- **VMs** get 384MB and 0.5 vCPUs (one vCPU, capped at half a core with cgroup v2; a host without it gives one vCPU), the hob's `egress` plus the hosts of its secrets, the secrets as placeholders, and an internal handler bound to the hob. A blocked egress request is logged as an `egress-blocked` event. Secrets are fixed when a VM starts, so an invocation that finds them changed starts a new VM and retires the old one.
- **Deploy** (the delivery `Deploy` hook): ensure the build, apply the version's new migrations to the hob DB (a failure counts as "did not start" and triggers auto-revert), switch crons and HA triggers (`syncProjectTriggers`) to the new version, start the new VM and wait for `/ready`, switch, then retire the old VM: wait for its running invocations (up to the invocation timeout) and stop it. Without a runtime VM backend the bookkeeping still happens and invocations fail with an explanation.
- **Invocations** time out after 5 minutes on the host. Gondolin cannot signal the handler, so it may keep running until the VM stops. A runner that exits is logged as a `crash`, and the next invocation starts a new VM.
- **Routes** answer on two addresses. On the Hobwork host, `/p/<hob>/api/*` takes only an agent token (`Authorization: Bearer`) within its [access limits](#access-limits); the check is a `RouteAuthorizer` function in `server/src/runtime/http.ts`. Session cookies are not accepted there, since no page on the Hobwork origin calls hob routes. On the hob's app origin, `/api/*` takes only that origin's app session (see [Hob app origins](#hob-app-origins)). `authorization`, `cookie` and `proxy-authorization` headers are never passed to the handler. Request bodies are limited to 10MB. Handler responses on the Hobwork host (routes and webhooks) get `Content-Security-Policy: sandbox; default-src 'none'` and `X-Content-Type-Options: nosniff`, and lose `Set-Cookie`, so a handler that reflects input into HTML cannot run script with the Hobwork session.
- **Crons and HA triggers** of a branch never run on their own: the scheduler and HA subscriptions only use the deployed version. A branch's crons and triggers run through `invoke` with `branch`.
- **Webhooks** at `<hob app origin>/_hobwork/hooks/<name>/<token>` (`server/src/apps/http.ts`) accept any method. They are served from the hob's own origin, not the Hobwork origin, so a bug in a webhook handler is on the same origin as that hob's other code and never on the origin that holds the user's session. The URL needs no app session: the token is the only credential, the app session cookie is not read, and `cookie` never reaches the handler. The cross-app rule of `crossAppRequests` does not apply to it, for the same reason. The response is sandboxed exactly like a route response on the Hobwork origin (`Content-Security-Policy: sandbox; default-src 'none'`, `nosniff`, no `Set-Cookie`), not with the hob UI's policy, so its output cannot act as the app even though it is on the app's origin (`/_hobwork/` is never a valid `returnTo` for the sign-in handoff, and the sandbox gives the page an opaque origin that cannot use the app session cookie). The old URL `<Hobwork origin>/hooks/<hob>/<name>/<token>` is no longer served: it answers 410 with the new URL shape (no hob-specific details) and logs one warning per hob and webhook. Tokens are unchanged, so a caller only has to change the host and path. There is no redirect: most webhook senders do not follow redirects for POST. Tokens are 256 random bits, stored as SHA-256 hashes in `webhook_tokens`, and created or replaced with `rotate_webhook_token`, which shows the URL once. A webhook without a token cannot be called. Unknown hob, webhook and token all answer 404. The handler sees the URL without the token.
- **Crons** use standard 5-field syntax, parsed by `server/src/runtime/cron.ts` rather than a dependency: numbers, ranges, lists, steps, month and weekday names, and Vixie cron's rule that a day matches either day field when both are restricted. Times are in the host's local time zone unless the cron has a `timeZone`; zoned times are computed with `Intl` (`packages/sdk/src/time.ts`, shared with handlers). Per-person crons keep one timer per person and are rescheduled when people or their zones change (a `people` change). The pipeline refuses zone names the host's `Intl` does not know. A time skipped by a DST change does not run, a time that happens twice runs once, and ticks missed while the host is down are not caught up.
- **HA triggers** fire through the trigger registry's `invoke` hook as invocations of kind `trigger` with HA's trigger variables as `payload`. Refused or failing triggers are logged as `trigger` events in the affected hobs' logs. HA connection losses that drop trigger events are logged there too, at `info`: HA at home restarts and drops connections now and then, so these are not problems. A trigger synced while HA is not connected, as on every host start, gets an `info` line, and a `warn` line only if HA is still not connected a minute later, so host restarts do not show up as problems.

### Branch previews

A branch can be tried out before it is merged: its UI at its own app origin, its routes, and its crons, webhooks and triggers by hand. `server/src/runtime/runtime.ts` runs a preview like a deployed version, keyed by hob and branch.

- **What runs**: the branch's latest commit in the bare repo, so only committed changes. Rejected: running the workspace checkout, which would show half-written files and need a build per request. Each request reads the branch head; a new commit makes the next request start a new VM and retire the old one, like a deploy. Previews have version `null`.
- **Build**: on first use, from that commit in a fresh pipeline VM (`createBuilder`, the same as for a version without a stored build). Builds are keyed by tree, so a branch that is merged unchanged reuses its build.
- **VM**: a separate runtime VM per branch with the same runner, resources (384MB, 0.5 vCPUs where the host can cap one), egress and secrets as the deployed version, labelled `preview <hob>/<branch>`. It stops after the branch's `idleTimeout`, at most 15 minutes. Rejected: a runner inside the workspace VM, which lives as long as agents run commands and has the registry in its egress allowlist.
- **Data**: the branch DB copy from [Branch and test DBs](#branch-and-test-dbs), with the preview commit's migrations applied the same way as for workspace queries. A workspace VM start copies production again, so preview data does not survive it.
- **Records**: invocations and log lines carry the branch (`invocations.branch`, `logs.branch`; `NULL` for the deployed version). Auto-revert never watches previews.
- **Cleanup**: deleting a hob stops its preview VMs and closes their branch DBs. Build cleanup keeps the builds that preview VMs run or are starting with; a preview's build is never one of the kept versions, so it goes with the next cleanup after its VM stops (a preview VM stopping runs one).
- **App origin**: `<branch label>--<hob>.<apps host>`, with its own app session (a session for main or another branch is rejected), through the same sign-in handoff as main with `branch` in `/auth/app`.
- **Branch labels** (`server/src/apps/origins.ts`): a whole host label is at most 63 characters of `a-z`, `0-9` and `-`. A branch that is already a lowercase label of at least three characters, with single hyphens, keeps its name (`add-spools--filament`). Any other branch (uppercase, `/`, `.`, `_`, two characters or fewer, which would put `--` at positions 3 and 4 like `xn--`, or too long) becomes a slug of its name plus the first 6 hex digits of its SHA-256 (`feature/Spools` becomes `feature-spools-3f9a1c`), so labels never collide. Labels never contain `--`, and hob names cannot, so the last `--` splits the label. Hob names are at most 40 characters, which leaves at least 21 for the branch. The host resolves a label by computing the labels of the hob's branches (cached for 5 seconds).
- **Webhooks**: `<branch label>--<hob>.<apps host>/_hobwork/hooks/<name>/<token>`, with tokens per branch (`branch_webhook_tokens`), created with `rotate_webhook_token` and `branch`. Main's tokens do not work on a branch origin and the other way round. Resolving the branch label runs git (cached for a few seconds), as for every request to a preview origin.
- **Home Assistant**: see [Hobwork to HA](#hobwork-to-ha-actions).
- **Web UI**: the hob page lists branches with their last commit, recent runs, a Preview page with the app in an iframe, and the Home Assistant switch. Activity has a filter for the live version and each branch, and the activity across hobs names the branch of preview runs and events. `GET /api/projects/<name>/branches` returns this; `GET /api/projects/<name>/invocations?branch=<name>` filters (`main` for the live version).

### Internal endpoint

The SDK talks to the host at `http://hobwork.internal/` (HTTPS works too, through Gondolin's TLS interception). The hostname does not exist anywhere. Every sandbox is created with its own `internal` handler, and Gondolin's egress `onRequest` hook answers requests for `hobwork.internal` with that handler's `Response` before any DNS lookup, allowlist check or upstream connection.

- The handler is bound to the VM when it is created, so the host knows which hob, version and workspace a call comes from without a token in the guest.
- Nothing else on the host is reachable. Host services on `127.0.0.1`, `10.0.2.2` and internal ranges are blocked by the egress policy, and no TCP port is forwarded.
- Secrets are substituted after `onRequest`, and none is bound to `hobwork.internal`, so the handler only ever sees placeholders.

Rejected: an allowed internal host (a real host port through `allowedInternalHosts`) would need auth tokens in the guest and exposes a real socket.

### Invocations and logs

Every invocation is recorded: ID, hob, version, kind (route, webhook, cron, trigger), whether it was started by hand, start, duration, result, error with stack trace. Console output from handlers is captured per invocation. Pipeline output and runtime lifecycle events (start, stop, crash, auto-revert) go to the same log store.

Output from guests is bounded on the host. The runtime's stdout and stderr are split into lines of at most 8192 characters (`server/src/runtime/line-splitter.ts`; the rest of a longer line is dropped, so a guest that never writes a newline cannot grow host memory). Each VM may log 100 lines in a burst and 10 per second on average while no invocation is running (`log-limiter.ts`); excess lines are dropped and the next line that gets through is preceded by a `N log lines dropped` warning. Inside an invocation the per-invocation line limit applies. Command output (`bash`, pipeline steps, builds) is collected as its first and last 14,900 characters with a marker of how much was cut (`HeadTailOutput` in `server/src/mcp/output.ts`), while it streams, so it never sits in host memory in full.

Agents read this through MCP (`list_invocations`, `get_logs`, `tail_logs`) and the `hobwork logs` CLI over SSH. Branch previews are kept out unless asked for: logs, runs and problems in the API, MCP and CLI show the deployed version (`branch IS NULL`) by default, a branch name (`-b` in the CLI) shows its previews and `*` shows all, and the web UI pages have a version picker for it. Preview runs fail often while an agent works on a branch, so they would drown out problems of the deployed version. The nav's problem count only counts the deployed version. Users see it on a hob's Activity (invocations, filtered by kind, status and time, and each one with its error, stack trace and lines) and Log (all lines, only lifecycle events, or warnings and errors) pages. The top-level Activity page lists runs of every hob with the same filters plus a hob filter (`GET /api/activity`), and a Problems view (`GET /api/activity/problems`) that merges failed runs with lifecycle events at warn or error level: blocked requests, rollbacks, crashes, DB warnings, refused triggers and failed deploys, paged by time. The nav shows how many problems happened since the browser last showed that view (`GET /api/activity/attention?since=`, the time kept in `localStorage`, at most a week back). A partial index on `logs (time) WHERE event IS NOT NULL` keeps these queries off the full log. The Log page follows new lines over [live updates](#live-updates): on a `logs` change for its hob it asks for `GET /api/projects/<name>/logs?after=<cursor>`, again while a whole page (200 lines) comes back, and once more after reconnecting. Rejected: a long poll per open Log page, which held a request open per page next to the socket that already says when lines arrive.

Storage (`server/migrations/0004_runtime.sql`, `server/src/runtime/logs.ts`):

- `invocations`: kind (`route`, `webhook`, `cron`, `trigger`), name (route key or entry name), `manual`, status (`running`, `ok`, `error`), HTTP status for routes and webhooks, error and stack. Invocations still running at host start are marked failed.
- `logs`: one row per line with source (`handler`, `runtime`, `pipeline`), level, an optional invocation, and for lifecycle lines an event kind (`start`, `stop`, `crash`, `deploy`, `auto-revert`, `egress-blocked`, `trigger`, `pipeline`, `migration`, `db`, `secret`, `ai-limit`). Pipeline runs stream each step's output into the log store line by line (`server/src/pipeline/output-log.ts`, prefixed `run <id> <step>:`), plus one summary line per step. A run stores at most 5,000 lines and a burst limiter applies; when the cap is hit a marker line says so. `pipeline_status` has each step's output as its first and last 14,900 characters. Log line IDs are the cursor for `get_logs` and `tail_logs`.
- Bounds: messages are cut to 8,000 characters in the middle, an invocation keeps at most 1,000 lines (then one line saying the rest was dropped), and rows older than 30 days or beyond the newest 200,000 lines per hob are pruned hourly. MCP output is cut at whole lines with a cursor to continue, and `tail_logs` waits at most 60 seconds.

## Data

- **Host DB**: SQLite for Hobwork's own state (users, agents, tokens, hobs, versions, invocations, logs, pipeline runs, secrets, AI settings and requests).
- **Hob DBs**: one SQLite file per hob at `data/projects/<hob>/db.sqlite`, owned by the host. Hob code reaches it through the SDK, which sends queries to the host. VMs do not open DB files directly, because SQLite locking and WAL shared memory do not work reliably through the guest filesystem bridge across VMs.
- All SQLite databases use WAL, `busy_timeout`, `synchronous = NORMAL`, `foreign_keys = ON` and `STRICT` tables. Hob DB connections also turn on SQLite's defensive mode.

### Query API

Handlers get `ctx.db` (`packages/sdk/src/index.ts`): `query(sql, params)` (rows), `get` (first row), `run` (`changes`, `lastInsertRowid`) and `batch(statements)`. Parameters are an array for `?` or an object for named placeholders. Values are null, numbers, strings, bigints, booleans (stored as 1 and 0) and `Uint8Array`. Blobs and bigints travel as `{ $blob }` and `{ $bigint }` in JSON.

- **Transport**: the runner POSTs `{ statements, transaction, invocation }` to `http://hobwork.internal/v1/db` (`DbRequest` in `packages/sdk/src/runner/protocol.ts`). The answer is the rows and change counts, or the SQLite error with the index of the failing statement (`DbError` in the handler).
- **Transactions**: there are no interactive transactions. A transaction held open across HTTP round trips would hold the hob's write lock while handler code runs, and a handler that crashes or times out would leave it open. `batch` sends all its statements in one request, and the host runs them in one `BEGIN IMMEDIATE` transaction that rolls back on the first error. Read-then-write logic uses single statements (`UPDATE ... WHERE`, `INSERT ... ON CONFLICT`, `RETURNING`) or a batch.
- **Rules** (`packages/sdk/src/db/execute.ts`, enforced with SQLite's authorizer and a small lexer): one statement per SQL string (node:sqlite would silently ignore the rest); no schema changes, which belong in migrations so the dry run sees them; no `BEGIN` or `SAVEPOINT`; no `ATTACH`, `VACUUM` or `load_extension`, which could read or write files on the host; only introspection PRAGMAs (`table_info` and similar) and `data_version`, which FTS5 runs internally; no writes to `hobwork_migrations`. Results are limited to 10,000 rows.
- **Execution**: each open hob DB has a worker thread with one connection (`server/src/data/db-pool.ts`), so a slow query blocks that hob's queries and not the host. A query that runs longer than 30s is abandoned: SQLite cannot be interrupted from Node, so the worker is terminated and the next query opens a new connection. Workers close after 5 idle minutes. A worker sets `PRAGMA trusted_schema = OFF`, so triggers and views in a DB that a migration produced cannot call unsafe functions. node:sqlite has no `setLimit`, so `SQLITE_LIMIT_ATTACHED` is not available; the authorizer above is what keeps `ATTACH` out of queries.
- **Isolation**: the internal handler is bound to the VM when it is created, so a runtime VM reaches only its hob's DB and a workspace VM only its branch DB.
- **Vector search** (`packages/sdk/src/db/vector-functions.ts`): the executor registers `vec_distance_cosine(a, b)` (1 minus the cosine similarity, `NULL` for a zero vector), `vec_distance_l2(a, b)` and `vec_dot(a, b)` with node:sqlite's `db.function()`. Vectors are BLOBs of little-endian float32 values, which `vector.encode(numbers)` and `vector.decode(bytes)` from `@hobwork/sdk` write and read. `NULL` in gives `NULL`; vectors of different lengths or BLOBs that are not whole float32 values are an error. Queries compare every row (brute force), which is fast enough for hob-sized tables; there is no native extension and no index. Because the executor registers them, handler queries on the production DB, branch DBs (copies opened by the same worker) and `createTestDb()` all have them. Migrations (in the VM and in the host fallback) do not: the functions are `directOnly`, so views, triggers, `CHECK` constraints and index expressions cannot use them, and a DB file never depends on Hobwork's functions to open. A view that calls one fails the dry run with "no such function". Rejected: sqlite-vec, a native extension the host would have to ship per platform and that `load_extension` rules keep out. Usage with `embed()`:

  ```ts
  const ai = openrouter(ctx)
  const { embeddings: [query], model } = await ai.embed(text)
  const similar = await ctx.db.query(
    'SELECT id, name, vec_distance_cosine(embedding, ?) AS distance FROM notes WHERE embedding_model = ? ORDER BY distance LIMIT 10',
    [vector.encode(query!), model],
  )
  ```

### Migrations

- `migrations/NNNN_name.sql` in the repo, applied in version order, each in its own transaction, and recorded with a SHA-256 checksum in `hobwork_migrations` in the hob DB. Forward-only: there are no down migrations. The host reads the files from git, never from a checkout, and refuses symlinks, so a migration cannot make the host read other files.
- **Migrations run in a VM, never on the host.** Migration SQL is written by agents. On the host it could `ATTACH` other DBs, or end its own transaction with `COMMIT` and then `VACUUM INTO` any path, so it runs in a short-lived VM (`server/src/data/migration-vm.ts`, runner `packages/sdk/src/db/migrate-main.ts`) with no network. The host snapshots the DB into a fresh directory (`VACUUM INTO` from the DB's worker), mounts the directory at `/migrate` with `input.json` (the migration files), and the runner applies the migrations to `db.sqlite` there, with `journal_mode = DELETE` so one file comes back. The VM is stopped before the host reads anything. The host takes back only `db.sqlite` (`server/src/data/db-file.ts`): opened with `O_NOFOLLOW` and `O_NONBLOCK`, a regular file, at most twice the snapshot's size (at least 512 MB), copied byte by byte into a new file it owns, which must start with the SQLite header and pass `PRAGMA integrity_check`. The mount has a quota (`Mount.maxBytes`, enforced by `mountQuota` in `server/src/sandbox/quota.ts` through Gondolin's VFS hooks) of twice that limit plus the input, counted in logical file sizes with at least 4 KB per entry: a write past it fails inside the VM with ENOSPC before it reaches the host disk, so a migration cannot fill the host's disk. The VM reserves from the VM budget as a pipeline VM of the hob. Anything else in the directory, and the runner's own answer beyond "ok" or an error text, is ignored. A DB that fails a check never replaces the real one. Costs about a second of VM boot per run.
  A migration that fails leaves the DB as it was, since the copy is thrown away (before, earlier migrations of the same run stayed applied). Without a guest image the host applies them itself as a fallback, with an authorizer that denies `ATTACH`, `DETACH` and `load_extension` and a check that refuses `VACUUM` statements; it is not the path a normal host takes.
- **Deploy** applies the new migrations of the deployed version before it starts. It reads which versions the production DB has applied, and starts no VM when nothing is pending. Otherwise queries to the hob DB wait while the migration runs (the snapshot, the VM, the checks and the swap, a few seconds), so no write lands between the snapshot and the swap. Then the DB's worker is closed (which checkpoints the WAL), the WAL files are removed and the new file is renamed over `db.sqlite`. A restore of an older version has fewer migrations, and nothing is undone.
- **Dry run** (the pipeline's `migrations` step, `server/src/data/project-data.ts`): all migrations are applied to an empty in-memory DB (what tests and new hobs start from), then the new ones to a copy of the production DB. Both run in one VM, and the checks below read the DB that comes back, not what the VM reports. The production DB's worker writes the copy with `VACUUM INTO`, a consistent snapshot while handlers keep writing. node:sqlite's `backup()` was tried first and took seconds per copy under Vitest. The step fails with the SQL error, and also when:
  - an applied migration's file changed,
  - a new migration creates a table without `STRICT` (tables from earlier migrations are not checked again),
  - a table, view or column that existed before is gone afterwards.
- **Additive check**: comparing the schema before and after (tables and views with their columns, from `pragma_table_list` and `pragma_table_xinfo`) catches `DROP TABLE`, `DROP COLUMN` and both kinds of `RENAME` in any spelling. It still allows SQLite's usual way to change constraints: create a new table, copy the rows, drop the old table and rename the new one to the old name with the same columns. Rejected: matching `DROP` and `RENAME` in the SQL text, which cannot tell that rebuild apart from a real drop. Dropping indexes and triggers is allowed, since older versions still run without them.

### Branch and test DBs

- **Workspaces**: when a workspace VM starts, the host copies the production DB to `data/workspaces/<hob>/<branch>/db.sqlite` (an empty DB if the hob has none yet). Before each query from the VM, the branch's own `migrations/` (read inside the workspace VM with `hobwork-tool files`, so uncommitted ones count; only regular files named like `0001_name.sql`, up to 1MB each and 8MB in total, and the host checks the answer; the VM runs that command while the calling command is still running) that the copy has not seen are applied in a migration VM like a deploy, on a copy of the branch DB that replaces it (no gate is needed, since queries to one branch DB run one at a time). The host remembers the migrations (names and checksums of what the VM returned) each branch DB was brought up to, so only a change to `migrations/` starts a VM. The branch DB is in the workspace directory but outside the `files` directory the workspace VM mounts, so the VM cannot write it. If an applied one was edited, which is normal while developing, the branch DB starts over from a fresh production copy. The workspace VM reaches the branch DB at `hobwork.internal/v1/db`, and `hobwork sql "<statement>"` runs a statement on it.
- **Tests**: `@hobwork/sdk/testing` has `createTestDb()`, a fresh in-memory `node:sqlite` DB inside the VM with every migration from `migrations/` applied and the same executor and rules as the host, and `createTestContext()`, a handler context with one. Each call gives an empty DB, so tests are independent, and nothing crosses the VM boundary, so tests work the same in workspace and pipeline VMs. Rejected: an internal handler with a host-side empty DB for pipeline VMs, which would make tests share one DB and depend on the host.

### Files

Hobs store files with `ctx.files` (`Files` in `packages/sdk/src/index.ts`), for what does not fit a DB row, like uploaded photos, and `static` in `hobwork.json` serves directories of them on the hob's app origin without starting the VM.

- **API**: `put(path, body)` (a string, `Uint8Array`, `ArrayBuffer`, `Blob` or `ReadableStream`; creates or replaces), `get(path)` (`{ path, size, modified, body, bytes(), text() }` or `undefined`), `stat(path)`, `delete(path)` (true when there was a file) and `list({ prefix, after, limit })` (path order, at most 1000 per call, `after` pages). Errors throw `FilesError` with `code` `invalid_path`, `not_found`, `too_large`, `conflict` or `unavailable`.
- **Paths**: segments of `A-Z a-z 0-9 . _ -`, none starting with `.`, separated by `/`; at most 255 characters per segment, 16 segments and 512 characters (`filePathProblem` in `packages/sdk/src/runner/protocol.ts`, checked by the SDK and the host). So there are no `.` or `..` segments, dotfiles, backslashes or characters that need escaping. A path is a file or a directory, never both: storing `a/b` while `a` is a file fails with `conflict`, and so does the other way round. Directories exist only while they hold files; deleting the last file in one removes it.
- **Storage** (`server/src/runtime/files.ts`): `data/projects/<hob>/files/`, next to the hob DB, so deleting, restoring and renaming the hob move the files with it. Uploads are written to `data/projects/<hob>/files.tmp/` and renamed into place, so a reader never sees half a file and gets either the old or the new one. Files are at most 1 GB. There is no quota; [Storage use](#storage-use) shows the size.
- **Transport**: `PUT` and `GET http://hobwork.internal/v1/files/<path>` with the bytes, and `POST /v1/files` with `{ action: 'stat' | 'delete' | 'list', ... }`. Runtime VMs opt uploads into Gondolin's streamed request bodies (`streamsFileBody`), and answers stream back, so files skip the 5 MB limit of the other internal calls and are never held in memory. The host stops reading an upload once it passes 1 GB. A download is read from a file handle opened before the headers go out, so a file replaced meanwhile is not mixed in.
- **Uploads** (`server/src/runtime/uploads.ts`, `server/src/apps/http.ts`, `packages/sdk/src/uploads.ts`): route bodies are buffered and capped at 10 MB, so large files (photos, 3MF models) skip handlers. `uploads` in `hobwork.json` names folders the app and scripts may store files in: `{ "inbox": { "prefix": "inbox/", "maxBytes": 209715200, "types": ["image/*", ".3mf"] } }` (`maxBytes` defaults to 100 MB, at most 1 GB; `types` are MIME patterns matched against the declared Content-Type or extensions matched against the path, and filter what a person picks rather than protect anything, since `static` decides how files are served). A path belongs to the upload with the longest prefix it starts with. The host writes uploads into `files.tmp/` and renames them into place like `ctx.files.put`, so they replace a file at the same path. Endpoints, on the hob's app origin:
  - `POST /_hobwork/uploads` with `{ path, size, type? }` checks the path, size and type and answers `{ id, path, size, received, chunkBytes }` (8 MB parts); `PUT /_hobwork/uploads/<id>?offset=<received>` appends a part (409 with the current offset when it does not start there, one part at a time per upload); `GET` answers the status, `DELETE` gives up. The answer to the last part is `201 { done: true, file }`. State is in `chunked_uploads` (migration 0043) with the bytes in `files.tmp/upload-<id>`, so an upload survives a host restart and a dropped connection; housekeeping drops ones not continued for 24 hours. Rejected: one streamed request from the browser, which `fetch` cannot report progress for and which reverse proxies with body limits (Cloudflare's 100 MB) refuse.
  - `PUT /_hobwork/files/<path>` with the whole file, for scripts (`curl -T`).
  - **From the share sheet**: the app's share extension uploads with its device token through `/api/devices/uploads` (see [Share targets](#share-targets)), into the upload a share target names, as the device's owner.
  - **Who**: a signed-in person's app session, with the CSRF header, the same-origin and cross-app checks as routes (share links cannot upload), or `Authorization: Bearer hwu_...`, an upload token. Tokens are per hob and upload, like webhook tokens (only a SHA-256 hash in `upload_tokens`, rotating replaces the old one, kept through delete and restore), created by people on the hob's page (`POST /api/projects/<hob>/uploads/<name>/token`) and by agents with `rotate_upload_token`. A token reaches only its own upload, never another upload's folder, and only the deployed version; branch previews take uploads from the app only. A person can continue only their own chunked uploads, a token only uploads started with a token of the same upload.
  - **Triggers**: `{ "upload": "<name>", "handler": ... }` in `triggers` runs once a file is in, on the version (or branch preview) that took it, with `ctx.payload` an `UploadEvent` (`upload`, `path`, `size`, `modified`, `contentType`) and `ctx.caller` the uploader, or null for a token. Triggers start after the answer is decided and do not hold it up; a failing trigger shows in the hob's log, and the file stays.
  - **SDK**: `files.upload(path, blob, { onProgress, signal, type })` in `@hobwork/sdk/browser` starts the upload, sends the parts, reports progress after each part and, when a part fails to send or its answer is lost, asks for the status and goes on from there (3 retries). It throws `RouteError` with the host's message.
- **Branches**: previews use the same files as the deployed version, not a copy like the DB, so a preview can change and delete production files. Tests get empty in-memory files from `createTestFiles()` (and `createTestContext()`) in `@hobwork/sdk/testing`, with the same rules. Workspaces have no access to the files.
- **Static serving** (`serveStaticFile`): `"static": { "/photos": { "dir": "photos" }, "/shared": { "dir": "out", "public": true } }` serves the file `photos/2026/cat.jpg` at `/photos/2026/cat.jpg`. Keys are URL paths of the same segments as file paths, not under `/api`, `/_hobwork` or `/theme`; the longest matching prefix wins, and a mount wins over the UI's files (no `index.html` fallback below it). Only `GET` and `HEAD`; missing files and paths that are not valid file paths answer 404, and links are not followed. Without `public` a mount needs the app session or a share link and passes the cross-app check, like the UI; with `public: true` anyone with the URL can fetch it, from any site, so it is checked before both. The mounts come from the `hobwork.json` the origin serves (deployed version, or the branch for a preview); a config that cannot be read serves none. Responses have an ETag (size and modification time) with `no-cache` (`public` or `private`), byte ranges (`Range`, `If-Range`, for video and audio seeking; the UI's files get them too) and `nosniff`.
- **Content types**: the files come from users and handlers, so only types that cannot run script on the app origin are shown in the browser: images (AVIF, GIF, ICO, JPEG, PNG, SVG, WebP), audio (AAC, FLAC, M4A, MP3, Ogg, Opus, WAV), video (MP4, M4V, MOV, Ogg, WebM), PDF, CSV, JSON, Markdown, plain text, WebVTT and fonts. Everything else, HTML, JavaScript, CSS and XML included, is `application/octet-stream` with `Content-Disposition: attachment`, and `nosniff` keeps a page from loading it as a script or stylesheet. An SVG opened on its own is a document that can run script, so it gets `Content-Security-Policy: sandbox; default-src 'none'; ...`. Other types get no policy, since a sandbox would block the browser's PDF viewer. Rejected: a separate origin for files, which would need its own sign-in and a CSP source in every hob UI that shows them.
- **Backups**: see [Backups](#backups).

### Warnings

- Statements slower than 500ms on a production DB are logged as `db` events (with the invocation, when the runner sent one), at most once per statement text every 10 minutes, and counted.
- DB size (file plus WAL) is checked at most once a minute after queries, and after migrations. Every time it crosses another 100 MB, a `db` warning is logged.
- `get_hob` shows `database`: size, a size warning once over 100 MB, and the slow query count, slowest time and last slow statement since the host started.

### Storage use

The hobs list in the web UI shows how much disk each hob uses, with the hob DB broken out since it is the part that grows (a tooltip has every part). `GET /api/projects`, `GET /api/projects/<name>` and the `list_hobs` and `get_hob` MCP tools return it as `storage`, in bytes (`server/src/storage.ts`):

- `database`: `data/projects/<hob>/` (the DB file, WAL and shared memory), without the files.
- `files`: the hob's [files](#files), `data/projects/<hob>/files/` and uploads in progress in `files.tmp/`.
- `branchDatabases`: the `db.sqlite*` files in each `data/workspaces/<hob>/<branch>/`. `workspaces`: everything else there (checkouts and their git directories).
- `repo`: `data/repos/<hob>.git`. `builds`: `data/builds/<hob>/`.
- `logs`: the text of the hob's log lines and invocation errors and stacks in the host DB (`octet_length`), which shares one file with every other hob. Row and index overhead is left out.
- `total`: the sum. Sizes are apparent file sizes, and symlinks are not followed.

Walking a hob's directories is too slow for every request, so the host keeps the last measurement in memory, keyed by hob ID so a renamed hob keeps it until the next one. A rename measures the hob again under its new name, and a deletion drops its entry. Requests answer from it, and a hob with no measurement or one older than 5 minutes is measured again in the background, one hob at a time. `storage` is `null` until the first measurement. The host measures every hob when it starts. Rejected: storing sizes in the host DB, which needs a migration for numbers that are cheap to measure again after a restart.

## Backups

The host backs itself up to an S3-compatible bucket (AWS S3, Backblaze B2, Cloudflare R2, Hetzner Object Storage, MinIO) with [Kopia](https://kopia.io), daily at 03:30 local time by default (`server/src/backup/`).

- **What**: the host DB, every hob DB, every hob's [files](#files), every hob repo, `secret.key` and the SSH host key. Left out: builds (rebuilt on demand), workspaces (branches are in the repos; uncommitted workspace files are lost) and the Home Assistant and Pocket ID dev data.
- **Consistency while the host runs**: each run writes a copy into `data/backup-staging/`, laid out like a data dir. DBs are copied with `VACUUM INTO` from a worker thread, as for the migration dry run. Repos are copied with `git clone --mirror --no-local`, which goes through git's pack protocol and gets a consistent set of refs and objects while pushes and merges go on. Hob files are hard-linked into the staging dir (copied across file systems): they are only ever replaced by a rename, never changed in place, so a link keeps the version it was made from and takes no space. Rejected: copying under the per-hob merge lock, which does not cover pushes over HTTP and SSH. The hob list comes from the copied host DB, so a hob created during the run is left out whole. Kopia then snapshots the staging dir, which is deleted afterwards.
- **Incremental**: Kopia splits files into content-defined chunks (4 MB on average) and uploads only chunks the repository does not have yet, so an unchanged DB or repo costs nothing and a changed DB costs the chunks around the change. Compression is zstd.
- **Secret key**: included, since the encrypted values in the host DB are useless without it. The Kopia repository is encrypted with its own password (`HOBWORK_BACKUP_PASSWORD`), which must be kept outside Hobwork, e.g. in a password manager: without it nothing can be restored, and anyone with it and the bucket credentials can read every secret. With `HOBWORK_SECRET_KEY` there is no key file, so that key must be kept the same way.
- **Kopia**: the host runs the `kopia` binary (`HOBWORK_KOPIA_BIN`, default `kopia` on `PATH`). Tested with 0.17.0, the version on `colossus` (`/usr/bin/kopia`, AUR `kopia-bin`); it uses no flags or JSON fields newer than that. Credentials and the password reach it through its environment (`KOPIA_PASSWORD`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`), never through arguments or logs. Its config, cache and logs are in `data/kopia/`. The first run connects to the repository, or creates it when the bucket prefix is empty, with `--no-persist-credentials` and the fixed identity `hobwork@hobwork`, so a host restored on another machine continues the same history. Kopia runs its own maintenance after snapshots.
- **Retention**: Kopia's global policy keeps 14 daily, 8 weekly and 12 monthly snapshots (`HOBWORK_BACKUP_KEEP_DAILY|WEEKLY|MONTHLY`), no hourly ones, and Kopia's defaults of the latest 10 and 3 annual ones. The policy is set again when the numbers change.
- **Runs**: the host's cron scheduler starts them (`HOBWORK_BACKUP_SCHEDULE`, a cron expression, `off` for manual backups only). A lock file (`data/backup.lock`) keeps the host and the CLI from running two at once. Each run is a row in `backup_runs` with its start, duration, snapshot ID, size, file count, uploaded bytes (how much the repository's blobs grew, since Kopia 0.17 does not report uploads) and error. Failures are logged as `BACKUP FAILED: ...`. Runs left as running by a stopped host are marked failed on start. Settings in the web UI shows the last backup, the next one, recent runs and a "Back up now" button (`GET|POST /api/backups`, users only).
- **Config**: backups are on when `HOBWORK_BACKUP_S3_BUCKET` is set, together with `HOBWORK_BACKUP_S3_ACCESS_KEY_ID`, `HOBWORK_BACKUP_S3_SECRET_ACCESS_KEY` and `HOBWORK_BACKUP_PASSWORD`. Optional: `HOBWORK_BACKUP_S3_ENDPOINT` (a host, or a URL where `http://` turns TLS off; default `s3.amazonaws.com`), `HOBWORK_BACKUP_S3_PREFIX` (default `hobwork/`), `HOBWORK_BACKUP_S3_REGION`.
- **Setting up on `colossus`**: Kopia 0.17.0 is already installed. Create a bucket (and a key limited to it) at the S3 provider, put the `HOBWORK_BACKUP_*` settings into the systemd unit's environment (or a credential file), store the password in the password manager, and run `backup now` once to create the repository and check the settings.
- **CLI**: `pnpm --filter @hobwork/server backup now|list|verify [--percent <n>]|restore <empty-dir> [--snapshot <id>]`. `verify` runs `kopia snapshot verify`, which reads every snapshot's directories and a random share of the files (default 10 percent).
- **Restore**: on the new machine, with the same `HOBWORK_BACKUP_*` settings, run `pnpm --filter @hobwork/server backup restore <empty-dir>` (the newest snapshot, or `--snapshot <id>` from `backup list`). It connects with a throwaway Kopia config, restores into the dir and sets the key files to mode 0600. Then start the host with `HOBWORK_DATA_DIR` pointing there (and the old `HOBWORK_SECRET_KEY`, if one was used). On start the host reinstalls repo hooks; workspaces are cloned again when used and builds are rebuilt on the first invocation. By hand, the same is `kopia repository connect s3 ...`, `kopia snapshot list --all` and `kopia snapshot restore <id> <dir>`.
- **Tests**: unit tests use a fake `kopia`. `HOBWORK_BACKUP_TESTS=1` runs an integration test against MinIO with Kopia in Docker (`dev/backups/`): two backups with a change in between, where the second uploads a small fraction of the first, then a restore into an empty dir and a host started on it with its hobs, DBs and secrets intact.

## Releases

The host ships as a tarball built by `.github/workflows/release.yml`. Pull requests, pushes to `main`, `v*` tags and manual runs all run install (frozen lockfile), typecheck, lint and test. Except on pull requests, it then packages the host on an x86_64 runner and attaches the tarball to a GitHub release for a tag, or keeps it as a workflow artifact for 30 days otherwise. `release/package.sh <version>` does the packaging and runs anywhere with git, Node and pnpm, but packages only for the architecture it runs on.

- **Contents**: `hobwork-<version>-linux-x86_64.tar.gz` (about 160MB, 560MB unpacked) holds one directory, `hobwork-<version>-linux-x86_64/`, laid out like the repo: the committed `server/` source and migrations, `vendor/gondolin`, `packages/sdk`, `packages/theme`, `templates/project`, `images/platform`, the built `web/dist`, the x86_64 guest image at `images/build/x86_64` built from the same commit (it contains `packages/sdk`), production `node_modules` installed for linux-x64, and `VERSION` with the version and commit. A `.sha256` file sits next to it. The version is the tag without its `v`, or `<branch>-<short commit>` otherwise.
- **`node_modules`**: installed with `pnpm install --prod --filter @hobwork/server --filter @hobwork/sdk --filter @hobwork/theme` in the staged tree (the server uses `jsonc-parser`, a dependency of the SDK). `pnpm deploy` would give the server a standalone directory and break its relative imports of `packages/sdk` and `packages/theme`. pnpm's links are relative symlinks, so the tree works from any path; the script fails on an absolute one.
- **From the machine**: Node >= 24.12 (`colossus` runs 26), `qemu-system-x86_64` and `qemu-img` 7.2 or newer (Gondolin 0.12 uses `-netdev stream`; `qemu-img` makes the copy-on-write root disks), git with `git http-backend` (part of git on Arch and Debian), Kopia 0.17 when backups are on, read-write `/dev/kvm` for the service user, and for `HOBWORK_SANDBOX_ISOLATION=namespaces` bubblewrap (`bwrap`) with unprivileged user namespaces allowed.
- **Install and upgrade**: releases go to `/opt/hobwork/releases/`, with `/opt/hobwork/current` a symlink to the running one. The data dir lives elsewhere (`HOBWORK_DATA_DIR=/var/lib/hobwork`), since the default `data/` is inside the release.

  ```sh
  sha256sum -c hobwork-1.2.0-linux-x86_64.tar.gz.sha256
  sudo tar -xzf hobwork-1.2.0-linux-x86_64.tar.gz -C /opt/hobwork/releases
  sudo ln -sfn releases/hobwork-1.2.0-linux-x86_64 /opt/hobwork/current
  sudo systemctl restart hobwork
  ```

  The systemd unit runs `/usr/bin/node server/src/index.ts` with `WorkingDirectory=/opt/hobwork/current` and the `HOBWORK_*` settings in its environment, plus `RuntimeDirectory=hobwork` for the VM directories when isolation is on. Host CLIs run the same way, e.g. `cd /opt/hobwork/current && HOBWORK_DATA_DIR=/var/lib/hobwork node server/src/cli/create-token.ts <name>` (the release has no pnpm). Rolling back is pointing `current` at the previous release. Host DB migrations are forward-only, so an older release then runs against a DB that newer migrations may have changed.
- **Private repo**: downloading a release needs a GitHub token with read access to the repo's contents, e.g. `gh release download v1.2.0 -R Barmore-Genc/hobwork` on a machine that is signed in to `gh`, then copying the files over.

### Upgrade notes

Changes that need action from people or agents when a host is upgraded across them. Newest first.

**Links to hob pages open the app (2026-10-10)**

- **Apps host.** For links to hob pages (`https://<hob>.<apps host>/...`) to open the iOS app, `https://apps.<host>/.well-known/apple-app-site-association` must reach the host: point DNS for the apps host itself at it, add the name to the TLS certificate (`*.apps.<host>` does not cover it) and route it in the reverse proxy. Without that, those links keep opening in Safari. The app also needs a build with the apps host in Associated Domains (`HOBWORK_APPS_HOST` in `apple/README.md`).

**Handlers run unprivileged (2026-09-30)**

- **Handlers no longer run as root.** The runtime VM runs the runner, and with it every handler, as the `agent` user (uid 1000, `HOME=/home/agent`), like commands in workspace and pipeline VMs. A handler that writes outside `/tmp` and its home directory (for example to `/root`, `/var` or `/opt`), runs `doas`, or reads root-only files now fails with `EACCES`. Write scratch files to `/tmp` or `os.tmpdir()` instead; state belongs in the hob DB. Hob tests already ran as `agent` in the workspace, so code covered by tests is not affected. No image rebuild is needed beyond the one for the security hardening changes.

**Push through the relay (2026-10-01)**

- **Pushes go through `https://relay.bgenc.dev`.** Set `HOBWORK_PUSH_RELAY_URL=off` to send none. The host makes its push keys in `HOBWORK_PUSH_KEY_DIR` (default `<data dir>-push-keys`) on first start; keep that directory out of backups. The APNs tokens the host stored are deleted, and devices push again once their app is updated and opened.

**Push off until the relay (2026-09-29)**

- **`HOBWORK_APNS_KEY_FILE`, `HOBWORK_APNS_KEY_ID` and `HOBWORK_APNS_TEAM_ID` are ignored.** The host sends no pushes, so notifications and device commands only reach devices whose app is connected; the rest fail with `unreachable`. Hobs that send notifications to phones should expect `unreachable` while the phone's app is closed. Remove the settings; they return with the push relay.

**Security hardening (2026-09-29)**

For the person running the host:

- **Webhook URLs moved.** Webhooks are served at `<hob app origin>/_hobwork/hooks/<name>/<token>` (for a branch preview, `<label>--<hob>.<apps host>/_hobwork/hooks/...`). The old `/hooks/...` on the Hobwork address answers 410 and runs nothing. Tokens are unchanged: in every service that calls a webhook (Home Assistant, GitHub and others), change the host and path and keep the token.
- **Secrets are sent in fewer places.** Hobwork fills a secret in only over https, and only into the `Authorization` header or a header listed on the secret. A hob that sends a key in another header (for example `X-Api-Key`) gets a 403 and a `secret` line in its log until someone adds that header to the secret on the Secrets page (or with `secret update --header` on the host, which replaces the list). Secrets in query strings or bodies were never filled in.
- **Home Assistant services and events need a list.** A hob calls no HA service and fires no event unless its list on the hob's Home Assistant page names it. On the first start after the upgrade, each hob gets the domains and event types its deployed code names as string literals, plus those seen in its log. A hob that names them in variables gets a warning in its log, and someone has to add them by hand. `hassio`, `homeassistant`, `shell_command`, `recorder.purge` and HA's own event types stay blocked.
- **Reverse proxy.** The host answers only its public host and app hosts, and 421 for any other `Host`. The proxy must forward the original `Host` header. `/api/health` answers for any host.
- **Configuration checks at start.** The host refuses to start with an `http` public or apps URL that is not loopback, and when the public host is the apps host or below it.
- **Sign-in.** Once a user has signed in through an identity provider, only that `(issuer, subject)` signs in as them from that provider. A new subject with the same email from the same provider is refused.
- **Git pushes.** Pushes to the host's git repos are checked with `receive.fsckObjects`, so a push with malformed objects is refused.
- **Guest image.** The image is built with an unprivileged `agent` user and a patched `sandboxfs` (see Guest image under [Components](#components)). The release tarball contains a matching image; a host that builds its own must rebuild it with `images/build.sh`.

For hobs and the agents working on them:

- **Lockfile.** Merges and builds install with `--frozen-lockfile --ignore-pnpmfile`. A hob without a committed, up-to-date `pnpm-lock.yaml` fails its pipeline until an agent runs `pnpm install` in the workspace and commits the lockfile. A restore of an old version with extra packages and no lockfile fails to build.
- **New releases and install scripts.** Package versions published in the last 3 days are not installed. Dependencies run install scripts only when `pnpm-workspace.yaml` lists them under `allowBuilds`. The pipeline refuses a hob with a `.pnpmfile.cjs` or `.pnpmfile.mjs`, or with settings in `pnpm-workspace.yaml` or `.npmrc` that lower the release age, allow all builds, change the registry or add a pnpmfile.
- **Egress applies after commit.** A workspace VM reads `egress` from the committed `hobwork.json`, so a new host is reachable from the next `bash` command after the change is committed.
- **Hob UIs.** App origins send a strict Content-Security-Policy: no inline scripts, no scripts from other origins. A UI that loads a CDN script or uses inline scripts breaks until its `hobwork.json` lists the sources under `csp`. Requests from other hobs' apps are refused unless `crossAppRequests` names them.
- **AI.** The OpenRouter gateway forwards only the paths the SDK uses (completions, messages, responses, embeddings, decisions, and model, key and generation lookups), only over https on port 443, with the model Hobwork picked. Other paths get 403 `hobwork_path_not_allowed`. Answers without a cost are estimated from tokens and count against spend limits.
- **Runtime VMs.** A runtime VM is replaced after an hour and after an invocation times out. Handler responses are limited to 24MB.
- **Read-only access.** Read-only credentials read committed files only and cannot see uncommitted diffs.
- **Existing hobs' `AGENTS.md`.** New hobs get the updated template. Existing hobs keep their own `AGENTS.md`; the MCP server instructions tell agents about the lockfile, egress, CSP and webhook changes.

## Secrets and network

- **Library and assignments**: there is one library of secrets. A secret has a name for people (`Spoolman API key`, unique ignoring case, at most 80 characters), a value, the hosts it may be sent to, and optionally the names of headers besides `Authorization` it may be sent in (`headers`, JSON in the `secrets` table from migration 0031, lowercased, at most 10, no connection headers like `host`). Only people set headers, like hosts; agents see them in `list_secrets`. Existing secrets have none, so hobs that put a secret in another header (for example `X-Api-Key`) fail with the 403 above until someone adds the header; secrets in a URL or body were never filled in. A hob gets a secret only when it is assigned to it, and each assignment picks the env name the hob sees (`SPOOLMAN_TOKEN` in one hob, `API_KEY` in another). A hob has at most one assignment per secret and one secret per env name. A secret can also be given to all hobs under an env name (`all_hobs_secrets`, migration 0037, one secret per env name and one env name per secret): every hob without its own assignment under that env name gets it, and an own assignment wins. Only people set these, and only the OpenRouter API key in Settings, AI uses them so far. They cannot be unassigned from one hob; `list_secrets` shows them as `allHobs`, and the Secrets pages link them to the AI settings. Env names are env var style and must not replace variables the guest relies on (`PATH`, `NODE_OPTIONS`, `HOBWORK_*` and similar). Host patterns follow Gondolin: `api.example.com` or `*.example.com`. `*` alone and `hobwork.internal` are refused.
- **Who does what**: only people create secrets and set their values (web UI or the host command). A secret can be created without hosts; it is then sent nowhere. Agents can list the library, assign and unassign secrets, and ask for hosts over MCP, and nothing else. An agent that could set hosts could assign any secret to a hob and send its value anywhere, so hosts an agent asks for apply only after a person approves them.
- **Host requests** (`secret_host_requests`): `request_secret_hosts(secret, hosts, reason)` stores the full list of hosts the agent wants and a reason, and returns a link to `/secrets/requests/<id>`. That page shows only the request: the secret, the agent, the reason, and each host as added, kept or removed compared to the current hosts. Approving replaces the secret's hosts with the requested ones (logged like any change, as the approving user). A newer request for the same secret supersedes an unanswered one. The Secrets page links to a waiting request, and `list_secrets` shows its hosts as `pendingHosts`. Web API: `GET /api/secrets/host-requests/<id>`, `POST .../approve|deny`. Assignments, and changes and deletions of assigned secrets, are logged as `secret` events in each affected hob's log with who did it (user, agent, or the host command line).
- **Storage** (`server/src/secrets.ts`, `secrets` and `secret_assignments` tables): values are encrypted with AES-256-GCM, a random 96-bit IV per value, and `hobwork-secret:v2:<secret id>` as additional authenticated data, so a ciphertext copied to another row does not decrypt. The name is left out so a secret can be renamed without re-encrypting. `secrets` records the user who created and last changed it (null for the host command), `secret_assignments` the user or agent that assigned it.
- **Migration from hob and global secrets** (0010): each old hob secret becomes a library secret assigned to its hob, and each global secret becomes one library secret assigned to every existing hob that did not have its own secret of that name, so no hob's secrets change on upgrade. Old names become both the library name and the env name. When several old secrets shared a name (a global one and hob overrides, or several hobs), the global one keeps it and hob ones get the hob appended (`SHARED (filament)`); old names are env var style, so this cannot clash. The migration is SQL and has no key, so it keeps each ciphertext and stores its old additional data in `legacy_aad`. When the host opens the store with the key, it re-encrypts those values with the new additional data and clears the column. A value that does not decrypt (wrong key) is left as it was and fails when a VM needs it, as before.
- **Key**: `HOBWORK_SECRET_KEY` (32 bytes as hex or base64) when set. Otherwise `data/secret.key`, generated on first start with mode 0600. The host refuses to start when the file is readable by other users. The file protects against a leaked copy of `hobwork.db` alone. Hobwork's own backups include it, inside the encrypted Kopia repository (see [Backups](#backups)). The env var, e.g. from a systemd credential, keeps the key out of backups. With a different key, existing secrets do not decrypt and VM starts fail with that message instead of using wrong values.
- **In VMs**: the host decrypts values only to hand them to the `Sandbox`'s `secrets` option, keyed by env name. The guest sees `GONDOLIN_SECRET_...` placeholders in env vars of the assigned env names, and the runner gives handlers `ctx.secrets` (env name to placeholder). Gondolin replaces a placeholder with the value in request headers to the bound hosts only, after the internal handler ran, so neither handler code nor the host's internal endpoint sees values. Substitution in URLs and bodies is off.
- **APIs**: no API or MCP tool returns values. MCP: `list_secrets` (the library with each secret's hosts, headers and assignments, or with `hob` the hob's env names), `assign_secret(hob, secret, env_name)`, `unassign_secret(hob, env_name)` and `request_secret_hosts`; no tool takes a value, and hosts from an agent wait for approval. `get_hob` lists the env names. The web API in `server/src/api/routes.ts` needs a signed-in user and the CSRF header, so agent and OAuth tokens get 401 on every secret endpoint, assignments included (agents assign only over MCP): `GET /api/secrets` (the library with assignments), `POST /api/secrets` with `{ name, value, hosts?, headers?, assign?: { project, envName } }` (create, optionally assigning in the same step), `PATCH /api/secrets/<id>` with `{ name?, value?, hosts?, headers? }`, `DELETE /api/secrets/<id>` (also unassigns it everywhere), `GET /api/projects/<name>/secrets` (the hob's secrets by env name), `PUT /api/projects/<name>/secrets/<ENV_NAME>` with `{ secretId }` (assign) and `DELETE` on the same path (unassign). On the host, `pnpm --filter @hobwork/server secret list|create|update|delete|assign|unassign` does the same from a shell and reads values from stdin.
- **UI**: the Secrets page lists the library with the hobs each secret is assigned to, and creates, changes (name, value, hosts and headers), deletes (the confirmation names the hobs that use it) and assigns secrets. A hob's Secrets tab lists its secrets by env name with who added them and when, assigns an existing secret or creates and assigns a new one, and removes them.
- **Egress**: a runtime VM may reach the `hobwork.json` `egress` hosts (with a port, only on that port) and the hosts of the secrets assigned to the hob. Private addresses also need `HOBWORK_PRIVATE_EGRESS` (see [Sandboxing](#sandboxing-gondolin)). Requests to OpenRouter go through the [AI gateway](#ai-limits). Workspace VMs get the same plus `registry.npmjs.org`, pipeline VMs only the registry. Blocked requests get a 403 and an `egress-blocked` line in the hob log with the host and port, so an agent can see why a fetch failed. A request refused because a secret is in a header it may not go in, or would go over http, gets a 403 and a `warn` line with event `secret` naming the secret and header, at most once a minute per host and reason for each VM. Changes to `hobwork.json` show up in the version diff in the UI.
- Secret changes apply without a restart: runtime and workspace VMs compare a fingerprint of the hob's assigned secrets (secret IDs, env names, hosts, headers, update times) and are replaced on the next invocation or `bash` call, so assigning, unassigning, changing or deleting a secret reaches running VMs and their egress allowlist.

## Dashboards and UI

- Hob UIs are plain React + Tailwind pages: `index.html` at the hob root with the code in `ui/`, built by the pipeline with Vite to `dist/index.html` and `dist/assets/`, and served by the host from the deployed version's build at the root of the hob's own origin (`server/src/apps/`, `server/src/runtime/project-ui.ts`). A version without a stored build is built on the first request, as for invocations.
- The UI is optional. A hob without `index.html` has none: `hobworkViteConfig()` then builds only the handlers (and clears `dist/`, so a page from an earlier build is not served), the hob page shows no "Open app", and its app origin answers 404.
- Serving: only a signed-in user's app session for that origin (see [Hob app origins](#hob-app-origins)). A path serves the file from the build if there is one, except `dist/handlers/`, and `index.html` for paths without an extension, so client-side routes work. The host adds `<base href="/">` to `index.html` (unless it has one), so relative URLs from older builds (`./assets/...`) resolve on any client-side route; the template builds with `base: '/'`. Files under `assets/` are cached as immutable (Vite hashes their names), `index.html` is revalidated. The host also serves the theme (`/theme/...`) on app origins, and the hob's `static` mounts of its [files](#files), which win over the build's files and can be public. Old links to `/p/<hob>/<path>` on the Hobwork host redirect to the app origin.
- The host provides one theme stylesheet with CSS variables (colors, radii, fonts, light/dark). The template's Tailwind setup maps these to utility classes (`bg-surface`, `text-muted`, ...). Anything that uses them stays on theme, including third-party components.
- The theme lives in `packages/theme/` (`@hobwork/theme`), which the image build copies into the platform set next to the SDK, so hob builds import `@hobwork/theme/tailwind.css` like the web UI does and the mapping is versioned with the image. The template's `index.html` loads `/theme/theme.css` from the host (marked `vite-ignore`, so Vite leaves the URL alone), and `ui/index.css` imports Tailwind and the mapping. The host serves `theme.css` at `/theme/theme.css` and its fonts (Bricolage Grotesque for headings, Atkinson Hyperlegible Next for text, from the fontsource packages) at `/theme/fonts/`. `tailwind.css` is the Tailwind v4 `@theme inline` mapping, so utilities read the variables and follow light/dark without `dark:` variants. Pages follow the system setting unless the root element has `data-theme="light"` or `"dark"`.
- Variables: colors `--hw-bg`, `--hw-surface`, `--hw-surface-raised`, `--hw-border`, `--hw-fg`, `--hw-muted`, `--hw-accent` (fills), `--hw-accent-fg` (accent text), `--hw-on-accent`, `--hw-success`, `--hw-warning`, `--hw-danger`, `--hw-on-danger`, `--hw-focus`; radii `--hw-radius-sm|md|lg`; fonts `--hw-font-sans|display|mono`. Utilities drop the prefix: `bg-surface`, `text-muted`, `text-accent-fg`, `border-border`, `rounded-md`, `font-display`.
- The Hobwork web UI (`web/`) uses the same stylesheet and mapping. The host serves the built UI (`web/dist`) for every path the other handlers (API, auth, git, MCP, hob routes, webhooks, theme) do not take, with `index.html` as the fallback for client-side routes. In development the Vite server proxies `/api` (with WebSockets), `/auth`, `/theme`, `/oauth`, `/.well-known` and `/mcp` to the host, and hob apps are opened on the host's own port.
- No component library in core. Hobs can add any npm package.
- `@hobwork/sdk/native` reaches native features (haptics, printing, the share sheet, the clipboard, local notifications, app info) when the UI runs in the Apple apps; see [Web bridge](#web-bridge).
- `@hobwork/sdk/browser` is the browser client for the hob's own routes: `api.get|post|put|patch|delete(path, body?)` requests `/api/<path>` on the app origin with the app session and the CSRF header, parses JSON and throws a `RouteError` with the handler's error message; `callRoute` is the same as a plain `fetch`.
- The Hobwork web UI shows a hob's UI in an iframe of its app origin on the hob's app page ("Open app", shown when the deployed build has `index.html` or is not built yet), with a link to open it in its own tab. `GET /api/projects/<name>` returns the origin as `appUrl`. The iframe signs in through the same redirects, which need no user action while the Hobwork session exists. The Apple app shows the same page in its web view.

### Hob app origins

Hob UIs run agent-written JavaScript. On the Hobwork origin that code would run with the user's session and could call Hobwork's API as the user, for example to change which hosts a secret may be sent to. So every hob UI has its own origin, with its own session that grants nothing but that hob's UI and routes.

- **Origins**: `HOBWORK_APPS_URL` (default: `apps.` in front of the host of `HOBWORK_PUBLIC_URL`, same scheme and port) names the apps host. A hob's app is at `<scheme>://<hob>.<apps host>`, a branch preview at `<branch label>--<hob>.<apps host>` (see [Branch previews](#branch-previews)). Both are a single DNS label below the apps host, so one wildcard DNS record and one wildcard certificate cover every hob and branch. The host tells app requests apart by the `Host` header: a host name one label below the apps host is an app origin, anything else is Hobwork (`server/src/apps/origins.ts`). The Hobwork host must not be at or below the apps host: `HOBWORK_PUBLIC_URL` on `apps.example.com`, `hob.apps.example.com` or the same host on another port would be a hob's origin (or shadow one), so the host refuses to start when its host equals the apps host or is a subdomain of it (`loadAppsUrl` in `server/src/config.ts`). Put the apps host beside or below Hobwork, like `apps.hobwork.example.com` for `hobwork.example.com`.
- **Same site**: the Hobwork web UI shows the app in an iframe. Browsers only send SameSite=Lax cookies to a framed page, and through the sign-in redirects inside it, when the frame is the same site as the page around it: same scheme and registrable domain. `hobwork.example.com` and `filament.apps.hobwork.example.com` (or `filament.apps.example.com`) are the same site; a different registrable domain would make app cookies third-party cookies, which browsers increasingly block. In development, `hobwork.localhost` and `filament.apps.hobwork.localhost` are the same site in Chromium, while plain `localhost` and `filament.apps.localhost` are not (checked with Playwright: `Sec-Fetch-Site` and cookies in the iframe), so the dev setup uses `http://hobwork.localhost:<port>` and the host warns when `HOBWORK_PUBLIC_URL` is on `localhost`.
- **Sign-in handoff** (`server/src/apps/http.ts`):
  1. A request to an app origin without its app session: a page load (`GET` accepting HTML) is redirected to `<HOBWORK_PUBLIC_URL>/auth/app?project=<name>[&branch=<branch>]&returnTo=<full app URL>`; other requests get 401.
  2. `/auth/app` checks that `returnTo` is on exactly the app origin of that hob and branch (scheme, host and port) and not under `/_hobwork/`, and answers 400 otherwise. Without a Hobwork session it sends the browser to `/login?returnTo=/auth/app?...`; the Pocket ID flow (`/auth/login` keeps `returnTo` in its flow cookie) and the passkey flow (the web UI reloads `returnTo` when it is under `/auth/`) both come back to it.
  3. With a session, it creates a code (256 bits, stored as a SHA-256 hash in `app_codes`, 60 seconds, single use, bound to the Hobwork session, hob and branch) and redirects to `<app origin>/_hobwork/callback?code=...&returnTo=<path and query>`.
  4. The app origin exchanges the code on the server. It deletes the code in the same statement that reads it, so a code works once even when used on the wrong origin, and turns it into an app session: a random token stored as a hash in `app_sessions` with the Hobwork session's ID, hob and branch. The cookie (`hobwork_app`, `__Host-hobwork_app` on https) is HttpOnly, SameSite=Lax, host-only and lasts as long as the Hobwork session. `returnTo` is checked again (a path on the same origin, not `//` or `/\`); anything else goes to `/`.
- **What an app session can do**: load that origin's UI and call its routes, nothing else. It is looked up by token together with the hob and branch of the origin it arrives on, so another hob's origin, a branch preview and Hobwork's own API (which only reads `hobwork_session`) reject it. The `__Host-` prefix on https keeps a sibling app from planting a cookie for another app with a `Domain` attribute; each app's cookie is host-only, so no other origin receives it.
- **Sign-out**: app sessions reference the Hobwork session with `ON DELETE CASCADE`, so signing out of Hobwork (or the session expiring) ends every app session made from it. The allowlist is checked on every request, like for Hobwork sessions.
- **CSRF**: sibling apps are same-site, so their requests carry SameSite=Lax cookies. Route writes on an app origin need `x-hobwork-csrf: 1` (which a cross-origin page cannot send without a CORS preflight, which is never allowed), and `Origin` and `Sec-Fetch-Site`, when present, must be the app origin itself and `same-origin`. The Hobwork web UI answers with `frame-ancestors 'self'`, so apps cannot frame it either.
- **Cross-app requests** (`crossApp` in `server/src/apps/http.ts`): a page on one app origin can send requests to another, and they carry the SameSite=Lax cookie (same site), so an app that is not listed refuses them. An app's `hobwork.json` lists the hobs whose apps may send it requests: `"crossAppRequests": ["sleep"]`, empty by default. A request is judged by `Sec-Fetch-Site` and the origin it comes from (`Origin`, else `Referer`). Requests that are same-origin, from the Hobwork origin (the web UI framing the app) or from another branch of the same hob pass. A same-site request from an app origin passes only if its hob is listed, on every method including GET and for assets, and a listed hob also passes the CSRF origin check (the `x-hobwork-csrf` header is still required for writes). Everything else that is same-site is refused with 403: another app that is not listed, and a sibling site that is not an app. Not affected: requests that are not same-site (they carry no cookie), the sign-in callback, the theme, icons and manifest (no session), and webhooks (their token is the credential). A top-level navigation to a page (`Sec-Fetch-Dest: document`) from an unlisted app is allowed, so a link from one app to another works, but not to `/api/*`. A request that names no source at all passes only as a page load or frame of the UI, never to `/api/*`. The list is read from the version the origin serves (deployed, or the branch for a preview), like `csp`; a `hobwork.json` that cannot be read lists no one.
- **Content security policy**: every response from an app origin (UI, assets, route responses, errors) carries one `Content-Security-Policy` and `X-Content-Type-Options: nosniff`, so most XSS bugs in agent-written UIs cannot run script: `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; font-src 'self' data:; connect-src 'self'; form-action 'self'; object-src 'none'; base-uri 'self'; frame-ancestors <HOBWORK_PUBLIC_URL>` (`server/src/runtime/csp.ts`). The theme and its fonts are served from the app origin, so `'self'` covers a Vite + React + Tailwind build (Vite writes no inline scripts). Inline styles stay allowed for React `style` props. `base-uri` is `'self'` rather than `'none'` because the host adds `<base href="/">` to the page. Branch previews serve builds like the deployed version, so they get the same policy. `csp` in `hobwork.json` adds sources per directive (`script-src`, `style-src`, `img-src`, `font-src`, `connect-src`, `media-src`, `frame-src`, `worker-src`, `manifest-src`, `form-action`): `http(s)://` and `ws(s)://` origins (host with optional `*.` prefix, port and path), `data:` and `blob:` where they are not code (not in `script-src`, `worker-src`, `frame-src`, `manifest-src`, `form-action`), and `'unsafe-inline'`, `'unsafe-eval'` and `'wasm-unsafe-eval'` in `script-src` only. A bare `*`, scheme-only sources, nonces and every other directive (`frame-ancestors`, `base-uri`, `object-src`, `default-src`) are rejected by the schema, and the host drops anything that does not pass the same check before it builds the header. The policy comes from the hob's `hobwork.json` at the commit the app serves (deployed version, or the branch for a preview); a config that cannot be read gets the default. A route handler that sets its own `Content-Security-Policy` gets both sent (the browser enforces every policy, so the handler can only tighten). Routes on the Hobwork origin keep `sandbox; default-src 'none'`.
- **Web UI policy**: the Hobwork web UI (`web/dist`, `server/src/static.ts`) runs with the user's session, so it gets its own policy and `X-Content-Type-Options: nosniff`: `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self' data:; connect-src 'self'; frame-src 'self' <scheme>://*.<apps host>[:port]; form-action 'self'; object-src 'none'; base-uri 'none'; frame-ancestors 'self'`. The build has no inline scripts (Vite writes a module script that loads from `/assets/`), `connect-src 'self'` covers the live and device WebSockets, and `frame-src` names the apps host with a wildcard so the app and preview iframes load, plus `'self'` because an app without a session redirects its frame through `/auth/app` on the Hobwork origin. Sign-in through Pocket ID and passkeys work under it: OIDC is a top-level navigation, and WebAuthn and the API calls go to the Hobwork origin. Every other response on the Hobwork origin (the JSON API, the OAuth and MCP endpoints, git, the theme, icons) carries `X-Content-Type-Options: nosniff` (`createServer` in `server/src/app.ts` sets it before any handler runs).
- **Host allowlist**: a request whose `Host` is neither an app origin (one label below the apps host) nor the public host (`HOBWORK_PUBLIC_URL`'s host name, any port, so a proxy may change the port) gets 421 Misdirected Request (`createApp` in `server/src/app.ts`), WebSocket upgrades too. The one exception is `GET /.well-known/apple-app-site-association` on the apps host itself (see [Links to hob pages](#links-to-hob-pages)). Otherwise any name pointed at the host (DNS rebinding, a stray record, the apps host itself, `x.y.<apps host>`) would reach the API and UI. `GET /api/health` answers for every host, so health checks by address work. SSH is separate, and the VMs reach the host in-process (`hobwork.internal`), not through this listener. Behind a reverse proxy, the proxy must forward the original `Host` (it already must for app origins); `X-Forwarded-Host` is not read. With the Vite dev server the proxy does not change the `Host` header, so `hobwork.localhost:5173` reaches the host as such; opening the host by another name (for example `localhost:7420` when the public URL is `hobwork.localhost:5173`) answers 421 with the address to use.
- **Framing**: only the Hobwork web UI may frame an app (`frame-ancestors <HOBWORK_PUBLIC_URL>` in that policy), except pages opened with a share link (see [Share links](#share-links)). The web UI's app and preview iframes are sandboxed without `allow-top-navigation`, so an app cannot navigate the Hobwork page (`APP_FRAME_SANDBOX` in `web/src/ui.tsx`). The Apple app shows apps inside the web UI's iframe like a browser, and keeps links to app origins in its web view (`apple/Hobwork/Web/LinkPolicy.swift`).
- **Production setup**: a wildcard DNS record `*.apps.hobwork.example.com` pointing at the reverse proxy, a wildcard certificate for it (Let's Encrypt issues those only with the DNS-01 challenge, which Caddy and Traefik do with a DNS provider plugin), and the proxy forwarding those hosts to Hobwork with the original `Host` header. `HOBWORK_TRUSTED_PROXIES` names the proxy's address (e.g. `127.0.0.1` for a proxy on the same machine), so the host sees each client's own address (see [Client address](#client-address)). Hobwork itself stays at `hobwork.example.com`, and `HOBWORK_APPS_URL=https://apps.hobwork.example.com` (the default for that public URL). Use https: the `__Host-` cookie prefixes depend on it.
- Rejected: one origin per hob on the same host with different ports (cookies ignore ports, so every app would receive every other app's cookies); paths on the Hobwork origin with a sandboxed iframe (`sandbox` without `allow-same-origin` gives the page an opaque origin, so it cannot keep a cookie of its own, and opening the app in its own tab would lose the sandbox).

### Share links

An agent can show the user a hob's app inside the chat, and look at it itself, without the user signing in to Hobwork in that client. `show_hob` (`server/src/mcp/hob-view.ts`) takes `hob`, `branch` (default `main`) and `path` (default `/`) and returns a link that opens that one app origin for 7 days.

- **Link**: `<app origin>/_hobwork/share?token=<token>&returnTo=<path>`. The token (`hws_` and 256 random bits) is stored as a SHA-256 hash in `app_share_links` (`server/migrations/0035_app_share_links.sql`, `server/src/apps/share-links.ts`) with the hob (by ID, so a rename keeps it; the old origin redirects with the path and query), the branch (`NULL` for main), the agent, the agent token or OAuth connection that made it, and whether that credential is read-only. `path` must pass `appReturnPath` like `returnTo` in the sign-in handoff. A branch that does not exist is refused.
- **What it opens**: only the origin of its hob and branch, like an app session: the UI and the routes. Revoking the agent token or OAuth connection, or deleting the agent or the hob, ends its links. A link made by a read-only credential sends only `GET` and `HEAD` to routes (403 otherwise), like read-only agent tokens on hob routes, so a read-only connection cannot make a link that changes things. A link is a bearer credential for its lifetime: anyone with the URL can open the app until it expires.
- **Cookie**: the share path checks the token and sets `hobwork_share` (`__Host-hobwork_share` on https) to it, `HttpOnly; SameSite=None; Secure; Partitioned`, host-only, expiring with the link, then redirects to `returnTo`. The app is framed by the MCP client's sandbox, a different site, so a SameSite=Lax cookie would never be sent; `Partitioned` (CHIPS) stores it per top-level site, so browsers that block third-party cookies keep it, and a page on another site that frames the app gets no session from it. Browsers accept `Secure` on loopback http, so the dev setup works too.
- **Cross-site use**: since the cookie is SameSite=None, every site's requests carry it. It counts only on navigations to pages (opening or framing the UI, `Sec-Fetch-Mode: navigate`) and on requests whose `Sec-Fetch-Site` is `same-origin`, `none` or absent; a cross-site route call or subresource load gets 401. Same-site requests from sibling apps still go through the cross-app check first. Route writes need the CSRF header and same origin, as with app sessions.
- **Bearer**: `Authorization: Bearer <token>` works on the app origin as well, for agents that fetch pages or call routes without a browser (`curl`, a fetch tool). It needs no CSRF header, since browsers never send it on their own. The header is never passed to handlers. Agents with a browser tool open the link itself.
- **Framing**: a response to a request authenticated by a share link (and the share path's own answers) carries `frame-ancestors *` instead of the Hobwork origin, since MCP clients frame views from origins Hobwork cannot know (claude.ai uses a hashed subdomain per server). A signed-in user's app session keeps `frame-ancestors <HOBWORK_PUBLIC_URL>`, and wins over a share cookie on the same request (a share token in `Authorization` is read first). A request with an expired or revoked link answers 401 with a short text instead of the sign-in redirect, because the sign-in pages refuse to be framed.
- **MCP App**: `show_hob` carries `_meta.ui.resourceUri` `ui://hobwork/hob-view` (MCP Apps, the `io.modelcontextprotocol/ui` extension, spec 2026-01-26). The resource is `text/html;profile=mcp-app` (`server/src/mcp/hob-view.html`) with `_meta.ui.csp.frameDomains` set to `<scheme>://*.<apps host>[:port]`, so the client lets it frame app origins and nothing else. The view speaks the postMessage protocol by hand (no SDK bundle): `ui/initialize`, then `ui/notifications/initialized`; it takes the link from `structuredContent.url` of `ui/notifications/tool-result`, frames it with the same sandbox flags as the web UI, and offers "Open" (`ui/open-link`) and "Full screen" (`ui/request-display-mode`, when the host lists it). It applies the host's theme variables and reports its size. The MCP endpoint is stateless and never sees the client's capabilities, so the tool always names the view. Clients without MCP Apps show the text result, which starts with the link and names the bearer token for routes.
- **Cleanup**: making a link deletes expired ones, and so does the daily housekeeping job.
- Rejected: the token in the URL path of every request (hob UIs use absolute paths with `<base href="/">`, so the prefix would be lost); a separate origin per link (one label below the apps host has no room for a token, and each would need its own certificate name); frames without a cookie, with the token in storage the SDK reads (page and asset loads need the session too).

### Hob icons

Each hob has an icon for its app's favicon and home screen icon and for hob lists. `icon` in `hobwork.json` is one emoji (`"🧵"`) or the path of an SVG, PNG, JPEG or WebP file in the repo (`"ui/icon.svg"`); the schema describes it and the template sets a placeholder, so agents see it. Hob code never deals with sizes or formats.

- **Rendering**: in the pipeline VM, right after `pnpm run build`, the host runs `node /opt/hobwork/icons/main.ts <hob>` in the checkout. The renderer is `packages/sdk/src/icons/`, mounted read-only from the host like the runner and the CLI, since it writes files the host serves. It uses `sharp`, `@twemoji/svg` and `@hobwork/sdk/hobwork-json` from the platform set, and fontconfig finds Inter (from Alpine's `font-inter`, copied in by `images/build.sh`) through `/opt/hobwork/fonts/fonts.conf`. It writes `dist/_hobwork/icons/icon-<size>.png` for 32 (favicon), 180 (`apple-touch-icon`), 192 and 512 (web manifest; the hob list uses 192), replacing anything the build put under `dist/_hobwork/`. Rejected: rendering on the host, which would put an image library with a native binary into the host for untrusted input.
- **Look**: emoji are drawn from Twemoji SVGs rather than a font, so they look the same everywhere and stay sharp at 512px. Images are fit into the square. All sizes but the favicon are opaque squares (the theme's surface color behind emoji and transparency), because iOS fills transparent home screen icons with black and masks the corners itself; the favicon keeps transparency. Without `icon`, the icon is the hob name's first letter in bold Inter on one of the theme's accent, success, focus, danger and warning colors, picked by a hash of the name.
- **Failures**: a wrong icon (not one emoji, a missing file, a path outside the repo, a file that is not an image) fails the pipeline's build step with a message for the agent. When a build for a restore or branch preview renders no icon, the build is kept without icons.
- **App origins**: `index.html` gets `<link rel="icon">`, `<link rel="apple-touch-icon">` and `<link rel="manifest">` at the start of `<head>` when the build has icons, so the page's own links win. `/_hobwork/icons/<file>` and `/_hobwork/manifest.webmanifest` (name, `start_url` `/`, `display` `standalone`, the 192 and 512 icons) answer without an app session, because browsers fetch the manifest without cookies; they only use a build that is already stored, so they never start a build, and show nothing but the hob's name and icon.
- **Hobwork**: `GET /api/projects` and `GET /api/projects/<name>` return `iconUrl` (`/api/projects/<name>/icon`, session required), which answers the deployed version's 192px icon, or the default letter as SVG when the deployed build has no icons (versions from before icons, or not built yet). The web UI shows it in the hob list and on hob pages. The Apple app shows the web UI, so it gets the icons there.

### Live updates

Open web UI pages refresh what they show when something changes, whoever changed it: a person in another tab, an agent over MCP, git or SSH, the runtime or the scheduler.

- **Socket**: `GET /api/live` is a WebSocket (`ws` package, like the device socket; `server/src/live.ts`). The upgrade needs a web session and an `Origin` that is exactly `HOBWORK_PUBLIC_URL`, and answers 401 or 403 otherwise. Browsers send cookies with WebSocket requests from any page and never check origins for them, and hob apps on sibling origins are the same site, so the origin check is what keeps them out. Every 30 seconds the host checks the session again, closing with 4001 when it ended (signed out, or no longer on the allowlist), and pings; a page that missed a ping is dropped. Pages send nothing. The host ends these sockets when it closes the server.
- **Messages**: `{ "type": "changes", "changes": [...] }`. A change names what changed and never carries it, so a page loads it again with the usual API calls and gets only what it may see: `{ kind: "projects" }` (hobs created, deleted, renamed or restored), `{ kind: "project", project }` (versions, status, the deployed version, webhook tokens), `{ kind: "invocations", project, id }` (a run started or finished), `{ kind: "logs", project }`, `{ kind: "branches", project }` (created, deleted, committed to, previews starting and stopping, Home Assistant approvals), `{ kind: "secrets" }` (the library, assignments and host requests), `{ kind: "agents" }` (agents, keys, OAuth connections and SSH keys), `{ kind: "devices" }` (paired, renamed, removed, connected or not), `{ kind: "trash" }` and `{ kind: "backups" }`. Deleting, restoring or renaming a hob also sends `agents` and `secrets`, whose lists name hobs. Changes within 100ms go out as one message, each once, so a handler writing many lines costs one message. Every signed-in person may see everything, so every socket gets every change.
- **Host**: the code that changes state publishes changes on an in-process bus (`server/src/changes.ts`), keyed by the host DB so code that only has the DB can publish and test hosts stay apart. Publishing happens where state changes (`recordVersion`, `startInvocation`, `appendLogs`, the secret store, `createBranch`, the runtime's VM start and stop, ...), not in routes, so changes by agents and the runtime reach pages too. Last-used times, which change on every agent call, are not published. Host commands (`create-token`, `secret`, ...) run in their own process, so pages show their changes when they next load. Pushes over git HTTP are published as branch changes when `git http-backend` ends.
- **Web UI**: one socket per browser tab (`web/src/live.ts`), opened by the first page that listens and closed 10 seconds after the last one stops, so moving between pages keeps it. It reconnects with backoff (1 to 30 seconds, with jitter) and right away when the tab becomes visible or the network comes back; after reconnecting every page loads again, since changes during the gap are lost. `useLoad` takes a filter of the changes that concern it, and lists with "show older" (activity, problems) load their first page again and keep the older pages shown (`usePaged`). A page loads again at most once a second however busy the host is.

## Users and authentication

- **Users**: a small fixed set (the household). Login with OIDC (pocket-id) and passkeys (WebAuthn), so Hobwork works for other people who do not run pocket-id.
- **Who may sign in**: `HOBWORK_ALLOWED_USERS`, a comma-separated list of email addresses and `sub:<subject>` entries. An email only matches when the provider marks it verified. There is no first-user bootstrap: an open window where the first person to sign in becomes a user is a risk when the IdP serves more people than the household, and the allowlist is one line of config. The first sign-in of an allowed identity creates the user. The allowlist is checked on every request, so removing someone signs them out. `*` instead of a list lets in everyone the provider signs in, for a provider that already limits who can use Hobwork (a Pocket ID client restricted to a group); it cannot be combined with entries. An empty or unset allowlist still lets nobody in, so a missing setting never opens the host.
- **OIDC**: authorization code flow with PKCE (S256), state and nonce, through `openid-client` against `HOBWORK_OIDC_ISSUER` with `HOBWORK_OIDC_CLIENT_ID` and `HOBWORK_OIDC_CLIENT_SECRET` (client_secret_basic; without a secret the client is public). `HOBWORK_OIDC_NAME` is the provider name on the sign-in button (default `Pocket ID`). The redirect URI is `<HOBWORK_PUBLIC_URL>/auth/callback`. The login state (state, nonce, PKCE verifier, return path) lives on the host in `oidc_flows` (10 minutes, single use, at most 1,000 at a time); the browser only holds a random ID (stored hashed) in an HttpOnly cookie, `__Host-hobwork_oidc` when `HOBWORK_PUBLIC_URL` is https, so a page on a sibling subdomain cannot plant a flow of its own. Users and their identities are separate tables (`users`, `user_identities`). A new identity whose verified email matches an existing user joins that user, unless that user is already linked to another subject of the same issuer: one identity per issuer, so once linked, only that `(issuer, sub)` signs in as them, and a new subject with the same email is refused.
- **Sessions**: random 256-bit tokens, stored as SHA-256 hashes in the host DB, valid 30 days. The cookie is HttpOnly, SameSite=Lax, and `__Host-` prefixed and Secure when `HOBWORK_PUBLIC_URL` is https. The host refuses to start with an `http` `HOBWORK_PUBLIC_URL` (or `HOBWORK_APPS_URL`) unless the host name is loopback (`localhost`, `*.localhost`, `127.0.0.0/8`, `[::1]`), so cookies and tokens never travel in clear text past the local machine. A request that sends a cookie name more than once (a sibling subdomain can set one with `Domain=` on the parent) has that cookie dropped, so a doubled session or flow cookie counts as no session or no flow (`parseCookies` in `server/src/http.ts`).
- **CSRF**: state-changing requests with a session cookie must send `x-hobwork-csrf: 1` (a cross-site page cannot set it without a CORS preflight, which the host never allows), and their `Origin` and `Sec-Fetch-Site`, when present, must be the public origin and same-origin. Code that serves other routes uses `requireUser` (writes the 401/403) or `sessionUser` from `server/src/auth/auth.ts`, which do both checks. Hob routes on the Hobwork host take only agent tokens; hob UIs call them on their own origin with an app session and the same CSRF rules, checked against the app origin (see [Hob app origins](#hob-app-origins)). Cookies never reach the handler.
- **Hob status** in the UI: `updating` while a pipeline run is in progress, `running` while the runtime VM is up, otherwise `ready` (starts on demand). The current version is the deployed one from the runtime, which can lag behind the newest version while a deploy runs or after it failed.
- **Passkeys**: WebAuthn through `@simplewebauthn/server` and `@simplewebauthn/browser`. The RP ID is the host name of `HOBWORK_PUBLIC_URL` and the expected origin is `HOBWORK_PUBLIC_URL`. Credentials are discoverable (resident key required) with user verification required, so sign-in needs no user name. They live in `passkeys`, attached to `users`, with a random WebAuthn user handle per user (`users.webauthn_id`). Challenges are stored in the host DB (`webauthn_challenges`, 5 minutes, used once) and referenced by a `flowId`. Endpoints: `POST /auth/passkey/options` and `POST /auth/passkey` (signed out, CSRF header required), `GET /api/passkeys`, `POST /api/passkeys/options`, `POST /api/passkeys`, `PATCH /api/passkeys/<id>` (`{ name }`, rename), `DELETE /api/passkeys/<id>`. The allowlist still decides: a passkey only signs in a user who is allowed. Each passkey has a name (at most 64 characters) so people tell several apart in Settings. A new passkey takes the name the person gives; without one, the name of its password manager or platform authenticator, looked up by the AAGUID in the registration (Apple Passwords, Google Password Manager, Windows Hello, 1Password and others); else the device the browser runs on, which the web UI sends as `device` (`Mac`, `iPhone`, ...); else `Passkey`.
- **Bootstrap without an identity provider**: only a signed-in user can add a passkey, so there is no open enrollment. For someone without pocket-id, the host operator runs `pnpm --filter @hobwork/server sign-in-link <email> [--name <name>]`. The email must be on `HOBWORK_ALLOWED_USERS`; the command finds or creates the user with that email and prints a one-time link (`/auth/link?token=...`, 15 minutes, hashed in `sign_in_links`) that signs them in and opens Settings to add a passkey. Like `/auth/device`, the link is refused (403) when the request's `Sec-Fetch-Site` is anything but `none` (address bar, mail and chat apps), so a page cannot sign a browser in to someone else's account by linking to it. A missing header is allowed there, since older browsers do not send it and the link is single use. Running the command vouches for the email, like the provider does for OIDC.
- **Web UI API** (all need a session): `GET /api/session` (also works signed out, lists sign-in methods), `GET|PUT /api/me/time-zone` and `POST /api/me/time-zone/report` (see [People and time zones](#people-and-time-zones)), `GET /api/projects` (`q` to search) and the star, tag and move endpoints (see [Organizing hobs](#organizing-hobs)), `GET /api/projects/<name>/icon` (see [Hob icons](#hob-icons)), `GET /api/projects/<name>` (the deployed version's number and entry points with next cron runs, webhook token dates and each entry point's last invocation; reachable hosts; DB status; whether it has a UI), `GET /api/projects/<name>/versions` (`before` a version number, `limit`; newest first with `more`), `POST /api/projects/<name>/versions/<n>/restore`, `GET /api/projects/<name>/invocations` (`kind`, `status`, `since`, `before`, `branch` (main by default, `*` for all), `limit`; newest first with `more`), `GET /api/projects/<name>/branches` and `PUT|DELETE /api/projects/<name>/branches/<branch>/home-assistant` (see [Branch previews](#branch-previews)), `GET /api/projects/<name>/invocations/<id>` (with stack and log lines), `GET /api/projects/<name>/logs` (`view=all|events|problems`, `branch` like for invocations, `after`, `limit`), `GET /api/live` (a WebSocket, see [Live updates](#live-updates)), `POST /api/projects/<name>/webhooks/<webhook>/token` (a new URL, shown once), `DELETE /api/projects/<name>` (see [Deleting hobs](#deleting-hobs)), `POST /api/projects/<name>/rename` (see [Renaming hobs](#renaming-hobs)), `GET /api/trash` and `POST /api/trash/<id>/restore` (see [Restoring deleted hobs](#restoring-deleted-hobs)), `GET /api/activity` and `GET /api/activity/problems` (across hobs, `branch` like for invocations) and `GET /api/activity/attention` (deployed versions only), `GET|PUT|DELETE /api/settings/homeassistant` and `POST /api/settings/homeassistant/test` (see [Home Assistant](#home-assistant)), `GET|PUT /api/settings/ai` and `GET|PUT /api/projects/<name>/ai` (see [AI limits](#ai-limits)), `GET|PUT /api/projects/<name>/home-assistant-services` (see [Hobwork to HA](#hobwork-to-ha-actions)), the device endpoints under [Host implementation](#host-implementation), the secrets endpoints under [Secrets and network](#secrets-and-network), `GET|POST /api/agents`, `POST /api/agents/<id>/tokens`, `POST /api/tokens/<id>/revoke`, `POST /api/agents/<id>/ssh-keys`, `POST /api/ssh-keys/<id>/revoke`, `POST /api/connections/<id>/revoke` (an OAuth connection), `GET /api/oauth/requests/<id>` and `POST .../approve|deny` (the consent page). Restores by a user are recorded with the user (`versions.user_id`) and use their name and email as the git author.
- **Agents**: separate identities, not tied to a user. Users create and revoke agent access in the UI.
- **MCP auth**: Hobwork is the OAuth 2.1 authorization server for its own MCP endpoint, following the MCP authorization spec revision 2026-07-28, which claude.ai, Claude Desktop, Cowork and Claude Code custom connectors use. Static agent tokens keep working next to it. Tested with the MCP SDK client, with Claude Code (`claude mcp add`, then `claude mcp login`) and with claude.ai custom connectors.
  - Discovery: a 401 from `/mcp` carries `WWW-Authenticate: Bearer resource_metadata="<public URL>/.well-known/oauth-protected-resource/mcp"` (also served without the `/mcp` suffix). Protected resource metadata (RFC 9728) names the resource `<HOBWORK_PUBLIC_URL>/mcp` and the issuer `<HOBWORK_PUBLIC_URL>`, whose metadata (RFC 8414) is at `/.well-known/oauth-authorization-server`. MCP clients must use the `/mcp` URL under `HOBWORK_PUBLIC_URL`, since the resource has to match. Hobwork has no OAuth scopes: the `scope` parameter is stored but ignored, and the person picks the connection's access on the consent page (see [Access limits](#access-limits)).
  - Clients: Client ID Metadata Documents (the spec's preferred way, `client_id_metadata_document_supported`) and dynamic client registration (RFC 7591, deprecated in the spec but still the fallback of many clients) at `/oauth/register`. A client ID that is an https URL with a path is fetched on demand (https only, public addresses only, checked at connect time, no redirects, 16 KiB, 5 seconds; blocked ranges include the IPv4 private ranges, IPv4-mapped IPv6, `::/96` (IPv4-compatible), `64:ff9b::/96` and `64:ff9b:1::/48` (NAT64), `2002::/16` (6to4), `2001::/32` (Teredo), `fc00::/7`, `fe80::/10` and multicast) and cached for its `max-age`, between 1 minute and 1 day. Claude uses `https://claude.ai/oauth/mcp-oauth-client-metadata`, Claude Code `https://claude.ai/oauth/claude-code-client-metadata` and ChatGPT `https://chatgpt.com/oauth/client.json`. Registered clients live in `oauth_clients`; ones never approved are deleted after a day. Registered clients use `none`, `client_secret_basic`, `client_secret_post` or `private_key_jwt`; metadata document clients use `none` or `private_key_jwt`. `private_key_jwt` (RFC 7523) is what ChatGPT uses: the registration or document names an https `jwks_uri`, and the token and revocation endpoints take a `client_assertion` JWT signed with RS256 (2048-bit keys or more) or ES256 by a key from it. The assertion's `iss` and `sub` must be the client ID, its `aud` the issuer or the endpoint's URL, it must expire within an hour, and its `jti` is accepted once (`oauth_client_assertions`, kept until it expires). The JWKS is fetched like the metadata document and cached for its `max-age`; an unknown `kid` fetches it again, at most once a minute. Redirect URIs must be https or http on localhost/127.0.0.1/[::1] and match exactly, except that loopback ones match on any port (RFC 8252), which Claude Code needs.
  - Flow: `/oauth/authorize` takes the authorization code flow with PKCE S256 only and an optional `resource` (RFC 8707) that must be the MCP resource. Errors before the client and redirect URI are validated go to the web UI (`/connect?error=...`), never to the redirect URI. A valid request is stored (`oauth_requests`, 15 minutes) and the browser goes to the consent page `/connect?request=<id>`, which needs a signed-in user like every page. The page shows the app name, its domain for metadata document clients (or a warning that the app is unverified), what it can do, the redirect host, and a warning for loopback redirects. Approving creates a grant (`oauth_grants`) for a new agent named after the client (with a number added when the name is taken; the user can rename it) or for an existing agent the person picks, and redirects with a code (5 minutes, single use) plus `state` and `iss` (RFC 9207).
  - Tokens: `/oauth/token` exchanges the code (checking PKCE, redirect URI, client and resource) and refreshes. Access tokens (`hwa_...`) last 1 hour; refresh tokens (`hwr_...`) last 30 days and rotate on every use, so a connection in regular use stays connected. Reusing a rotated refresh token or a used code revokes the whole grant. Tokens are 256 random bits stored as SHA-256 hashes (`oauth_tokens`). `/oauth/revoke` (RFC 7009) revokes an access token, or a refresh token together with its grant. Refused requests to the token, revocation and registration endpoints are logged with the client ID and the error, like refused authorization requests, since clients rarely show the error to the person connecting. MCP accepts an access token only for the resource it was issued for.
  - Limits, since registration and authorization requests need no sign-in: `/oauth/register` takes 30 registrations per hour and `/oauth/authorize` 60 requests per 10 minutes from one [client address](#client-address), with IPv6 addresses counted per /64 (in memory, fixed windows). Over the limit, registration answers 429 `temporarily_unavailable` with `Retry-After`, and authorization sends the browser to `/connect?error=too_many_requests`. The tables are capped as well: at most 200 registered clients that were never approved and at most 200 pending authorization requests (15 minutes each). A new one evicts the oldest instead of being refused, so a flood cannot keep a real client out.
  - The consent page asks what the connection may do (see [Access limits](#access-limits)) and starts on read-only access to all hobs, so full access takes a choice; `POST /api/oauth/requests/<id>/approve` takes `{ agentName, access? }` for a new agent or `{ agentId, access? }` for an existing one.
  - Reconnecting: a client that lost its tokens often registers again and gets a new client ID, so the consent page offers the existing agents (`GET /api/oauth/requests/<id>` returns `agents`, each with the access of its latest grant or token, and `suggested`). The suggestion is the agent of the latest grant with the same client name, or else the agent with that name, and the page starts on it and its access. Only the person approving attaches a connection to an existing agent; a client name alone never does. The agent keeps its SSH keys, and its earlier grants stay as they are.
  - Agents that connected this way show their connections on the Agent access page with their access, where revoking one ends its tokens. Agents stay; they can also hold static keys and SSH keys.
- **git HTTP**: agent token as the password. A read-only token can fetch but not push (any path or `service` parameter that mentions `receive-pack`, in any case or encoding, is refused with 403), and a token limited to some hobs gets 403 on the others. `git http-backend` gets the [client address](#client-address) as `REMOTE_ADDR`.

### People and time zones

- **Callers**: a route called from the hob's UI with an app session gets `ctx.caller`: `{ person, device }`, where `person` is `{ id, name, email, timeZone }` and `device` is `{ name, platform }` when the Hobwork session behind the app session belongs to a paired app's web view (`sessions.device_id`), else null. The host builds it from the session on every request (`server/src/apps/http.ts`) and passes it in the invoke message (`InvokeRequest.caller`), never as a header, so a hob cannot be fooled by headers the browser sends. Crons, webhooks, triggers, manual invocations, share links and agents (`/p/<hob>/api/...`) get `caller: null`.
- **People**: `ctx.people()` lists the users on `HOBWORK_ALLOWED_USERS` by name. `Person.id` is `users.id`, stable for the life of the host, for keying per-person settings in hob DBs. `ctx.person(id).devices()` lists a person's devices, most recently used first (unknown IDs throw `DeviceError('unknown_person')`), and `.lastActiveDevice()` is the first of them. Both go through the internal devices endpoint (`{ action: 'people' }`, `{ action: 'list', person }`), so workspaces and previews can read them too.
- **Last activity**: `devices.last_active_at` records when the person last used the device: a `hello` (the app connects, and says hello again when it comes to the foreground on an open connection), a `notifications/action` or `nfc/scanned` event (over the socket or `POST /api/devices/events`), and every request of the device's web view to a hob's app origin. Health samples, Focus changes and pings do not count, since they arrive while nobody holds the device. Writes are throttled to one per 10 seconds per device. `DeviceInfo` has `ownerId` and `lastActiveAt` next to `lastSeenAt`.
- **Time zones**: `users.time_zone` holds the person's IANA zone. The app sends `timeZone` in `hello`, and the web UI reports the browser's zone after sign-in (`POST /api/me/time-zone/report`); reports are ignored once the person chose a zone in Settings (`PUT /api/me/time-zone` with `{ timeZone }`, or `{ timeZone: null }` to follow reports again; `users.time_zone_manual`). `GET /api/me/time-zone` answers `{ timeZone, manual, host }`. `Person.timeZone` falls back to the host's zone when nothing was reported. Handlers turn a zone or a person into local time with `localTime(person)` and back with `fromLocalTime(person, '2026-10-09', '08:00')` from `@hobwork/sdk`.

### Client address

The OAuth limits and `git http-backend` need the address of the client, which behind a reverse proxy is the proxy's (`server/src/client-address.ts`). `HOBWORK_TRUSTED_PROXIES` lists the proxies (IP addresses and CIDR ranges, IPv4 and IPv6, comma-separated; empty by default, and an invalid entry stops the host from starting). List only addresses of proxies you run: any address in the list can name any client, so a range that also covers other machines on the network lets them make up their address. A request from a trusted proxy gets its client from `X-Forwarded-For`: the entries of every such header, walked from the right, skipping trusted addresses, and the first untrusted one is the client. Entries to the left of it came from the client and can be made up. When every entry is trusted, the leftmost is the client. A malformed entry on the way (not an IP address, or an IP address with a zone) stops the walk and the proxy's address is used. Entries may carry a port (`1.2.3.4:80`, `[2001:db8::1]:80`). Requests from any other address use the socket address and ignore the header, since anyone can send it. `Forwarded` (RFC 7239) is not read. IPv4-mapped IPv6 addresses (`::ffff:127.0.0.1`, how a dual-stack socket reports IPv4 clients) count as IPv4, in the setting and in requests, and IPv6 addresses are compared in one spelling. The OAuth limits count all IPv6 addresses of a /64 as one client, since one person usually holds a whole /64.

### Access limits

Every agent token and OAuth connection has an access limit, chosen when the key is created (web UI or `create-token`) or on the consent page. Credentials from before limits existed, and ones created without a choice, have full access. The model is two independent settings:

- **Read only, or build and change**. Read-only access allows the MCP tools annotated `readOnlyHint` (listings, `get_hob`, `show_hob` (its links are read-only too), `read_file`, `list_files`, `search`, `diff`, `log`, `pipeline_status`, `list_versions`, `list_invocations`, `get_logs`, `tail_logs`, `list_secrets`, `list_ssh_keys`, `list_devices` and the `ha_*` tools), fetching over git, and `GET`/`HEAD` on hob routes. Every other tool is left out of the tool list and refused, so a new tool is refused to read-only access unless it is marked read-only. Read-only access cannot add SSH keys, open SSH sessions or push.
- **All hobs, or a list of hobs**. With a list, tools that take a `hob` refuse other hobs, `list_hobs` shows only the listed ones, `list_secrets` shows the library but only assignments to the listed hobs, `create_hob` and the `ha_*` tools (which read the whole house) are left out, hob routes and git answer 403 for other hobs, and SSH sessions to other hobs are refused. "All hobs" includes hobs created later. Hobs are stored by ID (`agent_token_projects`, `oauth_grant_projects`), so a renamed hob stays in the list and a deleted one drops out. The trash entry records which tokens and connections listed it, and restoring puts it back in the lists of those that still exist. Tools that do not concern a hob (devices, `request_secret_hosts`, the agent's own SSH keys) work with either setting.

Storage: `read_only` and `all_projects` on `agent_tokens` and `oauth_grants` (`server/migrations/0021_credential_access.sql`). `server/src/access.ts` parses, stores and loads access; `verifyAgentToken` and `verifyAccessToken` return it with the agent. MCP applies it in `server/src/mcp/access.ts`, which wraps `registerTool` before any tool is registered. An SSH key an agent adds over MCP has the access of the token or connection it used (looked up at sign-in), so a limited credential cannot give itself wider access through SSH; keys a person adds have full access. The `hobwork` CLI in a workspace acts only on that workspace's hob, so the SSH check covers it.

APIs: `POST /api/agents` with `{ name, access? }`, `POST /api/agents/<id>/tokens` with `{ access? }`, and the consent approval take `access: { readOnly: boolean, projects: string[] | null }` (`null` for all hobs; a list must name existing hobs and not be empty). `GET /api/agents` returns `access` for every token and connection. On the host: `pnpm --filter @hobwork/server create-token <agent-name> [--read-only] [--project <name>]...`.
- **SSH**: public keys registered to an agent (see [SSH gateway](#ssh-gateway)).
- Agents can do everything on hobs except delete, rename or restore them, manage users and agents, change the Home Assistant connection, pair, remove or notify devices (deployed handlers notify them), change AI limits (they can set AI models), and create secrets or set their values and hosts (they can assign existing secrets to hobs).

## Devices (Apple apps)

- The app keeps a WebSocket to the host and registers the device and its capabilities.
- Scripts call capabilities through the SDK: `ctx.device("kaan-iphone").notifications.send(...)`.
- Capabilities: notifications, alarms (AlarmKit), Focus, NFC, Health (HealthKit), Live Activities and widgets (iOS). The macOS app has notifications and Focus: macOS 26 has no AlarmKit or Core NFC, and HealthKit has no data on a Mac.
- The iOS app closes its socket in the background, so most calls need push to reach a phone: the notification service extension runs them. Pushes go through the push relay (see Push below). The macOS app keeps running with its window closed and keeps its socket open, reconnecting when the Mac wakes; the same extension handles pushes there. If a capability needs the app in the foreground (NFC), the push is a notification to tap, which opens the app straight into the action.
- The apps send only what a person explicitly chose to share. They send no location, no device identifiers (`identifierForVendor`, the advertising ID), no Wi-Fi or network names, and nothing else that could look like tracking. New capabilities follow this rule.
- NFC tags written by Hobwork contain `<public URL>/nfc/<tag>`, which opens the app (universal link) when it is built with the host in its Associated Domains, and a host page otherwise. Hobs can also write any link, and handle scans of tags with other links (see NFC scans).

#### Notifications

- **Sending**: `ctx.device(name).notifications.send(notification)` returns `{ id, delivery: "app" | "push" | "scheduled" }`; `ctx.person(id).notifications.send(notification)` sends to every device of the person that reported `notifications` (`devices: "all"`, the default) or only the one they used last (`devices: "lastActive"`, by `last_active_at`), and returns `{ id, scheduled, devices: [{ device, delivery } | { device, error: { code, message } }] }`: one device failing does not fail the others, and the send throws only for an unknown person (`unknown_person`) or one without such a device (`unreachable`). The notification is `{ id?, title, body?, actions?, data?, open?, interruptionLevel?, sound?, thread?, deliverAt? }` (`Notification` in `packages/sdk/src/devices.ts`). The title is at most 200 bytes and the body at most 2,000 bytes as UTF-8, with up to 4 actions with IDs of letters, digits, `-` and `_` and titles of at most 64 characters; `data` is up to 4 KB of JSON that comes back with an action and is never sent to the device. The push the relay would build is then measured, so every notification that is accepted can go by push. Failures throw a `DeviceError` with a code: `unknown_device`, `unsupported` (the app never reported `notifications`), `unreachable` (not connected and no push), `too_large` (the push would be over 4,096 bytes; nothing is sent), `push_failed` (the relay refused it or could not be reached), `bad_request`, `read_only`, or the app's own code. Calls are logged with the invocation.
- **IDs**: `id` is the hob's own key (letters, digits and `-_.:`, at most 64, e.g. `print-stopped:42`); without one the host makes up a UUID. Keys are per hob. Devices show the notification under an internal UUID (`notifications.id`), the same on every device and for every send with that key, so a later send, update or withdrawal reaches the same notification everywhere. A send with a key in use replaces it: the new targets get the new version under the same ID (it alerts again), and devices that held it but are not targets lose it. `revision` counts sends and updates of a key; the app treats a later revision as new instead of a repeat.
- **Delivery options**: `interruptionLevel` is `passive` (no sound, no screen wake), `active` (default) or `timeSensitive` (breaks through Focus and the scheduled summary; the app has the `com.apple.developer.usernotifications.time-sensitive` entitlement). `sound` is `default` or `none`. "Silent" in a product spec means `sound: "none"`: the banner still shows, without a sound; passive notifications are always silent. Named sounds are not supported, since the app bundles none. `thread` groups notifications in Notification Center as `<hob>/<thread>`; without it a hob's notifications are one group (`<hob>`). `open` is a path of the hob's UI that a tap on the notification opens (default: the hob's page in Hobwork).
- **Update**: `ctx.notifications.update(id, changes)` changes `title`, `body`, `actions`, `data` or `open` and returns `{ updated, devices }`. It goes to every device that holds it and where no action was tapped (iOS removes a notification whose action was tapped), as `passive` with no sound, so it replaces the text in place without alerting. Over the socket the app replaces it only while it shows, so a notification someone dismissed stays gone; by push (collapse ID = the notification ID) iOS replaces a shown one and shows a dismissed one again, quietly. `updated: false` for a withdrawn or unknown key. An update of a scheduled notification changes what will be sent.
- **Withdraw**: `ctx.notifications.withdraw(id)` returns `{ withdrawn }` and resolves once every device that holds it was told: a connected app gets `call` `notifications`/`withdraw` with `{ ids }` (waiting up to 4 seconds), others a background push (relay kind `background`, `content-available`, priority 5) with `hobwork: { withdraw: [ids] }`, which wakes the app to remove them. iOS throttles background pushes and drops them after a force quit, so until a connected app confirms the removal (`notification_deliveries.removed_at`), every `hello` sends the withdrawal again. A withdrawal also cancels a notification that waits for `deliverAt`. Apps from before withdrawals answer `unsupported`, which counts as done.
- **Scheduled**: with `deliverAt` (an ISO date-time within 30 days; a past time sends at once) the host stores the notification with its target (`{ device }` or `{ person, devices }`) and sends it when the time comes: a timer wakes for the earliest one, and at least once a minute while any wait. Pending ones are rows in `notifications` (`deliver_at`), so they survive restarts. Devices of a person are picked at delivery time. A target that is gone by then and failures on single devices are `warn` lines in the hob's log.
- **Over the socket** when the device is connected: `call` with capability `notifications`, method `send` and args `{ id, project, title, body?, actions, interruptionLevel?, sound?, thread?, open?, revision?, update? }` (fields at their defaults are left out: `active`, `default`, the hob's thread, revision 1). Actions are `{ id, title, foreground?, destructive?, open? }`; routes and bodies stay on the host. The app shows it with `id` as the request identifier and answers `ok: true` (the value is ignored), or an error (for example `not_authorized` when notifications are off), which fails the send. A timeout or a dropped connection falls back to push.
- **By push** otherwise: kind `alert`, collapse ID = the notification ID (so a notification that reached the app both ways shows once, and a later revision replaces it), expiring after a day. Payload, sealed: `{ aps: { alert: { title, body }, sound?: "default", "interruption-level"?: "passive" | "time-sensitive", "thread-id": <hob or hob/thread> }, hobwork: { id, project, actions, open?, revision?, update? } }`. With actions, `aps` also has `category: "hobwork.<id>"` and `mutable-content: 1`: actions differ per notification, so the app's notification service extension registers that category from `hobwork.actions`, with each action's options, before the system shows it.
- **Actions**: a tap sends `event` `{ capability: "notifications", name: "action", data: { id, action } }`, over the socket or, when iOS wakes the app in the background for the tap, with `POST /api/devices/events`. The host checks that the notification went to that device and has that action. An action with a `route` (a path as in `hobwork.json`, `method` default `POST`) runs that route of the deployed version (`callRoute` in `server/src/runtime/http.ts`) with `ctx.caller` set to the device's owner and the device, and a JSON body: the action's `body`, or `{ notificationId, action, data? }`; the app stays closed unless the action also has `foreground` or `open`. An answer of 400 or more, or a failed handler, is a `warn` line in the hob's log. An action with `open` and no route only opens the app there (`/p/<hob><open>`, which redirects to the hob's address). Any other action runs each trigger of the hob declared as `{ "device": { "capability": "notifications", "event": "action" }, "handler": ... }` in `hobwork.json`, with `ctx.payload` `{ device, capability: "notifications", event: "action", notificationId, action, data? }` (`NotificationActionEvent`, `notificationId` is the hob's key). `destructive` actions show in red. Each device's copy of each revision answers once, when its route or triggers start; repeats after that are ignored. A tap on a hob without such a trigger (or whose triggers cannot be read) is logged as a `trigger` warning in its log and leaves the notification unanswered, so the app sending the event again runs the trigger once the hob has one. Notifications are kept 30 days after their last change (`notifications`, `notification_deliveries`).

#### Commands

- Every device call except `notifications.send` is a command, recorded in `device_commands` (`id` UUID, device, hob, invocation, `capability`, `method`, `args` as sent, `status` `pending`/`done`/`failed`/`expired`, `result`, `created_at`, `expires_at`, `answered_at`). Commands expire 10 minutes after creation and are kept 30 days.
- The host checks arguments per method before anything is sent (`bad_request` saying what is wrong; unknown fields are refused too) and the size of the push (`too_large` over 4,096 bytes). The app checks them again.
- **Delivery**, in order:
  1. **Socket**: a `call` with `id` = the command ID when the device is connected. A background command whose socket stays silent for 10 seconds, or whose connection closes before it answers, also goes by push, since a half-open socket after a network change still looks connected.
  2. **Command push** for background methods when the device is not connected: kind `command`, collapse ID = the command ID, expiring at `expiresAt`. Payload, sealed: `{ aps: { alert: { title: <hob>, body: <fallback> }, "mutable-content": 1, "interruption-level": "passive", "thread-id": <hob> }, hobwork: { project, command: { id, capability, method, args, expiresAt } } }`. The notification service extension runs the command, posts the result and replaces the text with what happened. The fallback body (for example `Health request for this device. Open Hobwork to answer it.`) shows if it fails or runs out of time. Background pushes (`content-available`) are throttled and dropped after a force quit, so commands do not use them.
  3. **Prompt push** for foreground methods (NFC, alarms): kind `prompt`, an ordinary alert (`sound: "default"`) such as `Write an NFC tag` / `<hob> is waiting. Tap to start.` or `Start a timer` / `<hob> wants to start the timer "Tea". Tap to start it.`, with the same `hobwork.command` plus `"foreground": true`. Tapping it opens the app, which runs the command from the payload.
  4. **On hello**, as described under Connection.
- A command that no path reached (not connected and no push, or the relay refused it) fails at once with `unreachable` or `push_failed` and is marked `failed`, so it does not run later by surprise.
- The app and its extensions remember the IDs of commands they ran (1 day), so a command that arrives more than once runs once and answers again. Commands past `expiresAt` answer `expired` without running.
- **Results**: `result` over the socket, or `POST /api/devices/results` (Bearer device token, JSON `{ id, ok: true, value }` or `{ id, ok: false, error: { code, message } }`, up to 1 MB; 204, 404 for an ID that is not this device's command, 400 for another body). The first result wins; later ones answer 204 and are ignored. A result for a command the host already marked `expired` is still recorded, since the app ran it.
- **Waiting**: the handler waits 30 seconds for background methods and 2 minutes for foreground ones, then gets `DeviceError('timeout')`, whose message says that the command was sent and may still run until `expiresAt`. Results after that go to the hob log with the invocation (info when ok, warn for failures). A command still pending at `expires_at` becomes `expired` (checked every minute, on hello and on each new command), with a warn line in the hob log.
- Calls are logged with the invocation (`Device kaan-iphone: alarms.set answered {...}`).

#### Capabilities

Background methods: all of `focus` and `health`. Foreground methods: all of `nfc` and `alarms`. AlarmKit authorizes each bundle on its own and the notification service extension cannot ask (on an iPad, its state stays `notDetermined` and `requestAuthorization` throws), so only the app sets alarms. Besides the codes listed per capability, the app answers `bad_request`, `not_authorized` (the person has not allowed it), `expired` and `locked`. Date-times are ISO 8601 with a time zone. Times of day are local `"HH:MM"`. `days` are `"mon"` to `"sun"`, a non-empty list without repeats.

- **alarms** (AlarmKit): `set({ title, at?, time?, days?, id?, subtitle?, tint? })` → `{ id }`, with exactly one of `at` (one-off, in the future) or `time` (repeating on `days`, or once at the next occurrence without them; `days` only with `time`). A known `id` (UUID) replaces that alarm. `timer({ title, seconds, id?, subtitle?, tint?, repeat?: { seconds, title? } })` → `{ id }`, a countdown of 1 to 86,400 seconds with a Live Activity. `repeat` is the alert's second button next to Stop: the countdown's post-alert duration (`Alarm.CountdownDuration.postAlert`, secondary button behavior `.countdown`), so AlarmKit itself starts a new countdown of `repeat.seconds` under the same ID without the app; its text is `title` (at most 20 characters) or the interval (`+2 h`, `+15 min`). `reschedule({ id, seconds?, title?, subtitle?, tint?, repeat? })` → `{ id }` schedules a timer again under its ID with the changes: `seconds` is a new countdown from now (default: what was left, from the Live Activity), `repeat: null` removes the button (the oven's 2 h cap); `unknown_alarm` when the timer is gone. `cancel({ id })` → `{}`, for unknown IDs too. `list()` → `[{ id, title, state: "scheduled" | "countdown" | "paused" | "alerting", at?, time?, days?, seconds?, subtitle?, tint?, repeat?, endsAt? }]`, only alarms Hobwork made. Titles and subtitles are at most 100 and 200 characters; `tint` is `#RRGGBB` and colors the Live Activity, its buttons and the Dynamic Island. Errors: `limit_reached`, `unknown_alarm`.
  - Alarms and timers ring in silent mode and through Focus: that is AlarmKit's behavior and needs no setting. Authorization is per app: the app asks (`AlarmManager.requestAuthorization`, with `NSAlarmKitUsageDescription`) when the person taps "Allow Alarms" in Settings, when they tap a prompt push for an alarms command, or the first time a hob page sets one; after a refusal only the Settings app can turn it back on, and the device stops reporting `alarms`. On iOS 26.1 and later the alert's Stop button is the system's and its text cannot be changed.
  - The Live Activity (widget extension, `AlarmAttributes<HobworkAlarmMetadata>`) shows the title, the subtitle, the countdown and Pause/Resume/Cancel, and while ringing Stop and the repeat button (`AlarmControlIntent`), in the alarm's tint.
- **focus**: iOS and macOS have no API to turn a Focus on or off. The app offers a Focus filter (`SetFocusFilterIntent`) with a `label`, which the person adds to a Focus in Settings (System Settings on a Mac); the system runs it when that Focus turns on or off. `status()` → `{ active: string[] }` (labels). Changes arrive as the `changed` event.
- **nfc** (Core NFC, foreground, system scan sheet): `write({ text?, alertMessage?, successMessage? })` → `{ tag, url, uid?, verified? }`. The host creates a random tag ID (22 base64url characters) owned by the hob in `nfc_tags` and sends `{ tag, url: "<public URL>/nfc/<tag>", text? }`; the app writes one NDEF URI record, plus a text record with `text` (at most 1,024 bytes). A failed or expired write deletes the tag again. `write({ url, text? })` → `{ url }` writes any link instead and creates no tag: an absolute URL without whitespace or control characters, with the scheme `http`, `https`, `mailto`, `tel`, `sms`, `facetime`, `facetime-audio` or `shortcuts` (what iOS opens from a tag without an app), no user name or password in `http`/`https` URLs, and at most 2,048 bytes after the host normalizes it (WHATWG URL serialization: lowercase scheme and host, `https://example.com` becomes `https://example.com/`). The host sends `{ url, text? }` with the normalized URL, and the result is that URL. Tag sizes vary (NTAG213 holds 137 bytes of NDEF, NTAG216 868), so long links answer `too_small`. Every write reads the tag back in the same session and compares the records (`verify_failed` when they differ); the result adds `uid`, the tag's hardware ID as lowercase hex, and `verified: true`. `read({ alertMessage?, successMessage? })` → `{ records: [{ type: "url" | "text" | "other", value }], tag?, uid? }`, with `tag` when the first URL is a Hobwork tag URL of this host. `alertMessage` and `successMessage` (at most 200 characters) replace what the scan sheet says while it waits and when it is done. The app uses `NFCTagReaderSession` (polling ISO 14443 and ISO 15693) rather than an NDEF reader session, since only tag sessions expose the hardware ID: NTAG21x tags are MiFare Ultralight (`NFCMiFareTag.identifier`), and ISO 15693 and ISO 7816 tags have `identifier` too. ISO 14443 polling needs `com.apple.developer.nfc.readersession.iso7816.select-identifiers` in Info.plist, which lists the NFC Forum NDEF application. Errors: `cancelled` (also when iOS closes the sheet after 60 seconds), `not_writable`, `too_small`, `verify_failed`.
- **health** (HealthKit): the person connects Health in the app's settings, which asks for all types at once, and picks what Hobwork may read in the Health sheet: `sleep`, `steps`, `heartRate`, `restingHeartRate`, `activeEnergy`, `bodyMass`, `workouts`, `mindfulness`. `query({ type, from, to, limit? })` → `[{ type, start, end, value?, unit?, stage?, workoutType? }]`, with `from` before `to` and at most `limit` samples (1 to 1,000, default 1,000). `stage` is the sleep stage (`inBed`, `asleep`, `awake`, `core`, `deep`, `rem`). Units are count, count/min, kcal, kg and min. HealthKit does not tell apps which read types were allowed, so types the person did not allow return no samples. Errors: `locked` (Health data cannot be read while the phone is locked), `not_shared` (Health is not connected).

#### Events and triggers

- Triggers in `hobwork.json`: `{ "device": { "capability": "focus", "event": "changed", "device": "kaans-iphone" }, "handler": "src/focus.ts" }`. Valid pairs: `notifications`/`action`, `focus`/`changed`, `nfc`/`scanned`, `health`/`samples`, `alarms`/`fired`, `alarms`/`stopped`, `alarms`/`repeated`; the schema refuses others. `device` is optional and limits the trigger to one device by name. `url` (`nfc`/`scanned` only, 1 to 2,048 characters) limits it to scanned links that start with it; a `url` that parses as a URL is normalized first, so `"https://Example.com"` matches `https://example.com/a` but not `https://example.com.evil.example/`, and `"https:"` matches every https link.
- `ctx.payload` is `{ device, capability, event, ...data }` (`DeviceEvent`): `NotificationActionEvent`, `FocusChangedEvent` `{ label, active }`, `NfcScannedEvent` `{ tag?, url, records? }` (`tag` for Hobwork tags, whose `url` is `<public URL>/nfc/<tag>`; `records` when the app read the tag itself; `device` is null for a scan from the tag's web page), `HealthSamplesEvent` `{ type, samples }`, `AlarmEvent` `{ id, title?, seconds? }` (`seconds` for `repeated`: the new countdown).
- Routing: `notifications`/`action` goes to the hob that sent the notification (see Notifications). `nfc`/`scanned` of a Hobwork tag goes only to the hob that owns the tag (triggers without `url`, or whose `url` matches the tag URL), with a `trigger` warning in its log when it has no matching trigger. `alarms/*` go to the hob the app names in the event (`hob`, which the host put in the command's args, or the page's hob for alarms set from the web bridge), only to its matching triggers and without a warning when there is none. `nfc`/`scanned` of any other link, `focus`/`changed` and `health`/`samples` go to every hob whose deployed version declares a matching trigger; for other links only triggers with a matching `url` match, so hobs that only handle their own tags never see them. Events with invalid data (a label over 64 characters, an unknown Health type, more than 500 samples, an unknown tag, a scan without a tag or a URL, a URL over 8,192 bytes, more than 16 records, a record over 8,192 bytes or of another type) are dropped, as are events from devices whose owner is off the allowlist. The events endpoint takes bodies up to 1 MB.
- **Alarm events**: the app reports a ring (`fired`), Stop (`stopped`) and the repeat button (`repeated`) of alarms that have a hob. AlarmKit runs the alarm's `stopIntent` and `secondaryIntent` (`AlarmEventIntent`, a `LiveActivityIntent`) in the app, launching it in the background when needed, and the Live Activity's buttons do the same; while the app runs it also watches `AlarmManager.alarmUpdates` (alerting means fired; alerting to countdown means repeated; alerting to gone or scheduled means stopped). `AlarmEventReporter` keeps the last state per alarm in the app group (`alarm-states.json`) so each ring is reported once, and reports `fired` just before `stopped` or `repeated` when the app was not running at the ring, so `fired` can be late. Events go to the host like other events and to open pages of the hob as bridge events. Stop and repeat count as using the device (`last_active_at`).
- Health samples come from background delivery (`HKObserverQuery`) in batches of at most 500, each sample once (an `HKAnchoredObjectQuery` anchor per type).
- **Scans while a hob page is open**: a Hobwork tag link the app opens (iOS background tag reading, a universal link) or a tag the Scan NFC Tag action reads still runs the triggers, and when a page of the hob that wrote the tag listens for `nfc.scanned` (the app asks the host with `POST /api/devices/nfc/lookup`), that page gets `nfc.scanned` `{ url, tag?, records? }` and the app stays on it instead of showing "Tag scanned". A scanned link to a hob's own origin goes to a listening page on that origin the same way. Links to hob origins that open the app as universal links (a tag read in the background, a QR code, another app) go to an open page of that hob as `link.opened`, or as `nfc.scanned` to a page that only listens for that, and load in the web view otherwise (see [Links to hob pages](#links-to-hob-pages)).
- **NFC scans** of Hobwork tags come from the app's "Scan tag" button, from `hobwork://nfc/<tag>`, from a universal link to `https://<public host>/nfc/<tag>`, or from iOS background tag reading, which opens the URL in Safari when there is no universal link. Universal links need the app built with that domain in Associated Domains (build setting `HOBWORK_APPLINKS_HOST`, empty by default); the host serves `/.well-known/apple-app-site-association` with `applinks.details: [{ appIDs: [<HOBWORK_APPLE_APP_ID, default 63QQLP356Q.dev.bgenc.hobwork>], components: [{ "/": "/nfc/*" }, { "/": "/devices/paired" }] }]` and `webcredentials: { apps: [<same app ID>] }` (which `ASWebAuthenticationSession` needs to finish on a universal link). The app adds `webcredentials:<host>` with `applinks:<host>` in Associated Domains and uses the universal link for pairing when the host it pairs with is `HOBWORK_APPLINKS_HOST`.
- **Scan event data** from the app: `{ tag, records? }` for a Hobwork tag of its host, `{ url, records? }` for any other link. The host also treats a `url` of the form `<public URL>/nfc/<tag>` as that tag. `records` is `[{ type: "url" | "text" | "other", value }]` as in `nfc.read()`; the app sends at most 16 and leaves out records over 8,192 bytes. A tag without a URL record sends nothing.
- **Tags with other links**: iOS background tag reading opens a link in Safari (or the app that claims it), and an app can only claim universal links of domains whose `apple-app-site-association` lists it, so Hobwork cannot take over taps of tags with `https://example.com/...`. What works instead:
  - The app's "Scan tag" button reads any tag and sends its first link with the records.
  - The App Intent "Scan NFC Tag" (`ScanTagIntent`, `supportedModes: .foreground(.immediate)`, also an App Shortcut) opens the app and does the same, for the Action Button, Control Center (the Shortcuts control) or Siri. Core NFC scans need the app on screen, so this cannot run in the background.
  - The App Intent "Send Tag to Hobwork" (`SendTagIntent`, `supportedModes: .background`) takes a link and posts the scan event with `POST /api/devices/events` without opening the app. In the Shortcuts app, a personal automation "When I tap an NFC tag" (for one tag, which Shortcuts identifies by the tag's serial number and not its content) runs it with the link typed in, so any tag, even one without a link, runs hobs with a single tap. The event cannot tell a tap from a shortcut run by hand, so handlers should not treat it as proof that someone was at the tag.
- **Tag page** `GET /nfc/<tag>`, rendered by the host: an unknown tag answers 404. Without a session the page shows a link to `hobwork://nfc/<tag>` and a sign-in link that returns to the page, and records nothing. For a signed-in person it records the scan (`device: null`) and redirects (303) to `/nfc/<tag>?scanned`, which shows the result, so reloading does not scan again. A request from another site (`Sec-Fetch-Site` missing or other than `none` or `same-origin`, or a foreign `Origin`) only gets a "Run it" button that posts to the same URL.

#### Live Activities

A hob shows something that runs (a print, a dryer, a timer, what someone holds in their hand) on the Lock Screen and in the Dynamic Island of iPhones and iPads. Code: `server/src/devices/live-activities.ts`, tables `live_activities` and `live_activity_devices` and the column `devices.live_activity_start_token` from `0044_live_activities.sql`; app: `HobworkActivityAttributes` and the `LiveActivities` manager.

- **Calls**: `ctx.person(id).liveActivities.start(activity)` (devices of the person that report `liveActivities`, `devices: "all" | "lastActive"`) or `ctx.device(name).liveActivities.start(activity)` returns `{ id, devices: [{ device, delivery: "app" | "push" | "queued" } | { device, error }] }`. `ctx.liveActivities.update(id, changes)` / `.end(id, { content?, dismissAt? })` reach every device that shows it, `ctx.person(id).liveActivities.update/end` and `ctx.device(name).liveActivities.update/end` only theirs; they return `{ updated | ended, devices }`, false when no device shows it. Types in `packages/sdk/src/live-activities.ts`.
- **Content** (`LiveActivityContent`): `title` (64 characters), `subtitle` (120), `swatches` (up to 4 `#RRGGBB`), `icon` (an SF Symbols name), `tint`, `endsAt` and `startedAt` (ISO; the countdown, "ends 19:10" and the progress bar run on the device), `progress` (0 to 1), `value` and `valueLabel` (big text instead of the countdown, "41%" / "paused"), one `button` `{ title (24), route, method?, body?, opensApp? }`, `open` (path a tap opens), `data` (4 KB, host only), `staleAt`, `relevance`. Changes merge into the content and `null` removes a field. The button's route and body stay on the host: a tap is the event `liveActivities`/`action`, and the host runs the route of the deployed version like a notification action (`ctx.caller` the person and device, body `button.body` or `{ activityId, data? }`). The app only gets `{ title, opensApp? }`.
- **IDs**: `id` is the hob's key (letters, digits, `-_.:`, 64). The host gives each run a UUID, which devices know it by (`HobworkActivityAttributes.id`). Starting a key that runs replaces the content and adds devices; one that ended starts a new run with a new UUID, so reports about the old one cannot touch it. One activity per key per device.
- **Delivery**: an app on its socket gets `call` `liveActivities.start | update | end` and runs ActivityKit itself (`Activity.request(..., pushType: .token)`). Otherwise the host pushes through the relay (relay kind `liveactivity`): a start goes to the device's push-to-start token, updates and ends to the token of the activity on that device. The app registers both kinds of ActivityKit token with the relay under this pairing's grant and tells the host only the relay's IDs (events `liveActivities`/`startToken` and `liveActivities`/`state`), since hosts never see APNs tokens. A device whose activity has no token yet (started by push, the app not woken yet) gets the latest content once the app reports it (`queued`). A grant that changes takes its activity tokens with it.
- **Privacy**: Live Activity pushes are decoded by ActivityKit, not the notification service extension. The host seals `{ v: 1, sentAt, expiresAt: 0, aps: {}, hobwork: { liveActivity: { hob, id, state } } }` like every push, the relay puts the envelope in `content-state` (and for a start in `attributes`), and `HobworkActivityAttributes` and its `ContentState` decode by opening it with the pairing keys from the shared Keychain, in whichever process ActivityKit decodes them (the widget extension, the app). When it does not open they show "Hobwork" / "Open Hobwork to see this.". The relay and Apple see the token, the times (`timestamp`, `stale-date`, `dismissal-date`), the relevance score and the size bucket; a push-to-start alert shows the relay's text "A hob started a Live Activity.". No expiry or repeat check applies, since ActivityKit decodes the same content again for hours, and ActivityKit itself drops pushes whose `timestamp` is not newer than the last one (the host keeps its timestamps increasing).
- **Budget**: iOS gives each app a budget of priority 10 Live Activity pushes per hour that Apple does not publish (`NSSupportsLiveActivitiesFrequentUpdates` raises it unless the person turns "More Frequent Updates" off; `status().frequentPushes` in the bridge). Priority 5 pushes are not budgeted but arrive when the system chooses. The host sends a change of anything but `progress` at once at priority 10; a progress-only change goes at priority 5, and only when it moved by at least 2 percentage points or 5 minutes passed since the last push, else it waits (`queued`) and the minute tick sends the latest content once 5 minutes are up. Apps on their socket get every update at once. Countdowns and time-based bars need no updates.
- **8 hour limit**: iOS ends an activity 8 hours after it started and keeps it on the Lock Screen up to 4 more hours. The host keeps when each device's activity started, and 7 h 45 min in: with `pastLimit: "restart"` (default) it ends it (dismissed at once) and starts a new one with the same content by push-to-start (or over the socket), which needs a start token; with `pastLimit: "stillRunning"`, or when a restart cannot be sent or fails, it sends a last update with `stillRunning: true`, which the app shows as "Still running, ends 06:40", the end time large with "ends" under it and no countdown.
- **Dismissed**: the app reports `dismissed` when the person swipes one away. That device is skipped (error `dismissed`) for the rest of the run, also by a new start of the same key, until the activity ends. `ended` (iOS ended it, or the app's own end) stops updates there.
- **End**: `dismissAt: "now"` removes it at once, an ISO date-time (within 4 hours) then, and the default leaves it to iOS. Ended runs are deleted a day later.
- **Per-person settings** (on/off, a "show from" window) are hob data. `DeviceInfo.capabilities` lists `liveActivities` while the person allows Live Activities for Hobwork (`ActivityAuthorizationInfo().areActivitiesEnabled`).

#### Widgets and intents

- **Widget**: `"widget": { "route": "/widget" }` in `hobwork.json` names a GET route (the pipeline checks that one matches). The app's widget (Home Screen small and medium, Lock Screen rectangular and inline) is configured with a hob, fetches `GET /api/devices/widgets/<hob>` with the device token from the shared Keychain, and the host runs the route of the deployed version with `ctx.caller` = the device's owner and the device. The answer is `WidgetContent` (`packages/sdk/src/widgets.ts`): `title` (64), `subtitle` (120), up to 6 `lines` `{ text (80), detail? (40), swatches? (4) }`, `swatches` (8), `open`, `refreshAt`. The host cuts long text, drops invalid fields and lines, and clamps `refreshAt` to 5 minutes to a day ahead (default 30 minutes); a missing title or a failing route answers 502 and a `warn` line in the hob's log, and the widget keeps showing its last content. `ctx.person(id).widgets.reload()` / `ctx.device(name).widgets.reload()` asks devices that report `widgets` to fetch again: `call` `widgets.reload` over the socket, else a background push `hobwork: { reloadWidgets: true }` (iOS throttles and drops these, so a widget may wait for its timeline).
- **Intents**: `"intents": [{ id, title, route?, method?, parameters?, opensApp?, open? }]` (at most 32; each needs `route` or `open`; parameters `{ id, title, type: "text" | "number" | "boolean", optional? }`, at most 4). The app lists them from `GET /api/devices/hobs` as entities of the App Intent "Run Hob Action" (Shortcuts, Siri, Spotlight, the Action Button) and of the Control Center control "Hob Action"; "Open Hob Page" and the control "Hob Page" open a hob at a path. Running one is `POST /api/devices/intents`: the host checks the parameters and runs the route (default POST) with body `IntentRequest` `{ intent, parameters }` and `ctx.caller`; the route answers `IntentResult` `{ say?, open? }`. `say` is what Siri says or Shortcuts shows, `open` (or the intent's `open` with `opensApp`) opens the app there. An intent with only `open` opens the page without the host running anything. This is the endpoint the Siri catch-all also needs: it runs a handler and returns what Siri says.

#### Share targets

"Share to Hobwork" in the iOS share sheet sends a link, text or files from another app to a hob. Code: `share` in `hobwork.json` (`ShareEntry` in `server/src/runtime/config.ts`), `server/src/devices/hob-surfaces.ts` (`startUpload`, `uploadChunk`, `runShare`), `packages/sdk/src/share-targets.ts`; app: the `HobworkShare` extension (`apple/ShareExtension/`) and `apple/Hobwork/Shared/Share/`.

- **Declaring**: `"share": [{ "id": "queue", "title": "Add to the queue", "accepts": { "urls": true, "files": ["model/3mf", ".3mf", "image/*"] }, "upload": "inbox", "route": "/share" }]` (at most 16). `accepts` takes `urls` (http and https links), `text` and `files` (MIME types or extensions, matched like `uploads` types); `files` needs `upload`, an upload of `uploads`, whose folder the files go into. The pipeline checks that `route` matches a POST route and `upload` names an upload, and refuses duplicate IDs.
- **Running**: the extension uploads each file the target takes with the device endpoints (see `docs/device-protocol.md`), then `POST /api/devices/share`; the host checks each file is stored under the upload's prefix and runs the route of the deployed version with `ShareRequest` `{ target, url?, text?, files: [{ path, name, size, contentType }] }` and `ctx.caller` the device's owner and the device. The route answers `ShareResult` `{ say? }` (1,000 characters), which the sheet shows; without it the sheet says "Sent to <title>.". The upload's triggers run too, as for `files.upload` from the app. The host names each file: the original name made a valid path segment (`Headphone stand (v2).3MF` becomes `Headphone-stand-v2.3mf`), with `-2`, `-3` added when a file or an unfinished upload already has that path, so a share never replaces a file.
- **Extension**: lists the targets that take something of what was shared (a target for text also gets a link as text when it takes no links; text that is only a link counts as the link), grouped by hob, the last choice selected (`share.lastTarget` in the app group's defaults). It shows the cached hob list (`share-targets.json` in the app group) at once and asks the host again with the device token from the shared Keychain. A file over the target's `maxBytes` is refused before anything is sent. Progress shows per part, then "Sending to <hob>…", then the route's `say`.
- **Limits**: share extensions get about 120 MB of memory. Files arrive from `NSItemProvider.loadFileRepresentation` as a temporary file, which the extension copies to its own temporary folder (file to file), and parts of 8 MB are read from it one at a time, so a 200 MB 3MF needs about 8 MB. The upload runs while the sheet is open, in the foreground: the protocol has three steps (start, parts, route), and a background `URLSession` would run only the parts after the sheet closes, with nobody to call the route; the sheet says to keep it open, and Cancel drops the upload on the host. A part that fails is retried after asking the host where the upload stands (3 times). On a LAN 200 MB takes seconds; over a slow uplink it takes as long as it takes, see `docs/todo.md`. iPhone and iPad only.

#### Links to hob pages

`https://<hob>.<apps host>/spool/78` opens the Hobwork app when it is installed and built for the host (in Safari otherwise), as do links to branch previews. Code: `server/src/apps/app-links.ts`, `apple/Hobwork/Web/HobLinkRouter.swift`, `apple/Hobwork/Shared/Hobs/HobLinks.swift`.

- **Association**: the app's Associated Domains have `applinks:*.<apps host>` next to `applinks:<host>` (build setting `HOBWORK_APPS_HOST`, `apps.<HOBWORK_APPLINKS_HOST>` by default; see `apple/README.md`). For a wildcard domain iOS reads `/.well-known/apple-app-site-association` from the apps host itself, so the host answers that path on `apps.<host>` (the only path it answers there; every other request to the apps host is still refused) and on every hob origin, without a session. The apps host needs DNS and a TLS certificate of its own: `*.apps.<host>` does not cover `apps.<host>`.
- **Paths**: `components` exclude `/api/*`, `/_hobwork/*` (the sign-in callback must stay in the browser), `/theme/*` and `/.well-known/*`, then (on a hob origin) the hob's `static` directories and its `appLinks.exclude`, and include its `appLinks.include` (default `/*`). `"appLinks": { "include": ["/spool/*", "/bin/*"], "exclude": ["/print/*"] }` in `hobwork.json`, patterns with `*` and `?` as in the association file, at most 32 each. iOS only reads the apps host's file, which no hob's rules can be in, so `GET /api/devices/hobs` lists each hob's rules (`appLinks`) and the app applies them: a link to an excluded path opens in an in-app Safari view (`SFSafariViewController`, which never hands it back as a universal link). The app keeps the rules for 5 minutes and waits at most 5 seconds for them, then uses the defaults.
- **In the app**: a link to a hob origin goes to an open page of that hob (same origin, so the same branch) that listens for `link.opened`, as `{ url, path }` (`path` with the query), and the app stays on that page; to a page that only listens for `nfc.scanned` as a scan (the triggers run, as before links opened the app); otherwise the web view loads it, signing in as for any hob page. So `/spool/78` from an NFC tag read in the background reaches the open page, which decides what to show. Query forms such as `/?spool=78` are the hob's to handle.
- The redirect from old links on other sites (for example Home Assistant dashboard URLs on existing tags) to a hob is set up on that site, not in Hobwork.

### Web bridge

Hob UIs in the Apple apps' web view reach native features through `window.hobworkNative`, which `@hobwork/sdk/native` wraps in a typed API (`apple/Hobwork/Web/Bridge/`, `packages/sdk/src/native/`). In a browser the object is missing, `native.available` is false and every call rejects with `NativeError` code `unavailable`, so the same UI works in both.

- **Who gets it**: a user script (`BridgeScript.swift`, at document start, in every frame, page content world) defines the object only when the page's host is one label below an apps host (`apps.<Hobwork host>` or `apps.<parent>`, as `LinkPolicy` reads them). The script only keeps the object out of other pages; `NativeBridge` checks every message itself. The frame's security origin must be a hob app origin (`LinkPolicy.hobOrigin`: same scheme as the Hobwork host, `<hob>` or `<branch label>--<hob>` one label below the apps host; ports are not compared, since in development the web UI and the apps run on different ports). A main frame passes. A subframe passes only when the top-level page is the Hobwork origin (the web UI frames hob apps) or the same hob's origin. Everything else, the Hobwork web UI's own pages and other sites included, answers `unavailable`. Hob apps cannot be framed by other hobs or sites (`frame-ancestors`), so a hob frame inside the Hobwork page is that hob's own code. An apps host the app cannot derive from the Hobwork host (a custom `HOBWORK_APPS_URL` elsewhere) gets no bridge, as it gets no in-app links.
- **Protocol** (version 1): `hobworkNative` is frozen `{ version, platform: "ios" | "macos", capabilities: { <name>: [methods] }, call(capability, method, args), listen(event, listener) }`. `call` posts `{ capability, method, args, page }` to the `hobworkNative` script message handler (`WKScriptMessageHandlerWithReply`) and resolves with `{ ok: true, value }` or `{ ok: false, error: { code, message } }`; it does not reject on errors, so codes survive. Codes: `unavailable` (no such capability or method in this app or on this platform, or not set up), `denied` (the person said no), `cancelled` (the person closed the sheet or dialog), `failed` (anything else, bad arguments too). Arguments and values are JSON; files travel as base64 (`data`), which the SDK encodes from a `Blob`, `ArrayBuffer`, typed array or a same-origin URL it fetches with the page's session, up to 50 MB. `capabilities` lists what this build and device implement (a capability with no method here is left out), so `native.has('print', 'pickPrinter')` works without a call; authorization (notifications turned off) shows at call time.
- **Events**: `listen(event, listener)` registers the page with `{ capability: "bridge", method: "subscribe", args: { event } }` on its first listener for that event and unsubscribes after its last one. Each page load picks a random `page` ID, and the app keeps subscriptions per hob origin and page ID with the frame that sent them. A capability calls `context.emit("<name>", data)`, which reaches every subscribed page of the same hob as `<capability>.<name>` (`native.on('nfc.scan', fn)`): the app runs a script in that frame (`evaluateJavaScript(_:in:contentWorld:)`) that checks the page ID and `location.origin` again before calling the listeners, since the frame may have navigated, and drops the subscription when the page is gone. A new top-level page clears all subscriptions. Events only reach pages that are open. Events that belong to no capability: `link.opened` `{ url, path }` (see [Links to hob pages](#links-to-hob-pages)), which `native.links.onOpened(fn)` wraps.
- **Permissions**: a method that reads from the device without a system sheet the person confirms asks once per hob with a native alert ("Let “filament” read your clipboard?"), and the answer is kept in `UserDefaults` under `<apps host>/<hob>`, so branch previews share it with the hob. Concurrent calls share one alert. A refusal answers `denied` until the person changes it under Settings, Hob Permissions, which lists every answer. An alert that cannot be shown is not remembered. Sizes are points; the SDK converts `mm` and `in`. Without `mediaSize` the paper is the PDF's first page size. iOS: `UIPrintInteractionController` with the PDF as `printingItem`; the delegate picks `UIPrintPaper.bestPaper(forPageSize:withPapersFrom:)`, and `paper` is the paper the printer chose. `printer` (a printer URL) preselects that printer in the dialog (`UIPrintInfo.printerID`), and with `dialog: false` the PDF goes straight to it (`print(to:)`). The printer used (`printInfo.printerID`, named with `contactPrinter`) is remembered for the hob. `printers()` lists the remembered ones, most recent first (at most 10), `forgetPrinter({ id })` removes one, and `pickPrinter({ printer? })` (iOS) opens `UIPrinterPickerController` and remembers the choice. iOS has no API to list printers or their papers without the picker or a print, so media lists are not offered. macOS: `PDFDocument.printOperation` with zero margins, no scaling and the paper size, as a sheet on the window; printer IDs are printer names (`NSPrinter(name:)`). Cancelling answers `cancelled`.

Popovers (iPad, macOS) point at the middle of the web view's bottom (iPad) or top (macOS) edge, since the page's button is inside a frame whose position the app does not know.

Local writes need `url`. Failures are `cancelled` or `failed` with `reason` (`not_writable`, `too_small`, `verify_failed`, `busy`); errors carry `reason` in the reply (`{ code, message, reason? }`, `NativeError.reason`). Sessions: `startSession({ alertMessage?, successMessage?, keepOpen? })` → `{ session }` keeps one sheet open and emits `nfc.tag` `{ session, records, uid?, tag? }` for each tag (a tag left on the reader counts once until another tag comes or 3 seconds pass; after each tag the app calls `restartPolling`), and `nfc.ended` `{ session, reason: "stopped" | "timeout" | "cancelled" | "failed", message? }` once; `updateSession({ session, alertMessage })` changes the sheet text; `stopSession({ session, successMessage? })` closes it. iOS ends a reader session after 60 seconds (`timeout`), so pages start a new one. One session at a time (`busy`). The SDK wraps these in `native.nfc.session({ onTag, onEnd, ... })`. `nfc.scanned` is a scan from outside the page (see Scans while a hob page is open). On devices without NFC (iPads, Macs) the methods are only `read` and `write`, and they need `device`: a device name or `"lastActive"`. The app then calls `POST /api/devices/handoff` and the person's iPhone gets the prompt push `Write an NFC tag` / `<hob> on <iPad> is waiting. Tap to write the tag with this device.`; tapping it opens the app and the scan sheet, and the result comes back to the page. The page's call waits for all of it, up to 2 minutes (the host's wait for foreground commands), and gets `failed` with reason `timeout` after that, while the phone may still write until the command expires 10 minutes later. Expect 5 to 30 seconds in practice: a push, a tap, the sheet, the tag.
  - **alarms** (iOS): `set`, `timer`, `reschedule`, `cancel`, `list` as the device capability (`AlarmsBridge` over `AlarmsCapability`), with the page's hob as the alarm's hob. A hob only lists, changes and cancels its own alarms (cancelling another's ID does nothing; `reschedule` answers `unknown_alarm`). Without AlarmKit authorization the call asks iOS first and answers `denied` when it is refused. Events: `alarms.fired`, `alarms.stopped`, `alarms.repeated` `{ id, title, seconds? }` to the hob's open pages (on its own origin and branch previews).
  - **camera** (iOS; not on Macs, so `has('camera')` is false there): `startScan({ symbologies?, multiple?, torch?, guidance?, regionOfInterest?, shutter?, photo?, buttons? })` → `{ session }` presents VisionKit's `DataScannerViewController` full screen over the web view (`CameraBridge`, `VisionKitCamera`), always dark, with a close and a torch button at the top, the page's `guidance` text in a pill, up to 3 page buttons (`{ id, label }`) and, with `shutter`, a shutter button at the bottom. The page draws nothing over the camera: a web layer over a native viewfinder would need a transparent web view and touches routed between the two, so the page names its controls instead. `symbologies` are `ean13`, `ean8`, `upca`, `upce`, `code39`, `code93`, `code128`, `itf14`, `i2of5`, `codabar`, `gs1DataBar`, `qr`, `microQR`, `dataMatrix`, `pdf417`, `microPDF417`, `aztec`, `msiPlessey` (none: every kind). Vision reads UPC-A as EAN-13 with a leading 0, so with `upca` asked for those come back as `upca` with 12 digits. `regionOfInterest` and code `bounds` are fractions of the camera view. Events, each with `session`: `camera.codes` `{ codes: [{ id, payload, symbology, bounds }] }` whenever codes come or go (position changes at most every 200 ms), `camera.button` `{ id }`, `camera.photo` (a shutter photo, as `capture` answers), `camera.torch` `{ on }` (the person switched it), and `camera.ended` `{ reason: "selected" | "stopped" | "cancelled" | "failed", code?, message? }` once. Without `multiple` the first code read ends the scan (`selected`); with it the scan reports every code in view and ends when the person taps one. `updateScan({ session, guidance })` changes the text (VoiceOver reads it out), `setTorch({ session, on })` uses `AVCaptureDevice.torchMode`, `capture({ session, maxDimension?, quality? })` → `{ data, type: "image/jpeg", width, height }` takes a still with `capturePhoto()` without ending the scan (scan a barcode, then photograph the label), and `stopScan({ session })` closes it. `photo({ maxDimension?, quality? })` takes one photo with the system camera (`UIImagePickerController`), `cancelled` when the person closes it. Photos are not uploaded by the app: the page sends the `Blob` with `files.upload` (see [Files](#files)) or in a route body when it is small, since the page already knows where it belongs and the session to send it with. Errors: `denied` (the per-hob question or iOS's camera access), `unavailable` with `reason` `unsupported` (no `DataScannerViewController.isSupported`: devices before the A12 chip and the simulator; methods are then left out of `has()`) or `restricted` (Screen Time), `failed` with `reason` `busy` (one scan or photo at a time). The SDK wraps the scan in `native.camera.scan({ onCodes, onButton, onPhoto, onTorch, onEnd, ... })` → `{ ended, stop, capture, setTorch, setGuidance }` and `native.camera.scanCode(options)` → the code or null.
  - **liveActivities** (iOS): `status()` → `{ enabled, frequentPushes }` (`ActivityAuthorizationInfo`). `start(activity)` → `{ id }` posts `POST /api/devices/live-activities` `{ hob, op: "start", args }`; the host records the activity for this device and answers `{ id, activity: { hob, id: <UUID>, state, staleAt?, relevance? } }`, and the app starts it with ActivityKit right away (the page is in the foreground, which a local start needs). `update({ id, changes })` and `end({ id, content?, dismissAt? })` post `op: "update" | "end"` and answer the host's `{ updated | ended, devices }`, reaching every device that shows it. `denied` when Live Activities are off for Hobwork, `unavailable` in branch previews (the button runs the deployed version's route). Not sensitive: the person sees it on the Lock Screen and can turn Live Activities off.

- **Offline storage**: the web view uses the persistent `WKWebsiteDataStore.default()`, so each hob origin's `localStorage`, IndexedDB and Cache API data survive app restarts and updates; signing out of the app clears them with the cookies. WebKit may still evict data under storage pressure, so the host stays the source of truth: a hob keeps its last copy of the data and a queue of unsent writes in IndexedDB or `localStorage` and sends the queue when requests work again (hob work). Service workers do not run in the app: WKWebView runs them only for app-bound domains (`WKAppBoundDomains` in Info.plist), a fixed list of at most 10 domains built into the app, which cannot name each person's Hobwork host, and turning that on would also limit the web view to those domains. Offline support in the app therefore cannot rely on a service worker; in Safari and other browsers a hob may still use one (with `worker-src` in `csp`).

### Push relay

`relay/` (Rust: axum, tokio, rusqlite, reqwest; not part of the pnpm workspace) is the service that sends APNs pushes for every host, since only a key of team 63QQLP356Q can push to `dev.bgenc.hobwork` (why and the parts not built yet: "Push relay" in `docs/todo.md`). It ships as one binary and a Dockerfile, CI publishes the image as `ghcr.io/barmore-genc/hobwork-relay` (tags `main`, versions and `sha-<commit>`), and it runs at `relay.bgenc.dev` behind Cloudflare and Caddy on a VPS. Hosts are not trusted: a host pushes only to devices whose app granted its sidecar key, never sees APNs tokens, and cannot choose the text a push shows before the app decrypts it. See `relay/README.md` for running it.

- **Settings**: `HOBWORK_RELAY_APNS_KEY_FILE` (the `.p8` key) and `HOBWORK_RELAY_APNS_KEY_ID` (required), `HOBWORK_RELAY_APNS_TEAM_ID` (default `63QQLP356Q`), `HOBWORK_RELAY_APNS_TOPIC` (default `dev.bgenc.hobwork`), `HOBWORK_RELAY_APP_ID` (App Attest app ID, default `<team>.<topic>`), `HOBWORK_RELAY_LISTEN` (default `0.0.0.0:8080`), `HOBWORK_RELAY_DB` (default `data/relay.db`, `/data/relay.db` in Docker), `HOBWORK_RELAY_TRUSTED_PROXIES` (IPs and CIDR ranges whose `X-Forwarded-For` names the client).
- **Code**: `api.rs` (routes, auth, the push endpoint), `apns.rs` (the APNs client, ported from the host's earlier `apns.ts`: HTTP/2 over rustls, sandbox and production origins, ES256 provider tokens renewed every 40 minutes or on `ExpiredProviderToken`, 5 idle minutes per connection, a 10 second timeout with one retry on a new connection pool), `attest.rs` (App Attest attestations and assertions, Apple's root in `certs/`), `store/` (the `Store` trait and its SQLite implementation, migrations in `migrations/`), `limits.rs` (in-memory token buckets), `payload.rs` (every APNs payload and its visible text), `tasks.rs` (renewal pushes and cleanup every 5 minutes).
- **Encoding**: JSON bodies, camelCase. Binary values (keys, attestations, assertions, signatures, ciphertext) are standard base64; IDs, secrets, nonces and challenges are opaque base64url strings; APNs tokens are hex. Errors answer `{ error, message }` with a code: `bad_request`, `unauthorized`, `rate_limited` (429), `bad_token` (APNs refuses the token), `push_failed` (502, with `apnsStatus` and `reason`), `attested_token` (409), `bad_challenge`, `bad_attestation`, `assertion_required`, `bad_assertion`, `bad_nonce`, `nothing_pending`, `not_active`, `unknown_grant` and `unknown_activity` (404), `gone`, `expired` and `activity_gone` (410), `bad_signature` (401), `too_large` (413), `internal`.
- **Older apps**: registration and token change bodies may carry a `filtering` field, which the relay ignores.
- **App auth**: `Authorization: Bearer <registration secret>`. An attested registration also needs `Hobwork-Assertion`: base64 of the App Attest assertion over the client data `<METHOD>\n<path>\n<hex SHA-256 of the body>`. The relay stores the counter and refuses an assertion whose counter is not above it, so the app sends these requests one at a time.
- **Registration**: `POST /v1/registrations` `{ token, environment: "sandbox" | "production", attestation?: { keyId, object, challenge } }` answers 201 `{ id, secret, status: "pending" }` and sends the ownership proof: an alert with `mutable-content`, `interruption-level: passive`, collapse ID `hobwork-proof` and `{ hobwork: { v: 1, proof: <nonce> } }`, with the fallback text "Notifications from Hobwork are set up.". The app answers `POST /v1/registrations/<id>/proof` `{ nonce }` within 5 minutes (200 `{ status: "active" }`), or asks for a new nonce with `POST /v1/registrations/<id>/proof-push` (204). A registration without a confirmed token is deleted after a day.
- **App Attest**: `POST /v1/attest/challenges` answers `{ challenge }` (5 minutes, single use). The app calls `attestKey` with `clientDataHash` = SHA-256 of the challenge string's UTF-8 bytes. The relay checks the chain to Apple's App Attest root, the nonce, the app ID, a zero counter, the credential ID and the environment (`appattestdevelop` for `sandbox`, `appattest` for `production`). A registration without an attestation is refused (`attested_token`) for a token that an attested registration holds.
- **Token changes**: `PUT /v1/registrations/<id>` `{ token, environment }`. The same token answers 200 `{ status: "active" }`; a new one answers 202 `{ status: "pending" }` and sends a proof push, and it takes effect when the proof comes back. Confirming a token deletes any other registration that held it. `GET /v1/registrations/<id>` answers `{ id, status: "pending" | "active" | "gone", environment, attested, grants: [{ id, pairing, expiresAt }] }`; `DELETE /v1/registrations/<id>` (204) deletes it with its grants.
- **Grants**: `POST /v1/registrations/<id>/grants` `{ pairing, publicKey }` (the sidecar's Ed25519 public key; `pairing` is an opaque ID of up to 128 bytes that the app picks per pairing) answers 201 `{ id, expiresAt }` and replaces any grant of the same pairing. Grants last 30 days. `POST /v1/registrations/<id>/grants/<grant>/renew` answers `{ expiresAt }` (410 `expired` once expired), `DELETE /v1/registrations/<id>/grants/<grant>` answers 204.
- **Activity tokens**: ActivityKit push tokens are APNs tokens, so hosts get opaque IDs for them. `POST /v1/registrations/<id>/grants/<grant>/activity-tokens` `{ kind: "start" | "update", token: <hex> }` (the registration must be active, the grant its own, else 404 `unknown_grant`) answers 201 `{ id, expiresAt }`. A grant has one `start` (push-to-start) token, which a new one replaces, with `expiresAt: null`; `update` tokens (one running activity) last 13 hours, and a grant keeps its newest 16. Posting a token the grant already has with that kind answers its existing ID. `DELETE /v1/registrations/<id>/grants/<grant>/activity-tokens/<token>` answers 204, also for unknown IDs. They go with their grant, and expired ones are deleted by the cleanup task.
- **Renewal pushes**: from 15 days after a grant was made or renewed, the relay sends one push a day at a random time per registration, with `{ hobwork: { v: 1, renew: [<grant IDs>] } }` and collapse ID `hobwork-renewal`, as a background push (`content-available`, priority 5).
- **Sending**: `POST /v1/grants/<grant>/push` with `Hobwork-Timestamp` (Unix seconds, within 5 minutes), `Hobwork-Nonce` (16 to 64 base64url characters, single use per grant) and `Hobwork-Signature` (base64 Ed25519 signature by the grant's key over `hobwork-push-v1\n<timestamp>\n<nonce>\n<METHOD>\n<path>\n<hex SHA-256 of the body>`). Body: `{ kind: "alert" | "command" | "prompt", priority?: 1 | 5 | 10 (default 10), expiration?: <Unix seconds or 0, at most 30 days ahead, default a day>, collapseId?, keyId, ciphertext }`. The relay sends `{ aps: { alert: { title: "Hobwork", body: <fallback for the kind> }, "mutable-content": 1, sound: "default" (alert, prompt) or "interruption-level": "passive" (command) }, hobwork: { v: 1, grant, keyId, ciphertext } }` and answers 200 `{ apnsId }`, 413 `too_large` over 4,096 bytes, 502 `push_failed`, or 410 `gone` when APNs says the token is gone (410, `BadDeviceToken`, `DeviceTokenNotForTopic`): the registration then has no token, its grants answer `gone`, and they are deleted when the app confirms a new token. There is no queue.
- **Live Activity pushes**: kind `liveactivity` adds `activity` (an activity token ID), `event: "start" | "update" | "end"` and `timestamp` (Unix seconds), all required, and optional `staleDate`, `dismissalDate` (Unix seconds) and `relevanceScore` (a number of 0 or more); other kinds refuse these fields, and `liveactivity` refuses `collapseId` and priority 1. `start` needs the grant's start token, `update` and `end` an unexpired update token of the grant, else 404 `unknown_activity`. The relay sends `{ aps: { timestamp, event, "content-state": { hobwork: <envelope> }, "stale-date"?, "dismissal-date"?, "relevance-score"? } }`, where the envelope is `{ v: 1, grant, keyId, ciphertext }`; `start` adds `"attributes-type": "HobworkActivityAttributes"`, `attributes: { hobwork: <envelope> }`, `alert: { title: "Hobwork", body: "A hob started a Live Activity." }` and `"input-push-token": 1`. It goes to the activity token with `apns-push-type: liveactivity` and topic `<topic>.push-type.liveactivity`. When APNs says the activity token is gone, the relay deletes that token only and answers 410 `activity_gone`.
- **Limits**: per IP (IPv6 per /64), 10 registrations, token changes or proof pushes at once refilled at 20 an hour, and 30 grants, activity tokens or challenges refilled at 120 an hour; 5 proof pushes per registration refilled at 6 an hour; 60 pushes per grant refilled at 600 an hour, under a ceiling of 120 per registration refilled at 1,200 an hour. Bodies are at most 32 KB.
- **Logs**: the `events` table keeps the time, a client IP hash (HMAC-SHA256 with a key that is replaced every 7 days, first 16 bytes), the registration or grant ID, the action, the result code and the APNs status, for 14 days. Nothing logs tokens, secrets or IPs. `GET /privacy` serves `relay/PRIVACY.md`; `GET /health` answers `ok`.

#### Hosts and apps on the relay

How a host and the app use the relay. The relay sees grant IDs, key IDs and ciphertext, never what a push says or which host sent it.

- **Push keys**: the host holds an Ed25519 signing key and an X25519 encryption key (`server/src/devices/push/`, outside the data dir: `HOBWORK_PUSH_KEY_DIR`, default `<data dir>-push-keys`, so backups never contain them). Public halves are raw 32 bytes in standard base64: `signingKey` and `encryptionKey`. `keyId` is base64url, without padding, of the first 8 bytes of SHA-256 of the raw `encryptionKey`.
- **Relay setting**: `HOBWORK_PUSH_RELAY_URL` (default `https://relay.bgenc.dev`, `off` for no push). The app has its relay URL built in and uses push with a host only when the host's `relay` is exactly that URL, so a host cannot send the app's APNs token to a relay of its choosing.
- **Host to app**: the token exchange answer adds `push: { relay, signingKey, encryptionKey, keyId } | null` (null when the relay is `off`), and after every `hello` the host sends `{ type: "push", relay, signingKey, encryptionKey, keyId }` or `{ type: "push", relay: null }`.
- **App to relay**: one registration per device for all pairings, with the APNs token, attested with App Attest where the device supports it. The notification service extension answers the ownership proof push; the app answers it too when the extension could not. Per pairing the app makes an X25519 key pair and a grant for the host's `signingKey`, with a random `pairing` ID that says nothing about the host. A new `signingKey` gets a new grant, and the app deletes the old one. Renewal pushes renew the grants they list.
- **App to host**: `hello` carries `push: { grant, key } | null` (`key` is the app's X25519 public key for this pairing, raw 32 bytes in standard base64), and `PUT /api/devices/push` takes `{ grant, key }` or `{ grant: null }` (204). The host keeps both per device and forgets them when the relay answers `gone`.
- **Sealing**: the plaintext is the APNs payload the host would send itself plus times, `{ v: 1, sentAt, expiresAt, aps, hobwork }` (Unix seconds; `expiresAt` 0 for none). Its UTF-8 JSON is compressed with raw deflate, framed as a 4-byte big-endian length, the compressed bytes and zeros up to a multiple of 256 bytes, and sealed with ChaCha20-Poly1305 under a key from HKDF-SHA256 over the X25519 shared secret of the host's encryption key and the app's `key`, with salt = app key || host key (raw, 64 bytes) and info `hobwork-push-v1`, 32 bytes. The associated data is the grant ID as UTF-8. `ciphertext` is standard base64 of the 12-byte nonce, the ciphertext and the 16-byte tag (CryptoKit's `ChaChaPoly.SealedBox.combined`). `server/src/devices/push-vector.json` is a fixed example that the host and app tests both check.
- **Sending**: the host posts `{ kind, priority?, expiration, collapseId, keyId, ciphertext }` to `/v1/grants/<grant>/push`, signed with its signing key: `alert` for notifications, `command` for background commands, `prompt` for foreground ones, `background` (no alert, `content-available`, always priority 5) for withdrawals and widget reloads, `collapseId` = the notification or command ID, `expiration` = `expiresAt`. Live Activities use `liveactivity` with `{ activity, event, timestamp, staleDate?, dismissalDate?, relevanceScore? }` and no `collapseId` (see Live Activities). It checks the size of the push the relay will build before anything is sent (`too_large`).
- **Opening**: the extension finds the pairing by grant ID and the host key by `keyId`, opens the push, and drops it (showing the relay's text) when it does not open, when `expiresAt` has passed or `sentAt` is more than 5 minutes ahead, or when it already handled that notification or command ID, including over the socket. Then it rebuilds the notification from `aps` and handles `hobwork` as before.

## Home Assistant

The host keeps one WebSocket connection to HA, authenticated with a long-lived access token. The connection is pinged, and reconnects with exponential backoff (1s up to 60s) when it drops.

Connection settings (`server/src/homeassistant/settings.ts`, `homeassistant_settings` table):

- People set the URL and token in the web UI (Settings, Home Assistant), which shows the connection status, HA version and the last error, and has "Test connection" (a separate connection that signs in and closes, nothing saved) and "Disconnect" (forgets the token). Agents have no tool or API for any of it.
- The token is write-only: no response contains it. It is encrypted with AES-256-GCM using the secrets key (see [Secrets and network](#secrets-and-network)) with its own additional data. Keeping the saved token while changing the URL is refused, and a test only uses the saved token for the saved URL, so the token is never sent to an address someone typed in without also typing the token.
- Precedence: `HOBWORK_HA_URL` and `HOBWORK_HA_TOKEN`, when set, win over the saved setting, and the settings page shows the connection as set in the server configuration and cannot change it. The host operator's configuration is the explicit choice, and a page that looked editable but did nothing would mislead.
- Saving or disconnecting calls the client's `reload()`, which reads the setting again. Saving also reloads every hob's entry points, so triggers that failed while HA was not set up get subscribed.

### HA to Hobwork (triggers)

HA's WebSocket API has `subscribe_trigger`: the client sends a trigger definition in HA's own automation syntax, HA evaluates it, and pushes a message every time it fires. Hobwork uses this directly:

1. On deploy, the host reads the `homeassistant` triggers from `hobwork.json` and subscribes each one with `subscribe_trigger`.
2. A Zigbee button is pressed. ZHA or Zigbee2MQTT turns it into a device trigger, event or state change in HA. HA matches it against the subscription and pushes the trigger variables to Hobwork.
3. The host invokes the handler with the trigger variables, waking the hob VM if needed.

Any trigger HA supports works (device, state, numeric_state, event, zone, time, template), with the same syntax as in an HA automation, and HA does the filtering. The `homeassistant` block is passed to HA unchanged. HA accepts both the current `"trigger": "state"` key and the older `"platform": "state"`; templates and docs use `trigger`, and device triggers from `ha_list_device_triggers` (which use `platform`) work as they are. The handler receives HA's trigger variables (`{ trigger: { platform, entity_id, from_state, to_state, ... } }`), the same object `ha_listen` returns.

On deploy the host diffs the hob's triggers against its active subscriptions: unchanged triggers keep their subscription, changed ones are subscribed again, removed ones are unsubscribed. A trigger HA refuses (bad syntax, unknown device) is reported in the deploy result. On reconnect (e.g. HA restart) the host subscribes again. Triggers that fire while the connection is down are lost, and this is logged with the time range.

Agents find device IDs, entities and trigger payloads through the HA MCP tools. `ha_listen` lets an agent subscribe a trigger temporarily and ask the user to press the button, to see the real payload before writing the handler.

Home Assistant stays the source of truth for its own data. The MCP instructions and the template's `AGENTS.md` tell agents to read states, history and device details from HA instead of copying them into the hob DB, unless the user asks for a copy or the feature cannot work without one.

HA automations can also call a Hobwork webhook (`rest_command`), for anything easier to express on the HA side.

### Hobwork to HA (actions)

Handlers get `ctx.ha` (`packages/sdk/src/homeassistant.ts`): `callService(domain, service, data?, target?, { returnResponse? })`, `getState(entityId)` (undefined for an unknown entity), `getStates({ domain?, entityIds? })` and `fireEvent(type, data?)`. Calls go through the host, so the HA token never enters a VM and VMs do not need access to the LAN. Announcements on Google Home speakers are `tts.speak` or `media_player.play_media` calls.

- **Transport**: the runner POSTs `HaRequest` (`packages/sdk/src/runner/protocol.ts`) with the invocation ID to `http://hobwork.internal/v1/ha`, and the host answers it with its HA client (`server/src/homeassistant/internal.ts`). Failures answer `{ ok: false, error: { code, message } }` with HA's code and message, or Hobwork's (`not_configured` and `not_connected` 503, `timeout` 504, `read_only` 403, `bad_request` 400). The SDK throws them as `HomeAssistantError`. The runner and the handler bundle each have a copy of that class, so its `instanceof` checks a `Symbol.for` brand.
- **Timeouts and retries**: the host waits 10 seconds for HA by default. Every call takes `{ timeoutMs }` (at most 60 seconds, `bad_request` otherwise), which the host passes to its HA client. The runner retries `getState` and `getStates` twice after `timeout`, `connection_lost`, `not_connected` or `host_error`, waiting 0.5 and 1 second. `callService` retries only with `{ retries }` (at most 5): a call that timed out may still have run in HA, and Hobwork cannot tell a reading service like `recorder.get_statistics` from `light.toggle`. `fireEvent` never retries.
- **Logs**: every call is logged with its invocation, as a `runtime` line: service calls and events at `info`, reads at `debug`, failures at `warn`. The host checks that the invocation belongs to the VM's hob, and the lines count toward the invocation's 1,000 line limit.
- **Allowed services**: a hob calls only the services on its list (`project_ha_services`: a domain like `light` or one service like `light.turn_on`), which is empty for new hobs. `haResponse` checks it on every call, for the deployed version and previews alike (`server/src/homeassistant/services.ts`). A refused call answers `not_allowed` (403), which the SDK throws as `HomeAssistantError`, and is logged as a `warn` line ("Home Assistant: denied light.turn_on. This hob may not call ... People change this on the hob's Home Assistant page in Hobwork"). `hassio.*`, `homeassistant.*`, `shell_command.*`, `recorder.purge` and `recorder.purge_entities` are blocked for every hob even when listed, and cannot be added to a list. People edit the list on the hob's Home Assistant page (`GET|PUT /api/projects/<name>/home-assistant-services`), agents with `update_ha_services` (add and remove entries, with the same hob access as other tools); `get_hob` shows it. Changes are written to the hob log with who made them. Agents can add entries, so the list limits what a bug in a handler can do, not what a compromised agent can do. The same list holds the events a hob may fire, as `event:<type>` entries (type case is kept; letters, digits, `_`, `.`, `-`). `fireEvent` of an unlisted type answers `not_allowed` and is logged as a `warn` line. Events Home Assistant uses for itself are blocked even when listed: `homeassistant_*`, `hassio_*`, `*_registry_updated`, `call_service`, `state_changed`, `service_registered`, `service_removed`, `component_loaded`, `core_config_updated`, `themes_updated`, `panels_updated`, `logbook_entry`, `automation_triggered`, `automation_reloaded`, `script_started`, `scene_reloaded`, `user_added`, `user_removed`, `mobile_app_notification_action` and `shopping_list_updated`. Hobs that existed before the events (migration 0032 queues them in `project_ha_events_backfill`) get the types of `fireEvent('type')` calls with string literals in the deployed source and of `Home Assistant: fire event <type>` log lines on the first start, like the services. Hobs that existed before the list (migration 0029 queues them in `project_ha_services_backfill`) get, on the first start, the domains of the `callService('domain', 'service')` calls with string literals in the deployed source (`.js`, `.ts`, `.tsx`, not tests or `node_modules`) and of the `Home Assistant: domain.service` lines in their log, minus blocked domains. Calls that name the domain in a variable cannot be read from source; the hob log says so when the code has some. A hob whose code cannot be read is tried again on the next start.
- **Branch previews** read states. Service calls and events answer `not_approved` (403) unless "Let this branch control Home Assistant" is on for that branch. People turn it on on the hob page (`PUT|DELETE /api/projects/<name>/branches/<branch>/home-assistant`), agents with the `set_branch_home_assistant` MCP tool; `branch_ha_approvals` stores who (user or agent) and when, and the hob page shows it. This keeps work in progress from switching real devices by accident. It is not a boundary against agents, which can merge to `main` anyway. It is checked on every call, so turning it off applies right away. A denied call is logged as a `warn` line with the invocation (`Home Assistant: denied light.turn_on ... Turn it on with the set_branch_home_assistant MCP tool ...`), so the agent sees why.
- **Workspaces** read states only (`getState`, `getStates`, also as `hobwork ha state` and `hobwork ha states`). Code run there is work in progress and tests, and a test that switches off the heating by mistake has real effects, so service calls and events answer `read_only`. Tests fake `ctx.ha` with `createTestContext({ ha: { ... } })`, whose unstubbed methods reject. Pipeline VMs have no internal endpoint for HA. Rejected: an opt-in for service calls from workspaces; a deployed handler run with `invoke` does the same thing, with its version and logs recorded.

## Integrations

- **OpenRouter** (`packages/sdk/src/openrouter.ts`): `openrouter(ctx, { apiKey?, timeout? })` returns `chat(request, { timeout?, signal? })` (the completion and its text), `json(request, { timeout?, signal? })`, `embed(input, { timeout?, signal? })` and `decide(request, { timeout?, signal? })`. Requests name no model: the [AI gateway](#ai-limits) sets it. `chat` and `json` POST to `https://openrouter.ai/api/v1/chat/completions`, `embed` to `https://openrouter.ai/api/v1/embeddings`, `decide` to `https://openrouter.ai/api/alpha/decisions`, through `ctx.fetch` with the `OPENROUTER_API_KEY` placeholder in the `Authorization` header, so the key from Settings, AI (or a hob's own secret bound to `openrouter.ai`) never reaches the handler. `json` without a schema uses JSON mode. With a schema it sends `response_format: json_schema` (strict by default) with `provider.require_parameters` so OpenRouter only routes to providers that support it, and validates the reply. Schemas are Standard Schema with Standard JSON Schema (`~standard.validate` and `~standard.jsonSchema`), which zod 4 implements, so the SDK needs no zod dependency. Errors throw `OpenRouterError` with the HTTP status (or the error's code when OpenRouter reports it in an HTTP 200 answer), OpenRouter's message with the provider's own message (`metadata.raw`) appended, and the error metadata. When `json` with a schema finds no provider for the request's parameters, the message says the model may not support structured output. `timeout` (milliseconds, per call or as the client default) and `signal` stop a call that waits too long; they throw `OpenRouterError` with code `timeout` or `aborted`. Without them a call has no timeout of its own, and the invocation timeout applies. Checked once against OpenRouter: chat, tool calls, JSON mode, structured output and error answers.

  `embed(input)` takes a string or an array of strings and returns `{ embeddings, model, usage }`, one vector per input in input order (by `index`), and `invalid_output` when a vector is missing. `model` is the one that answered, which hobs store with their vectors, since vectors from different models cannot be compared.

  `decide({ state, questions })` is OpenRouter's Decisions API: `state` is a string, object or array, and each question is `noul` (whether a condition holds; answer `noul`, the probability of yes), `choice` (one of at least two `criteria` keys, each with a description or null; answer `choice`, with `probabilities` and `confidence` from decision models) or `score` (a level of at least two ordered `criteria`; answer `score`, the expected level). Answers are typed from the questions (`choice` is the union of the keys), and one whose type does not match its question, or a `choice` outside the keys, throws `OpenRouterError` with code `invalid_output`.

  `check(prompt, { input?, threshold?, timeout?, signal? })` and `pick(prompt, choices, options)` are the intended use of AI in hobs: an `if` (boolean) and a `pick` (one of at least two strings, or an object of choice to description), for conditions, categorizing, tagging and filtering. They are not for agentic workflows, chat interfaces or long text. They call `decide` with `input` as the state (`(no data)` without one; numbers and booleans as JSON) and one question: `noul` with the prompt as instructions (true when the probability of yes is at least `threshold`, default 0.5), or `choice` with the choices as criteria (null for an array). `pick` throws a `TypeError` for fewer than two or duplicate choices. Neither retries. The names follow `chat` and `json`: short verbs on the client.

### AI limits

People and agents decide which AI models hobs use through OpenRouter, and people how much, so a hob cannot run up a large bill or pick a model on its own. Hob code is untrusted, so the model and limits are enforced on the host, in the VMs' egress path, not in the SDK.

- **Where** (`server/src/ai/gateway.ts`): runtime, preview and workspace VMs are created with an [interceptor](#sandboxing-gondolin) for `openrouter.ai` and `*.openrouter.ai`, so every request to OpenRouter goes through the gateway, whether it comes from the SDK helper, a raw `fetch` or another client. The API key is a placeholder that is only filled in when the gateway sends the request on, after its checks. Pipeline VMs have no secrets and cannot reach OpenRouter. A key bound to other hosts, or another AI provider, is not covered.
- **What passes**: only https on port 443 (plain http to OpenRouter is refused, so the key is never sent in the clear, and so is any other port) and only these paths: `POST /api/alpha/decisions`, and under `/api/v1` `POST` `/chat/completions`, `/completions`, `/messages`, `/responses` and `/embeddings`, and `GET` `/models` (and `/models/<author>/<slug>/endpoints`), `/key` and `/generation`. Anything else (API keys, credits, other methods) is refused, since the API key is filled in for every OpenRouter path. A `POST` body must be a JSON object (400 `hobwork_invalid_request` otherwise), since the gateway sends on the body it rewrote.
- **What counts**: `POST` requests. `GET` requests (model lists, key info) pass through. The gateway sets `model` and drops `models` (OpenRouter's fallbacks, which would let a hob pick), and asks OpenRouter for usage on `/chat/completions` and `/completions` (`usage: { include: true }`, unless the request sets `usage`). It reads prompt and completion tokens and the cost in US dollars from the answer's `usage`, in JSON or from the last server-sent event that has it (chat, Messages and Responses formats). When an answer with a 2xx status has no cost, the gateway estimates it from the token counts and the model's prices in OpenRouter's public model list (`server/src/ai/catalog.ts`, `/api/v1/models` and the same with `?output_modalities=decisions` and `?output_modalities=embeddings`, fetched by the host and kept for an hour). The model is the one that answered, else the one Hobwork picked. A model without a known price (or a model list that could not be fetched) is priced at $15 per million prompt tokens and $75 per million completion tokens. An answer with no token counts either has them guessed from the sizes of the request and the answer (four characters per token). Answers with error statuses cost nothing. Spend limits therefore always see a cost for a successful request.
- **Models** (`server/src/ai/settings.ts`): four models, `model` for the chat, completions, messages and responses endpoints, `decisionModel` for decisions, `embeddingModel` for embeddings and `visionModel` for requests to the text endpoints whose body has `model: 'vision'` (the SDK's `chat({ model: 'vision', ... })`). Hobs name a role, never a model ID: any other `model` is replaced with `model`. Spend limits and records apply to vision requests like any other. Each comes from the hob's own setting, else the host-wide setting, else the host's environment: `HOBWORK_AI_MODEL` (default `deepseek/deepseek-v4.1-flash`), `HOBWORK_AI_DECISION_MODEL` (default `typesafe/jev-1.13`, `off` for none), `HOBWORK_AI_EMBEDDING_MODEL` (default `openai/text-embedding-3-small`) and `HOBWORK_AI_VISION_MODEL` (default `google/gemini-3.1-flash-lite`, a cheap, stable OpenRouter model that reads images). Changing the embedding model makes new vectors incomparable with ones a hob stored, which the UI and `set_ai_model` say. A setting can also turn decision models off (stored as `''`), and then decisions run on `model`: the gateway sends a chat completion with the questions in the system message, the state alone in the user message between `<data>` tags, a strict JSON schema with one property per question (`boolean`, an enum of the options, or an enum of the level numbers), `temperature: 0`, `provider.require_parameters` and `reasoning: { enabled: false }` when the catalog says the model can turn reasoning off (`server/src/ai/decisions.ts`). It answers in the Decisions API's format with `noul` 0 or 1, the `choice`, or the `score` level and its `legend`, and 502 `invalid_output` when the reply does not fit, 400 `hobwork_invalid_request` for questions it cannot ask. New models are checked against the catalog when set (the model must exist and be a text, decision or embedding model to match its field; a vision model must also take image input), unless the catalog could not be fetched. Changes apply to the next request, without a merge.
- **Limits**: requests per minute and per hour, and spend per 24 hours and per 30 days, all rolling windows. Defaults: on, 20 per minute, 200 per hour, $1 per day, $10 per 30 days. Each can be empty for no limit, and the throttle can be turned off, which lifts them all. Host-wide limits apply to every hob that has no limits of its own; a hob's own limits replace them (they can be higher). Requests still running count. Spend counts only after the answer arrived (with the estimate above when OpenRouter reported no cost), so a request can go over the spend limit once. Refused requests do not count, so a handler that retries is let through when the window moves.
- **Refusals** answer in OpenRouter's error format, so the SDK throws them as `OpenRouterError`: 403 `hobwork_https_required`, `hobwork_port_not_allowed` and `hobwork_path_not_allowed` and 400 `hobwork_invalid_request` (not counted, not recorded in usage), 429 `hobwork_rate_limit` and `hobwork_spend_limit` (with `metadata.limit`, `max`, `used` and `retry_after_seconds`, and a `Retry-After` header). Messages say what happened, when to try again and that people change the settings on the hob's AI page. Each refusal is also a `warn` line with event `ai-limit` in the hob log, at most once a minute per hob, VM kind and branch, with the branch for previews and `Workspace <branch>:` for workspaces.
- **Records** (`server/src/ai/usage.ts`, `ai_requests` from `server/migrations/0028_ai_limits.sql`): one row per `POST`, with hob, branch, VM kind, path, model, HTTP status, tokens, cost and whether and why it was refused. A request whose upstream fails is recorded as 502. Housekeeping deletes rows older than 90 days. Settings are in `ai_settings` (one row) and `project_ai_settings` (`model`, `decision_model`, `embedding_model`, `vision_model`, limits as JSON; the `models` lists from before `0034_ai_models.sql` are no longer read), with the person or agent who changed them.
- **Who changes them**: people in the web UI: Settings, AI (host-wide models and limits, and spend per hob over 30 days) and a hob's AI tab (spend in the last 24 hours and 30 days, requests in the last minute and hour, spend by model, and the hob's models and limits). Web API, signed-in users only, so agent tokens get 401: `GET|PUT /api/settings/ai` (`{ model, decisionModel, embeddingModel, visionModel, limits }`) and `GET|PUT /api/projects/<name>/ai` (the same). `null` uses the level above and `decisionModel: false` turns decision models off; answers add `models`, what hobs get. Agents see the hob's models, limits and spend in `get_hob` and change only models, with `set_ai_model`: a hob's for connections with access to it, the host-wide ones for connections with access to all hobs, none for read-only ones.
- **API key**: Settings, AI takes an OpenRouter API key for all hobs. It is stored as a library secret (`OpenRouter API key`, numbered when the name is taken, bound to `openrouter.ai`) given to all hobs as `OPENROUTER_API_KEY` (see [Secrets and network](#secrets-and-network)), so a hob with its own `OPENROUTER_API_KEY` keeps using that. Saving again changes the secret's value. Removing the key takes it away from all hobs and deletes the secret unless a hob has it assigned. Web API, signed-in users only: `PUT /api/settings/ai/key` with `{ value }` and `DELETE` on the same path; `GET /api/settings/ai` returns `apiKey` (the secret's name and who changed it last, and the hobs with their own key), never the value. VMs pick up a new key like any secret change, through the secrets fingerprint.
- Settings are read on every request, so changes apply to running VMs right away.

## Open questions

- Public hob routes: routes need an app session or an agent token, and only webhooks are public. NFC links and pages shown without signing in would need public routes. One option is a per-route setting in `hobwork.json`.
- Can one hob call another hob's routes or send events to it?
- Visual programming: whether people should be able to build automations without code, and how.
