### Device protocol

- **Discovery**: the app asks for the host URL in a native view and checks it with `GET /.well-known/hobwork` (no auth), which answers `{ "hobwork": 1, "name": <host name of the public URL>, "version": <host version> }`.
- **Pairing**: the app opens `ASWebAuthenticationSession` at `<public URL>/devices/connect?name=<device name>&platform=ios|macos&challenge=<PKCE S256, base64url, 43 characters>&state=<random>&redirect_uri=<redirect URI>`. `redirect_uri` must be exactly `<public URL>/devices/paired` (a universal link, so no other app can catch the code; the app waits for it with `ASWebAuthenticationSession.Callback.https`) or the older `hobwork://paired`, which apps built without the host's domain in Associated Domains keep using; `state` is optional and at most 512 characters. The page needs a signed-in person like every page (so Pocket ID or a passkey happens inside the session), shows the device name, suggests the name hobs use for it (a slug: `Kaan's iPhone` becomes `kaans-iphone`, which the person can change) and asks to approve. Approving redirects to the redirect URI the app sent, `?code=<code>&state=<state>` added (code: 5 minutes, single use; a wrong verifier also uses it up). Cancelling redirects to the same URI with `?error=access_denied&state=<state>`. If the link is opened in a browser instead of the app, `GET /devices/paired` shows a page that tells the person to open the Hobwork app and start pairing again from there. The app sends `POST /api/devices/token` with JSON `{ code, codeVerifier }` (`code_verifier` works too) and gets `{ deviceId: number, name, token }`; errors answer 400 `{ error }`. The exchange creates the device, owned by the person who approved; if another device took the name in between, the new one gets a number (`kaans-iphone-2`). The device token (`hwd_...`, stored hashed) does not expire; people remove devices in the web UI, and the app removes its own device when someone signs out in it (`DELETE /api/devices/self`, Bearer device token, 204), which works exactly like removing it in the web UI: the web view's session and its app sessions end, the push token is forgotten and the socket closes with 4001. `GET /api/devices/self` (Bearer device token) answers `{ id, name, platform, person: { id, name } }`, which the app shows hob UIs through the web bridge (`app.info`). The app keeps the token in the Keychain. Every device endpoint, the WebSocket upgrade included, answers 401 for a removed or unknown token, which the app takes as unpaired, and 403 `{ "error": "not_allowed" }` for a device whose owner is no longer on `HOBWORK_ALLOWED_USERS`: the app keeps its token, since it works again once the owner is added back, and retries slowly.
- **Web session in the app**: device tokens never go to the WebView. The app calls `POST /api/devices/web-session` (Bearer device token) with JSON `{ returnTo }` (a path on the Hobwork origin, default `/`; anything else answers 400) and gets `{ url }`: a one-time `<public URL>/auth/device?token=...` (60 seconds, single use) that sets a normal Hobwork session cookie for the device's owner and redirects to `returnTo`. A used or expired link redirects to `/login?error=link_expired`. The app loads that URL in its `WKWebView` (persistent data store) directly with `load(URLRequest)`, which then signs in to hob apps through the usual app-origin redirects (for example `returnTo=/auth/app?project=filament&returnTo=...`). The link answers 403 unless `Sec-Fetch-Site` is `none` (what WebKit sends for a load the app starts) or missing, so a page cannot sign the web view in to someone else's account by linking there (login CSRF); a link followed from a page, JavaScript navigation included, does not work. The session belongs to the device (`sessions.device_id`): each new sign-in replaces the previous one, and removing the device ends it and every app session made from it.
- **Connection**: `GET /api/devices/ws` upgraded to a WebSocket, `Authorization: Bearer hwd_...` (401 or 403 before the upgrade otherwise, as for the HTTP endpoints). Messages are JSON text frames, objects with a `type`; the host ignores types it does not know:
  - app → host `hello`: `{ appVersion, platform: "ios" | "macos", capabilities: string[], push?: { grant, key } | null, timeZone?: string }`. Sent on every connect, and first: the host sends no calls before it and closes a connection without one after 30 seconds. The host answers it with `push` (see "Hosts and apps on the relay"). The app sends it again when it comes to the foreground on an open connection; each `hello` marks the device as used (`last_active_at`). `timeZone` is the IANA zone of the device, stored as the owner's time zone unless they chose one in Settings; unknown zones are ignored. `push` is the app's relay grant for this host and its X25519 key; `push: null` turns push off, and the APNs tokens older apps send are ignored. `capabilities` lists only what is set up and allowed on the device (`notifications`, `alarms`, `focus`, `nfc`, `health`, `homekit` on iOS, `liveActivities` while Live Activities are allowed, `widgets` on iOS); the host rejects calls to others with `unsupported`. HomeKit is an exception: iOS reports support before Home authorization, so its first use can ask for access without creating `HMHomeManager` at launch. The grant can also be updated with `PUT /api/devices/push` (`{ grant, key }` or `{ grant: null }`, 204) while disconnected. The platform is fixed at pairing.
  - host → app `call`: `{ id, capability, method, args, expiresAt? }` (commands carry `expiresAt`, and the app answers `expired` without running one that has passed it); app → host `result`: `{ id, ok: true, value }` or `{ id, ok: false, error: { code, message } }`. For `notifications.send` the host waits 15 seconds for a result, for `notifications.withdraw` 4 seconds; other calls are commands (see Commands). After every `hello` the host sends a `call` for each pending, unexpired command of the device, oldest first, and one `notifications.withdraw` with every notification ID the device has not confirmed removing.
  - `notifications.send` args: `{ id, project, title, body?, actions: [{ id, title, foreground?, destructive?, open? }], interruptionLevel?: "passive" | "timeSensitive", sound?: "none", thread?, open?, revision?, update?: true }`. `id` is the request identifier for every send, update and withdrawal of the notification. `revision` (left out for 1) tells a new version from a repeat. With `update`, the app replaces the notification only while it is delivered and answers `{ id, shown: false }` otherwise. `open` is a path of the hob's UI; the app opens `/p/<project><open>` on a tap (the notification's `open`) or for a `foreground` action (the action's `open`, or `/projects/<project>`).
  - `notifications.withdraw` args: `{ ids }`. The app removes delivered and pending notifications with these identifiers and answers `ok: true`; the host then stops sending them.
  - app → host `event`: `{ capability, name, data }` (see Events and triggers). The same object without `type` can be sent with `POST /api/devices/events` (Bearer device token, 204), for when iOS wakes the app in the background to handle an action and a socket would take too long.
  - `alarms.set`, `alarms.timer` and `alarms.reschedule` args carry `hob` (the hob that called), which the app keeps with the alarm and sends back with its events: `alarms` / `fired`, `stopped`, `repeated` with `{ id, hob, title?, seconds? }`. Apps from before this ignore it.
- **Hand-off** (the web bridge's NFC on an iPad or Mac): `POST /api/devices/handoff` (Bearer device token) `{ hob, device, capability: "nfc", method: "write" | "read", args }` runs the command on another device of the same person: `device` is a device name or `"lastActive"`, the one they used last that reported the capability. The host checks the args as for `ctx.device(name)`, sends the command (a prompt push saying `<hob> on <device> is waiting`), waits up to 2 minutes, and answers 200 `{ ok: true, device, value }` or `{ ok: false, error: { code, message } }` (`unknown_device` for devices of other people or unknown names, `unreachable` when no other device of theirs can, `bad_request`, `timeout`, or the other device's code). The app sets a 150 second request timeout.
- **Live Activities** (see Live Activities in `docs/architecture.md`): host → app `call` `liveActivities.start` `{ hob, id, state, staleAt?, relevance? }` → `{ activity: <ActivityKit ID> }`, `liveActivities.update` `{ id, state, staleAt?, relevance? }` → `{ updated }` (false when no activity with that `id` runs), `liveActivities.end` `{ id, state?, dismissAt? }` → `{ ended }`. `id` is the host's UUID of the run; times are Unix seconds. `state` is the `ContentState`: `{ title, subtitle?, swatches?, icon?, tint?, endsAt?, startedAt?, progress?, value?, valueLabel?, button?: { title, opensApp? }, open?, stillRunning? }`. App → host events `liveActivities`/`startToken` `{ token: <relay activity token ID> | null }`, `liveActivities`/`state` `{ id, activity, state: "active" | "dismissed" | "ended", token? }` (only reports about the activity the host knows for that device count; `token` is the relay's ID of the activity's update token) and `liveActivities`/`action` `{ id }` (the button, counts as using the device). The web bridge's `POST /api/devices/live-activities` (Bearer device token) `{ hob, op: "start" | "update" | "end", id?, args }` answers `{ id, activity: { hob, id, state, staleAt?, relevance? } }` for a start, which the app then starts itself, or `{ updated | ended, devices }`; 403 `{ error, code: "unsupported" }` when the device does not report `liveActivities`, 400 `{ error, code }` for bad arguments.
- **Widgets and intents**: `GET /api/devices/hobs` → `{ hobs: [{ hob, widget, intents: [{ id, title, parameters: [{ id, title, type, optional }], opensApp, open?, runs }], share: [{ id, title, accepts: { urls, text, files }, maxBytes? }], appLinks: { include, exclude } }] }` (every hob with a deployed version; `files` is empty and `maxBytes` missing for targets without an upload; `appLinks` are the hob's link rules, see Links to hob pages in `docs/architecture.md`). `GET /api/devices/widgets/<hob>` → `WidgetContent` with `refreshAt` always set, 404 for a hob without a widget, 502 `{ error, code }` when its route failed or returned no title. `POST /api/devices/intents` `{ hob, intent, parameters? }` → 200 `{ ok: true, say?, open? }` or `{ ok: false, error: { code, message } }` (`bad_request` for a missing or mistyped parameter, `unknown_intent`, `route_failed`, `unavailable`). Host → app `call` `widgets.reload` `{}` → `{}`.
- **Share targets** (the share extension): `POST /api/devices/uploads` `{ hob, target, name, size, type? }` → 201 `{ id, path, size, received, chunkBytes }`; the host picks `path`, a free name in the target's upload folder. `PUT /api/devices/uploads/<hob>/<target>/<id>?offset=<received>` with at most `chunkBytes` bytes → 200 with the new status, or 201 `{ done: true, file: { path, size, modified } }` for the last part; 409 when the part does not start at `received`. `GET` the same path answers the status, `DELETE` drops the upload. Errors are `{ error, code }` with 400 (`bad_request`, `not_accepted`), 404 (`unknown_target`, or an upload that does not exist or belongs to another person), 413 (too large) and 415 (`not_accepted`: a type the target does not take). `POST /api/devices/share` `{ hob, target, url?, text?, files?: [{ path, name, contentType }] }` → 200 `{ ok: true, say? }` or `{ ok: false, error: { code, message } }` (`bad_request`, `not_accepted`, `unknown_target`, `route_failed`, `unavailable`). The uploads are the owner's, like `files.upload` in the hob's app, and only reach the target's own upload; `files` must be under that upload's prefix and stored.
- **Tag owner**: `POST /api/devices/nfc/lookup` (Bearer device token) `{ url }` answers `{ tag, url, hob }` for a Hobwork tag URL of this host and 404 otherwise, so the app can hand a scan to an open page of that hob.
  - Both sides send `{ "type": "ping" }` every 30 seconds and answer `{ "type": "pong" }`. The host counts any message as a sign of life and closes a connection that stays silent through two of its pings.
  - A device that connects again replaces its old connection. Close codes: 4000 replaced by a newer connection, 4001 the device was removed, 4002 protocol error (no hello, a message that is not a JSON object), 4003 no answer to two pings, 4004 the owner was taken off `HOBWORK_ALLOWED_USERS` (checked at every ping; the device token works again if they are added back), 1001 host shutting down.
- **Background pushes**: a sealed push of relay kind `background` has `aps: { "content-available": 1 }` and no alert, so iOS wakes the app (`application(_:didReceiveRemoteNotification:)`, not the extension) without showing anything. The app opens it like any sealed push; `hobwork: { withdraw: [ids] }` removes those notifications, `hobwork: { reloadWidgets: true }` reloads the widgets and controls. It does not answer the host: the next `hello` confirms the removal.
- **Push**: through the push relay (`HOBWORK_PUSH_RELAY_URL`, default `https://relay.bgenc.dev`, `off` for none), since APNs only accepts pushes to `dev.bgenc.hobwork` signed with a key of team 63QQLP356Q. The host seals the payloads below for the app and sends them to the app's grant ("Hosts and apps on the relay"); the relay and Apple see neither the text nor the host. `GET /api/devices` reports `push: true` for devices with a grant. A grant the relay reports as `gone`, `expired` or unknown is forgotten until the app sends a new one. A grant belongs to one device: a device paired again on the same app install takes it over.
- **SDK**: `ctx.device(name)` returns the capabilities; `ctx.person(id).notifications.send(...)` notifies a person's devices and `ctx.notifications.update(id, ...)` / `.withdraw(id)` change a sent notification everywhere (see Notifications in `docs/architecture.md`); `ctx.devices()` lists devices (`name`, `platform`, `owner`, `ownerId`, `capabilities`, `connected`, `lastSeenAt`, `lastActiveAt`); `ctx.people()` and `ctx.person(id).devices()` / `.lastActiveDevice()` find a person's devices (see "People and time zones" in `docs/architecture.md`). Devices whose owner is no longer on `HOBWORK_ALLOWED_USERS` are left out, get nothing, and lose their socket; the web UI still lists them, so people can remove them. Deployed handlers use devices. Workspaces and branch previews list them, but their calls answer `read_only`, since code there is work in progress and a stray notification reaches a real person. Every capability and method is typed in `packages/sdk/src/devices.ts`. Tests fake them with `createTestContext({ device: (name) => ({ notifications: { send } }) })`; methods a fake leaves out reject. Agents see devices and their capabilities with the `list_devices` MCP tool; they cannot pair, remove or call devices.


- **Apple Home** (iPhone and iPad): `homekit.homes` `{}` → `[{ id, name, primary }]`, `homekit.accessories` `{ home }` → `[{ id, name, room, serialNumber, bridge }]`, `homekit.services` `{ accessory }` → `[{ id, name, type, characteristics: [{ id, type, readable, writable, format, unit, min, max, step }] }]`. Characteristic metadata fields `format`, `unit`, `min`, `max` and `step` are nullable. `homekit.get` `{ accessory, characteristic }` → a JSON scalar (`string | number | boolean | null`), `homekit.set` `{ accessory, characteristic, value }` → null, where value is a string, finite number or boolean. `homekit.assignRoom` `{ accessory, room }` and `homekit.rename` `{ accessory, name }` → null. IDs are raw HomeKit UUID strings, with no prefixes; names are trimmed, nonempty and at most 255 characters. The host rejects unknown argument keys and adds the trusted `hob` to every HomeKit command. All HomeKit methods are foreground commands, so a disconnected phone receives a prompt push rather than an extension command. The app must be on screen and asks for approval for each remote call, naming the hob and operation. Native UI calls instead use separate per-hob permissions for reading, moving/renaming and controlling characteristics. iOS asks for Home access on first use. HomeKit does not emit device events or support device triggers.
